## M0-A — v1

Empty repository to release 1.0.0 on 2026-08-16. RFC 0001 was the work order: thirteen
packages in dependency order, one agent session each.

**The bet, and why `docs/spec/` has the shape it does.** Writing the specification as the
code went along, the default for human teams, was rejected before the first package. The
whole contract was written first: a data model with named invariants, exact query
orderings, an API, normative UI copy, a decided architecture, and 115 numbered acceptance
criteria written by a role that never implements. Sections 4 and 7 were then frozen. The
reason is who the implementers were. AI agents in isolated sessions have no channel back
to a reviewer and cannot resolve an ambiguity in a hallway, so every gap in a partial
spec becomes a silent wrong guess rather than a question. The product and stack
alternatives that lost are normative, with their reasons, in spec 1.3 and 11.14.

**2026-08-13: a restyle rejected, and the markup replaced wholesale (RFC 0002).** A
package had been chartered to carry the designer's visual values onto markup an earlier
package built. The owner opened both applications side by side that day and rejected the
result; the client's markup and components were replaced with the designer's committed
prototype instead, wired to the data layer that already existed. Two things outlived the
interface that produced them, and a punctuation ruling outlived it too: **Dana's own
user-facing copy takes a comma where a designer's em dash arrived**, cited at
`app/src/client/README.md`. It governs product copy and not prose in this repository.
**Nobody had run the prototype**: not the kickoff, not the audit, not one of the six
implementing sessions, in a package whose entire subject was appearance. And the
instruction that failed did so by generalisation: a narrow, correct ruling about the
prototype's data wiring was widened into a rule covering the whole package, and the
composition the owner was actually rejecting sat inside the part that got widened away.

**2026-08-14: log retention, on vendor facts checked that day (RFC 0003).** Checked
against the plans themselves rather than taken from the candidate list recorded before
implementation:

| Checked 2026-08-14 | Free tier |
| - | - |
| Axiom | 30 days retention; HTTPS ingest free, Secure Syslog paid only |
| Better Stack Logs | 3 days |
| Render Hobby log explorer | 7 days |

Spec 10.5 requires 30 days, so Axiom's free tier over HTTPS was the only option that met
it, and it replaced a planned Render-to-Syslog drain. The owner chose the free route that
day, Dana being an MVP still, and accepted that Render's own platform and build logs keep
Render's shorter retention. These are facts that cost research and go stale, which is why
they are kept with the date they were checked.

**2026-08-16: the release gate, two legs the automated suite cannot run.** Lifted from
`CHANGELOG.md` when that file was deleted on 2026-09-20; it was the only record of either.

The **first restore drill**, green. Render's free instance type carries no point-in-time
recovery, so the drill ran the runbook's other route: a custom-format `pg_dump` of
production restored into a scratch `dana_restore_drill` database on the local PostgreSQL
18, created with 11.10's builtin C.UTF-8 locale, with AC-001's constraint catalog
asserted against the restored copy. 24 of 24 green. **The negative control is the part
worth keeping**: the run was proved to have used the restored database rather than
falling back to PGlite by repeating it against a nonexistent database name and confirming
it fails instead of passing. The scratch database was dropped and `dana_test` was not
touched.

The **production smoke**, green, including one reminder email that really arrived. That
leg found the only defect the automated suite cannot see: a `RESEND_FROM` that was not an
address, which Resend refused with HTTP 422 while the scheduler retried silently every 60
seconds. Configuration only, no code change.

## M0-B — v2

RFC 0005 was the contract, accepted 2026-08-24 and re-accepted 2026-08-27 after its delta
grew; RFC 0004 was the work order. Thirty-one packages, one agent session each, released
as 2.0.0 on 2026-08-30. Its scope, recorded so that nobody has to reconstruct it from a
diff: what the sidebar asks, a due date as a day rather than a moment, who may do what to
a shared folder, and six systems v1 could not store (the event record, object storage,
the page model, the conversation, the object acts, and the person's bundle). It
introduced no decision of its own: it was the pricing session's cut list written as
specification text.

**2026-08-27 and 2026-08-30: the folds (S29, S29a).** Every accepted unit was written
into a numbered section of `docs/spec/`. The spec, not the RFC, has been the contract
ever since, and it has moved past the RFC: when RFC 0005 was trimmed on 2026-09-01, two
thirds of its delta was already byte-identical to the spec, and where the two differed
the spec was newer.

**The patch strategy was superseded rather than extended, because it missed the same
target twice with a recorded mechanism both times.** First, no numbered section ever
named `prototype-v2/`, so the client packages built from the v1 prototype while reading
the rulebook correctly. Second, the parity audit that followed measured 31 surfaces for
appearance and structure, and the packages closed what that audit measured: a surface
audit marks a task card ported without ever noticing that the prototype's card carries a
comment thread. Patching fixes what the last instrument measured, so when the target is
the prototype itself, the instrument has to be the prototype itself.

**Lift, do not re-derive.** The client was replaced by the prototype's own code, surface
by surface, bound to the existing API through an adapter seam, on a measurement taken
first: the prototype's coupling to its fixtures was concentrated rather than spread. The
discipline that made it checkable is still checkable. A lifted file diffs empty against
its prototype original except at named seams, and every seam carries a comment saying
which adapter it crosses, so a session rewriting a component's body has left the strategy
and found an escalation.

**One package per chat, from measurement.** A session that carried one and a half
packages spent 72% of its window and about 280 million cached tokens. Running out of
window mid-package is the expensive failure, because the next session pays to rediscover
what the last one knew.

## M0-C — Hardening

2026-08-31 to 2026-09-14. No release, no RFC, and the only era that left no document of
its own, which is why it is the one a newcomer most needs. Nothing was promised at the
start of it: it was reactive, and what it produced was a codebase safe to keep changing
rather than a more usable product.

**The tracker starts mid-story.** GitHub issue #1 was created 2026-08-30. Before that
date this repository has no issues at all, work having run as RFC packages with no
tracker, so nothing earlier can be found by issue number. Roughly 190 issues were filed
in the ten days that followed, #1 to #196 by 2026-09-09.

## The citations, and the tags they need

Code comments and `docs/spec/` cite v2's decisions by number about 480 times, mostly as
`RFC 0005 change control item N`, alongside unit numbers and the S- and P-row numbers of
the v1 and v2 work orders. Counted 2026-09-20: 401 references in `app/` and 76 in
`docs/spec/`, counting no RFC file itself.

Two commands resolve them, and they do different jobs. The **index** is the trimmed
version's sixty-one-row table, one row per change-control item giving its date, what it
decided and which spec sections took it, which is the fastest route for an item number:

```bash
git show f9773f2:docs/rfcs/0005-v2-specification.md   # item 44 is line 289
```

The **full originals** are what a unit number, an S-row, a P-row, or the full text of an
item needs:

```bash
git show v2.2.0:docs/rfcs/0005-v2-specification.md    # item 44's text starts at line 997
```

The second carries the originals rather than the versions trimmed on 2026-09-01: RFC
0005 is 6,763 lines there, its sixty-one change-control items in full.

So the release tags `v1.0.0`, `v2.0.0`, `v2.1.0` and `v2.2.0` are load-bearing and must
not be deleted, and a clone fetched without tags resolves none of those citations:
`git fetch origin --tags` first.
