# Dana PDD v3: Adversarial Audit

Phase 1 of the v4 upgrade. Input: dana_pdd_v3.md. Audit date: 2026-07-24. Purpose: find every contradiction, undefined state, and integrity hole before any v4 text is written. Citations of the form "Section N, Heading" refer to v3; the audit's own divisions are called Parts to avoid collision.

## Part 0. Verdict and how to read this document

The audit found **34 issues: 8 blockers, 14 majors, 12 minors.**

No finding forces a change to the fundamental shape of the product. Flat folders, folder-only sharing, single ownership, derived task homes, and the three-state status model all survive contact with the edge cases. The prominent-stop clause of the brief (its section 9) is therefore not triggered.

Rules of interpretation:

- Every **Resolution** below is this audit's proposal, not a fact from v3. Where a resolution overturns v3 text, the exact sentence is quoted first. Where v3 is silent, the gap is named and the decision is marked as the auditor's.
- Severity: **blocker** means shipping as written produces data loss, a security hole, or a feature that cannot behave as described. **major** means an implementing agent must invent a rule and plausible inventions diverge. **minor** means an internal inconsistency or missing detail that confuses but does not corrupt.
- Issues are ranked by severity, and within a band by how much of the system they touch.
- Part 5 states plainly which issues are data loss or security holes and which are merely confusing, as the brief requires.
- Part 6 maps the brief's ten open questions to the issues that resolve them. All ten receive a specific proposed answer.

## Part 1. Issues, ranked

### Blockers

#### ISSUE-01
**Severity:** blocker
**Location:** Section 3, My Day, "Nothing here is ever silently removed", against the implementation notes of Tasks, Planned, Important, and All.
**Quote:** "Abandoning something never deletes it or hides it from the rest of the app, it only stops nagging you specifically here." Against: "the query is folder_id in (every folder you have access to) AND due_date IS NULL AND status = pending" (Section 3, Tasks, implementation note; the Planned, Important, and All notes carry the same status = pending condition). Also Section 3, Done: "they already stay visible in their real home and in All".
**Problem:** The four query sketches filter to status = pending, so an abandoned task matches none of them. It also fails Done (status = completed) and My Day (abandonment stops resurfacing there by rule). Worked example: Hassan abandons "Renew Imran's passport" (undated, folder Work). The prose promises it stays visible in Tasks and in All. The queries make it visible nowhere: not Tasks, not Planned, not All, not Important, not Done, not My Day. The row still exists but is unreachable from every page, which is indistinguishable from deletion for the user and contradicts two explicit sentences.
**Resolution:** Change the scope of Tasks, Planned, All, and Important from status = pending to status IN (pending, abandoned). Abandoned rows render visually distinct (faded, struck through, with a restore affordance) and sort after pending rows within whatever group they appear in. My Day excludes abandoned entirely, both automatic and pulled. Done remains completed only. Search returns all three statuses. The rejected alternative, surfacing abandoned only behind a filter on Done, contradicts both quoted sentences.
**Cost of resolution:** One predicate change per page query, one visual state, one status-first sort key per page. No schema change.

#### ISSUE-02
**Severity:** blocker
**Location:** Section 3, My Day, "Recurring tasks need no special handling here", against Section 3, Planned, "Recurring tasks".
**Quote:** "Completing or just passing the due time/date of a recurring task generates a new task, it never generates stuff up to infinity from the get go, it generates the next occurrence with its own future date, which won't qualify for today's list until its own day comes." Against: "Only ever one real row in the database for a recurring task, its current occurrence, exactly as already established."
**Problem:** "Just passing the due time/date" as a generation trigger contradicts the one-real-row rule. Worked example: "Take out the bins", weekly, due Monday 2026-07-20, not completed. If passing midnight into Tuesday generates the 2026-07-27 occurrence while the overdue one stays pending (it must, since My Day snowballs it), there are now two pending rows. Miss three weeks and there are four, produced by a background process v3 never mentions, firing at a timezone-dependent midnight v3 never defines. The stated properties (one live row, snowballing, a Done trail) cannot all hold under time-based generation.
**Resolution:** Generation happens on exactly one trigger: the current occurrence leaving pending, that is, on completion or on abandonment. Nothing is generated by the passage of time; no background job exists for recurrence. A missed occurrence snowballs as overdue until acted on. Next occurrence due date = the earliest rule instance strictly after max(current occurrence due_date, today in the acting user's timezone). Consequences, each deliberate: completing on time advances one slot; completing late skips slots already in the past instead of spawning instantly-overdue occurrences; completing early advances from the due date, not the completion date, so weekday alignment ("every Monday") is preserved; completing after the next slot has already passed skips that slot, and the calendar shows an honest gap. The generated row copies title, notes, folder, assignee, important flag, reminder configuration, and the rule; steps are copied with done reset to false; My Day pull entries are not copied; status starts pending. The completed or abandoned row keeps its date forever as the trail entry, which preserves the Done page history v3 wants. Series linkage via a series id; the rule lives only on the single pending occurrence. Invariant: at most one pending occurrence per series.
**Cost of resolution:** Removes a background job entirely, an operational win. Adds a series id column and a generation step inside the complete and abandon transactions. The late-completion skip rule needs one line of UI copy.

#### ISSUE-03
**Severity:** blocker
**Location:** Section 2, Folders, "What folder sharing grants, concretely", and Section 2, Workspace, People paragraph.
**Quote:** "All members currently have equal standing, no admin or owner-only actions exist yet in this version, though the underlying member record should carry a role field now so a real permission tier can be added later without a schema change." And: "Once connected, either person can share any folder with the other without inviting again, for as long as the connection exists."
**Problem:** Read literally, "no owner-only actions" lets any member delete a folder they did not create, rename it, or remove other members including the owner. Worked example: Imran, a member of Hassan's folder Work, deletes Work, or evicts Hassan from his own folder. That is a security hole, not a style question. Separately, "either person can share any folder" cannot be literal: the Default Folder is unshareable, and whether a non-owner member may share a folder onward to a third person is unstated. Finally, v3 never mentions deleting a task anywhere; the word delete appears only for folders, members, and accounts, so task deletion rights are wholly undefined.
**Resolution:** A minimal permission matrix, enforced server-side; the client only hides controls.
- Owner only: rename folder, delete folder, remove a member other than themselves.
- Any member: create tasks; edit any task field; complete, abandon, restore, and delete any task; move tasks per ISSUE-15; add members, from their roster or by email invite, including the assignment-triggered path of ISSUE-08.
- Any non-owner member: leave the folder. Leaving applies the removal rule: their assigned tasks in it become unassigned.
- Owner leaving is governed by ISSUE-05 (transfer or delete).
- Default Folder: sharing and deletion remain impossible; it never has a second member.
Letting any member add members is the literal reading of the equal-access ethos and is required by Section 2, People, "Sharing triggered indirectly", which any member can hit by assigning; restricting adds to the owner would break that flow. Restricting rename, delete, and eviction to the owner overturns the quoted "no owner-only actions exist" sentence, deliberately: destructive control over a folder belongs to the one account that cannot be removed from it. The role column v3 asks for is kept, holding a single value in v1, with ownership read from the folder row, one source of truth.
**Cost of resolution:** One authorization check per endpoint, a matrix table in v4, the role column v3 already wanted. Task deletion gains a definition it never had.

#### ISSUE-04
**Severity:** blocker
**Location:** Section 2, Folders, "Two kinds of folder, same underlying object".
**Quote:** "It cannot be shared and cannot be deleted, those two actions are simply hidden for this one folder."
**Problem:** The sentence implies custom folders can be deleted, and nothing anywhere states what happens to the tasks inside. Every task must have a folder (Section 2, Folders: "Every task lives in exactly one folder, always"), so deletion as written either orphans rows in violation of that rule or cascades silently. Worked example: Hassan deletes Work, which holds 40 tasks, 12 of them completed history, 3 assigned to Imran. Whether anything survives, and what Imran sees afterward, is unspecified.
**Resolution:** Deleting a folder hard-deletes the folder and everything in it: tasks of all three statuses, their steps, their My Day entries, their reminders, plus pending invites carrying the folder, plus membership rows. The confirmation dialog states the counts (open, completed, abandoned) and that this affects all members. No trash or soft delete in v1; a named simplification, revisited if real users lose data. The alternative, moving tasks to the owner's Default Folder, was rejected: it silently converts shared, visible tasks into private invisible ones, which is worse than honest deletion.
**Cost of resolution:** Cascade rules on five tables, one counting confirmation dialog, one destructive endpoint restricted to the owner per ISSUE-03.

#### ISSUE-05
**Severity:** blocker
**Location:** Section 2, Folders, closing italic note. Open question 1.
**Quote:** "Still to decide: what happens to a folder if its owner, the one person who created it, removes themselves or deletes their account, while other members still have access to it. This hasn't come up yet and needs an explicit answer before this ships."
**Problem:** v3 flags this itself. Unanswered, account deletion either breaks referential integrity (folders owned by a nonexistent user, tasks created by nobody) or forces cascade deletion of shared folders other people depend on. Worked example: Hassan owns Home, shared with Imran, holding a year of completed history. Hassan deletes his account. Either Home disappears from under Imran, or it survives pointing at a dangling owner.
**Resolution:** Two rules, one transfer mechanism.
- Owner leaves a shared folder: ownership transfers automatically to the earliest-joined remaining member (tie broken by lower user id), then the leave proceeds as a normal removal. With no other members, leave is not offered; the owner deletes the folder instead (ISSUE-04).
- Account deletion: the user row is soft-deleted, kept but scrubbed (email, name, avatar, Google id removed, deleted_at set), so created_by and completed_by references on surviving tasks stay valid and render as "Deleted user". Their memberships are removed with the normal unassignment rule. Roster connections are deleted in both directions. Pending invites they sent are canceled. Owned shared folders transfer by the leave rule above. Owned private folders and the Default Folder are hard-deleted with their contents per ISSUE-04.
Google requires apps that offer account creation to offer account deletion; the exact current policy text needs verification before v4 freezes, but the mechanism stands regardless.
**Cost of resolution:** Soft-delete semantics on users (pickers and rosters must exclude deleted users), one transfer routine reused by two paths, one deletion transaction touching seven tables.

#### ISSUE-06
**Severity:** blocker
**Location:** Section 3, My Day, "What lands here automatically", and every use of the word today. Open question 2.
**Quote:** "Any task assigned to you, due today or earlier. This runs on its own, every day, no manual step involved."
**Problem:** "Today" is undefined without a timezone anchor, and v3 stores none. Worked example: Hassan is in Karachi (UTC+5), Imran in London (UTC+1). At 2026-07-24 01:00 in Karachi it is still 2026-07-23 in London. A task due 2026-07-24 in their shared folder is due today for Hassan and due tomorrow for Imran. Undefined: whether that is intended, what happens when Hassan flies to London, which timezone anchors a reminder, and under which day a completion groups on Done.
**Resolution:** Floating civil time, the Todoist and Things model, pinned down as follows.
- due_date is a calendar date (ISO 8601 date, no timezone). due_time is a wall-clock time (no timezone). Every member sees the same digits. Members in different timezones therefore reach today at different moments; accepted and documented. Known caveat: a shared "Dentist at 15:00" reads as each member's local 15:00, right for household coordination, wrong for cross-timezone joint calls; accepted for v1 and documented.
- Every user has a stored IANA timezone, captured from the browser at first login and auto-updated whenever a session reports a different one. Traveling shifts today to where you are. No manual lock in v1.
- Today, for My Day inclusion, snowball grouping, overdue styling, and calendar highlighting, is computed in the viewer's timezone at query time; the client sends its IANA zone with each request and the server evaluates with it. Logic stays server-authoritative; only the anchor is client-supplied.
- completed_at is an absolute UTC instant (timestamptz). Done groups it by date in the viewer's timezone at render time.
- Reminder fire instant = due_date plus (its own time, or due_time minus the offset) interpreted in the assignee's stored timezone; recomputed when the date, time, offset, assignee, or that assignee's timezone changes (ISSUE-16). IANA tzdb rules absorb DST; a nonexistent local time during a spring-forward gap resolves to the next valid instant.
- The recurrence comparison against today (ISSUE-02) uses the acting user's timezone.
**Cost of resolution:** One users.timezone column, a timezone parameter on time-scoped queries, recompute hooks for reminders. Deliberately avoided: storing due dates as UTC instants, which is the classic wrong choice this resolution exists to prevent.

#### ISSUE-07
**Severity:** blocker
**Location:** Section 3, My Day, implementation note. Open question 3.
**Quote:** "two things drive inclusion, due_date and a separate marker for manual pull-ins, both checked the same way, on or before today, not equal to it"
**Problem:** "A separate marker" reads as a column on the task, which makes a pull global to every member. Worked example: Imran pulls "Buy paint" (folder Home, shared, unassigned, undated) into focus. As a task column, the marker drags it into Hassan's My Day too, though Hassan never chose it, in the one page whose premise is personal focus. v3 also never says what the marker stores, whether a pull can be undone, how pulled rows group, or what the completed-today section queries.
**Resolution:** The marker is per user: a my_day_entries table, primary key (task_id, user_id), with added_on, a date in the adder's timezone.
- Inclusion for viewer V: status pending, folder accessible to V, and either (assignee = V and due_date on or before today(V)) or an entry (task, V) exists. added_on is never in the future, so the on-or-before check holds by construction.
- Grouping: qualify_date = the earliest of (due_date, when assigned to V) and (added_on, when an entry exists). Today group when qualify_date = today(V); carried group when earlier. A task due yesterday and pulled today is carried, because it already qualified yesterday.
- Un-pull exists: deleting the entry, offered on rows whose inclusion came from an entry. A row that also qualifies automatically stays after un-pull.
- Pulling a future-dated task or a task assigned to someone else is allowed; the row shows its assignee chip. The settled decision that My Day filters by assignee applies to automatic inclusion only; a pull is the user's explicit override. This is a clarification of the settled decision, flagged here, not a silent change.
- Entries are never cleared by completion or abandonment (the recap below needs them; abandoned rows are already filtered by status). They are deleted on manual un-pull, on task deletion, and on loss of folder access.
- Completed-today recap section: status completed, completed_at falling on today in V's timezone, and (assignee = V, or completed_by = V, or an entry (task, V) exists). completed_by comes from ISSUE-10. Abandoned tasks never appear in the recap; abandoning is not finishing.
**Cost of resolution:** One small table with cascade rules, one recap predicate, one un-pull endpoint. This is the marker v3 asked for, made safe for shared folders.

#### ISSUE-08
**Severity:** blocker
**Location:** Section 2, People, "Sharing triggered indirectly", against Section 2, Folders, task rules.
**Quote:** "If they're not, it starts the same invite flow, with the relevant folder attached automatically." Against: "A task's assignee must be a member of the folder that task lives in."
**Problem:** Between sending that invite and its acceptance, the assignment cannot exist without violating the membership rule, and v3 never says what the assignee field holds meanwhile. Worked example: Hassan assigns "Book venue" (folder Wedding) to sara@example.com, who has never used Dana. For days Sara is not a member. If the task stores her as assignee, the invariant breaks and every assignee-scoped query must special-case a ghost. If it stores nothing, the intent is silently lost when she accepts.
**Resolution:** The invite row carries an optional task_id. The task's assignee stays unchanged (usually null) while the invite is pending; the UI derives an "invite pending: sara@example.com" chip on the task from that row. On acceptance, membership is created first, then the assignment applies only if the task still exists, still lives in the invited folder, and is still unassigned; otherwise the assignment step is skipped silently and acceptance proceeds as a plain share. On cancel or decline, the task is untouched. Creating a new pending assignment-invite for the same task clears task_id on the previous one: at most one intended assignee per task.
**Cost of resolution:** One nullable column on invites, one conditional step in the accept transaction, one derived chip. The assignee-membership invariant stays unconditional.

### Majors

#### ISSUE-09
**Severity:** major
**Location:** Section 3, Planned, opening paragraph, and Section 2, Task Creation, field dependencies.
**Quote:** "The moment someone clears a task's date, it leaves Planned and lands back in Tasks automatically, same as the reverse direction already works."
**Problem:** Clearing due_date is described as a clean home change, but three fields depend on the date and v3 gates only their creation, not their survival. Worked example: "Dentist", due 2026-07-28 at 15:00, reminder 30 minutes before, recurring every 6 months. Hassan clears the date. Now due_time attaches to no day, the reminder counts back from nothing, the recurrence has no anchor, and the reminder scheduler may still fire.
**Resolution:** Clearing due_date cascades in the same transaction: due_time set null, reminder deleted, recurrence rule deleted (the series ends; the client warns that clearing the date ends the recurrence). Check constraints make the dependency structural: due_time null unless due_date set; recurrence rule null unless due_date set; no reminder without a due date. The client keeps dependent inputs disabled until a date exists (ISSUE-27 picks disabled over hidden), but the constraints are the enforcement.
**Cost of resolution:** Three check constraints, one cascade in the update path, one warning dialog.

#### ISSUE-10
**Severity:** major
**Location:** Section 2, Folders, "What folder sharing grants, concretely". Open question 9.
**Quote:** "Any member can open, complete, or edit any task in the folder."
**Problem:** Concurrent edits are guaranteed by design and v3 says nothing about conflict behavior. Worked example: Hassan and Imran both open "Buy paint". Hassan sets due 2026-07-25 while Imran completes it; or both complete it at once; or Imran completes it while Hassan deletes it. Undefined whose write survives and whether a double completion double-fires recurrence generation (ISSUE-02).
**Resolution:** v1 policy, boring by intent.
- No realtime channel. Clients refetch on window focus and after their own mutations. Stale reads are accepted.
- Field edits use PATCH carrying only changed fields; concurrent edits to different fields both survive; the same field is last write wins. The lost-update window is accepted for v1 and documented; no version column, no ETags.
- Status changes are not field edits: dedicated endpoints (complete, un-complete, abandon, restore) enforce the state machine as guarded updates, of the form UPDATE tasks SET status = completed, completed_at = now(), completed_by = actor WHERE id = X AND status = pending. Zero rows updated means the caller lost the race. Completing an already-completed task returns success as a no-op, idempotent. Complete on abandoned returns 409, restore first. Abandon on completed returns 409.
- Recurrence generation runs inside the winning transition's transaction, so the guard makes generation exactly-once under any race.
- Any operation on a deleted task returns 404 and the client drops the row.
- completed_by is the one schema addition; it also feeds the My Day recap (ISSUE-07) and the eventual v2 activity log.
**Cost of resolution:** One column, guard clauses on four endpoints, a refetch-on-focus rule. Explicitly deferred: websockets, presence, CRDTs, offline merge.

#### ISSUE-11
**Severity:** major
**Location:** Section 2, People, "Accepting an invite". Open question 7.
**Quote:** "If their Google account's email matches the invited address exactly, the pending invite is waiting for them, one tap to accept. A different Google account sees nothing, the invite was never tied to it."
**Problem:** "Matches exactly" is undefined against real email behavior. Worked example: Hassan invites Sara.Khan@gmail.com. Sara's Google account reports sara.khan@gmail.com (case differs) or sarakhan@gmail.com (Gmail ignores dots). Byte-exact matching strands the invite forever, and v3 offers no way to see or fix a stranded invite. There is also a real security edge: a typo invites a stranger, and whoever owns that mailbox can sign in and accept.
**Resolution:** Matching is case-insensitive and nothing more: emails stored lowercased, compared lowercased. No Gmail dot or plus normalization; guessing provider aliasing rules risks matching the wrong account, which is worse than missing a match. Whether Google's email claim returns the dotted variant as registered needs verification and must not be assumed either way. The mitigations carry the weight: pending invites are listed with their exact email in the folder's sharing panel and in a sent-invites list, each with cancel and resend, so the failure mode is visible and correctable instead of silent. The typo risk is inherent to email invites in every product that has them; visibility plus cancel is the standard mitigation, and it is how Notion and Linear handle the same edge.
**Cost of resolution:** Lowercasing at write and compare, a pending-invites list, cancel and resend endpoints shared with ISSUE-12.

#### ISSUE-12
**Severity:** major
**Location:** Section 2, People, "Starting an invite". Open question 6.
**Quote:** "Dana creates a pending invite tied to that exact email. If a folder was attached, the invite carries it. One notification email goes out."
**Problem:** The invite has a birth and no lifecycle. Undefined: expiry, cancellation, resending, declining, duplicates, inviting yourself, inviting an existing member, invites whose folder is deleted or whose sender deletes their account, and acceptance by someone who became a member through another path meanwhile.
**Resolution:** Invite states: pending, accepted, declined, canceled, invalidated.
- No time-based expiry in v1. The email link carries no secret; acceptance is gated by Google login plus email match, so an old invite is a standing intention, not a credential. Inviter-side cancel is the control. Revisit if stale grants confuse anyone.
- Cancel: by the inviter or the folder owner, pending only.
- Decline: by the matched recipient, terminal, visible to the inviter, no notification email.
- Resend: re-sends the email on the same pending row, throttled to one resend per invite per 24 hours.
- Invalidated automatically when the attached folder is deleted or the inviter's account is deleted.
- Uniqueness: at most one pending invite per (inviter, email, folder), folder null included, enforced by a partial unique index. Sending again surfaces resend, not a duplicate.
- Validation: inviting your own email is rejected; inviting a current member of that folder is rejected with "already a member"; typing the email of someone already in your roster converts to the instant-share path Section 2, People already implies.
- Accepting when already a member (added meanwhile by another member): the membership grant is a no-op, the roster connection is still created if absent, the invite is marked accepted. Accepting any one of several pending invites creates the roster connection once; each folder-carrying invite grants only its own folder.
- Rate limiting on sending is a v4 non-functional requirement with a concrete number, because unlimited invite email to arbitrary addresses is a spam vector.
**Cost of resolution:** One status enum and one partial index on invites, five small endpoints, one throttle.

#### ISSUE-13
**Severity:** major
**Location:** Section 3, Done, "Un-completing a task from this page", against recurrence generation.
**Quote:** "Reverses status back to pending, and the task simply disappears from this view and reappears wherever it actually lives, Tasks or Planned depending on whether it has a due date. Nothing else about it changes."
**Problem:** For a recurring occurrence, "nothing else changes" is false: completing it generated a successor (ISSUE-02). Worked example: the bins occurrence due 2026-07-20 was completed; its successor exists due 2026-07-27, and Imran has already renamed the successor. Hassan un-completes the 2026-07-20 row. The series now has two pending occurrences, violating the one-pending invariant, with the rule on the wrong row.
**Resolution:** Un-complete on a recurring occurrence is guarded: allowed only while the successor still exists and is still pending, in which case the successor is deleted (edits to it are lost; the confirmation dialog says it removes the next scheduled occurrence), the rule moves back, and the restored row becomes the current occurrence. If the successor was itself completed or abandoned, un-complete returns 409 with copy explaining the series has moved on. Non-recurring un-complete stays exactly as v3 wrote it, with completed_at and completed_by cleared. The same guard applies to restoring an abandoned occurrence (ISSUE-34).
**Cost of resolution:** One guard branch, one confirmation dialog, symmetric handling in restore.

#### ISSUE-14
**Severity:** major
**Location:** Section 3, Planned, "Recurring tasks" and "Completed tasks, with one real exception this page needs and the others don't".
**Quote:** "So the calendar draws virtual instances, computed fresh from the recurrence rule, purely for whatever date range is currently visible, and throws that computation away the moment you scroll elsewhere."
**Problem:** Unbounded projection double-draws and fabricates history. Worked example: bins, weekly Monday, current occurrence due 2026-07-27, completed rows on the 13th and 20th. July month view: the rule projects onto the 6th, 13th, 20th, and 27th. The 13th and 20th each show a real completed row plus a virtual instance, drawn twice. The 6th shows a virtual instance for a week where nothing was materialized and nothing was done, fabricated history. The 27th shows the real pending row plus its own projection.
**Resolution:** Virtual instances are projected only for rule instances strictly after the current occurrence's due date, intersected with the visible range. On or before that date, only real rows draw: completed and abandoned occurrences on their dates (faded, per Planned's look-back rule), the pending current occurrence on its date, and honest gaps where nothing was materialized. Virtual instances render in a ghost style and open the series' current occurrence when clicked. Year zoom projects by the same rule; a daily rule at year zoom is hundreds of ghosts, so year zoom may render density markers instead of rows, a v4 rendering decision flagged here for performance.
**Cost of resolution:** One lower bound in the projection function, one ghost style. Deduplication becomes unnecessary by construction.

#### ISSUE-15
**Severity:** major
**Location:** Section 2, Folders, "What a task's folder membership means".
**Quote:** "This field is never empty in the data model, moving a task between folders, including into or out of the Default Folder, is always the same operation."
**Problem:** The move operation has no stated permission bound and no assignee revalidation. Worked example: "Book venue" sits in Wedding (members Hassan, Imran, Sara), assigned to Sara. Imran moves it to Home (members Hassan, Imran). Sara is not a member of Home, so the assignee-membership rule breaks silently. Worse, Imran can move it to his own Default Folder, where it vanishes from Hassan's and Sara's view entirely: any member can privatize any shared task.
**Resolution:** A move requires the mover to be a member of both source and target folders. On move, if the current assignee is not a member of the target, the task becomes unassigned and the client warns before confirming; moving into any single-member folder auto-assigns to that member (ISSUE-20). Steps, reminder, and recurrence travel with the task; My Day entries persist and simply stop matching for users who lose access, since the query joins on access. The privatization path through the mover's own Default Folder remains possible and is accepted, plainly: members you share with already hold full edit, complete, and delete rights over everything in the folder, so movement adds no new trust exposure, and comparable products (Todoist among them) allow the same. Named here so it is a decision, not an oversight; the v2 activity log is the eventual mitigation.
**Cost of resolution:** Two membership checks, one revalidation rule, one warning dialog.

#### ISSUE-16
**Severity:** major
**Location:** Section 3, Planned, reminder paragraph, and Section 2, Task Creation, reminder field.
**Quote:** "If due_time is set, a reminder is naturally an offset before that exact moment, remind me 30 minutes before or whatever time (still debatable) via email or sms or anything."
**Problem:** "Email or sms or anything" is not a delivery spec, and the recipient is undefined. Worked example: Imran sets a reminder on "Dentist" in the shared folder, assigned to Hassan. Who gets pinged, over what channel, scheduled by what process, and what happens when Sara later moves the due date? None of it is answered. SMS in particular smuggles in a vendor, per-message cost, and sender registration, a real operational burden for a two-person team.
**Resolution:**
- Channel, v1: email only. The invite flow already forces an email provider with domain authentication (SPF, DKIM), so reminders reuse it. SMS is cut from v1 outright. Web push is deferred: per-device subscriptions, and on iOS it requires an installed PWA with platform-version constraints that need verification; not v1.
- Recipient: the assignee at fire time. If the task is unassigned at fire time, the reminder is skipped and logged, not broadcast to all members.
- Storage: with due_time set, the reminder is an offset in minutes before the due instant; with only a date, it is a wall-clock time on the due date, exactly as v3 describes. Fire instant computed per ISSUE-06 in the assignee's timezone.
- Rescheduling: the fire instant is recomputed whenever due_date, due_time, the offset or time, the assignee, or the assignee's timezone changes; the reminder is canceled when it is removed, the date is cleared (ISSUE-09), or the task leaves pending. A recomputed instant already in the past does not fire retroactively.
- Delivery machinery, burden named explicitly: something must wake up and send. v1 uses a per-minute scheduler polling due reminder rows, at-least-once, with a sent marker. This is the single piece of background execution v1 needs (recurrence needs none after ISSUE-02), and it constrains the hosting choice in v4 section 7.11.
- On recurring carry-forward (ISSUE-02), the configuration copies to the next occurrence and its fire instant is computed fresh.
**Cost of resolution:** One reminders table or column set, one scheduler loop, email templates. Cut: an SMS vendor and push subscription plumbing.

#### ISSUE-17
**Severity:** major
**Location:** Section 2, People, "Revoking access" and the roster paragraphs. Open question 8.
**Quote:** "This does not remove them from your workspace roster, that's a separate action, and it only affects future sharing, not anything already granted elsewhere."
**Problem:** The separate action is named and never specified. Undefined: whether a pair can hold duplicate connections, whether removal is unilateral, whether it is symmetric, and what happens to already-shared folders. Worked example: Hassan removes Imran from his roster. Does Imran still see Hassan in his own roster, an asymmetric state the symmetric-creation rule cannot even represent? Do the three folders they share break?
**Resolution:** A roster connection is one row per unordered user pair, unique on (lower id, higher id), so duplicates are structurally impossible and the answer to more-than-one-connection is no. Removal is unilateral in initiation and symmetric in effect: either side deletes the row and both lose each other, mirroring symmetric creation. Existing folder memberships are untouched, exactly as the quoted sentence requires; the pair loses only the pick-from-list shortcut, and a future share requires a fresh email invite, which recreates the connection on acceptance. No notification on removal. Concurrent mutual acceptance upserts the same row, idempotent.
**Cost of resolution:** One table with one unique index, one delete endpoint, one line of copy explaining that removal unshares nothing.

#### ISSUE-18
**Severity:** major
**Location:** Section 2, Folders, "Completion tracking". Open question 4.
**Quote:** "A folder shows a direct count of its own tasks, done versus total."
**Problem:** Two ambiguities. Per viewer or global: an assignee-scoped count would differ per member, and v3 gives no scoping. Abandoned: with 10 tasks, 4 completed, 2 abandoned, the count is 4/10, 4/8, or 6/10 depending on unstated choices, and under 4/10 a folder containing any abandoned task can never read complete.
**Resolution:** The count is global, identical for every member, computed over the folder's tasks with no assignee filter, matching the everyone-sees-everything model. Formula: completed over (pending plus completed). Abandoned tasks are excluded from both sides; giving up neither blocks completeness nor counts as finishing. A folder with zero pending and zero completed shows no count rather than 0/0. Recurring series accrete: each completed occurrence adds one to both sides over time, so long-lived folders trend upward; accepted as honest, it is the same data the Done trail celebrates.
**Cost of resolution:** One aggregate in the folder list query, one definition line in the spec.

#### ISSUE-19
**Severity:** major
**Location:** Section 1, Concept. Open question 10.
**Quote:** "Dana is a webapp, built as a PWA. This means it can be installed and used like real software, but without needing separate OS-level compilations, builds, or signatures for iOS/Android/desktop."
**Problem:** Installability is claimed; offline behavior is never mentioned. An installed app that white-screens without network reads as broken, but each step past that ratchets complexity: cached reads need invalidation, offline writes need a sync and conflict engine, the largest hidden subsystem a to-do app can take on, and one that contradicts the last-write-wins simplicity chosen in ISSUE-10.
**Resolution:** v1 is online-only with a cached shell. The service worker precaches the application shell and static assets, so the installed app always opens instantly. Data requests require network; without it the app shows its last in-memory state if any, plus a persistent offline banner, and writes fail fast with a visible error instead of queueing. No IndexedDB mirror, no background sync, no optimistic offline queue. The upgrade path, read-only cache first and a write queue much later, is v2 material. This still satisfies PWA install criteria: manifest, service worker, and an offline-capable start URL answering with the shell.
**Cost of resolution:** A precache manifest and an offline banner. Deliberately avoided: a sync engine.

#### ISSUE-20
**Severity:** major
**Location:** Section 2, People, "Revoking access", against Section 3, My Day, automatic inclusion.
**Quote:** "Any task assigned to them inside it stays, it just becomes unassigned, nothing gets deleted."
**Problem:** Unassignment exists, so assignee is nullable, and combined with assignee-scoped My Day this creates a silent pit: an unassigned task due today appears in nobody's My Day, forever, while remaining due today in Planned. Worked example: Sara is removed from Wedding; "Book venue", due 2026-07-25, becomes unassigned; the 25th arrives and it surfaces on no one's My Day, and nothing points at it. In single-member folders the pit is worse: a solo user who unassigns a task loses My Day for it entirely, in the app's main view.
**Resolution:** Three rules.
- In any folder with exactly one member, every task is assigned to that member: creation forces it, moving in forces it (ISSUE-15), and explicit unassignment is rejected server-side. This makes the Default Folder case structural (v3 already hides the field there) and closes the solo pit completely.
- In multi-member folders, explicit unassignment is allowed; member removal requires the state anyway. The pit is narrowed by surfacing, not prohibition: unassigned dated tasks carry an "unassigned" chip in Planned, All, and folder views, so members can see what fell off everyone's radar. They deliberately do not appear in every member's My Day; spamming all members was considered and rejected.
- Assignment defaults to the creator everywhere, exactly as v3 says.
**Cost of resolution:** One server-side guard, one chip, no schema change.

#### ISSUE-21
**Severity:** major
**Location:** Section 3, All, search paragraph, and Section 3, Tasks, "Completed tasks".
**Quote:** "Search needs to live in the global chrome, available from anywhere in the app, completely independent of whether All itself is shown in the sidebar."
**Problem:** Search is load-bearing (completed tasks are "still reachable by search" per Section 3, Tasks; abandoned reachability partly leans on it after ISSUE-01) yet has no specification at all: no scope, no fields, no ordering, no UI beyond "global chrome".
**Resolution:** v1 search: a persistent control in the top bar with a keyboard shortcut, matching title and notes, case-insensitive substring or trigram matching (Postgres pg_trgm; boring and sufficient, ranked full-text deferred), scoped to every folder the viewer can access, all three statuses, results grouped pending then abandoned then completed, each row showing folder, due date, and status, capped with a load-more. No filters or operators in v1.
**Cost of resolution:** One endpoint, one index, one overlay UI. Confirmed dependency: none on the All page, per the quote.

#### ISSUE-22
**Severity:** major
**Location:** Section 2, Folders, Custom Folder paragraph, and the hierarchy block.
**Quote:** "Can carry an optional label or color, used purely for the owner's own sidebar sorting when they have a lot of folders."
**Problem:** The sidebar and the folder detail view, the two surfaces where folders are actually used, are unspecified. Undefined: whether folders list in the sidebar at all (only the six pages are specified), in what order, where per-member labels and colors live in the data model, and what opening a folder shows. Section 2, Task Creation references "whichever sub-view of that folder you're looking at", and those sub-views are defined nowhere.
**Resolution:**
- Sidebar: pages first, per visibility settings, then the folder list: Default Folder pinned first, then custom folders ascending by name, case-insensitive. Label and color live on the membership row (folder_members.label, folder_members.color), per member by construction, which is what the quote's personal-grouping behavior requires. Labeled folders render under their label as collapsible groups, labels sorted ascending, unlabeled folders after. No drag ordering of folders in v1 (ISSUE-30 makes the same cut for tasks).
- Folder detail view: scoped like All: a dated section rendered exactly as Planned's list mode, then an undated section in creation order, both filtered to the folder, abandoned rows inline per ISSUE-01, plus a collapsed completed section at the bottom, cursor-paginated like Done, because the completion count of ISSUE-18 needs its history inspectable in place. Task creation from here pre-fills the folder, and the date per sub-view, as Section 2, Task Creation already states. The member management panel hangs off this page.

**Cost of resolution:** Two columns on folder_members, one full page specification, reuse of two existing render modes.

#### ISSUE-23
**Severity:** minor
**Location:** Section 2, Task Creation, fields list.
**Quote:** "Steps. Add one, press enter, get a blank row for the next, freely reorderable."
**Problem:** Steps have no completion semantics. Undefined: whether checking every step completes the task, whether completing the task checks remaining steps, whether steps carry dates or assignees, whether order is shared, and any cap.

#### ISSUE-29
**Severity:** minor
**Location:** Section 3, Planned, "Recurring tasks".
**Quote:** "Also recurring tasks must have a start and end date also so it's not recurring up to hell."
**Problem:** The mandate conflates storage with projection. Nothing recurs "up to hell" structurally: only one occurrence is ever materialized (ISSUE-02) and calendar projection is bounded by the visible range (ISSUE-14). Forcing an end date on "take out the bins weekly" makes the commonest recurrence use case invent a fake horizon.
**Resolution:** Overturned. A recurrence rule requires an anchor, the first occurrence's due date, and optionally an end, either an until-date or a count, per RFC 5545 RRULE semantics, which v4 will adopt as the storage format. Unbounded rules are legal and safe.
**Cost of resolution:** Removes a required input; aligns with the standard v4 would use anyway.

#### ISSUE-30
**Severity:** minor
**Location:** Section 3, Tasks, "Sort order inside a group", and every page's implementation note.
**Quote:** "No due date to sort by, so it defaults to creation order, newest first, and can be manually reordered by drag if someone wants a specific order within a folder's undated pile."
**Problem:** Two gaps. First, no page defines a total order: ties on the same due date and time, all-day against timed rows on one date, folder group ordering, and My Day's within-group order are all unspecified, while the brief requires two independent agents to produce identical result sets. Second, drag reordering smuggles in a position system v3 never models, with the shared-against-personal question unanswered: whose view does Imran's drag change?
**Resolution:** Two parts.

Defaults to lock there: Tasks, groups ordered Default Folder first then folder name ascending, rows by created_at descending; Planned, due_date ascending, all-day rows before timed rows within a date (calendar convention), then due_time ascending, then created_at, then id; Important, dated block then undated block per v3, same internal orders; Done, completed_at descending then id; My Day, carried group before today group, internally by due_date then due_time then id; pending before abandoned everywhere per ISSUE-01.
- Drag reordering of tasks is cut from v1, flagged per the brief: creation order only. The cut removes the personal-against-shared ambiguity and a position-maintenance subsystem; v3 itself calls the choice "Small detail, not architecture". Revisit with real usage.
Also recorded: only Done specifies pagination; v4 must state the strategy per page, with cursor pagination on Done and folder completed sections and a bounded fetch with a cap elsewhere.
**Cost of resolution:** Deterministic order clauses; one feature deferred.

#### ISSUE-34
**Severity:** minor
**Location:** Section 3, My Day, "Nothing here is ever silently removed". Open question 5.
**Quote:** "Abandoned means it stops resurfacing here going forward, its due date stays exactly as it was for the record, and it remains fully visible in its actual home and in All."
**Problem:** Abandonment is specified as an exit and never as reversible. Undefined: whether an abandoned task can return to pending, and what happens to its dates if so.
**Resolution:** Resurrection exists: a restore action, available anywhere the abandoned row renders (its home per ISSUE-01, search results), transitions abandoned to pending. **Cost of resolution:** One transition in the state machine, already needed for symmetry with un-complete.

## Part 2. Undefined-state enumeration

The page-visibility state space is status (3 values) by due_date (null or set), with important, assignment, and pull entries modulating only Important and My Day. All six combinations, as v3's queries read, for a viewer V with folder access:

| status | due_date | Tasks | Planned | All | Important (if flagged) | Done | My Day |
| - | - | - | - | - | - | - | - |
| pending | null | yes | no | yes | yes | no | only via V's pull entry |
| pending | set | no | yes | yes | yes | no | if assigned to V and due on or before today(V), or pulled by V |
| completed | null | no | no | no | no | yes | recap section if completed today (ISSUE-07 predicate) |
| completed | set | no | no | no | no | yes | recap section same; also drawn faded on past calendar dates in Planned |
| abandoned | null | none | none | none | none | none | none |
| abandoned | set | none | none | none | none | none | none |

The two abandoned rows are visible on zero pages as written, which is ISSUE-01. After its resolution they appear in Tasks or Planned by date, in All, and in Important when flagged, rendered distinct, still never in My Day's open list or Done.

Combinations that must be impossible, enforced as constraints (ISSUE-09, ISSUE-10, ISSUE-20):
- due_time set with due_date null.
- recurrence rule set with due_date null.
- a reminder existing with due_date null.
- status completed with completed_at null, or completed_at set on a non-completed row.
- an assignee who is not a current member of the task's folder.
- an unassigned task in a single-member folder.

## Part 3. Query consistency verification

The brief asks whether the six page queries are mutually consistent and whether Tasks and Planned partition All.

As written, over the pending scope: All = accessible AND pending. Tasks = All AND due_date IS NULL. Planned = All AND due_date IS NOT NULL. A single nullable column is either null or not, exhaustively and exclusively, so Tasks and Planned partition All with no gap and no overlap. The partition claim in Section 3, Tasks is correct as stated, and it survives ISSUE-01 unchanged, since the widened status condition is identical on all three pages.

Important is a strict subset of All (one added conjunct): consistent. Done is disjoint from All by status: consistent. My Day is not a subset of All: its recap section intersects Done for tasks completed today, by design, harmless because Done is historical; its open section is a subset of All restricted by assignment or pull.

Total coverage after resolutions: every task row is visible on at least one page. Pending and abandoned rows appear in All and their home page; completed rows appear in Done. Before the resolutions, abandoned rows escaped every page, the single worst query defect in v3.

## Part 4. Invariant sweep

Invariants the system must hold at all times, each with the operations that threaten it and the issue that closes the threat. v4 section 7.3 restates these as testable assertions.

- I1. Every task references an existing folder, non-null. Threats: folder deletion (ISSUE-04), owner account deletion (ISSUE-05).
- I2. Every non-deleted user has exactly one Default Folder; it is never shared, never deleted, and its owner never changes. Threats: concurrent first login (ISSUE-32, unique index), share and delete endpoints (ISSUE-03), account deletion ordering (ISSUE-05).
- I3. The Default Folder has exactly one membership row, its owner's. Threats: membership endpoints (ISSUE-03), folder-attached invites naming a Default Folder, rejected by ISSUE-12 validation.
- I4. A task's assignee is null or a current member of the task's folder. Threats: member removal (rule already in v3), task move (ISSUE-15), assignment-triggered invites (ISSUE-08), account deletion (ISSUE-05).
- I5. In a single-member folder, every task is assigned to that member. Threats: the unassign path (ISSUE-20 guard), moves into the folder (ISSUE-15).
- I6. due_time, recurrence rule, and reminders exist only while due_date does. Threats: clearing the date (ISSUE-09 cascade and constraints), racing form writes (ISSUE-27, server constraints).
- I7. A recurrence series has at most one pending occurrence. Threats: generation (ISSUE-02 single trigger), un-complete and restore (ISSUE-13 guard), concurrent completion (ISSUE-10 guarded transition).
- I8. status = completed exactly when completed_at and completed_by are set. Threats: every status transition (ISSUE-10 dedicated endpoints).
- I9. At most one roster connection per unordered user pair. Threats: concurrent mutual acceptance (ISSUE-17 upsert on the ordered-pair unique index).
- I10. At most one membership per (folder, user), and the owner always holds one. Threats: concurrent adds (unique index), owner leave and transfer (ISSUE-05 keeps the new owner's row).
- I11. At most one pending invite per (inviter, email, folder). Threats: repeat sending (ISSUE-12 partial unique index).
- I12. My Day entries are unique per (task, user) with added_on never in the future of the adder's timezone. Threats: the pull endpoint (ISSUE-07).

## Part 5. Data loss and security summary

Security holes as written: ISSUE-03 (any member can delete or rename any shared folder and evict its owner; the one finding that must not survive review), ISSUE-12 (unbounded invite email with no cancel path, a spam vector), ISSUE-11 (a typo'd invite is claimable by whoever owns that mailbox; mitigated by visibility plus cancel, inherent to email invites), ISSUE-15 (any member can privatize shared tasks by moving them into their Default Folder; accepted deliberately and documented, since members already hold full edit and delete rights).

Data loss as written: ISSUE-04 (folder deletion with unspecified task fate), ISSUE-05 (owner account deletion undefined), ISSUE-01 (abandoned tasks unreachable, indistinguishable from deletion for the user), ISSUE-13 (un-completing a recurring occurrence corrupts the series), ISSUE-09 (orphaned schedule fields, including reminders that can fire for dateless tasks).

Merely confusing: ISSUES 24, 25, 26, 27, 31, 33, and the determinism half of 30. The remaining issues are behavioral gaps that produce divergent implementations rather than corrupted data.

## Part 7. v3 decisions confirmed as deliberate

Recorded so they read as chosen rather than accidental, each with the standard or precedent it matches:

- Three-state status: matches Things 3 (open, completed, canceled). A boolean cannot express abandonment. Confirmed.
- Home derived from due_date alone: one predicate, no move operation to build or break. Confirmed.
- Folder as the only shareable unit, flat, single owner: matches Todoist project sharing; the complexity firewall held everywhere the audit pressed. Confirmed.
- Workspace as a non-entity granting nothing: confirmed, and reduced to no table at all (ISSUE-32).
- Hybrid My Day, automatic on-or-before-today plus manual pull with permanent snowball: the automatic half matches Todoist's Today with overdue, the manual half matches Microsoft To Do's My Day; sound once the marker is per-user (ISSUE-07). Confirmed.
- important as a boolean, not a tag system: matches Microsoft To Do. Confirmed.
- Single materialized occurrence with computed calendar projection: matches how Todoist stores recurrence; confirmed, with the generation trigger fixed (ISSUE-02) and RFC 5545 RRULE as the v4 storage format.
- All-day against timed rendering split: matches every calendar product. Confirmed.
- FAB bottom-right on every page except Done, plus the inline quick-add row: Material convention and the Things quick-entry pattern; inline row kept as the optional lean path v3 describes. Confirmed.
- Tasks page grouping with Default Folder ungrouped on top: v3 already cites Things 3. Confirmed.
- Done as cursor-paginated history grouped by completion day: confirmed.
- Page visibility toggles with three permanent pages: confirmed, defaults per ISSUE-26.
- Google-only OAuth, no separate auth system: confirmed for the team size; deletion obligations covered in ISSUE-05.
- Invite matching at login by email: the standard pattern (Notion, Linear), confirmed with the matching rule and safety valves of ISSUE-11 and ISSUE-12.
- No natural-language date parsing, no attachments, no activity log, all AI deferred: scope hygiene, confirmed; the landing page must stop contradicting it (ISSUE-24).
- One form for create and edit: confirmed.
