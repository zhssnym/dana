### 8.3 Concurrency policy

- Reads: no realtime channel in v1. Clients refetch the active view on window focus and
  after each own mutation. Staleness between those points is accepted.
- Field writes: PATCH sends only changed fields. Two members editing different fields both
  win; the same field is last write wins, and the lost update is accepted. No version
  columns, no ETags in v1.
- Status writes: only through the four transition endpoints, each a guarded update that
  changes the row only when it is still in the expected source status (implementation: the
  `transitionTask` in `app/src/server/domain/tasks.ts`). When the guard matches no row,
  the task is reloaded: already in the target status is an idempotent no-op returning the
  task; missing is 404; any other status is 409 per 5.1.

The guard makes recurrence generation exactly-once under any race: only the single winning
transition executes it, inside the same transaction. Operations on deleted rows return 404
and the client drops the row.

One narrow exception to otherwise field-local page writes: mixed page placement and
prose-to-task conversion lock the folder row and complete in one transaction. Callers name
adjacent item identities, never keys. Concurrent placements into one gap may produce equal
fractional keys; the read's final id key makes that one deterministic sequence without
losing either write. Block content and conversion require the `updated_at` evidence read by
the caller and answer 409 before any write when it is stale.
