### 8.7 Invites and sharing

**V-INV validations on create**, in order: email syntactically valid and lowercased; not
the inviter's own email; folder, when given, accessible to the inviter and not a default
folder; when a folder is given, the email must not belong to a member of it (409 "already
a member"); task, when given, inside that folder; if the email belongs
(case-insensitively) to an active user already connected to the inviter and a folder is
attached, convert to an instant share, subject to the 10.3 member cap (a full folder
refuses 422 and creates nothing, neither membership nor invite row): create the membership
immediately, send the share-grant email, create no invite row; if it belongs to such a
user and no folder is attached, 409 "already connected", since the connection the bare
invite exists to create already holds (INV-9); if a pending invite by this inviter to this
email for this folder exists, 409 pointing at it; rate limits per 10.4. Implementation:
`createInvite` in `app/src/server/domain/invites.ts`.

**Three entry paths, one mechanism**: 1. Direct: enter an email in the sharing panel
(folder attached) or in the People screen (bare). 2. Roster pick: choose a connected
person in the sharing panel; no invite, immediate membership, share-grant email. 3.
Indirect via assignment: assigning a task to someone outside the folder. Connected target:
membership created instantly, then the assignment applies, one transaction. Unconnected
target: an invite is created with folder_id and task_id set; the task's assignees stay
unchanged, and the UI shows the "invite pending" chip derived from that row.

**Acceptance transaction** (`acceptInvite` in `app/src/server/domain/invites.ts`), all or
nothing. The acceptor's lowercased email must equal the invite's and the invite must be
pending. Then:

1. The connection between inviter and acceptor is upserted (INV-9, idempotent).
2. When the invite carries a folder: the folder row is locked; a folder in Trash refuses
   409 `folder_deleted`; when the acceptor is not yet a member, a folder already at the
   10.3 cap refuses 422, otherwise the membership is inserted (INV-10).
3. When the invite carries a task that still exists and is still in that folder, the
   acceptor is added to its assignees unless already present; otherwise that step is
   skipped silently.
4. The invite becomes accepted, with accepted_by and responded_at set.

**The 10.3 member cap binds every membership this section grants**: the instant-share
conversion and the acceptance each lock the folder before counting, so the count and the
insert are one decision. A refused acceptance rolls back whole and leaves the invite
pending, acceptable once the folder has room; a silent skip would consume the invite and
grant nothing. A refused conversion tells the inviter the folder is full now rather than
parking an invite the same cap would refuse.

**A folder sitting in Trash refuses the acceptance** with 409 `folder_deleted`, and the
whole transaction rolls back, so the invite stays pending and no connection is written.
Refusing rather than cancelling the folder's invites at deletion means a restore within
the Trash window makes the invite acceptable again with nothing else to do; letting the
acceptance through would grant a membership on a folder nobody can open. The guard is
checked even when the acceptor is already a member, because the acceptance response
carries the folder (7.5). It takes the same folder lock as the cap, so a deletion
committing first refuses and one arriving later lands after the grant, which is 8.8's
ordinary case of a folder deleted out from under its members.

The three refusals of an acceptance carry distinct codes because a person needs a
different sentence for each: an invite that is not the caller's reads 404 (7.5's leak
rule), an invite no longer pending reads 409 `conflict`, and a folder in Trash reads 409
`folder_deleted`.

Matching is case-insensitive equality and nothing more; no Gmail dot or plus
normalization. Stripping dots is right for Gmail and wrong for every domain that treats
them as significant, and getting it wrong merges two people; 10.1 carries the same rule
for accounts. A stranded invite (address variant mismatch) is repaired by the inviter
through the visible pending list with cancel and resend. Multiple pending invites to one
email are all surfaced at login; each acceptance grants only its own folder; the
connection is created once. Creating a new assignment-invite for a task clears task_id on
any earlier pending invite for that task.

**Assumption: invites never expire.** Safe because acceptance is login-gated and the link
carries no secret. Revisit on any report of confusing stale grants; the change is a status
sweep plus an expiry display, with no schema change.
