### 12.15 Files, images and avatars

Upload, quota, what is served back and under which headers, and what a deletion takes with it. The composer's media blocks that name these files are 12.9.

- AC-194 Given an upload within the 10.3 caps, then a files row exists and the uploader's quota is spent; given an account at quota, then 413; given a mime that does not match the declared kind, then 422 naming the field.
- AC-195 Given a stored file in a shared folder, when a non-member requests it, then the 10.2 not-found shape; when a member requests it, then the bytes.
- AC-196 Given an avatar upload, then users.avatar_url resolves to the stored object.
- AC-230 Given a stored file requested with no session, then 401, never the bytes and never 404.
- AC-231 Given an upload declaring an image kind with mime image/svg+xml, then 422; and given a raster upload carrying an HTML tail behind a valid image, then what is served is re-encoded with no tail surviving.
- AC-232 Given a served file of kind file, then the response carries X-Content-Type-Options: nosniff and Content-Disposition: attachment; given a served image, then nosniff and inline.
- AC-233 Given an account at its 1 GB storage quota, when it uploads another file, then 413 with section 9's copy and no files row is created.
- AC-234 Given a deleted account (8.10), then its avatar answers 404 to a signed-in account that held the id, and no files row owned by the deleted account remains.
- AC-235 Given a folder in Trash past 30 days holding stored files, when the 11.7 pass purges it, then the files rows are gone and their objects are absent from the store.
- AC-360 Given an uploaded avatar, when `DELETE /api/v1/me/avatar` is called, then 204 with no body, `GET /me` answers `avatar_url` null, no avatar files row of that account remains, and the object stops being served; and a second call answers 204 again (spec 7.15, 4.1, 4.16, 9.7).
- AC-361 Given an image upload, then the `files` row and the 201 answer carry the width and height of the stored re-encode, so an image past the 2048px edge records its downscaled shape (spec 4.16, 7.15).
- AC-362 Given an upload of a kind that carries no picture, then its width and height are null on the answer and the row; and a row claiming a dimension for such a kind, half a pair, or a zero or negative edge is refused by the database's CHECK (spec 4.16).
- AC-370 Given POST /api/v1/files with kind cover and no folder_id, then the picture stores as the caller's, downscaled and measured like any image; and given kind `voice`, the only kind that takes its visibility from a folder, with no folder_id, then 422 naming the field (spec 4.16, 7.15, 10.3).
- AC-371 Given a picture stored with no folder, then its owner is served the bytes and every other signed-in account, a folder-mate included, meets the 10.2 not-found shape; an avatar still serves to any signed-in account; a folder-scoped file is its members'; and the same predicate decides which file a cover may name (spec 4.16, 7.15, 7.19, 10.2).
- AC-398 Given a file in a shared folder, when a member who is neither uploader nor folder owner reads it and tries to delete it, then 200 and 403 `forbidden` with the bytes surviving; a non-member's delete is 404; the uploader and the folder owner each delete at 204; and a stranger's delete of anybody's avatar is 403 and removes nothing (spec 7.15, 10.2, 4.16).
- AC-490 Given kind `file`, when a payload with an unknown, missing, double or self-contradicting extension is uploaded, then each is stored as a `file` keeping its name and declared MIME verbatim, none reclassified by its filename; and one byte past 10.3's 25 MiB is 422 (spec 4.16, 7.15, 10.2, 10.3).
- AC-491 Given one file uploaded twice under the same name and type, once as previewable media and once through the File command, then two independent rows keep the kind each was declared with, and the media one serves `Content-Disposition: inline` and the File one `attachment`, both with `nosniff` (spec 4.16, 7.15).
- AC-492 Given kind `audio`, then `audio/mpeg`, `audio/mp4`, `audio/ogg`, `audio/wav` and `audio/webm` over bytes of the named container store as `audio`; an unlisted type, a non-audio type, or a listed label over another container's bytes is 422; and the same refused payloads sent as kind `file` store as `file`. The check is declared type against the list plus a leading-bytes container signature, never codec validation (spec 4.16, 7.15, 10.3).
- AC-493 Given kind `video`, then `video/mp4`, `video/webm` and `video/ogg` over bytes of the named container store as `video`; QuickTime, an unlisted type, an audio type declared as video, or a listed label over another container's bytes is 422, on AC-492's two-part check (spec 4.16, 7.15, 10.3).
- AC-494 Given kind `voice`, then `audio/ogg;codecs=opus` still stores, a non-audio type is 422, an upload naming no folder is 422, and a note past 10.3's ten minutes is 422; the media allowlists do not apply to voice (spec 4.16, 7.14, 7.15, 10.3).
- AC-495 Given a stored `file` read by its uploader, then 200 with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff` whatever MIME was declared, a `text/html` payload under a `.png` name included (spec 4.16, 7.15, 10.2).
- AC-496 Given a `file`, `audio` or `video` uploaded with no `folder_id`, then it stores and is its uploader's alone: they read it at 200 and a second account, even one sharing a folder with them, meets the 10.2 not-found shape (spec 4.16, 4.18, 7.15, 10.2).
- AC-497 Given a `file`, `audio` or `video` scoped to a folder, then it follows that folder's boundary both ways: a non-member meets not-found, reads it at 200 once added as a member, and meets not-found again once removed (spec 4.3, 4.16, 7.15, 10.2).
- AC-601 Given `kind=audio`, when a payload carries an allowlisted leading signature over other content (an executable behind `ID3`, a ZIP behind RIFF/WAVE, a UTF-16LE HTML document whose `FF FE` mark is a legal MPEG sync), then each stores as `audio`, while bytes with no allowlisted signature are 422; and serving such a row carries `nosniff`, the declared audio `Content-Type`, and 10.8's policy with `default-src 'self'`, `object-src 'none'` and no `unsafe-inline` in `script-src`, while the same bytes as a `file` are an attachment — the headers, not the container check, are what make such bytes harmless (spec 4.16, 7.15, 10.3, 10.8).
