### 11.11 Hosting and delivery

- **Render**: one Starter web service plus one Render Postgres instance (cheapest paid
  tier), same region, deployed from GitHub on every push to `main`. Merging deploys.
  Production is exactly one instance (11.1).
- **Backups**: Render Postgres is paid from day one because the free tier expires after 30
  days and has no recovery. The paid tier's point-in-time recovery (3-day window on the
  Hobby workspace) is the primary backup; a monthly `pg_dump` kept off-platform guards
  against account-level failure. A restore drill goes into a scratch instance, runs the
  constraint catalog test against it, and destroys it.
- **CI** is GitHub Actions on a self-hosted runner on the owner's machine, with that
  machine's own Postgres cluster as the test database (11.10). It runs on every pull
  request and every push to `main`: lint, typecheck, the test suite on a real Postgres, and
  build, then a Playwright browser smoke against that build. A job queued while the machine
  is off waits rather than fails. A self-hosted runner executes whatever a workflow on any
  pushed branch tells it to, on a machine holding the owner's data; that is acceptable only
  while the repository is private and every writer is trusted, and making it public or
  admitting an outside collaborator means moving CI off that machine.
- **Locally**, `npm run gate` in `app/` runs the same six steps (npm ci, lint, typecheck,
  test on a real Postgres, build, Playwright) and prints a record of what each reported.
  Without `TEST_DATABASE_URL` the tests fall back to PGlite and the record says
  `incomplete` rather than green, because it has not answered for the engine production
  runs. `docs/troubleshooting.md` covers what goes wrong with either.
- **Environments**: production and local only, no standing staging. After a deploy, the
  production smoke is health, an auth round trip, and one CRUD cycle. A throwaway Render
  service restored from point-in-time recovery stands in for staging when a release
  warrants a rehearsal.
- **Secrets**: Render environment variables in production, `app/.env` locally, and an
  `.env.example` naming every variable. A credential for a resource GitHub cannot reach is
  never stored at GitHub: every workflow on every branch can read a repository secret, so
  storing it there widens exposure and buys nothing. The runner's `TEST_DATABASE_URL` lives
  in the runner installation's own `.env`, outside every working tree. It authenticates as
  a dedicated `dana_ci` role with CREATEDB, never the superuser (pg_trgm is a trusted
  extension, so a database owner can install it). The workflow never echoes it.

**Exactly one proxy hop stands in front of the process.** Render's edge terminates TLS and
opens its own socket to the service, so without Express's `trust proxy` every request
appears to come from the edge and every address-keyed rate limit is one bucket for the whole
deployment. `createApp` sets `trust proxy` to `1`, never `true`, which would trust a header
the client writes. The count is a claim about this hosting: a CDN or second proxy in front
of Render makes it `2`, and anyone changing what stands in front of the service owes that
number an edit. 10.4 carries what the limits mean under it (AC-410).

Render does not document that its edge sets `X-Forwarded-For`; that it does is strongly
implied (Render defaults `FORWARDED_ALLOW_IPS=*` for Python services) but unverified. If it
does not, one trusted hop makes `req.ip` whatever the caller writes in that header, and
per-address limits stop limiting without announcing it. Checking `req.ip` against the
deployed service once is what settles it, and that check needs a one-off exception to
10.5's rule keeping caller addresses out of the log.

**This deployment answers on exactly one host and redirects every other one to it.**
APP_ORIGIN names the canonical host, and the Google callback, the CSP reporting endpoint and
every link in an 11.8 email are built from it, never from the request. Session cookies are
host-only (10.1), so two addresses serving the application are two cookie jars: a sign-in
always lands on the canonical host, and the Render address of the same service would show
no session at all. When APP_ORIGIN is set, a request whose `req.hostname` (trust-proxy
aware, compared case-insensitively) is not its hostname is answered ahead of everything
else:

- **GET and HEAD: 301** to the same path and query on the canonical origin, permanent so a
  stale bookmark heals itself.
- **Every other method: 404** in the 7.0 envelope; a mutation on the wrong host carries no
  cookie for it anyway, and a 301 cannot move a body.
- **`/api/health` is exempt**, because Render's health check reaches the service by its
  non-canonical Render hostname and a redirect there fails every deploy.

It compares hosts, not origins, because cookie jars are keyed by host; the wrong scheme on
the right host is the TLS edge's concern, the same ground 10.8 gives it HSTS on. Nothing is
logged per request (10.5); the boot writes one line naming the host it enforces. Unset,
nothing redirects (AC-414). Implementation: `app/src/server/http/canonical-host.ts`.
