### 11.10 Testing infrastructure

The suite is a deliberately small core: security, data loss, and core smoke paths, plus the
colocated unit tests of pure logic. What is kept and the rule for adding a test:
`app/tests/README.md`.

- Vitest runs unit and acceptance tests. Acceptance tests exercise section 7 over HTTP
  against the real Express app in-process.
- **One construction seam.** Tests reach the application through `createApp(options?)` in
  `app/src/server/index.ts` (options: `AppOptions` there). It is synchronous, performs no
  I/O, and opens no database. options.dbClient injects the `app/db/client.ts` handle, the
  only way a test database arrives; the boot path always passes its own. options.auth
  injects the OIDC configuration and wins over the environment variables that remain the
  production path; the issuer is injectable because a module that hardcodes
  accounts.google.com cannot be tested at all. options.notifications injects a sink: when
  present, the 11.8 notification module delivers each outbound message to it instead of
  logging, which is what makes a send observable under test, since 11.8 forbids real
  sending there and 10.5 keeps recipient addresses out of the logs. Each delivered message
  identifies its template and its recipient. Routes that touch the database require
  options.dbClient and fail only when called without it, so database-free surfaces
  (health, route-presence probes) can construct the application bare.
- **One engine seam.** `app/db/client.ts` selects the database: PGlite (embedded Postgres
  18, in-process, no setup) by default, or a real Postgres via TEST_DATABASE_URL. The
  variable is scoped to test and database-script processes: a server entrypoint passes its
  connection string explicitly (DATABASE_URL) and clears TEST_DATABASE_URL from its
  environment before opening the seam. Real Postgres is the authoritative leg (11.11),
  being the engine production runs: a real client and server across a socket, a pool
  holding several sessions so that a second concurrent transaction is expressible where
  PGlite cannot hold one (11.15), the real planner, and the packaged pg_trgm. PGlite is the
  fallback for a machine without TEST_DATABASE_URL. The named fallback behind the same seam,
  should PGlite fail, is the embedded-postgres npm package.
- **The text ordering the suite runs on is fixed by the test database's own locale, never
  inherited from whatever cluster hosts it.** Section 6 asks its orderings to produce
  byte-identical result sequences, and neither the migrations nor the queries write
  COLLATE, so every ordering over a text column takes the database default. The Postgres
  leg's database is created with this statement, its normative form:

  ```sql
  CREATE DATABASE dana_test OWNER dana_ci TEMPLATE template0 ENCODING 'UTF8'
    LOCALE_PROVIDER builtin BUILTIN_LOCALE 'C.UTF-8' LC_COLLATE 'C' LC_CTYPE 'C';
  ```

  The builtin provider is code point order over Postgres's own Unicode tables, identical on
  every platform and version, and it is what PGlite does, so a disagreement between the two
  engines can only be an engine difference. A server older than 17 cannot parse
  `LOCALE_PROVIDER builtin` and falls back to libc `LC_COLLATE 'C' LC_CTYPE 'C.UTF-8'`.
  The ctype there must be `C.UTF-8` and not `C`: sorting is LC_COLLATE, but folding
  (`lower()`, `upper()`, ILIKE) is LC_CTYPE, and `C` folds ASCII only, so Q2's
  `lower(name)` order and Q8's ILIKE would diverge over accented text while ordering
  identically. Two checks prove a database conforms:

  ```sql
  SELECT datlocprovider, datlocale, pg_encoding_to_char(encoding)
    FROM pg_database WHERE datname = current_database();  -- must answer b, C.UTF-8, UTF8

  SELECT string_agg(v, '|' ORDER BY v) FROM (VALUES
    ('Zebra'),('apple'),('Apple'),('a-b'),('ab'),('coté'),('côte'),('_x')) AS s(v);
  -- must answer Apple|Zebra|_x|a-b|ab|apple|coté|côte, on Postgres and on PGlite alike
  ```

  No leg runs a linguistic collation, so the ordering production's Postgres serves is
  checked by nothing; that is accepted.
- **Tests never assert server message prose.** The message language is the cluster's
  superuser-context `lc_messages`, which a database owner cannot set. A rejection is
  asserted by its SQLSTATE and its structured schema, table, column and constraint fields,
  which no locale translates (`serverErrorFields`, `expectRejectedWith` in
  `app/tests/support/helpers.ts`). Likewise a catalog assertion reads structured facts
  from pg_constraint and pg_index, never deparsed SQL text.
- **Each Vitest worker gets a database of its own on the Postgres leg**, so no two test
  files running at once share rows. The unit is the pool slot (`VITEST_POOL_ID`): each
  slot's database, `<base>_r<run>_w<slot>`, is created with the statement above, migrated,
  and emptied before every file. TEST_DATABASE_URL names the base database these are
  derived from, and no test runs against it. A run holds a Postgres advisory lock for its
  whole length; the next run drops only the databases of runs whose lock it can take, so
  overlapping runs on one cluster never delete each other's databases. Implementation:
  `app/tests/support/postgres-leg.ts` and its siblings.
- **A pool the seam opens carries an error listener on both idle and checked-out
  connections.** node-postgres re-emits a socket error as an EventEmitter 'error', which
  with no listener throws and ends the process; a reset connection must instead be logged
  once and discarded by the pool, while a query in flight still rejects. This is a
  requirement of the seam, not a test convenience: it is also the production boot's pool.
- Playwright drives end-to-end tests, using the seed dataset and the development login
  endpoint for sessions. The browser leg runs against PGlite alone: every case is a
  rendering, a route, a control's presence, or a request the client did or did not send,
  and SQL behaviour is the Postgres leg's to catch.
