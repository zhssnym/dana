### 11.12 Observability

- Sentry (free tier) receives server and client errors (AC-104). The error tracker takes a
  message as well as an exception, because a condition worth alerting on is not always
  something that threw.
- Better Stack (free tier): an uptime monitor on /api/health, and a heartbeat the scheduler
  pass pings after each successful cycle; heartbeat silence beyond 10 minutes alerts.
  /api/health also reports seconds since the last completed pass and `database`, the
  engine the seam of 11.5 chose (`"postgres"`, `"pglite"`, or null where nothing has
  declared one); a production process answering `"pglite"` is the condition 11.5
  describes.
- A database connection lost from the pool sends one warning-level message per loss,
  fingerprinted on (`database_connection_lost`, the driver's code) so a night of resets is
  one issue with a count, and tagged with the event name its 10.5 line carries. The code is
  whitelisted to an identifier before it becomes a tag or fingerprint. The log line is the
  record and this is the alert: the error a route sees when a socket dies inside a
  transaction is drizzle's failed ROLLBACK, so the original code is reported only here.
- Dana's privacy-policy logger writes its structured application events to stdout, which
  keeps Render's deploy diagnostics and log explorer intact. When both `AXIOM_DATASET` and
  an ingest-only `AXIOM_TOKEN` are present, the same pino records are also sent directly
  over HTTPS to that Axiom dataset, whose retention is at least 30 days; with neither the
  external destination is disabled, and an incomplete pair logs only the missing variable
  name and stays stdout-only. Only the closed, whitelisted logging surface of 10.5 reaches
  Axiom. Render platform and build logs are not copied. This direct destination stands in
  for a Render log stream because the free Axiom plan lacks its Secure Syslog endpoint and
  the free Better Stack Logs plan does not meet 10.5's retention period.

**Any event a browser can produce once per page view is fingerprinted on what makes two of
them the same event, and the fingerprint is the caller's to choose.** 10.8's CSP violation
report is the first: each kept report sends one warning-level message fingerprinted on
(`csp-violation`, effective directive, blocked URI), so a policy refusing a script on every
load is one issue with a count rather than an issue per load that buries the next real
error and spends the free quota.

A fingerprint groups issues but the quota counts events, and a fingerprint built from a
caller's string has a key space the caller chooses, so an unauthenticated path takes three
rules together, all enforced by the caller and none by the tracker:

- **Every value reaching Sentry has passed 10.5's whitelist**: fingerprint, message and tags
  are built from the same sanitised fields as the log line, never from the raw report.
- **A given fingerprint sends at most once per ten-minute window**, held in process (11.1's
  single instance) over a bounded map.
- **An absolute budget of twenty events per window** sits over both, with exactly one
  message when it is spent, because a channel that went quiet under load is
  indistinguishable from nothing being wrong.

The 10.5 log line is written every time regardless, so the log stays the record and Sentry
is the alert. `beforeSend` strips request, user and context from every event this process
sends.
