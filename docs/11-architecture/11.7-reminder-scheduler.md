### 11.7 Reminder scheduler

The 8.6 delivery loop runs in-process: a 60-second interval in the server, guarded against
overlapping passes, executing the poll-classify-send-mark cycle in a transaction that
claims due rows with SELECT ... FOR UPDATE SKIP LOCKED. Consequences, each intended:

- A missed tick self-heals: the poll is over fire_at <= now(), so the next pass picks up
  anything a missed one would have sent, inside the 6-hour stale window.
- The deploy overlap window can run two instances briefly; SKIP LOCKED makes concurrent
  ticks contend safely instead of double-sending. A crash between send and mark can
  duplicate at most one batch; 8.6 accepts duplicates.
- Tick liveness is monitored separately from process liveness (11.12), because a dead
  interval inside a live server is invisible to an uptime check.

**The same pass is the only background execution (8.6), and it carries every sweep.**
Besides delivering reminders it prunes expired session rows, purges Trash rows whose
deleted_at is older than 30 days, purges events older than 90 days, and reclaims pictures
nothing wears: a folder-less cover or page image that no column names and that is more
than 30 days old is deleted with its object (the rule and the window are 7.19's; the
statement is `reclaimUnwornPictures` in `app/src/server/domain/files.ts`). A picture with
no folder is reachable by no route, so nothing in section 7 could ever remove it, and it
would spend its owner's storage (10.3) forever; it is not deleted the instant nothing names
it because a caller still holding the id may set it back a moment later. Notification
fan-out is not a scheduler duty: it runs at the 10.2 chokepoint so that an act and its
notification commit in one transaction.

- The Trash purge collects the files rows its deletes will cascade away and removes their
  objects from the store after the delete commits, because those rows are the only index
  to the bytes and a purge that drops them without the objects grows the disk without
  bound.
- Every duty claims its rows the way the reminder duty does, SKIP LOCKED in its own
  transaction, and each is idempotent, so the missed-tick and overlap properties above
  hold for all of them.
- **Every sweep claim is capped** at `SWEEP_BATCH` rows (`app/src/server/database.ts`).
  The in-flight guard answers a long pass by skipping the next tick rather than queueing
  it, so an unbounded sweep would eat ticks; a capped one is safe because a repeat finds
  the rest, and a row that waits one more tick has already waited thirty days.
- **The pass writes its outcome**: one line carrying each duty's count and its duration,
  and nothing for a quiet tick (10.5); the reclaim also writes one `file_reclaimed` line
  per file. The pass writes it rather than the interval, so the record survives the
  driver being replaced.
- Every duty is one more reason the single-instance rule of 11.1 must be flagged before it
  ever changes, and none of these duties may migrate into request handlers.

The pass is a plain callable function and must stay one: if hosting ever moves somewhere
without an always-on process, the replacement is an external per-minute trigger (Google
Cloud Scheduler or equivalent) hitting an authenticated endpoint that runs one pass. The
callable is `createReminderPass(deps)` exported from `app/src/server/scheduler/index.ts`,
with deps including `{ dbClient, notifications }` under 11.10's option names; it is how
tests reach the loop, since section 7 offers no endpoint that runs a pass, and production
composes the same callable at boot.
