### 4.25 task_personal_labels

The first of the three assignment relations: one of the viewer's own Personal
Labels (4.24) applied to one Task. Columns, constraints and index:
`app/db/migrations/0022_labels.sql`.

**`owner_user_id` is stored rather than derived, and the composite foreign key
against `labels(id, owner_user_id)` keeps it honest**: the pair cannot name a
Label somebody else owns, and because the column is NOT NULL here while a Folder
Label's owner is NULL, **a Folder Label cannot be attached through this table at
all**. The same column answers the per-viewer read (a Task carries *your*
Personal Labels, never another member's) and the per-viewer cap in 10.3 without
joining `labels`.

**The Task cascade is the trash rule.** A soft-deleted Task keeps its
assignments and restores whole; only the permanent delete of 7.13 and the 11.7
purge take them. Archiving a Label removes nothing here: existing assignments
stand while new ones are refused (7.26).

**A retained assignment whose target the owner can no longer reach is
deliberate.** When the owner loses access to the Task's Folder the row remains,
contributes nothing to any answer the owner can get, and becomes visible again if
access returns, with no repair step.
