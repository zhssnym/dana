### 4.15 comments

A comment in a Folder's conversation: a Discussion's (4.31). A reply names the post it answers (`parent_id`),
which may be any post of the same thread, itself a reply or not; the thread reads flat, oldest
first, and a reply quotes the post it answers (9.6).

**A reply outlives the comment it answers.** `comments_parent_id_fkey` is ON DELETE SET
NULL (migration 0047): deleting a comment removes only that row, and each reply to it
stays in the thread as a top-level comment with its author's words intact. A reply is its
author's, so one person deleting their own words never removes someone else's.

Columns and constraints: `app/db/migrations/0003_v2_expand.sql` and
`0007_sample_objects.sql`.

- `folder_id` is the visibility scope.
- **A task has no thread of its own** (M5, migration 0059): its conversation is the
  Discussions linked to it (4.31 `discussion_tasks`). `comments_no_task_scope_check` holds
  `task_id IS NULL`; the column, `comments_task_scope_fkey` and `comments_thread_idx`
  stay, read by nothing, until a later migration drops them.
- `body` is null when the comment is attachments or a voice note alone; `comment_files`
  binds a comment to its files (the per-comment limit is 10.3).
- `content` (migration 0040, W-C) is a post written in the editor: a block tree
  (`postContent` in `app/src/shared/comments.ts`), NULL for a plain-text comment.
  `comments_content_check` holds version 1, a `blocks` array, at most 256 KiB. When
  it is set, `body` is derived from it by the server (its plain text, NULL when it
  has none), so every reader of `body` keeps working. A media block may name only
  one of the same comment's own files, enforced by the API.
- `comment_likes` rides beside it and holds reactions: one row per (comment, user,
  `reaction`), so a person may leave several different reactions on one comment but each
  once. `reaction` is a key from the fixed set `REACTIONS` in `app/src/shared/comments.ts`
  (`thumbs_up`, `heart`, `laugh`, `party`, `surprised`, `thanks`), held by
  `comment_likes_reaction_check` and stored by name, never as a glyph. Its default is
  `thumbs_up`, which is what a like is (migration 0068). `created_at` orders a comment's
  reactions by when each was first left, and each reaction's people earliest first.
- **A Folder-level comment belongs to a Discussion** (4.31, migration 0029, issue #320):
  `discussion_id` is held by `comments_discussion_scope_fkey`, (folder_id,
  discussion_id) against discussions (folder_id, id), ON DELETE CASCADE, DEFERRABLE
  INITIALLY IMMEDIATE since 0059 so 7.6's move can carry a task's Discussion and its
  comments in one transaction, and
  `comments_one_scope_check` refuses a comment that is both Task- and
  Discussion-scoped. Every Folder-level comment that existed was backfilled into its
  Folder's "General discussion". The CHECK does not yet require one of the two, so
  the deployed client's Folder-thread writes keep working until the route files them
  under a Discussion.
