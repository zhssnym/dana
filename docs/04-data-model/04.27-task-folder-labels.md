### 4.27 task_folder_labels

The third assignment relation: a Folder Label (4.24) applied to a Task in that
same Folder, shared with every member of it. Columns, constraints and index:
`app/db/migrations/0022_labels.sql`.

**The row carries the Folder, and both composite keys point at that one
column**: `(folder_id, task_id)` against `tasks(folder_id, id)` and
`(folder_id, label_id)` against `labels(folder_id, id)`. So a Folder A Label on
a Folder B Task is not a rule the handlers enforce but a row the database cannot
store, direct SQL included.

**The shape is 4.15's `comments_task_scope_fkey`, but not deferrable**: that
pair is deferrable so 7.6's move can re-scope a task's conversation in one
transaction, and nothing here needs to hold a broken pair across statements. A
Task moving to another Folder does not carry its Folder Labels to a catalog that
does not contain them.

**There is no `owner_user_id`, because these assignments are the Folder's.**
Every member sees all of them, so 10.3's per-Task cap on Folder Labels is shared
rather than per viewer, and is counted apart from each viewer's Personal Label
cap. Who may add or remove one is 7.26's `label.apply`.

Cascade and archive behaviour are 4.25's.
