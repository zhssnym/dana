### 7.24 Dana Link references

A **Dana Link** is an ordinary internal URL to a Task, a Folder, a Shelf, a supported Facet, a
Discussion, an Outcome or a Result, persisted
as a rich-content href and resolved live. It is a navigation aid: it is never a
dependency, a permission grant, an Authority grant, a membership grant, a copy or a
workflow relation, and resolving one creates nothing. **No table stores links** — a
Dana Link's durable form is the href a rich-content block already holds, and this
section resolves it rather than recording it.

**Supported targets and their client routes.** Task `/app/tasks/:id`, Folder
`/app/folders/:id`, Shelf `/app/shelves/:id`, Facet `/app/facets/:id`, Discussion
`/app/discussions/:id`, Outcome `/app/outcomes/:id` (#320) and Result `/app/results/:id`
(#213). The only
Since step 7 a facet is a tab (4.3) and keeps its id, so a stored Facet link resolves as that
page, labelled `<project name> · <tab name>`, by membership like any page; the picker offers a
project's other tabs as Folder links under the same label. The native **Purpose** and
**Results** facets were the kinds admitted before. Consultation, private and custom facets, and individual facet blocks other than a
native Result are not reference targets. The set is closed. A further kind becomes
referenceable only when it has a stable id and a stable client route, which is the
property this section turns on rather than a matter of taste.

**The reference summary.** Every answer below is one or more objects of exactly `kind`,
`id`, `label` (the target's own title or name, as that target's own read answers it) and
`path` (the canonical internal path), and no others: `referenceSummary` in
`app/src/shared/references.ts`. No folder, assignee, date, status, member count or any
other metadata rides a summary. A chip draws a label and navigates; it is not a
projection of the thing it points at.

**Following a Facet link.** The stable client address remains `/app/facets/:id`; since step 7 it
is an entry route that replace-navigates to `/app/folders/:id`, the tab that kept the facet's id.

- **GET /api/v1/references/:kind/:id.** Resolve one target. Requires a session. A
  `:kind` outside the supported set, an `:id` that is not a uuid, a target that does not
  exist and a target the viewer may not read **all answer 404 `not_found` with an
  identical body**: never 403, and never anything naming the row. A target the viewer
  may read answers 200 with the reference summary. Access resolves through exactly the
  reads that already govern the kind — a Task through its folder's membership, a Folder
  through its membership, a Shelf through its owner, a Purpose or Results facet through its Folder membership, a
  Result through membership of the live Folder of its live Results facet, a
  Discussion or Outcome through membership of the Discussion's live Folder — which is what makes "a link grants
  nothing" a property of the code rather than a promise.

- **GET /api/v1/references/search.** The picker's read. Requires a session. Query
  parameters (`referenceSearchQuery`): `q`, required, with 7.10's own length rule
  reused rather than a second one; `folder`, optional, a uuid naming the Folder the
  person is composing in. Answers 200 with `results`, capped at `REFERENCE_SEARCH_LIMIT`
  **across every kind together**. When `folder` is supplied, that Folder's
  matching Tasks lead and matches elsewhere follow: **the context is a priority and not
  a filter.** Matching is on title and name only — a match on a field the picker row
  does not draw reads as a bug. Results never include a target the viewer cannot access.
  A malformed `q`, or a `folder` that is not a uuid, answers 422 `validation_failed`
  naming the field; **a `folder` the viewer is not a member of answers 404 `not_found`**,
  identically to a folder id that names nothing. The endpoint carries 10.4's search
  limit, sharing the bucket with `GET /search`, whose contract (7.10, 7.18) this
  section deliberately does not widen.

**One visibility rule across both doors, and it is the point of the section.** An exact
URL paste and a typed search resolve through the same authorization path and must reach
the same verdict about the same row. An inaccessible target is indistinguishable from a
nonexistent one at both.

**The `folder` query parameter needs its own gate.** It arrives on the query string,
where a sweep over path parameters cannot see it. Without the 404 above nothing leaks
row data — the join returns no rows either way — but a caller would learn the difference
between a folder with no matches and a folder they cannot see, which is the distinction
this section exists to remove.

**Three exclusions, so that a later reader does not read them as oversights.** There is
no cursor and no paging: a picker's answer to "not here" is another keystroke. There is
no `kinds` filter and no `limit` parameter, for no caller needs one. And 10.4 does not move,
because the picker shares the existing search bucket rather than opening a second one.


#### Purpose references

Purpose is the first facet-level Dana Link target. Its **facet id** is the durable target:
renaming Purpose changes the resolved `label` but not the id/path, and hiding Purpose does
not revoke a reference because hide is presentation state rather than access state. Exact
resolution and picker search both require current Folder membership and treat an
inaccessible Purpose exactly like a missing target. Resolving or searching creates no
membership, Access, Authority, dependency, event or relationship row.

The label is the Page's live name and the tab's, `<folder name> · <display_name ?? "Purpose">`, because
every Page has a Purpose and the tab's name alone cannot tell them apart. Search matches that
label, so a Page's name finds its Purpose and Results. A contextual
Folder still prioritizes its matching results without becoming a filter. Individual Purpose
blocks are not referenceable; adding them would require their own stable navigation
contract rather than reusing the facet path.

**Results references (#213)** follow every rule above with Results in place of Purpose: the
facet id is the durable target, the label is the live `<folder name> · <display_name ?? "Results">`, hide does not
revoke, and an outsider's answer is the missing target's. A Task links to a Result through an
ordinary Dana Link in its notes or a document; that is a copy of an href, not a stored
relationship, and grants nothing.

#### Result references (#213)

A **native Result** is a `result` block of a Folder's Results facet, made only when a person
chooses Result on the Results tab (the `/` menu, Turn into, or Enter at the end of a Result, which
continues with the next; Enter on an empty one makes it Text); ordinary Results writing is never
promoted to one. Its block id
is the durable target, `/app/results/:id`. It carries an authored statement and nothing a Task has
(no assignee, dates, status or progress). **Access** is membership of the Folder of its Results
facet, the facet and the Folder live; anything else is the missing target at every door. Its
**label** is its statement on one line, cut as an Outcome's (`resultLabel`), or `Untitled result`.
Search matches the statement: the composing Folder's Results come right after its Tasks and
Purpose and Results tabs, every other Page's after Outcomes and before Shelves.

- **GET /api/v1/results/:id.** Where a Result lives, for its client route: `id`, `folder_id`,
  `facet_id`, `label` (`getResultLocationResponse`). Same gate, same bare 404. The client
  replace-navigates to `/app/folders/:folderId?facet=:facetId&result=:id`, and the block scrolls
  into view once; `result` then leaves the address, so a tab switch or reload does not replay it.

A Result is also a backlink target (`GET /api/v1/results/:id/backlinks`), and the Results tab
draws each Result's "Referenced from" under it (#214): the Task, Purpose or Discussion that links
to it is seen from the Result's side. That is the whole cross-tab relationship in M1 — a link read
from both ends. There is no typed relation ("contributes to", "satisfies"): a person says what a
link means in the words around it.

**Results never travel (R2).** A Folder Duplicate and a workflow import give the new Folder an
empty Results tab; no Result and no Results writing is copied, and a link to a source Result keeps
naming the source. An account export keeps every Result that exists, as a facet block of kind
`result`.

#### Discussion and Outcome references (#320)

A Discussion's id and an Outcome's id are both durable targets. **Access** is membership of the
Discussion's live Folder, with the Discussion not in Trash: a trashed Discussion, every Outcome of
it, a Discussion or Outcome in a trashed Folder, and one in a Folder the viewer is not a member of
all answer exactly as a missing target — 404, no label — at both doors and at `GET
/.../backlinks`. Restoring the Discussion restores the answer, because nothing was recorded.

**Labels.** A Discussion's label is its live title. Its state (open or resolved) is **not** in the
label or the summary: state is status, which this section keeps off every summary, and a chip that
drew "Resolved" would be stale the moment someone reopened it. An Outcome's label is its
statement, whitespace collapsed to one line and cut to 120 characters with a trailing `…`
(`outcomeLabel` in `app/src/server/domain/references.ts`).

**Outcomes are append-only, so an Outcome link is stable.** Resolving `/app/outcomes/:id` answers
that exact Outcome whether it is its Discussion's current one or has since been superseded; its
statement never changes. The client opens an Outcome link as its parent Discussion focused on that
Outcome.

**Search** matches Discussions on title and Outcomes on statement, and offers only each
Discussion's **current** Outcome — a superseded one stays resolvable by its link but is not
offered, so a picker is not buried under drafts. Both follow the Folder-context priority rule
above (the composing Folder's first) and share the one `REFERENCE_SEARCH_LIMIT`, placed after
Folders and Purpose/Results facets and before Shelves.

A Discussion's opening context and an Outcome's statement are plain text, so neither holds an href
and neither is a backlink **source**; both are backlink **targets** (below). Duplicating a Folder
copies no Consultation, so a copied page's link to a Discussion keeps pointing at the original.

#### Referenced from (issue #214)

The reciprocal presentation of a Dana Link, as a read. **No backlink is stored** (#320): the
answer is computed at request time by scanning the documents the reader can open, so a link
removed from a document stops being a backlink on the next read with nothing to reconcile.

- **GET /api/v1/tasks/:id/backlinks**, **GET /api/v1/folders/:id/backlinks**,
  **GET /api/v1/shelves/:id/backlinks**, **GET /api/v1/facets/:id/backlinks**,
  **GET /api/v1/discussions/:id/backlinks**, **GET /api/v1/outcomes/:id/backlinks** (#320),
  **GET /api/v1/results/:id/backlinks** (#213). Require a
  session. The target resolves first through the same gate as `GET /references/:kind/:id`: a
  target that does not exist, a target the viewer may not read, an id that is not a uuid and a
  facet that is not a native Purpose or Results all answer the same bare 404 `not_found`, and nothing is
  scanned. Otherwise 200 with `getBacklinksResponse` (`app/src/shared/backlinks.ts`):
  `results`, one object per referencing document — `surface` (`page` | `responsibility` |
  `post`), `home` (`folder` | `shelf` | `facet` | `task` | `discussion`; a reader tolerates a
  home it does not know),
  `home_id`, `folder_id` (null for a Shelf page; the Task's Folder for a Task document),
  `member_id` (the Responsibility's member, null on a page), `label` (the home's live name;
  the Task's title for a Task document)
  and `block_ids` (the page blocks holding the link, in document order; empty for a
  Responsibility; for `post`, the posts holding it, oldest first) — ordered by label, capped at `BACKLINK_LIMIT` (50), with `truncated`
  saying whether it was cut.
- **Sources scanned**: rich-content hrefs of page blocks on a Folder page, a Shelf page, a
  Facet page and a Task document (#221, `surface` `page`, `home` `task`), a `folder_ref` block's `ref_folder_id` when the target is a Folder, and the
  active Responsibility documents. An href counts when `parseDanaLink` parses it to the
  target — the relative `/app/<kind>/<id>` form, with any query or fragment, and an absolute
  URL only on the deployment's own `APP_ORIGIN`. And (W-C) the posts of a thread
  (`comments.content`), one result per thread: `surface` `post`, `home` `discussion` with
  the Discussion's title, or `home` `task` with the Task's title.
- **Every source is filtered by the reader's access to it**, with the predicate its own read
  applies: Folder page and Responsibility by membership of the live Folder; Shelf page by
  ownership; Facet page by membership of the live Folder, the facet live, and shared or
  private to the reader; Task document by membership of the Task's live Folder and the Task
  not in Trash (the `GET /tasks/:id/document` predicate); a thread's posts by membership of
  the live Folder and the Discussion or Task not in Trash. A source the reader cannot open is absent — not counted, not
  redacted.
- **Propagation.** Every name is read live from its one authoritative home; nothing is copied
  between the referencing document and the target. No interpretive content is ever rewritten
  automatically when a target changes (#203); a person edits it.
