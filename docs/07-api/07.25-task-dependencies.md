### 7.25 Task dependencies

TaskCard and TaskDetail (7.0) carry two counts and nothing else about
dependencies, so a row can show a compact blocked indicator without a request
per row; the relations themselves are read here.

- `blocked_by_count`: edges where the task is the dependent and the blocker is
  not completed. A pending blocker and an abandoned one both count, because an
  abandoned blocker leaves the dependency `unresolved`, not `satisfied`.
- `blocks_count`: edges where the task is the blocker, while the task itself is
  not completed.
- Only edges whose other end the viewer can read are counted. A count over an
  unreadable blocker would report that task's status, which is what `unknown`
  below exists to withhold, so such an edge appears only in this endpoint's
  read.
- Every list endpoint computes both in one statement for the whole page, never
  one per row.

One directed relation, stored once (4.23). **Reversal needs no second
contract**: to make A block B, post to B naming A.

**Shared shapes**: `TaskDependencyEdge`, `DependencyTaskSummary` and
`TaskDependencies` in `app/src/shared/task-dependencies.ts`. An edge's `task`
is the **far** end — the blocker in a `depends_on` entry, the dependent in a
`blocks` entry — or **null** when the viewer cannot read that task.

`state` is derived and never stored: the blocking task pending gives `active`,
completed gives `satisfied`, abandoned gives `unresolved`, and a far end the
viewer cannot read gives **`unknown`**. That fourth value is not a convenience.
`state` is a function of the far task's status, so a read that redacted the
summary and derived the state anyway would answer `satisfied` and leak exactly
what the redaction was for; `unknown` is what stands in its place. The
endpoints' own ids are never on the wire.

- **GET /tasks/:id/dependencies.** 200 with `depends_on` and `blocks`, each ordered by `created_at` then `id`. 401 without a
  session. 404 when the task does not exist, is trashed, or sits in a folder
  the viewer is not a member of.

- **GET /folders/:id/dependencies.** 200 with `{ dependencies }`, each
  `{ id, dependent_task_id, blocking_task_id }` (`getFolderDependenciesResponse`
  in the same shared module), ordered by `created_at` then `id`: every edge
  whose **both** ends are live tasks of that folder, and no other. 401 without
  a session; 404 when the folder does not exist, is trashed, or the viewer is
  not a member. Endpoint ids are safe here because a member can read every
  live task of the folder; an edge with either end elsewhere is never
  returned, so this read cannot name a task that `depends_on` would withhold.
  It exists so "Save as workflow" (7.16) reads a folder's internal ordering in
  one request rather than one per task.

- **POST /tasks/:id/dependencies.** The path id is the **dependent**; body
  `{ blocking_task_id }`. **201** with the edge when it is created, **200** with
  the existing edge when the pair is already related — a retry after a lost
  response and two members adding the same blocker are the same request twice,
  and it asks for a state that already holds. 401; 403 without CSRF; **404 when
  either end is missing, trashed or inaccessible, one answer for both**, so the
  status says nothing about which id was refused; 422 `validation_failed`
  naming `blocking_task_id` for a malformed value, a self-dependency, or an
  edge that would close a cycle of any length. Rate limited as a general
  mutation.

- **DELETE /tasks/:id/dependencies/:dependencyId.** 204, and removable from
  **either** end of the relation. 401; 403 without CSRF; 404 when the task is
  inaccessible, when no such edge exists, or when the edge exists but does not
  touch the task named in the path. Rate limited as a general mutation. The
  delete grammar is deliberately not the create's: 204 then 404 on a second
  removal, matching `DELETE /connections/:userId` and `DELETE /tasks/:id`,
  because a caller naming an edge that is not there asked for something that
  was never true.

**Cycles are refused against the whole graph, including edges the viewer cannot
see, and the cost of that is stated rather than hidden.** A refusal tells the
caller that *some* path exists between two tasks they can already read, through
tasks they cannot — a real disclosure of graph structure. The alternative is
worse in kind rather than in degree: a check over only the visible subgraph is
not a graph invariant, two members with complementary access would each see a
clean graph and between them close a ring, and a cycle in the data is a
correctness problem rather than a privacy one, because the state derivation
walks these edges. So the invariant is global and the disclosure is bounded to
"a path exists between two rows you may already read".

**Check and insert are serialized by a transaction-scoped advisory lock**, and
nothing else can do the job. Two concurrent opposite requests would each read a
clean graph and then close a ring, and row locks cannot prevent it: the
completing path runs through tasks neither request names, so there is no row to
lock.

**Relationships travel only when both ends travel together.** Folder
duplication builds the old-to-new task identity map first and copies only the
rows whose *both* endpoints are inside the duplicated set, remapping both; a
copied task never points at an original, and the whole act stays atomic.
Duplicating a single task carries no relation, because one end did not travel.

**The workflow file carries internal dependencies only, by file-local key.**
That format carries no task ids at all (7.16); the writer reads
`GET /folders/:id/dependencies` and keeps an edge only when both ends are in
the file, so an external relation never travels.
