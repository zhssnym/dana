### 7.26 Labels

The routes over the Label model of 4.24 to 4.27, in four groups: the definition listing,
Personal definition writes, Folder definition writes, and two idempotent assignment pairs.

**Shared shapes**: `labelDefinition`, `labelRef` and `taskLabels` in
`app/src/shared/labels.ts`, with the bodies, the query and the caps
(`PERSONAL_LABEL_DEFINITION_CAP`, `FOLDER_LABEL_DEFINITION_CAP`, `TASK_PERSONAL_LABEL_CAP`,
`TASK_FOLDER_LABEL_CAP`, `FOLDER_PERSONAL_LABEL_CAP`). A definition is what a picker or the
manage surface reads. A `LabelRef` is the compact reference a Task or Folder projection
carries once per applied Label per row; it drops `description` because a dense row renders a
chip and never a sentence.

`scope` is `personal` or `folder`, and there is no third. `archived` is a boolean on the
wire where the row holds an instant: exposing the instant would invite a client to compute
the state from it, which is a second definition of the same fact. `folder_id` is present on
both shapes and **null** for a Personal Label rather than absent, so that a stable key set is
read without narrowing a union. **Neither shape carries `owner_user_id`**: a Personal
definition a viewer can read is by construction their own, so the field would be a constant,
and a constant that happens to be an account id is a discovery surface rather than
information.

**The two projections.** A Task carries `labels` with `personal` and `folder` arrays — the
viewer's **own** Personal Labels and the Task's Folder Labels, and **never another member's
Personal Labels**, in `GET /tasks/:id` and in every list endpoint alike. A Folder carries
`personal_labels`, the viewer's own Personal Labels applied to that Folder; there is no second
array for Folder Labels, because a Folder Label classifies the Tasks in its Folder and never
the Folder itself (4.26). Both arrays are ordered active before archived, then `lower(name)`,
then `id`, in both producers.

**The status grammar, uniform across every route here** (5.4, 7.0, 10.2): 401 without a
session; **404 and never 403** for a Label, Task or Folder the viewer cannot see, so existence
never leaks; 422 naming the field for an invalid value; 422 naming the collection for a cap;
409 for a state conflict. Every mutation is CSRF-checked and rate limited as a general
mutation.

**A duplicate name is 409**, on all four doors: create and rename, in both scopes. A name
already held is the state of a catalog rather than a bad value: the same string is valid in
the next Folder along and in the viewer's own Personal catalog, and it will be valid here the
moment the Label holding it is renamed. The other 409 on this surface is applying an
**archived** Label. Both leave the row untouched.

**Definitions.**

- **GET /labels.** 200 with `rows` and `truncated`, capped at 10.3's list-response cap. One
  cap across the whole response rather than one per scope, which is section 6's per-response
  reading; the kept rows are the first of the order below, and `truncated` is true exactly
  when a row was dropped, so a full page and a complete one are told apart without counting.
  Query `scope` (default `all`), `state` (default `active`), and `folder_id` to narrow the
  Folder half to one Folder. 422 naming the field for an invalid value. **404 for a
  `folder_id` the viewer cannot reach** — not 403 and not an empty 200. That selector is in
  the query string, where no sweep over path parameters can see it, so its gate is
  hand-written and must stay.

- **POST /labels/personal.** 201 with the definition. The viewer is the owner and there is no
  field for it, because an owner a caller could name is an owner a caller could get wrong.
  409 on a duplicate name; 422 at the Personal definition cap.

- **PATCH /labels/personal/:labelId.** Any subset of `name`, `color`, `description`; an
  absent field is left alone. 200 with the definition. 404 for another account's Label. 409
  on a duplicate name. **Archived state is not in this body** — it moves through the two
  endpoints below, so that "rename" and "retire" are two acts with two audit lines rather
  than one body that can do both by accident. **An archived Label may still be renamed,
  recoloured and described without being restored.**

- **POST /labels/personal/:labelId/archive** and **POST /labels/personal/:labelId/restore.**
  200 with the definition. 404 for another account's Label.

- **POST /folders/:folderId/labels**, **PATCH /folders/:folderId/labels/:labelId**, **POST
  /folders/:folderId/labels/:labelId/archive** and **POST
  /folders/:folderId/labels/:labelId/restore.** The same four over a Folder's catalog, with
  the same bodies, the same statuses and the Folder definition cap. 404 for a Folder the
  viewer is not a member of, **403 for a member below Can edit** (below), and 404 for a Label
  that is not that Folder's — a Folder-B Label patched through Folder A resolves to nothing at
  all.

**Managing a Folder's Labels is Can edit's, applying them is Can edit's and Can
contribute's over their own current work, and neither is the owner's by virtue of
ownership.** The two acts resolve through the Folder Access resolver
(`app/src/shared/folder-actions.ts`) like every other Folder mutation:

- `label.vocabulary.manage`, at least Can edit — create, rename, recolour, describe, archive
  and restore. Below it, **403** carrying the rule's own sentence, never 404: the caller is a
  member and can already see the Folder and its Labels, which is the condition 10.2 makes a
  403 legitimate under.
- `label.apply`, at least Can edit, or Can contribute on the Task **currently assigned to
  them** and no other — putting a Folder Label on a Task and taking it off. Assigned work, Can
  comment and Can view may not, their own current Task included. The assignee is read in the
  same transaction and under the same row lock as the write.
- **Personal Labels are outside this entirely**, at every preset: a Can-view member still
  classifies work they can read with their own private vocabulary and still manages their own
  catalog.

There is no owner exception: ownership is custody and is no part of authority over shared
Work.

**Assignments.** Per-Label `PUT` and `DELETE` rather than a full-set `PATCH`: two members
labelling the same Task at the same moment must not erase each other, and a replacement body
cannot carry the Personal assignments of the member who did not send it without showing them
to the one who did. Each is idempotent and each answers 200 with the refreshed Task or Folder.

- **PUT** and **DELETE /tasks/:taskId/labels/:labelId.** The Label may be one of the viewer's
  Personal Labels or one of the Task's Folder's Labels; 422 naming `label_id` otherwise, 404
  for a Task or a Personal Label the viewer cannot see, **403 for a Folder Label the viewer
  may not apply under `label.apply`**, 409 for an archived Label on a `PUT`, 422 at either
  per-Task cap. The two caps are counted apart, and the refusal does not say which of them
  fired, because nothing a caller can do depends on knowing. **The order is decided:
  not-found, then wrong-target, then the 403, then the 409** — scope settles which act is
  being performed and so precedes the actor's standing, and the actor's standing precedes the
  Label's state, telling somebody who may not classify this work that the Label is archived
  being an answer to a question they are not owed.

- **PUT** and **DELETE /folders/:folderId/labels/:labelId.** Personal Labels only, at the
  per-Folder cap.

**`/folders/:folderId/labels/:labelId` means two different things depending on the verb.**
`PATCH` edits the **Folder** Label with that id. `PUT` attaches the viewer's **Personal**
Label with that id to the Folder. Each refuses the other's scope — a Personal id through the
`PATCH` is 404, a Folder-Label id through the `PUT` is 422 naming `label_id` — but `:labelId`
does not denote the same thing across the two.

**`label` means a Label of this section and nothing else anywhere in the contract.** A
person's shelf placement of a Folder is `shelf` in 7.4's `PATCH /folders/:id/my-membership`
body and `my_shelf` on the Folder object.
