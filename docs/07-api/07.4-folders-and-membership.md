### 7.4 Folders and membership

Bodies and responses: `app/src/shared/folders.ts`, with the Access administration shapes in
`app/src/shared/folder-access.ts` and the Responsibility shapes in
`app/src/shared/responsibility.ts`. The authority each route checks is an action of
`app/src/shared/folder-actions.ts`, and ownership is neither necessary nor sufficient for any
act except the custody acts named below. A 7.4 mutation answers what a fresh GET would.

**People belong to the project (step 8).** Every membership route below -- members, my
membership, Access changes, owner recovery, access history, Responsibility, the self-edit
grant, transfer of ownership, and `POST /invites` with a `folder_id` -- may name any page of
a project and acts on its project root; the gate is still on the named page, so a stranger
gets 404. A page's `members` and `member_count` are its project's.

- **GET /folders.** All accessible folders as Folder objects (`getFoldersResponse`). Sort:
  is_default first, then lower(name), then id.
- **POST /folders.** Body `postFoldersBody`. Creates the folder with owner = V plus the owner
  membership, in one transaction. 201 Folder. 422 on name length; 422 when V already has the
  10.3 maximum of custom folders. `description` rides the create rather than a follow-up
  PATCH because making a folder is one gesture with one outcome: a second call can fail
  after the folder exists, and a retry then makes a second folder. `kind`: absent makes a Work
  project, what every caller made before; `null` leaves the kind unpicked, so the page offers
  the picker (9.6). With `parent_folder_id` it makes a sub-page in the parent's project, a Doc
  when `kind` is absent; a Discussion page holds no pages (422). A Work tab holds tasks, not pages: a page made inside one goes under the project's Pages Doc tab, which is added right after that Work tab when missing, and the answer names the parent it got. The cap counts projects and
  sub-pages, not a project's other tabs.
- **POST /folders/:id/tabs.** Body `postFolderTabsBody`. `:id` is any page of the project; Can
  edit and above on the project root (`folder.page.edit`), 404 to a non-member. While the root's
  kind is unpicked, `kind` picks it, and `usual` makes it Work with a Purpose Doc tab before it
  and Results (Doc) and Discussion tabs after. Once picked, `kind` adds one tab after the last,
  named Doc, Work or Discussion; `usual` is then 422 and a second live Discussion 409. An unpicked root that holds a page block or a live task is never picked as a Discussion, which shows only threads (409). 201 with
  the project's live tabs in order. A new tab, like every page, has the project's owner and
  its people.
- **Tabs are pages.** Rename, Trash and restore use the routes above; a project root's name is
  the project's. `PATCH /folders/:id/location` with `parent_folder_id: null` on a tab moves it
  along its project's tab row (`after_id` a tab of the same project, else 422; null first;
  absent last). A tab never goes under a page, and a project with more than one tab never
  becomes a sub-page (422); a sub-page moved to the top level becomes a project that keeps
  its old project's people (each recorded as added by the mover), and a page moves under
  another project's page only when both projects have the same owner and the same people at
  the same presets (else 422, whoever asks), then joins it with its sub-pages. A project
  root that joins another project leaves its pending invites invalidated and takes its
  Responsibilities with it, each active one ended by the mover. Trashing a project
  root takes its tabs, and restoring it brings them back.
- **GET /folders/:id.** `getFolderResponse`: the Folder plus `members` and
  `pending_invites`. 404 if not a member. A member's `access` is visible to every member;
  `pending_invites` is `[]` for every member below Full control, since an invite's address
  and intended Access are member-administration data. The key is always present, so "you may
  not see this" and "there are none" are one shape.
  It also carries `section_progress`: one `sectionProgress` per section block of the folder,
  zeros included, in no promised order.
- **PATCH /folders/:id.** Body `patchFolderBody`: name, and the 4.3 identity (icon, color,
  cover, description). Can edit and above (`folder.profile.edit`): 403 below the bar, 404 to
  a non-member. Works for the default folder too. A body naming both a cover file and a
  cover preset is 422, and setting either source clears the other. A named cover file must
  be a file of that folder; its lifetime is 7.19's. 200 Folder.
- **DELETE /folders/:id.** Full control (`folder.trash`), whether or not V owns the folder;
  an owner whose Access is below Full control is refused 403. 409 if is_default (INV-2).
  Executes the deletion cascade (8.8). 200 `deleteFolderResponse`, so the client can confirm
  what the dialog promised. INV-1 via the cascade.
- **POST /folders/:id/archive.** Full control, the same authority as moving Work to Trash;
  409 for Desk. Marks this page and its live descendants archived, with their rows,
  tasks and hierarchy intact. 204. Archived Work answers 404 on ordinary active reads.
- **GET /archive/folders.** Lists archived Work initiators visible through current project
  membership, newest first, with name, archive date, actor name where available, and
  restore and permanent-delete authority for the viewer.
- **POST /archive/folders/:id/restore.** Full control or the owner; restores the same Work
  and its archived-with pages, returning the Folder at 200. A non-member or a page archived
  with another page gets 404.
- **DELETE /archive/folders/:id.** The owner while holding Full control permanently deletes
  that archived Work and its archived-with pages. It takes confirmation in the client and
  answers 204; refusal is 403 to a member, 404 to a stranger.
- **PATCH /folders/:id/my-membership.** Body `patchFolderMyMembershipBody`; any subset, null
  clears. Any member, own row only. Where V has no shelf of the named name, the endpoint
  makes it in the same transaction (4.18), since a shelf name with no shelf behind it is a
  Library heading nothing can link to. Clearing the shelf name leaves the shelf, a shelf
  outliving its folders (9.1). 200 Folder.
- **POST /folders/:id/members.** Body `postFolderMembersBody`. Full control (`member.add`).
  `access` is required and has no default, because a default would be one person's
  authority chosen by nobody. Guards per 5.3 row 1: 409 default folder, 409 already member,
  422 no roster connection between V and the target, 422 member cap (10.3). An optional
  `responsibility` becomes the new member's first Responsibility revision in the same
  transaction, attributed to V. Sends the share-grant email. 201 with the members element.
- **DELETE /folders/:id/members/:userId.** Three legal shapes per 5.3. Removing another
  member is Full control's (`member.remove`); the folder's owner cannot be removed by anyone
  (403), because ownership is given up by transfer and never taken. A non-owner may leave.
  The owner removing themselves is 409 "transfer ownership before leaving" while other
  members exist and 409 "delete the folder instead" when sole member; there is no automatic
  succession. Any removal or leave that would leave the folder with nobody in Full control
  is 409. All run R-CLEAN. 204. INV-4, INV-5, INV-10. 8.10's account deletion is the one
  path that transfers ownership automatically.
- **DELETE /folders/:id/my-membership.** The leave, addressed as V's own membership: the
  same rules as the members path with the target fixed to V (`member.leave`).
- **PATCH /folders/:id/members/:userId.** Body `patchFolderMemberAccessBody`. Changes a
  member's Access. Full control (`member.access.change`), except that any member may lower
  their own Access and nobody may raise it (403). 403 when the target is the owner and V is
  not; 404 when the target is not a member; 409 when the change would leave nobody in Full
  control; 409 when `expected_access` no longer matches the row, so two racing changes
  cannot both claim the same starting preset. 200 with the members element.
- **POST /folders/:id/owner-recovery.** The owner restores their own Full control
  (`owner.custody_recovery`), whatever preset they lowered themselves to, so an owner is
  never locked out by the people they delegated to. Recorded as a recovery, not as an Access
  change. 200 with the members element.
- **GET /folders/:id/access-history** and **GET /folders/:id/members/:userId/access-history.**
  Any current member (`member.access.history.read`). Response
  `getFolderAccessHistoryResponse`. A former member keeps their entries and loses the read.
- **GET /folders/:id/members/:userId.** The member-details projection,
  `getFolderMemberDetailsResponse`. Any member (`folder.read`), 404 to anybody else. Its
  `viewer_may_*` flags say whether a control is worth rendering and authorize nothing:
  every route re-asks for itself. It costs a constant number of statements however many
  members are asked about.
- **GET /folders/:id/members/:userId/responsibility.** `getResponsibilityResponse`. Any
  member, 404 to anybody else. A member who has written nothing and a former member both
  read the empty standing rather than 404, so "there is none" and "you may not see it" are
  one answer.
- **PUT /folders/:id/members/:userId/responsibility.** Body `putResponsibilityBody`,
  response `putResponsibilityResponse`. Full control writes any active member's, including
  their own; anybody else writes only their own, and only when
  `folder_members.can_edit_own_responsibilities` is set (4.4). 403 when refused; 404 when
  the target is not a member of a folder V can see; 422 on an invalid document, an unsafe
  link or an unknown document version. A commit whose content already equals the current
  content is 200 `committed: false` whatever `base_revision` said; only then is a stale
  `base_revision` 409. That order makes a retry after a lost answer safe without a receipts
  table. The decision is taken inside the write's transaction, under the lock that
  authorizes it.
- **GET /folders/:id/members/:userId/responsibility/history.**
  `getResponsibilityHistoryResponse`. Any current member, 404 to anybody else, a former
  member included. Newest first, capped at 10.3's list-response limit, with `truncated` true
  only when a row past the cap exists, because a list is never silently short. It is not a
  paged read.
- **PUT /folders/:id/members/:userId/self-edit-grant.** Body `putSelfEditGrantBody`. Full
  control only (`responsibility.self_edit_grant.manage`): 403 below it, 404 outside the
  folder, 403 when the target is the owner, who needs no grant. 200
  `{ member_id, can_edit_own_responsibilities, changed }`, `changed` false when the toggle
  already held. Both directions are recorded in 4.29 with the administrator as actor.

The self-edit grant is not a sixth Access preset and widens nothing else: it admits one
action, only when the member it names is the actor, and a holder can neither pass it on nor
grant it to themselves.

The Folder object carries the viewer's own `my_access` so that Library rows built from GET
/folders can gate Rename, Leave and Delete without a per-row detail fetch; `is_owner` cannot
answer any of those.

Duplicating a folder (7.16) copies its cover picture into the new folder, and a copy that
would take the caller past 10.3's storage quota answers 413 `quota_exceeded`.

Every Folder object carries `counts` (pending and completed Tasks, abandoned on neither side)
and `progress`, the finite progress a Folder or Section shows as "17/22 done · ↻ 3 recurring":
`done` and `total` count one-off Tasks (null `recurrence_rule`) that are completed, and
pending or completed; `recurring_active` counts pending Tasks with a recurrence rule. A
recurring Task is outside the finite denominator because each occurrence is its own row, and
a completed occurrence, whose rule 8.5 hands to its successor, is recognized by the
`series_id` it keeps and counted nowhere.
Abandoned and trashed Tasks count nowhere. `section_progress` applies the same three counts
to the Tasks whose `section_block_id` is that section; a section's count never includes a
nested section's Tasks. Both fields are optional in the schema, so a client never depends on
them being present.
