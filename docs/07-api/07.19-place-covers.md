### 7.19 Place covers

GET /api/v1/place-covers — the caller's own covers, one entry per place they have chosen one
for. PUT /api/v1/place-covers/:place — a `file_id` or a `preset`, exactly one of the two
(422 naming the pair otherwise), plus an optional focal point; idempotent, 200 with the
entry. DELETE /api/v1/place-covers/:place — removal, 204, idempotent. Shapes:
`putPlaceCoverBody`, `placeCover` and `getPlaceCoversResponse` in
`app/src/shared/covers.ts`. `:place` is 4.20's set and anything else is 404, a place page
being furniture rather than a resource that might exist elsewhere. Covers are the caller's
own throughout: no route reads or writes another person's, and a folder's or a shelf's cover
stays where 7.4 and 7.16 put it.

**A named file must be a picture the caller can read**: readable by 7.15's serving predicate
**and** `kind` in (`cover`, `image`). The kind clause is not decoration: the predicate admits
every avatar to every account, so without it a person could wear another person's avatar,
or store a voice note as a cover and draw it as a broken image. Absent, unreadable and not a
picture all answer **404 with one sentence** (10.2's rule, never 403).

#### A cover file's lifetime

This section owns the rule for every page kind; 7.4, 7.15 and 7.16 point here.

**1. Copy at set-time.** When a cover is set on a shelf (7.16), a built-in place page (this
section) or a folder (7.4) from a file that is not already a `cover` in that page's own scope
owned by the setter, the server copies it — a new `files` row of kind `cover` with the
original's bytes and dimensions — and the page stores the copy's id. **The copy's scope is
the page's**: a shelf or a place page gets a folder-less copy owned by the setter, a folder
one inside itself, a folder's cover being one look for every member. So a page's cover is
always a file its own owner holds outright, and **leaving a folder can never blank a cover**.
A folder-less cover uploaded or fetched by the photo tier (7.15) is already that shape and is
stored as it stands; the same folder-less picture worn on two of a person's own pages is not
copied and reads back the same id on both, rule 2's reference query keeping them
independent. A folder's cover never copies in practice, 7.4 already requiring a file of that
folder; the rule covers it anyway, for the day that gate widens.

**2. Reclaim when nothing references it.** A folder-less file of kind `cover`, `image`,
`file`, `audio` or `video` that no column names — every foreign key into `files(id)` from a
folder cover, a shelf cover, a place cover, a page block and a comment attachment — is marked
unreferenced by the 11.7 tick, and deleted, row and object, once it has carried the mark for
30 days. Such a file is listed by no surface and reachable by no route, and would otherwise
spend its owner's 1 GB (10.3) forever. The reference count is a query, not a counter column,
so the foreign keys stay the only record. The mark (`files.unreferenced_since`) is cleared
the moment something references the file again, so **the thirty days run from when the file
came off, not from when it was uploaded**, and a cover put back inside the window starts
over. Rows inside a folder are never reclaimed: they are listed in their folder, deletable
there, and 8.8's purge takes them with it. `avatar` is never in the kind list and must not
be, and `voice` cannot qualify, always having a folder. The reclaimable kinds are one
constant, `RECLAIMABLE_KINDS` in `app/src/server/domain/files.ts`, shared by the mark, the
clear and the delete.

**Why 30 days and not at once**: a file the server has stopped referencing is still one the
caller holds the id of. A cover picker that sets a picture, replaces it with a gradient and
sets the picture back would be answered 422 by an immediate delete.

**3. Legacy rows keep working and are not backfilled.** A cover that names a file inside a
folder, or a file a second page also names, is never reclaimed; it simply lacks rule 1's
protection until the person sets it again, and stops drawing if its wearer leaves that
folder.

**4. A copy spends the setter's quota.** A copy is a `files` row, so a set or a duplicate
that would take the account past 1 GB is refused **413 `quota_exceeded` with section 9's
sentence**, the upload path's own refusal, because a copy that will not fit is the same event
to a person as an upload that will not. A set that copies nothing spends nothing and is never
refused on storage, so a full account can still rearrange pictures it has already paid for.
