### 7.13 Trash

GET /api/v1/trash — the caller's reachable deleted tasks and folders (a tab is a folder; `facets` is always empty since step 7)
inside the 30-day window, as separate arrays, never one list. Wire shape: `getTrashResponse`
in `app/src/shared/trash.ts`. Every row carries `is_owner` and `my_access`, the viewer's own
Access preset for the row's folder, required and never defaulted: a trashed folder is not in
`GET /folders`, so the preset has to travel with the row, and the two permanent deletes turn
on different facts, so neither field answers alone.

POST /api/v1/tasks/:id/restore · POST /api/v1/folders/:id/restore — access by folder
membership, never by who deleted; a non-member is 404. A restore answers the restored
object. DELETE of a task or folder sets `deleted_at` (soft);
purge is the tick's, at 30 days, permanent.

DELETE /api/v1/trash/tasks/:id · DELETE /api/v1/trash/folders/:id — the permanent delete:
destroys a trashed row now, exactly as the 11.7 purge would at thirty days, through the
purge's own collection rather than a delete beside it. Only a row in Trash qualifies; a
live row is 404, the live delete being the soft one above.

- **A task's permanent delete is Full control, with ownership ignored**: it is an
  irreversible administrative act, so a Full-control member who owns nothing performs it
  and an owner below Full control does not.
- **A folder's permanent delete is Full control and the owner together**, permanent
  destruction of the whole folder staying with custody.
- A member below the bar is 403, the row being visible to them; a non-member is 404 (10.2).

The cascades fire at once: a folder's tasks, conversations, page blocks, memberships,
events and files rows; a task's steps, reminders, My Day entries, comments, and the files
that hung on its conversation and on nothing else. Every collected file's bytes leave the
store after the transaction commits, 7.15's order. 204 with no body; a task's destruction
is recorded as a `deleted` event against its folder, a folder's is not, its events going
with it.

The screen decides whether to draw Purge from `my_access` through the same table the route
resolves against (7.11's client convenience); the refusal is always the route's.
