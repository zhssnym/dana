# RFC 0001: MVP

- **Status:** Accepted
- **Created:** 2026-07-29
- **Target release:** 1.0.0
- **Spec sections touched:** none (bootstrap; see the delta section)
- **Frozen interfaces touched:** none

## Summary

Build the first shipping version of Dana: a collaborative to-do web application
delivered as an installable PWA, entirely manual, with no AI and no integrations.
This RFC is the one-time work order that takes the repository from empty to
released. What Dana must do is defined in `../spec/`; this document is
only the plan for building it.

The MVP is the single bootstrap case in this project's workflow. Every later RFC
proposes a change to a system that already exists and folds its behavior into the
specification once implemented. This one has no "before": the specification was
written first, in full, and this plan delivers it.

## Motivation

Dana's product thesis is small and specific: folders as the single organizing and
shareable primitive, and scheduling that is derived rather than filed, so a task
lives where its due date says it lives and every page is a query over the same
rows (section 1.1). The people building it are a two-person team with no
operations capacity, so version 1 is deliberately manual, boring, and cheap to
run: the goal is a correct core that costs minutes per week to operate, with AI,
integrations, offline writes, and realtime all deferred until that core has
proven itself (section 1.3).

The build order exists because of who implements it. The implementers are AI
coding agents working in isolated sessions with no channel back to a human
reviewer, so the contract had to be complete before the first line of code: a
full data model with named invariants, exact query orderings, a frozen API,
normative UI copy, a decided architecture (section 11), and 115 numbered
acceptance criteria written by a role that never implements. This RFC turns that
finished contract into a running system, in dependency order, one package per
agent session.

Why now: the specification is complete, the architecture is decided and
normative, the thirteen roles are defined against it, and nothing else blocks
the first package.

## Specification delta

None, and uniquely so. This is the bootstrap RFC the template preamble names:

## Compatibility and migration

Omitted: there is no prior system, no stored data, and no user; nothing exists

## Alternatives considered

Product-level alternatives, each already argued down with its reason recorded in
section 1.3 (the authoritative table; one line each here):

- **An AI-first launch** (chat, extraction, inbox scanning): needs model
  infrastructure and, for inbox scanning, a sensitive Gmail OAuth scope with an
  annual re-verification burden a two-person team cannot carry. Deferred to v2
  and v3.
- **Offline writes and a sync engine**: the largest hidden subsystem in this
  product category; deferred rather than half-built.
- **Realtime sync and presence**: last-write-wins with refetch is sufficient at
  v1 scale.
- **Task-level sharing**: rejected permanently; the folder is the only shareable
  unit by design, and the product's sharing model depends on that simplicity.
- **Permission tiers beyond a single member role**: the role column is reserved
  and carries one value in v1; tiers wait for evidence they are needed.
- **Native iOS, Android, or desktop builds**: the installable PWA covers
  installation without three more build targets.

One process alternative worth recording because it shaped everything: **building
spec-as-you-go**, the default for human teams, was rejected. Agent implementers
in isolated sessions cannot resolve ambiguity in a hallway; every gap in a
partial spec becomes a silent wrong guess. Writing the complete specification
first, then freezing its interfaces, is the project's core bet.

Stack-level alternatives (Next.js, Vercel, Supabase, Neon, the auth libraries,
and the rest) are recorded normatively with their rejection reasons in section
11.14 and are not repeated here. The full argumentation trail from product
description v1 through specification v4 is preserved in this repository's git
history.
