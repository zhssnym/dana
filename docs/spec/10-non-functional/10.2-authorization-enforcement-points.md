### 10.2 Authorization enforcement points

**Corrected 2026-08-31 against the code. The previous sentence opened "One chokepoint:"
and there is not one.** There cannot be, because what counts as authorized depends on what
is being asked for, so no single middleware can decide it. What the sentence described as
one mechanism is two, and the difference matters to anyone adding a route.

**The structural half.** Every data query joins folder_members on the viewer *inside the
FROM clause*, so a query that forgets the join returns nothing rather than returning
another person's rows. This half is genuinely hard to get wrong, and it is why the
original sentence felt true.

**The hand-written half.** Every mutation resolves the 5.4 matrix server-side before
touching rows, through roughly twenty `accessOf(...)` gates written by hand across nine
files. **Adding a route means adding its gate. Nothing adds it for you, and nothing fails
if you forget.** `app/tests/criteria/ac-236-structural-guard-sweep.test.ts` walks the mounted
router and refuses any POST, PATCH, PUT or DELETE that lacks a session or CSRF check.
**It covers GET as well, corrected 2026-09-02 under issue #33**, where every read must
answer 401 without a session unless it is one of three named public routes, each carrying
in the test the reason it can have no session: the platform health probe and the two legs
of the OAuth sign-in. That allowlist is asserted in both directions, so an entry naming a
route that is in fact gated, or a route that no longer exists, fails rather than widening
quietly. **What the sweep checks is still authentication, not authorization**, and no test
anywhere asserts that a given route gates on membership: a GET that requires a session and
then reads any row it is asked for passes everything here.
Inaccessible resources answer 404 (never 403) to avoid existence leaks;
permitted-visibility but forbidden-action answers 403. No endpoint trusts a folder_id,
task_id, or user_id from the client without these checks. The composite FK of 4.5 and the
constraints of section 4 are the last line, not the first.

**Amendment, 2026-09-04, issue #74: the hand-written half is now enumerated, and
`app/tests/criteria/ac-397-authorization-sweep.test.ts` is where.** The paragraph above ends "no test
anywhere asserts that a given route gates on membership"; that sentence was true when it was
written and is kept because the sweep is the answer to it rather than a replacement for it.
AC-397 walks the same mounted router `ac-236` walks, selects every route whose path carries a
parameter — 59 of them when it was written on 2026-09-04, and 60 an hour later when the
wave-1 integration merge brought `POST /api/v1/shelves/:id/duplicate`, which cost the one row
it should and moved the pinned count and nothing else — and drives each one as a signed-in
person with no
membership, no authorship and no connection to the row the id names, expecting 404, or 403 on
the eleven routes where 5.4 or 7.15 grants a member visibility and withholds the act. **It
found one defect on its first run and it was this second clause that was broken**: `DELETE
/api/v1/files/:id` answered 404 to a folder member who reads the same bytes at 200, so
visibility was permitted and the refusal was still hiding an existence the endpoint next door
had already disclosed. Fixed the same day under 7.15's dated amendment, with AC-398 asserting
the pair; the rule about who may delete is unchanged and only the status moved. **The reach is
wider than "a member of the folder" and the amendment says so**: readability there is the
serving predicate, which admits every avatar to every signed-in account by design, so that
route now answers 403 to a *stranger* aiming at anybody's avatar — bytes the same caller
fetches at 200, which is this section's rule holding rather than bending. **The table of
expected statuses is hand-written and always will be**, and it is worth having for one
property only, the property `PUBLIC_READS` has in `ac-236`: it is asserted against the
enumeration in both directions, so a new id-bearing route with no entry fails rather than
passing in silence, and an entry naming a route that is not mounted fails too. Four routes
carry a path parameter that names no row of ours — 4.20's two place surfaces and the
Openverse thumbnail proxy — and each holds an entry saying so with its reason, in the same
form and for the same reason as this section's three public reads.

**Three limits, stated because a guard nobody knows the edges of is worse than none.** The
enumeration is **path-only**: an id arriving in the query string or the body is invisible to
it, so `GET /events?folder=`, the `?task=` on a thread, and every `file_id` in a request body
are gated by hand exactly as before. It is **one level deep**, as `ac-236` is: a router
mounted inside a router would contribute nothing and the pinned count is the only thing that
would notice. And it can be satisfied by adding a route and its row in one change without
thinking about either — which is a reviewer's job, and the rule string every row carries is
what the reviewer reads.

**Amendment, 2026-09-20, issue #226: the path-only limit above now has a second standing
example, and it is on a surface that did not exist when that sentence was written.**
`GET /api/v1/labels` takes an optional `folder_id` in its query string, which narrows the
Folder half of the Label listing to one folder. It carries no path parameter, so `ac-397`
never enumerates it and never drives it with a stranger's id; its gate is a membership
probe written by hand in `listLabels`, answering 404 rather than 403 for this section's
usual reason, and **AC-473 is the only thing in the suite that asserts it**. The eleven
Label routes that *do* carry a path id are swept with everything else and each carries its
row.

Two things about that surface are worth recording here rather than only in #226, because
both are authorization facts a reader of this section would otherwise have to infer.
**Privacy has a second shape on it**: a Personal Label is private to one account, so every
statement touching `task_personal_labels` or `folder_personal_labels` carries
`owner_user_id = <viewer>` in the same position the membership join occupies for shared
work — the structural half of this section applied to a second kind of scope, and with the
same property, that a statement which forgets it returns nothing rather than somebody
else's rows. And **a 404 and a 422 mean different things on that surface and must not be
swapped**: 404 is "you cannot see this", which a Label of another account gets, and 422 is
"you can see this and it does not belong here", which a Folder Label aimed at another
Folder's task gets. Answering 422 to the first would confirm an existence, which is the
leak this section exists to prevent.

**Amendment, 2026-09-20, issue #274: there is now a third status on that surface, and the
three are three different facts.** Six of those Label routes answer **403** to a member of
the Folder who is below the bar the act sits at — `label.vocabulary.manage` at Can edit,
`label.apply` at Can edit or at Can contribute over the Task currently assigned to them —
superseding #208's interim rule that every member of a Folder could do all of it. So: 404
is "you cannot see this", 403 is "you can see it and you may not do this", and 422 is "you
can see it and it does not belong here". A 403 is legitimate here for this section's own
reason and only for it — the caller has already been proved a member, so the refusal
confirms nothing they did not know — and the sentence it carries is the resolver's `why`.
**`ac-397` does not enumerate any of these as a `member` row**, because its `fx.member`
holds Can edit and is therefore *at* the bar; the criterion that drives the refusals is
AC-800, one actor per preset. That is the same shape the paragraph above describes for the
query-string gate: the sweep is structural, and what a *member* is refused is a criterion's
to assert.
