### 10.8 Response security headers

Every response carries Content-Security-Policy with default-src 'self' and
frame-ancestors 'none', sized to what the client actually loads and no wider,
plus Referrer-Policy: strict-origin-when-cross-origin. HSTS is the edge's,
set by the host in front of the process, never by the process itself. The
7.15 serving rules keep their own stricter per-file headers (nosniff on
everything served, attachment for kind file) and this section does not relax
them. Added 2026-08-25 by change control item 18: section 10 was silent on
response headers, the whole posture was one disabled x-powered-by, and the
upload path's safety rested on a single predicate with no second line behind
it. One acceptance criterion is owed; its number is the test persona's to
assign.

Amended 2026-09-06 for issues #177 and #184: `frame-src` admits exactly
`https://www.youtube-nocookie.com` and `https://player.vimeo.com`. Those are the only remote
frames the folder composer creates. Direct mp4/webm/ogg URLs remain links, so `media-src`
does not gain a remote host; no wildcard or caller-chosen frame origin is admitted.

Amended at the polish round of 2026-08-30 (avatars F3): img-src admits
`https://*.googleusercontent.com`, because 7.2 stores Google's `picture`
claim in `users.avatar_url` at first sign-in and every surface that draws a
person has been trying to load it since 4.1. This is "sized to what the
client actually loads" applied rather than relaxed — the policy was
undersized for a thing the product has always drawn — and the failure was
invisible because a disc falls back to initials on an image that will not
load, so an account with a Google picture was indistinguishable from an
account with none. The host is fixed and is the identity provider the
session already rests on, the directive admits images alone, and no route
writes a caller-supplied string into that column: provisioning writes the
claim and 7.15's upload writes `/api/v1/files/:id`. A third-party host
chosen at *runtime* is the different case and is still refused — the cover
photo tier proxies its bytes through this origin for exactly that reason
(7.15, `routes/cover-photos.ts`).

Amended 2026-09-03 (issues #34 and #13). "Sized to what the client actually
loads" is recorded here as a set rather than left as a sentence, because the
previous set was never read back from a browser and four things the product
does were being refused. None of them can happen in development: `npm run dev`
serves the document from Vite, which sends no policy, and proxies only `/api`
to this process, so the header rides on API responses and never on the page.
Each addition below was measured with Chromium against the production build.

- **script-src 'self' '<sha256 of the theme script>'.** `app/index.html`
  carries one inline script, which paints the theme from the localStorage
  mirror before the first frame (9.7, and RFC 0005 change control item 43).
  With no script-src stated, `default-src 'self'` governed it and refused it,
  so every person on Dark saw a white frame on every cold load. **A hash and
  not `'unsafe-inline'`**: widening the one directive that decides whether an
  injected script runs, in order to remove a flash, is not a trade this
  section makes. **A hash and not a nonce**, because a nonce has to be minted
  per response and written into the document, and this process serves
  `index.html` as a static file it never templates; there is no render step to
  put a nonce in.
- **img-src blob:** and **media-src 'self' blob:**. The client loads a chosen
  File through an object URL to crop it, draws one as the preview of an
  attachment whose upload is still in flight, and plays a just-recorded voice
  note from one before it has been uploaded. `media-src` is written out rather
  than left to fall back so that `'self'`, which the uploaded note is served
  from, is stated too.
- **connect-src data:**. The crop hands its canvas `data:` URL back through
  `fetch()` to rebuild it as the File the multipart upload takes, and
  `connect-src` is the directive that governs fetching a `data:` URL.

**Neither scheme is a widening of what this document can talk to.** A `blob:`
or `data:` URL is bytes the document already holds; it reaches no network and
names no origin, which is the same ground `data:` was already admitted on for
`img-src`. The place a `blob:` source would matter is `script-src`, where it
defeats a hash or nonce policy by letting a script be assembled at runtime and
executed from a URL no policy can pin, and **it is deliberately not there**.
The only worker this client starts is `/sw.js` from this origin, so
`worker-src` needs no `blob:` either and does not get one.

**Adding `script-src` moves `worker-src`'s fallback, and the chain was checked
rather than assumed.** `worker-src` falls back to `child-src`, then
`script-src`, then `default-src`. Neither `worker-src` nor `child-src` is
stated, so the service worker was governed by `default-src 'self'` before this
amendment and is governed by `script-src 'self' '<hash>'` after it. Both
resolve to `'self'` for `/sw.js`, and a hash-source constrains inline code
rather than a URL, so there is no regression. This is the kind of consequence
that is invisible six months later, which is why it is written down.

**The hash is stable across checkouts only because of `.gitattributes`.** That
file sets `* text=auto eol=lf`, and `core.autocrlf` is true on at least one
machine that builds this repository. A CRLF working copy of `app/index.html`
digests to a different value, the policy would then name a hash the served
document does not carry, and the script would be refused in production exactly
as it was before this amendment — silently, because nothing reports a CSP
refusal. Changing that line, or checking the repository out in a way that
bypasses it, breaks production. `tests/ac-238-response-security-headers.test.ts`
recomputes the digest from the shell document and fails if `script-src` does
not name every inline script in it, preferring the built
`dist/client/index.html` the browser is actually served and falling back to
`app/index.html` when nothing has been built; CI reaches the vitest legs before
the build step, so there the fallback is what runs, and issue #96 carries the
version that reads a freshly built document.

Amended 2026-09-04 (issue #99). **The policy now says where a refusal is to
be reported, and this is the amendment that makes the four above findable
rather than found.** Every one of them was a directive sized wrongly against
what the client loads, and every one was silent for months, because a CSP
refusal raises no error the server can see, no error the client reports, and
nothing a person would read as an error rather than as a bug in something
else. Four defects, one cause, no signal.

- **The policy gains `report-uri /api/csp-report` and `report-to
  csp-endpoint`, and every response gains `Reporting-Endpoints:
  csp-endpoint="<APP_ORIGIN>/api/csp-report"`.** Both generations of the
  mechanism are sent because browsers are split across them: `report-uri` is
  implemented everywhere and deprecated in Chromium, `report-to` is its
  replacement and needs the header to say what the endpoint name means. A
  browser honouring both sends one report, not two. Sending only the modern
  pair loses Safari and Firefox today; sending only the old one loses
  Chromium on the day it finishes the removal, silently, which is the
  failure this whole amendment exists to end. The endpoint is absolute under
  `APP_ORIGIN`, which 11.11 makes certain in production, and relative when
  that is unset, which is development only.
- **The endpoint is `POST /api/csp-report`, outside `/api/v1` and beside
  `/api/health`.** The browser posts it from its own networking stack: there
  is no session cookie on it and no `X-CSRF-Token`, and nothing this
  application can do would put either there, so it cannot live under a mount
  that requires both. It is the fourth entry in
  `tests/ac-236-structural-guard-sweep.test.ts`'s exemptions and carries its
  reason there. What makes leaving it open acceptable is what it may do: it
  reads nothing, writes nothing, takes no database handle, and its whole
  effect is one log line and one Sentry message.
- **It answers 204 for a report it drops exactly as for one it keeps.** The
  status must not vary with the content of a report, or the endpoint becomes
  an oracle for this deployment's own filters, answerable one probe at a
  time. The status does vary with the shape of the *request*: a body over
  16 KB or one that is not JSON is 400, which is the answer 10.3 and AC-118
  already fix for every endpoint on this surface, and the limiter's refusal
  is 429 with `Retry-After` because 10.4 says every limit answers that way.
- **Two filters run before anything is logged.** A report whose document
  origin is not `APP_ORIGIN` is dropped: it is about somebody else's page.
  A report whose `blocked-uri` scheme is a browser-extension one is dropped —
  `chrome-extension:`, `moz-extension:`, `safari-extension:`,
  `safari-web-extension:`, `ms-browser-extension:`, `webkit-masked-url:`,
  `resource:` and `about:` — because extensions inject scripts and styles
  into every page they run on and the browser attributes the refusal to the
  document, so an unfiltered endpoint collects noise in proportion to how
  many people run an ad blocker, and an alert stream nobody can act on is an
  alert stream nobody reads. `data:` is dropped **only** under `style-src`,
  where it is what reader modes and translation widgets inject and where
  `'unsafe-inline'` already means no such refusal can be Dana's; a `data:`
  URL refused under `script-src` is a script being assembled at runtime,
  which is the one thing this policy exists to stop, and it is kept.
- **At most ten reports are read from one body**, the Reporting API being a
  batching one, which with 10.4's row bounds the endpoint at 300 log lines a
  minute per address on free tiers 11.12 sizes for ordinary volume.
- **Sentry receives at most 20 events per ten-minute window from this
  endpoint, and a given fingerprint at most one of them.** Two bounds and
  not one, because the first is not a bound at all on its own. Sentry's
  fingerprint groups *issues* while a free-tier quota counts *events*, so
  grouping left the arithmetic intact: 10.4's 30 requests a minute times the
  ten violations above is 300 events a minute from one stranger who knows
  `APP_ORIGIN`, against a plan allowing about 5,000 a month, and the real
  errors after that are the ones dropped. Per-fingerprint dedupe does not
  answer it either, because the fingerprint contains the blocked URI and
  that is the stranger's own string: one changed character is one more key.
  So the values in the fingerprint, the message and the tags are the same
  whitelisted ones the log line carries — never the report's — which makes
  the key space the directive crossed with a keyword, a `scheme://host` or
  `other`; and the absolute budget sits over the top of that. The worst case
  is then about 8,600 events a month rather than 130,000, which is a flood
  that must be sustained for a month to matter rather than for twenty
  minutes. **When the budget is spent, exactly one message says so**, since
  a quiet alert channel and a healthy deployment look identical and that is
  the disease this whole amendment is about. **The log line is never
  throttled**: the log is the complete record of how often a refusal
  happens, and Sentry is only how anyone finds out that it does.
- **A report is dropped unless its document was served on `APP_ORIGIN`, by
  design and not merely by accident of configuration.** A deployment
  reachable on more than one host — a Render subdomain beside the custom
  one, a preview URL, an IP — reports only from the canonical one, and every
  refusal a person meets on any other host is silent exactly as it was
  before this amendment. That is the right trade while `APP_ORIGIN` is also
  what 10.1 builds `redirect_uri` from and what 11.8's mail links use, so a
  second host is already a half-configured deployment; but it is a real
  blind spot and is written here rather than discovered from an absence of
  reports. The `Reporting-Endpoints` header names the endpoint absolutely
  under `APP_ORIGIN` for the same reason, so the two agree by construction.

What a kept report writes is 10.5's, and what it sends to Sentry is 11.12's.
AC-394 to AC-396 are this paragraph's.

**What this does not do, stated because the gap is the interesting part.**
Nothing here proves a browser actually delivers a report: the criteria drive
the endpoint directly, and the header arm reads the header rather than a
browser's behaviour under it. The first real evidence will be a
`csp_violation` line in production, and its absence for a week is not
evidence of a policy that fits — it is equally evidence of a header a
browser did not honour. Issue #96's browser-leg check, which reads a
freshly built document, is where that would be closed.
