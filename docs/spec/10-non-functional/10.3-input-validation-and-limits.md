### 10.3 Input validation and limits

Every value below is bounded, and the bound is product-visible contract: raising or
lowering one is a spec change. The number lives in the code named beside it, not here.

| Value | Where the limit is fixed |
| - | - |
| Task title, step title | `TASK_TITLE_LIMIT` in `app/src/shared/tasks.ts` |
| Notes | `TASK_NOTES_LIMIT` in `app/src/shared/tasks.ts` |
| Folder name | `folderName` in `app/src/shared/folders.ts` |
| Shelf membership, shelf name | `shelfName` in `app/src/shared/folders.ts` and `app/src/shared/shelves.ts` |
| Steps given when a task is created | `steps` in `postTasksBody`, `app/src/shared/tasks.ts` |
| Custom folders per account | folder cap in `app/src/server/domain/folders.ts` |
| Members per folder | `MEMBER_CAP` in `app/src/server/domain/invites.ts` |
| Recurrence rule string | rule schema in `app/src/shared/tasks.ts`; subset of 4.11 only |
| Reminder offset | reminder schema in `app/src/shared/tasks.ts` |
| Search query | query schema in `app/src/shared/views.ts`, measured after trimming |
| Calendar range | `CALENDAR_RANGE_MAX_DAYS` in `app/src/server/time/predicates.ts` |
| List responses | `LIST_ROW_CAP` in `app/src/shared/list-cap.ts`, with a truncated flag |
| Email address | `app/src/shared/invites.ts`; syntactically valid, stored lowercased |
| Timezone | `app/src/shared/timezone.ts`; a valid IANA identifier |
| Comment body | `app/src/shared/comments.ts` |
| Page paragraph, page section name | `app/src/shared/pages.ts` |
| Folder and shelf description | `PLACE_DESCRIPTION_MAX` in `app/src/shared/place-descriptions.ts` |
| Blocks per page | `MAX_BLOCKS_PER_PAGE` in `app/src/shared/pages.ts` |
| One uploaded file, voice note length | `MAX_FILE_BYTES` in `app/src/shared/files.ts`; `MAX_VOICE_MS` in `app/src/server/domain/files.ts` |
| Files per comment | `COMMENT_FILE_CAP` in `app/src/shared/comments.ts` |
| Storage per account | `QUOTA_BYTES` in `app/src/server/domain/files.ts`, across every kind of 4.16 |
| Workflow import | `app/src/shared/workflows.ts`; folders, blocks and tasks per file |
| Page image width, cover reposition | `app/src/shared/pages.ts`, `app/src/shared/covers.ts` (percentages) |
| Saved views per account | view cap in `app/src/server/domain/bundle.ts` |
| JSON request body | `express.json` limit in `app/src/server/index.ts` |
| Label name, label description | `app/src/shared/labels.ts`; the name measured after trim |
| Label definitions and applications | the `*_CAP` constants in `app/src/shared/labels.ts` |

**How a limit is refused.** Every limit is server-enforced and answered 422 with the field
named, except the storage quota, which answers 413 with the copy of section 9, and the body
ceiling, which the parser refuses as 400 before any field is read. The body ceiling sits
above the largest legal workflow file so that every other cap in this table is reachable.

**A cap on a count is taken under a lock in the same transaction as the insert it admits.**
A count not tied to its insert is a suggestion: two creates arriving together at the limit
both read it and both insert.

**Files per comment bounds a count, not bytes.** A comment names files 7.15 already stored,
so it carries no payload of its own; the bytes are bounded at upload by the file and storage
rows.

**What a workflow import carries**: structure, titles, and each task's notes, star, repeat,
reminder and step titles; never ids, people, due dates or states.

**"Shelf membership" is the viewer's own shelf on a folder**, 4.4's
`folder_members.shelf_name`, held in step with a shelf's name by 4.18. It is not a
classification Label; Labels are their own rows.

**Label caps are technical safety limits, not taxonomy guidance.** Two are counted **per
viewer**: a Personal assignment is private to its owner, so one person filling their quota
on a shared task cannot stop a co-member applying their first. The Personal and Folder
per-task caps are counted apart for the same reason read the other way: the Folder set is
shared and the Personal set is not.

**The list cap is per response.** It covers the section 6 lists and `GET /api/v1/labels`,
whose worst case is every Personal definition plus every Folder definition across the
viewer's folders; one cap across the response rather than one per scope.

**Assumption: personal scale, behind the caps.** Open lists cap rather than paginate,
because the data is assumed to be personal-scale. If real accounts approach the cap, the
change is keyset cursors on the view endpoints and is isolated to section 7.10's responses.

**Assumption: the folder list is deliberately uncapped.** `GET /folders` is not among the
capped lists. The bound is social rather than numeric: owned folders stop at the custom
folder cap, and every further membership needs a mutual roster connection plus a manual add
into a folder under the member cap. If that bound fails, the fix is a cap or cursor on the
7.4 list response and nothing else moves.
