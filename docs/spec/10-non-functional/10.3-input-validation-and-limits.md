| Value | Limit |
| - | - |
| Task title, step title | 1 to 300 characters |
| Notes | up to 10000 characters |
| Folder name | 1 to 100 characters |
| Shelf membership, shelf name | 1 to 40 characters |
| Steps per task | 50 |
| Custom folders per account | 200 |
| Members per folder | 25 |
| Recurrence rule string | up to 200 characters, subset of 4.11 only |
| Reminder offset | 0 to 10080 minutes |
| Search query | 2 to 100 characters |
| Calendar range | up to 62 days |
| List responses | capped at 1000 rows with truncated flag |
| Email address | up to 320 characters, syntactically valid, stored lowercased |
| Timezone | valid IANA identifier |
| Comment body | up to 4000 characters |
| Page paragraph | up to 4000 characters |
| Page section name | 1 to 120 characters |
| Folder and shelf description | up to 500 characters |
| Blocks per page | 500 |
| One uploaded file | up to 25 MB; a voice note up to 10 minutes |
| Files per comment | 10 |
| Storage per account | 1 GB across every kind of 4.16 |
| Workflow import | up to 50 folders, 500 blocks and 1000 tasks per file; structure, titles and each task's notes, star, repeat, reminder and step titles, never ids, people, due dates or states |
| Page image width | 25 to 100 percent of the column |
| Cover reposition | 0 to 100 percent |
| Saved views per account | 50 |
| JSON request body | up to 3 MB, sized above the largest legal workflow file so every cap in this table is reachable |
| Label name | 1 to 40 characters after trim |
| Label description | up to 100 characters |
| Personal Label definitions per account | 500 |
| Folder Label definitions per folder | 250 |
| Personal Labels applied to one task | 100, per viewer |
| Folder Labels applied to one task | 100 |
| Personal Labels applied to one folder | 100, per viewer |

All numbers are server-enforced and returned as 422 with the field named, except the
storage quota, which returns 413 with the copy of section 9, and the body ceiling, which
the parser refuses as 400 before any field is read. The task cap and the body row were
added 2026-08-25 by change control item 18: the parser's undocumented 100 kB default was
refusing legal workflow files before this table's own import cap could, and was the only
bound on the task array.

The "Files per comment" row was unenforced from the day it was written until
2026-09-03, and is recorded here rather than quietly fixed because "all numbers are
server-enforced" was false about it for the whole of v2. `POST
/api/v1/folders/:id/comments` took a single `file_id`, so a comment could carry one file
and the number ten bounded nothing; the endpoint was widened to the cap on Imran's ruling
of that date (issue #22), not the cap narrowed to the endpoint. It is now a count refused
by the shared request schema with the field named, like every other row here, and AC-345
measures both sides of it. The row itself did not move a character. The bytes behind the
count are the two rows above it, which bind at upload rather than at the comment: a
comment names files that 7.15 already stored, so it carries no payload of its own and
needs no total-size limit.

The seven Label rows were added 2026-09-20 by issue #226, for the M1 Label model of #208,
and the first row of this table was reworded in the same change. **The wording is the
substantive part of that edit.** "Personal label" in this table has always meant the
viewer's own Shelf membership on a folder — 4.4's column, held in step with a shelf's name
by 4.18 — and never a classification Label, which Dana had none of until #226. The two
readings sat on one phrase, and the row now says which one it is; the number did not move,
and the column it names is `folder_members.shelf_name`, which 0022 adds **beside** `label`
rather than renaming onto it — a rename would leave the instance Render has not drained yet
selecting a column that no longer exists, which is hard stop 1's case. Issue #247 is the
contract half and drops the old column once 0022 is live.

The five Label caps are **technical safety limits rather than taxonomy guidance**, which
is #208's own phrase and its own instruction: any hard limit is product-visible contract
and is recorded explicitly rather than left in an implementation. Two of the five are
counted **per viewer**, and that is the model rather than a convenience: a Personal
assignment is private to its owner, so one person filling their hundred on a shared task
cannot stop a co-member from applying their first. The two per-task caps are counted
apart from each other for the same reason read the other way — the Folder set is shared
and the Personal set is not, so they are not one number. Each is guarded by a count taken
under a lock in the same transaction as the insert it admits, which is this section's
existing cap discipline; `src/server/domain/cap-guards.test.ts` measures that ordering and
AC-478 measures the refusal.

**Assumption: personal scale, behind the caps.** Open lists cap at 1000 rows rather than
paginating, because the data is assumed to be personal-scale. If real accounts approach
the cap, the change is keyset cursors on the view endpoints and is isolated to section
7.10's responses.

**Assumption: the folder list is deliberately uncapped.** Section 6 enumerates the lists
the 1000-row cap covers and `GET /folders` is not among them. The bound is social rather
than numeric: owned folders stop at the 200-custom cap, and every further membership needs
a mutual roster connection plus a manual add into a folder holding at most 25 members. If
that bound fails, the fix is a cap or cursor on the 7.4 list response and nothing else
moves. Revisit when any real account's folder list approaches the row count the capped
lists stop at.
