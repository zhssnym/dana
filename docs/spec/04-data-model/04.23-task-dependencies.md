### 4.23 task_dependencies

**Added 2026-09-20 by issue #224, on the technical ruling recorded there.** One
directed relation between two tasks: the **dependent** depends on the
**blocking** one. `blocks` is the same row read from the other end and is never
a mirrored second row.

| Column | Type | Null | Default | Constraint |
| - | - | - | - | - |
| id | uuid | no | generated | PK `task_dependencies_pkey` |
| dependent_task_id | uuid | no | none | FK tasks(id) ON DELETE CASCADE (`task_dependencies_dependent_task_id_fkey`) |
| blocking_task_id | uuid | no | none | FK tasks(id) ON DELETE CASCADE (`task_dependencies_blocking_task_id_fkey`) |
| created_by | uuid | no | none | FK users(id) ON DELETE RESTRICT (`task_dependencies_created_by_fkey`) |
| created_at | timestamptz | no | now() | none |

UNIQUE (`dependent_task_id`, `blocking_task_id`) as
`task_dependencies_pair_key`. CHECK (`dependent_task_id <> blocking_task_id`)
as `task_dependencies_no_self_edge_check`. Index
`task_dependencies_blocking_task_id_idx` on (`blocking_task_id`), btree,
non-unique and non-partial; the dependent side is served by the unique pair's
leading column.

**No derived state is stored, and that is the point of the table being this
small.** Whether a dependency is active, satisfied or unresolved is a function
of the blocking task's status, read at the moment of the read: pending means
active, completed means satisfied, abandoned means unresolved and **not**
satisfied, and reopening a completed blocker makes it active again. A persisted
`blocked` status would be a second answer to a question the `tasks` row already
answers, and it would be the one that goes stale.

**Both endpoint cascades are the trash rule rather than a cleanup decision.** A
soft-deleted task keeps its edges and restores whole; only the permanent delete
of 7.13 and the 11.7 purge, which `DELETE FROM tasks`, take them. That is the
issue's "soft-deleted Tasks retain dependency rows for lossless restoration"
expressed as foreign-key behaviour, so nothing has to remember to do it.

`created_by` is RESTRICT on the `tasks_created_by_fkey` precedent: accounts are
scrubbed (8.10), never deleted, so the restriction can never fire in ordinary
operation and exists to make that assumption explicit.

**Why the row carries a surrogate `id` when its two endpoints already name it
uniquely.** An edge has to be removable, and the natural name for it is the
pair — but one of those endpoints may be a task the caller must not learn
anything about (7.25). Handing back a composite key to address a deletion would
hand back the id being withheld. So the row carries an id of its own and the
pair's uniqueness is a named constraint beside it rather than the primary key.
