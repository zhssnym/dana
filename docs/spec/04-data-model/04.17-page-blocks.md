### 4.17 page_blocks

The writing arranged on a folder page, a shelf page or a facet document:
sections, paragraphs, structured text, media and folder references, ordered.
The page is the folder's — one page for every member, any member edits, the
event log says who (pricing decision D1).

Columns and constraints: `app/db/migrations/0003_v2_expand.sql`, then
`0005_ruled_schema.sql`, `0016_compose_first_canvas.sql`,
`0017_folder_document.sql`, `0021_structured_text_blocks.sql`,
`0024_files_and_media_blocks.sql`, `0027_folder_facets.sql` and
`0028_purpose_document.sql`. Block-kind vocabularies and their rules live in
`app/src/shared/page-document.ts`.

#### Homes and order

- **Exactly one home** (`page_blocks_one_home_check`): a folder, a shelf, or a
  facet (4.30). A facet document reuses this table rather than a store of its
  own, and its file scope is the facet's Folder.
- A folder page shares one fractional order with its real task rows:
  `page_blocks.page_position` and `tasks.page_position` form one ordering
  domain (COLLATE "C", gaps and ties allowed). Task→section assignment stays on
  `tasks.section_block_id` and is not duplicated in a page-item row.
  `page_position` is nullable only for rolling-deploy compatibility.
- Concurrency is last-write-wins per block content with the standard 409 on a
  stale `updated_at` (7.0); placement actions serialize on the folder row and
  there is no operational transform.

#### Sections and headings

- `section_block_id` is explicit on each item — direct parent identity on
  blocks and Tasks alike — so a loose paragraph after a collapsed Section is
  never mistaken for part of it. Null means No section. Only folder-homed blocks
  carry one; shelf and facet documents have no Sections.
- **Folder Sections nest at most three levels** (`MAX_SECTION_DEPTH` in
  `app/src/shared/page-document.ts`): root is Heading 1, its Section child
  Heading 2, that child's Heading 3. A Section's level is its depth in the
  relation and is **not stored**, since a level column would be a second source
  of truth for what the parent already answers. A parent must be a Section in
  the same folder at depth one or two; depth four is refused before any write.
  Content and Tasks may belong to a Section at any level.
- `heading1`, `heading2`, `heading3` are **presentation-only** headings for
  facet documents: they create no `section_block_id` relation, Task grouping,
  progress, Responsibility or Authority. Main refuses them; Main's semantic
  headings remain `section`.
- Heading names may be empty and are limited to 120 projected characters.
- Removing a heading lifts its direct content to its parent and promotes its
  child headings. No document operation can remove a live Task reference or
  overwrite Task fields. Completed Tasks keep their place; Trash removes the
  reference until restoration.

#### Text

- Structured kinds (`bullet`, `numbered`, `checklist`, `quote`, `callout`,
  `code`) are **persisted as explicit kinds, not as editor document JSON**:
  BlockNote is the editor, not Dana's storage format. There is no generic
  property bag.
- `rich_content` is Dana version-1 text runs (`text`, optional `bold`,
  `italic`, safe `href`); null means plain text. Its projection must equal
  `text`, which is what search reads. **`code` carries none.** Unsupported
  fields or versions are refused. Limits live in the schema and the CHECKs.
- `checked` is a checklist item's tick and is **authored content only**: it
  completes no Task, assigns no work, creates no Responsibility or Authority,
  and moves no progress. Non-null exactly on `checklist`; an omitted value
  stores `false`.

#### List nesting

- `list_parent_block_id` is **a second parent relation, not
  `section_block_id` widened**: section membership is Work grouping, list
  parentage is writing structure, and one column meaning both would leave a
  nested item's Section unreadable.
- Only `bullet`, `numbered` and `checklist` nest, on either end, in a folder or
  facet document; a Task never has a list parent, and a row never parents
  itself.
- A list parent is a block of the same document that **precedes every
  descendant in the outline** — which is the whole no-cycle rule. A nested item
  carries the **same `section_block_id` as its parent**; a list spanning two
  Sections is refused, since no client can draw it.
- A client save that would break any of these (parent not a list item, not
  earlier, other Section) drops the parent and promotes the child rather than
  sending a write the server refuses.

#### Media

- `file`, `audio` and `video` blocks join `image`. A media block **names at
  most one file by `file_id` and copies none of its name, MIME or size**; the
  `files` row (4.16) is the only authority, because one file may be placed on
  several pages. A `file`, `audio` or `video` block carries no `text` or
  `rich_content`; an `image` keeps its own authored caption.
- `file_id` is **required on `file`, `audio` and `video` and optional on
  `image`**. An image block may stand empty before a picture is chosen, and any
  media block loses its file when 7.19 reclaims it (`ON DELETE SET NULL`), so
  **no write may refuse a null `file_id` on an existing row** or the page
  becomes unsaveable.
- **A media block's kind must match its file's kind** (`BLOCK_FILE_KINDS` in
  `app/src/shared/page-document.ts`); `image` also admits a `cover` row, which
  folder duplication produces. This spans two tables, so it is enforced in the
  document write validation rather than a CHECK. For the same reason — live
  rows may already carry the shape — `file_id` on a non-media block is refused
  by validation, not by a CHECK a forward-only migration would have to prove
  against production.
- `width_pct` is the person's dragged width **as a percentage of the column**,
  so a picture keeps its proportion at any window size. The 25–100 bounds are
  the drag's own clamp, held in the CHECK so no client can store a width no
  gesture produces. Only `image` and `video` carry it; audio and generic files
  do not resize. Player state is not persisted.

#### Other rules

- `ref_folder_id` belongs to `folder_ref` blocks on shelf pages only; a facet
  block carries none, a reference out of a Folder belonging on Main.
- New kinds are writable only through `document_transaction` (7.16); a read
  answers every stored kind.

#### Document receipts

`page_document_receipts` (migration 0017) records one row per
`(actor, folder, mutation_id)` with the payload hash, the committed revision and
the Task ids it created, for the folder's lifetime. An identical retry
acknowledges the original commit and returns the current authorized page
without repeating it. Revisions hash block content, mixed placement and live
Task identity, membership and placement — not Task status, title, notes or
other independent Task fields. Folder locks serialize structural writes and
coherent page reads.
