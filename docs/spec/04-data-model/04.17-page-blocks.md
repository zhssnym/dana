### 4.17 page_blocks

The writing arranged on a folder page or a shelf page: sections, paragraphs
and images, ordered. A folder page shares one fractional order with its real
task rows; `section_block_id` is explicit on each item, so a loose paragraph
immediately after a collapsed Section is not mistaken for part of it.
The page is the folder's — one page for every member, any member edits, the
event log says who (pricing decision D1).

| column | type | null | default | notes |
| - | - | - | - | - |
| id | uuid | no | generated | PK |
| folder_id | uuid | yes | none | FK folders(id) ON DELETE CASCADE |
| shelf_id | uuid | yes | none | FK shelves(id) ON DELETE CASCADE; CHECK exactly one of folder_id/shelf_id |
| kind | text | no | none | CHECK (kind IN ('section','paragraph','image','folder_ref','bullet','numbered','checklist','quote','callout','code','file','audio','video')) — six added by issue #219 and three by issue #220, both on 2026-09-20 |
| position | integer | no | none | ordering within the page |
| page_position | text | yes | none | COLLATE "C"; position in the mixed folder page, or the shelf's block sequence; gaps and ties allowed; nullable for rolling deploy compatibility |
| section_block_id | uuid | yes | none | self-FK page_blocks(id) ON DELETE SET NULL; a non-Section folder block's semantic Section; null is No section; CHECK null for Sections and shelf blocks |
| list_parent_block_id | uuid | yes | none | self-FK page_blocks(id) ON DELETE SET NULL; the list item this list item is nested under, **independent of `section_block_id`**; CHECK null unless the row is a folder block of kind bullet/numbered/checklist, and never the row's own id (issue #219) |
| checked | boolean | yes | none | a checklist item's tick, authored content only; CHECK non-null exactly when kind = 'checklist' (issue #219) |
| text | text | yes | none | section name (1-120) or paragraph body (up to 4000) |
| file_id | uuid | yes | none | FK files(id) ON DELETE SET NULL; the media kinds — image, and file, audio and video from issue #220. The named `files` row is the only authority on that file's name, MIME and byte size; the block copies none of the three |
| ref_folder_id | uuid | yes | none | FK folders(id) ON DELETE CASCADE; folder_ref kind, shelf pages only |
| updated_at | timestamptz | no | now() | stale-write 409 per 7.0's conflict rule |
| width_pct | integer | yes | none | CHECK (width_pct IS NULL OR width_pct BETWEEN 25 AND 100); CHECK (width_pct IS NULL OR kind IN ('image','video')) — `video` added by issue #220 on 2026-09-20; the person's dragged width as a percentage of the column |

Task→section assignment remains `tasks.section_block_id uuid null`; it is not
duplicated in a page-item row. `page_blocks.page_position` and
`tasks.page_position` form one ordering domain for a folder page. Concurrency
is last-write-wins per block content with the standard 409 on stale
`updated_at`; placement actions serialize on the folder row and there is no
operational transform.

Folder identity rides the folder: 4.3 gains `icon text null` (server-known
key set), `color text null` (#RRGGBB), `cover_file_id uuid null FK files`,
`description text null` (up to 500) — expand-only column additions.

#### 2026-09-13 amendment — #194 folder document persistence

Technical authority: Hassan approved the posted implementation plan at
https://github.com/zhssnym/dana/issues/194#issuecomment-5656128650.

**Amended 2026-09-20 by issue #218, on the technical ruling recorded there.**
Folder Sections now form at most three levels. A root Section is Heading 1, its
Section child Heading 2, and that child's Section child Heading 3. A Section's
level is its **depth in this relation and is not stored**; the ceiling is written
once, as `MAX_SECTION_DEPTH` in `app/src/shared/page-document.ts`, and a heading
level column would be a second source of truth for what the parent already
answers. `section_block_id` is direct parent identity on both blocks and Tasks.
A parent must be a Section in the same folder at depth one or two, and a Section
at depth four is refused before any write; ordinary content and Tasks may belong
to a Section at any of the three levels and are not themselves depth-limited.
Nothing about storage moved with this: 0017 already let a Section carry a
`section_block_id`, so the relation always expressed arbitrary depth and two
levels was one line of validation rather than a column. **Until #218's frontend
phase lands, the client still refuses to create or save a third level**, so a
three-level page arriving by API or workflow import renders and cannot yet be
edited.

The passage this amends read: at most two levels, a root Section Heading 1 and
its Section child Heading 2, a parent required to be a root Section, ordinary
content belonging to either level.
Shelf blocks cannot have parents. Heading names may be empty and are limited
to 120 projected characters. Existing row identities, placement and null root
membership are unchanged by migration 0017.

`rich_content` is nullable JSONB on paragraph and Section rows, with Dana
version 1 text runs carrying only `text`, optional `bold`, `italic`, and safe
`href`. Limits are 4000 projected characters (120 for headings), 4000 runs,
2048 characters per href and 64 KiB encoded content. The text projection must
match `text`. Null means legacy plain text. Unsupported fields/versions are
refused. Image file identity, dimensions, caption and width retain their
existing columns and authorization.

A complete outline contains contiguous subtrees, explicit root membership,
and stable block/Task identities. Removing a heading lifts its direct content
to its parent and promotes its child headings as needed. No document operation
can remove an existing live Task reference or overwrite Task fields. Completed
Tasks keep their place; Trash removes the reference until restoration. Creation
and prose conversion establish a client document-history checkpoint.

`page_document_receipts` has composite primary key `(actor_id, folder_id,
mutation_id)`, foreign keys to users and folders with ON DELETE CASCADE, payload
SHA-256, original committed revision, and JSONB created Task IDs. Receipts live
for the folder lifetime. Revisions hash block content and explicit mixed
placement plus live Task identity/membership/placement; Task status, title,
notes and other independent Task fields are excluded. Folder locks serialize
structural writes and coherent page reads. Identical retries acknowledge the
original commit and return the current authorized page, without repeating it.

Migration 0017_folder_document was taken unassigned with journal timestamp
1789200000000, after checking remote open PRs (none) and branches (origin/main
only). It names every new/changed constraint and makes no membership backfill.

#### 2026-09-20 amendment — #219 structured writing blocks

Technical authority: the ruling on issue #219, 2026-09-20.

A folder page's writing gains six Dana-native kinds — `bullet`, `numbered`,
`checklist`, `quote`, `callout` and `code` — **persisted as explicit kinds
rather than as stored editor document JSON**. BlockNote is the editor
implementation and is not Dana's storage format. No generic property bag is
added; the only additional state these kinds require is a checklist item's
`checked`.

**List nesting is a second parent relation and is not `section_block_id`
widened.** `section_block_id` continues to mean Work grouping — which Section a
block or Task belongs to. `list_parent_block_id` means writing structure —
which list item a list item is nested under. A nested list item inside a
Section carries both at once, neither is derived from the other, and neither is
inferred from visual proximity. Overloading one column to mean both would leave
a nested item's Section unreadable, which is the whole reason there are two.

Only `bullet`, `numbered` and `checklist` take part in list nesting, on either
end. A Task never carries a list parent, and a Section, paragraph, quote,
callout, code block or image is neither nested nor nested under. A list parent
is a block of the same document and **precedes every descendant in the
outline**, which is also the entire no-cycle rule: a relation whose every parent
appears earlier in one finite order cannot close a loop, so a two-item cycle and
a parent-after-child are the same refusal.

**A nested list item carries the same `section_block_id` as its list parent.**
This does not contradict the independence above: independence means either
relation stands without the other — a list at the page root belongs to no
Section, a Section requires no list. What is refused is the case where both
exist and *disagree*, because a bullet in Section A with a nested item in
Section B describes one list inside two Sections at once, which no client can
draw and no later fix can disambiguate.

`checked` is authored document content. A checklist item is not a Dana Task and
not a Task Step: ticking one completes no Task, assigns no work, creates no
Responsibility or Authority, and moves no Folder or Section progress. A
checklist item always records a tick, so an omitted value stores `false`; every
other kind stores none.

`rich_content` is admitted on `section`, `paragraph`, `bullet`, `numbered`,
`checklist`, `quote` and `callout`, under the existing version 1 run vocabulary
and limits. **`code` is plain code text and carries none.** `text` remains the
plain-text projection for every text-bearing kind and is what search reads. The
ceiling is 4000 projected characters for the six, 120 for headings as before. A
structured text block carries no `file_id`, no `ref_folder_id` and no
`width_pct`.

Migration `0021_structured_text_blocks`, journal timestamp 1789600000000, both
assigned before the work began with four branches open. It adds the two columns,
`page_blocks_list_parent_block_id_fkey` (ON DELETE SET NULL),
`page_blocks_list_parent_kind_check`, `page_blocks_checked_kind_check` and
`page_blocks_list_parent_block_id_idx`, and widens `page_blocks_kind_check`,
`page_blocks_text_length_check` and `page_blocks_rich_content_check` in place,
each keeping its name and column list. Every existing row passes by
construction; there is no backfill.

**Until #219's frontend phase lands, the client draws all six kinds as ordinary
paragraphs and expresses no nesting.** A page holding them opens and reads, and
the save path preserves the kinds, the ticks and the list parents it cannot yet
express rather than flattening them. That guard is the frontend phase's to
delete, and it must be: once the editor emits real kinds, the guard would start
undoing a genuine conversion.

##### 2026-09-20 correction — the paragraph above was false when it was written (#250)

**A correction of a sentence that was wrong about the code, not a change to
anything this section contracts.** Section 4 is frozen; no rule, column,
constraint or refusal above moves, and nothing here needed a ruling because
nothing here is a decision. What is recorded is that the claim was untrue of
the merged tree and is now true of it.

As merged, the guard could not fire. The client built the save baseline from
its own rendering rather than from the page the server sent, and that rendering
knows three kinds and no nesting, so the "kind this editor cannot express"
branch never had a stored kind to read: every save flattened all six to
`paragraph`, dropped every tick and wrote every `list_parent_block_id` null.
The paragraph above described the intent of a guard nothing reached.

Two things were needed for it to be true and both have landed. The baseline is
now the server's page reconciled with what the editor can draw of it, at mount
**and** re-derived from the response after every commit — a baseline right once
and stale afterwards loses the page on the second save instead of the first.
And restoring a kind now restores the rules that travel with it, `rich_content`
included: a restored `code` block is written with none, derived from
`RICH_TEXT_BLOCK_KINDS` rather than from a special case, because a restore that
kept the editor's text projection on it would be refused by
`page_blocks_rich_content_check` and by 7.16's own validation, turning silent
loss into a page that can never be saved again. AC-464, AC-465 and AC-466 pin
the three, driven through the client's own save path rather than through a
hand-built baseline, which is how the original went in green.

**What "preserves the list parents" means exactly, added the same day after a
review of the change above, and it is a limit rather than a promise (#250).**
A restored list parent is written into the outline the save sends, so 7.16
judges it, and 7.16 refuses three things about one: a parent that is not a list
item, a parent that does not precede the item nested under it, and a parent in
another Section. Two of the three were reachable from the editor — Move up on a
nested item puts the child above its parent, and retyping the parent as a
heading leaves the child naming a `section` — and restoring the parent in either
case produced a transaction the server answered 422 to, which latches the
client's writer and stops every later keystroke from reaching the server at all.
So the restore now drops the parent and promotes the child wherever any of the
three would be broken, exactly as the already-handled case of a deleted parent
does, and it reads the same `isListKind` the server does rather than a copy.
**That is a statement about the client's save path and about nothing in this
section**: the column, its foreign key, `page_blocks_list_parent_kind_check` and
7.16's refusals are all untouched, and a page's stored nesting is changed by
this only when the person's own gesture made that nesting unwritable. AC-580
pins it, and pins the other half — a nesting the server would accept is still
restored.

#### 2026-09-20 amendment — #220 files and media blocks

Technical authority: the ruling on issue #220,
https://github.com/zhssnym/dana/issues/220#issuecomment-5750490090, recorded before the
code as this section's freeze requires. Migration 0024 widens two of this table's CHECKs
in place and adds no column and no table.

**Three block kinds join `image`: `file`, `audio` and `video`.** A media block **names at most
one stored file by `file_id`, and copies none of that file's name, its MIME or its byte
size.** The reference is **required on `file`, `audio` and `video` and optional on `image`**,
which stands with a null `file_id` in two ways: before a picture has been chosen, every
picture in the composer beginning as an empty image block that the canvas saves; and after
7.19's reclaim has deleted a file that was chosen, `page_blocks_file_id_fkey` being
`ON DELETE SET NULL`. The second is why no write path may refuse a null `file_id` on a row
that already exists — the delete path produces that shape on every kind, and a write that
refused it would make a page permanently unsaveable the moment somebody deleted a picture.
The `files` row (4.16) stays the single authority on all three, for the reason the
2026-09-03 amendment there gives about a picture's dimensions: one file may be placed on
several pages, and a second copy of a fact is a second fact, free to disagree with the
first and written again at every placement. A reader draws the filename it shows by reading
the row, and a rename — if one ever exists — is one write rather than a sweep. A `file`,
`audio` or `video` block carries no `text` and no `rich_content` either: the name under the
player is the file's, and a caption is a paragraph next to it. An `image` block keeps the
caption it has always kept, which is authored text of its own and a copy of nothing.

**`page_blocks_width_pct_kind_check` admits `image` and `video`, and nothing else.** #220's
R1 extends the restrained centred width from a picture to a previewable video and stops
there: audio keeps its natural compact player width, so there is nothing for a person to
drag, and a generic file block does not resize in M1. Player state — position, volume,
speed — is not persisted at all and no column exists for it.

**Rationale for the width column, 2026-09-21, folded from RFC 0005 under the technical
ruling of that date** (https://github.com/zhssnym/dana/issues/280#issuecomment-5754491849,
issue #280). It changes no column, no constraint and no rule above; only the reasoning
moves.

*Why a percentage rather than a measurement.* A picture should keep its proportion of the
page at any window size, so what is stored is the share of the column the person dragged it
to. A stored width in pixels would mean something different on every screen that was not
the one it was dragged on, and the page would have to guess which.

*Why the bounds are in the CHECK.* 25 and 100 are the drag's own clamp, written where a
later client cannot edit them out: the database refuses a width no gesture in this product
can produce, so a stored value is always one somebody could have dragged to.

*Why the width began confined to one kind.* A constraint is cheaper to relax later than to
add to a column that already carries values nobody meant — a widening admits a strictly
larger set and needs no backfill, where a narrowing has to be validated against rows a
branch cannot see. #220's extension to `video` above is that relaxation arriving, which is
the shape this column was given in order to allow.

**The constraint that is deliberately absent, which is the part a later reader would
otherwise take for an oversight.** The obvious fifth widening is a CHECK confining `file_id`
to the media kinds, and **it is not here, and that is ruled correct rather than forgotten.**
Two halves, and both matter.

*Why not a CHECK.* 7.16's whole-page `PUT` and its `insert_block` action have always
accepted a `file_id` on a `section` or a `paragraph` block — nothing ever refused one — so a
production row may carry that shape today. A CHECK is **validated against every existing row
the moment it is added**; migrations here are forward only, run against production on merge,
and a failed one is recovered by a fix-forward migration or a restore. Writing a constraint
that refuses a shape live data may already hold, on evidence a branch cannot gather, is
exactly the wrong risk to take in a forward-only migration. The rule is stated instead where
it can be enforced without that risk: in the document contract's `put_block` schema and in
`applyDocument`'s pre-write validation, both of which refuse before the first write.

*And why a CHECK could not have carried the rule that actually matters anyway.* **It spans
two tables.** A `file` block must name a `files` row of kind `file`, an `audio` block an
`audio` row, a `video` block a `video` row; a CHECK sees one row of one table and can say
nothing about the kind of the file at the other end of the key. That pairing is the whole of
"insertion mode is preserved, not re-derived" — the same JPG is an Image block when it was
dropped as media and a File block when it was inserted through the File command, and the
server keeps the treatment that was declared and validated at upload rather than reading an
extension back off a filename, which is presentation and never security truth (4.16). It
fails closed in the direction that has consequences: a `file` row is untrusted bytes served
as an attachment and may never be dressed as previewable media. `image` additionally admits a
`cover` row, and only because that pairing was already reachable — a cover is a raster that
went through the same decode and re-encode, and folder duplication has produced `cover`
copies of page pictures since issue #128 — so refusing it would stop documents that save
today from saving. Nothing else gains a second home. AC-499 asserts every crossed pairing and
every matching one, so the rule is a rule rather than a ban.

**Both of this table's constraints are dropped and re-added under the same name over the same
columns**, as are 4.16's two. **AC-001's catalog does not move and cannot see this**; only a
behavioural case can, and AC-490 to AC-507 are those cases. Every existing row passes by
construction, each widening admitting a strictly larger set, so there is no backfill.

**The three kinds are writable only through `document_transaction`**, exactly as #219's six
are: 7.16's legacy write vocabulary is unchanged, and a read answers every stored kind. A
media block takes no part in list nesting on either end, `list_parent_block_id` being
confined to the three list kinds (#219), and it carries no `ref_folder_id` — a folder
reference is `folder_ref`'s whole job.

#### 2026-09-21 amendment — #210 the third home

Technical authority: Hassan's ruling of 2026-09-21,
https://github.com/zhssnym/dana/issues/210#issuecomment-5756722756, section 1. Product
authority: #210 (M1-F), the Folder facet framework.

**A blank facet's document reuses this table rather than getting a store of its own.** The
table gains:

| column | type | null | default | notes |
| - | - | - | - | - |
| facet_id | uuid | yes | none | FK folder_facets(id) ON DELETE CASCADE (`page_blocks_facet_id_fkey`); the blank facet this block belongs to (4.30) |

and a new index `page_blocks_facet_page_position_idx` on (`facet_id`, `page_position`, `id`)
WHERE `facet_id IS NOT NULL`, mirroring the folder one.

**`page_blocks_one_home_check` is dropped and re-added under the same name** over
`num_nonnulls(folder_id, shelf_id, facet_id) = 1`. It is a **strictly larger admitted set**:
every existing row has exactly one of the two old homes and a null `facet_id`, so every one
passes by construction and **there is no backfill**. The name and the constraint's job are
unchanged — exactly one home, never two and never none — and the catalog row in
`db/constraint-catalog.ts` moves only to gain the third column.

**`page_blocks_section_membership_check` is untouched and is already exactly right.** It
admits `section_block_id` only where `folder_id` is not null, so a facet document has no
Sections and nothing had to be written to make that true. 7.27 refuses a `section` block in a
facet document with 422 rather than letting the write reach this CHECK.

**`page_blocks_list_parent_kind_check` is untouched too, and unlike the one above that is a
limitation rather than a happy accident.** It also requires `folder_id IS NOT NULL`, so **a
facet document cannot hold a nested list item**. 7.27 refuses one with a 422 naming
`list_parent_block_id`, rather than answering 500 from the CHECK or dropping the nesting in
silence. Admitting nested lists in a facet document is a later change to this constraint and
to that refusal together, and is deliberately not made here.

**A facet block carries no `ref_folder_id` either**, which is 7.27's rule rather than this
table's: a facet is a view of one Folder and a reference out of it belongs on Main. The
column is nullable and the CHECK says nothing about it, so this one is the route's to hold.

`file_id` works exactly as it does on a folder page, and the scope is the facet's **Folder**:
a `files` row is folder-scoped (4.16) and a facet belongs to one Folder. Nothing about the
media rules, the width rule or the reclaim sweep changes — 7.19's `fileIsUnreferenced` asks
`page_blocks` without caring which home a block had, so **#210 creates no new foreign key
into `files(id)`** and the reclaim arms are untouched.
