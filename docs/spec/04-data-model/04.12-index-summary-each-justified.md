### 4.12 Index summary, each justified

| Index | Justifies |
| - | - |
| folder_members (user_id) | Q9 accessible-folder resolution on every request |
| tasks (folder_id, status, due_date) | Q2, Q3, Q5, Q7 home and view scans within accessible folders |
| tasks (assignee_id, status, due_date) | Q1 My Day automatic inclusion |
| tasks (series_id) WHERE series_id IS NOT NULL | INV-7 guards, successor lookup (section 8.5) |
| tasks (completed_at DESC, id DESC) WHERE status = 'completed' | Q6 Done keyset pagination |
| tasks GIN trigram on (title, notes) via pg_trgm | Q8 search |
| steps (task_id) | step loading for TaskDetail responses |
| my_day_entries (user_id) | Q1 pulled set |
| reminders (fire_at) WHERE state = 'scheduled' | Q11 scheduler poll |
| invites (email) WHERE status = 'pending' | Q12 at-login invite surfacing |
| invites (inviter_id) | sent-invites list |
| connections (user_b_id) | Q9 roster reverse lookup |

**Assumption: two queries run without an index of their own, and that is adequate for v1.**

Q4's Important page has no index on `tasks.important`, and Q3C's projection statement reads
a rule-carrying predicate for which this section names none. Both were justified against a
real Postgres 18 EXPLAIN rather than reasoned about, and both rest on scale rather than on
the plan: the rows are already bounded by the accessible-folder scope and by status, and the
response is capped at 1000. A partial index on either predicate would begin to pay only once
one account held tens of thousands of open starred rows or open series, and each would cost
a write on every star or every rule change.

Revisit when a real account's Important page or calendar reads slowly. The EXPLAIN records
are in `app/src/server/views/EXPLAIN.md`.
