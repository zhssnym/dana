### 4.12 Index summary, each justified

| Index | Justifies |
| - | - |
| folder_members (user_id) | Q9 accessible-folder resolution on every request |
| tasks (folder_id, status, due_date) | Q2, Q3, Q5, Q7 home and view scans within accessible folders |
| tasks (assignee_id, status, due_date) | Q1 My Day automatic inclusion |
| tasks (series_id) WHERE series_id IS NOT NULL | INV-7 guards, successor lookup (section 8.5) |
| tasks (completed_at DESC, id DESC) WHERE status = 'completed' | Q6 Done keyset pagination |
| tasks GIN trigram on (title, notes) via pg_trgm | Q8 search |
| steps (task_id) | step loading for TaskDetail responses |
| my_day_entries (user_id) | Q1 pulled set |
| reminders (fire_at) WHERE state = 'scheduled' | Q11 scheduler poll |
| invites (email) WHERE status = 'pending' | Q12 at-login invite surfacing |
| invites (inviter_id) | sent-invites list |
| connections (user_b_id) | Q9 roster reverse lookup |

Every index is named and defined in `app/db/migrations/`; this table records only why the
core ones exist.

**Assumption: two queries run without an index of their own.** Q4's Important page has no
index on `tasks.important`, and Q3C's projection reads a rule-carrying predicate with none.
Both rest on scale: the rows are already bounded by the accessible-folder scope and by
status, and the response is capped (10.3). A partial index on either predicate would pay
only once one account held very many open starred rows or open series, and each would cost
a write on every star or rule change. Revisit when a real account's Important page or
calendar reads slowly. `app/src/server/views/explain.ts` generates the query plans: run
`npx tsx src/server/views/explain.ts` from `app/`. It seeds in-memory PGlite, or the
database `TEST_DATABASE_URL` names when that is set.
