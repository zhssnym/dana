### 4.4 folder_members

Columns and constraints: `app/db/migrations/0000_core_schema.sql`, `0022_labels.sql`
(`shelf_name`), `0023_folder_access.sql` (`access`), `0025_responsibility_document.sql`
(`can_edit_own_responsibilities`) and `0026_contract_membership_label.sql`.

- **A row lives on a project root only (step 8, `0062_members_on_projects.sql`).** People
  belong to the project: a member of the root is a member of every page of the project
  (tabs and sub-pages), with the root's preset, and access is decided there
  (`visibleFolder`, `joinVisibleFolder`, `resolveScoped` join `folders.project_id`). A
  trigger refuses a row on any other page. 0062 made a page whose people differed from its
  project's a project of its own, so nobody's set of visible pages changed.
- **PK (folder_id, user_id) is INV-10.** The index on `user_id` is the accessible-folders
  lookup joined by every page query (Q9).
- **`role` is reserved** and admits only `'member'`; it never encodes ownership, which is
  `folders.owner_id` alone (4.3).
- **`access` is the member's one durable Access preset** (7.4).
- **`shelf_name` and `color` are per-member personal grouping**, which is why they live
  here rather than on folders: one member's shelf never changes what another sees.
  `shelf_name` is the viewer's own Shelf membership under the name 4.18 uses, and 4.18
  holds it in step with `shelves.name`. It never means classification; that is 4.24's
  Label.
- **`created_at` is the join instant** and drives ownership transfer order (8.9).
- **`can_edit_own_responsibilities` is a narrow grant, deliberately not an Access
  preset.** A preset is a point on a ladder and everything above it comes with it; this
  admits exactly one action, editing the member's own Responsibility (4.28), only when the
  actor is that member, and widens nothing else (`app/src/shared/folder-actions.ts`). It is
  a fact about one membership: it ends with the membership, and a rejoin starts from
  `false`, as does every path that inserts a row. Granting and revoking are recorded in
  4.29 with the administrator as actor.

A column rename here is expand-and-contract across releases, never one `RENAME COLUMN`:
during a deploy the old instance still serves while the new one passes health checks, and
every folder read it makes would select a column that no longer exists.
