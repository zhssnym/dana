### 4.22 user_page_descriptions

*Amendment to frozen section 4, written for issue #68 (from #21), which is a
sanctioned handoff from the design side: 9.4 has named an "editable
description" on the shared page head since RFC 0005 and there was no column
anywhere to store one, so the page drew a fixed sentence and the client hid
the control rather than accept words it would lose. Migration
`0008_place_descriptions.sql`; its four constraints are named in AC-001's
catalog. The freeze's rule is that section 4 moves only on a human decision,
and this one is the owner's, recorded on the issue.*

| Column | Type | Null | Default | Constraint |
| - | - | - | - | - |
| user_id | uuid | no | none | FK users(id) ON DELETE CASCADE |
| place | text | no | none | CHECK (place IN ('today','scheduled','assignments','important','all','done','abandoned','anytime')) |
| description | text | no | none | CHECK (char_length(description) BETWEEN 1 AND 500) |
| updated_at | timestamptz | no | now() | none |

PK (user_id, place). One person's own sentence under one of Dana's place
pages, private to them as 4.20's cover on the same page is. The place set is
4.20's, which is 4.19's native-view vocabulary minus `desk`: Desk is a folder
and carries 4.3's own `description` column, so its default is written at
provisioning (7.1) and rewritten through 7.4 like any other folder's.

**A row exists exactly when there are words.** `description` is NOT NULL and
at least one character, so clearing is the row's deletion and there is one
spelling of absence rather than two; the 500 is 4.3's and 4.18's limit
restated, not a new one.

**Why this is not a column on 4.20.** That table's one-source CHECK,
`(file_id IS NULL) <> (preset IS NULL)`, admits no row without a cover, so a
description with no cover would have nowhere to sit; and its file foreign key
cascades deliberately, so deleting a picture deletes the cover row, which
with a passenger column would mean deleting a photograph silently destroyed
the sentence a person wrote. Both of that table's rules are load-bearing and
neither survives the merge, so the second table is the cheaper of the two.

No index: the primary key serves the only read this table has, which is one
viewer's descriptions (4.12's rule, that an index needs a named consumer in
section 6).
