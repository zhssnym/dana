### 4.19 user_views

A saved view: a filter state given a name and a pin (DES-153's second half).
Serialized by ids, never display names.

| column | type | null | default | notes |
| - | - | - | - | - |
| id | uuid | no | generated | PK |
| user_id | uuid | no | none | FK users(id) ON DELETE CASCADE |
| name | text | no | none | length 1 to 40 |
| definition | jsonb | no | none | the filter model; zod-validated at write; ids only |
| pinned | boolean | no | false | none |
| created_at | timestamptz | no | now() | none |

`user_settings` gains (all with defaults, expand-only): row density, clock
(12/24), theme (system/light/dark), task-open surface, pinned native views
(migrating show_important/show_all/show_done in one migration — two records
of one fact are not kept), sidebar order, per-shelf/folder arrangement keys.

**Amendment, 2026-09-03, issue #30 (migration 0010): the task-open surface
defaults to `dialog`.** The column admits `dialog`, `panel` and `tab` and was
built at S12 with `DEFAULT 'panel'`, chosen when nothing consumed it. Imran's
ruling, which 9.3 has carried since, is that a task opens as a dialog and that
choosing the sidebar makes the sidebar the default until the dialog is chosen
again, so the stored default was simply wrong. Every surface that draws the
value already worked around it: `screens/settings-screen.tsx` reads
`task_open ?? "dialog"`, `lib/task-surface-preference.ts` answers `dialog`
before anybody has chosen, and AC-261's own afterEach restores `'dialog'` as
"what a fresh account carries". This is an addition to a frozen section under
the same rule 4.16's is: it corrects the record to the decision that had
already been made, and it changes no column, type, null or constraint.

**The migration moves the stored rows with the default, and that is the load-
bearing half.** Reading this column as the record was tried at S23 and turned
42 of 228 browser cases red, because every account provisioned before 2026-09-03
carried `panel` while the acceptance harness addresses the task surface as
`getByRole('dialog')`. That measurement is about the rows rather than about the
design, so `0010` moves the rows: `UPDATE user_settings SET task_open =
'dialog' WHERE task_open = 'panel'`. It cannot tell a deliberate `panel`, which
9.7's control has been able to write only since S27, from the S12 default it
was seeded with, so a person who chose Panel chooses it once more; `tab` is
untouched, being a value this build already honours as the record.

**The column becoming the record is the ruling, and the client half of it is
not built.** Today the record is split by value: `components/task-surface-host.tsx`
reads `task_open` from the account for `tab`, while `dialog` against `panel`
comes from `localStorage`, so one of a person's three possible choices follows
them between devices and two do not. 9.3's sentence — "Where a task opens
(dialog, panel, or tab) is a client-side preference" — is what produced that
split and is the sentence to amend when the client half lands; the pattern it
should take is the theme's, RFC 0005 change control items 43 and 52, where the
column is the record and the browser holds a mirror of it so the value can be
read synchronously before the bundle arrives. Until then the behaviour a person
sees is unchanged, which is why this migration is safe to ship on its own.
