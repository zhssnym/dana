### 4.16 files

One row per stored object: an image on a page, a comment's attachment or
voice note, a cover upload, an avatar. Bytes live in the object store
(section 11); this table is the authority on existence, ownership and quota.

| column | type | null | default | notes |
| - | - | - | - | - |
| id | uuid | no | generated | PK; also the object-store key |
| owner_id | uuid | no | none | FK users(id) ON DELETE RESTRICT; whose quota it spends |
| folder_id | uuid | yes | none | FK folders(id) ON DELETE CASCADE; visibility scope; null for an avatar, a cover or a page image, CHECK (folder_id IS NOT NULL OR kind IN ('avatar','cover','image')) |
| kind | text | no | none | CHECK (kind IN ('image','file','voice','cover','avatar')) |
| name | text | no | none | length 1 to 300 |
| mime | text | no | none | server-validated against the kind |
| bytes | integer | no | none | CHECK (bytes > 0); quota arithmetic |
| duration_ms | integer | yes | none | voice only |
| created_at | timestamptz | no | now() | none |
| width | integer | yes | none | CHECK (width IS NULL) = (height IS NULL) AND (width IS NULL OR (width > 0 AND height > 0)); CHECK (width IS NULL OR kind IN ('image','cover','avatar')); pixels of the **stored** object, after the 7.15 rotate and downscale |
| height | integer | yes | none | as width, and the same two CHECKs name both |

Per-user quota: 1 GB (D5, revisited with usage). Serving passes 10.2 like
every read; there are no public object URLs.

**Amendment, 2026-09-03, issue #27 (migration 0009). The two columns above are
an addition to a frozen section, made because the fault they close is a
correctness fault rather than a feature**, which is the ruling the issue
records; it was filed as item 13.47 when section 13 was retired. What was
wrong: a page jumped by the height of every image as it loaded, and could not
stop, because nothing Dana stored said how tall a picture was. This is the
kind of thing that looks like a client problem and half is: whoever uploads
the file holds it in the browser and knows its shape the moment it is chosen,
so an author sees the space reserved correctly on that one visit and every
other reader of the page — and the author on their next load — gets the jump
anyway. Nothing on the wire could tell them.

**They belong to the file and not to the block.** One image can be placed on
several pages, and its shape is a fact about the bytes; a ratio held per
block would be written again at every placement and the copies would be free
to disagree. So no write shape carries them: 7.16's `PageBlockWrite` has
`width_pct`, which is a decision a person made about one block, and not these,
which are a measurement.

**They cost nothing to record.** 7.15 already passes every image through
sharp — that pass is the security re-encode of AC-231 and the 2048px
downscale — and the numbers are read off that pass's own report of the buffer
it produced. They therefore describe the object the store holds rather than
the payload that arrived: rotation applied, downscale applied.

**Null means unknown, and every consumer must treat it as today's behaviour.**
Two rows have it: anything stored before this migration, and any kind that
never passes through the re-encode. **No backfill has been run.** The bytes
are on disk and re-reading them to fill these columns is possible, but it is a
production data operation and the owner's call, and it is entangled with issue
#80's suspicion that production may not have a durable disk at all. Until one
is run, a page with an image stored before 2026-09-03 must draw exactly what
it drew before these columns existed.

**Amendment, 2026-09-03, issues #20 and #100 (migration 0012). A picture may belong to a
person instead of to a folder, and the row above says so.** Imran ruled it on #20 —
"Folders, shelves, and built-in pages like Today should all have the same cover options:
gradients, uploads, links, and stock photos. Pictures should belong to the user instead of
only a folder" — and the owner directed the work, which is what this section's freeze asks
of a change to it: a human decision, recorded, and folded as text.

**The sentence "null for avatars" was a description of what the server did, not of what
this table allowed, and #20's account of the same thing is wrong in the other direction.**
The column has been nullable since migration 0003 and nothing in the schema ever forbade a
folder-less row; what forbade one were two lines of TypeScript, `domain/files.ts` refusing a
null folder for every kind but avatar and `routes/files.ts` declaring `folder_id` as a
required uuid. #20 reads the restriction as the schema's and proposes a data-model change to
lift it; the truth is the reverse, and this amendment therefore *adds* a constraint rather
than removing one. `files_folderless_kind_check` writes down the rule the server is now
enforcing differently, so it is enforced rather than remembered: **a row outside a folder is
an avatar or a cover and nothing else.** Every row stored before it passes, today's only
folder-less rows being avatars.

**Which kinds, and why those two.** A page image, a comment's attachment and a voice note
all hang on something that lives in a folder and take that folder's visibility; an avatar
and a cover are a fact about a person. And a cover may still name a folder, which is not a
concession: a folder's cover is one look for every member (4.3, D1), so it has to be
folder-scoped or the members could not read it. The rule is **a cover file's scope matches
its page's scope**, chosen by the caller sending a `folder_id` or not.

**Who may read a folder-less file, which is the load-bearing half and had no definition
before.** Serving (7.15) answers: a folder-scoped file is its members'; an **avatar** is
readable by any signed-in account, because a member list renders other people's pictures;
**every other folder-less file is its owner's alone**, a folder in common with the owner
buying nothing. Before this change the predicate was a single clause — folder-less means
everyone — which was harmless while avatars were the only folder-less rows and fails open
the moment they are not: measured on the wire, a second account's `GET /api/v1/files/:id`
against a folder-less `cover` row answered 200. The narrowing preserves the avatar arm
exactly. AC-370, AC-371 and AC-372 assert it; the quota (10.3) is untouched, summing `bytes`
by `owner_id` with no mention of the folder.

**Amendment, 2026-09-04, issue #116 (migration 0014). One nullable column,
`unreferenced_since timestamptz`, and it is an addition to a frozen section on
the ruling this table's 2026-09-03 amendment already records: a correctness
fault rather than a feature.** Imran ruled on #116 that "covers stay stable for
the user; genuinely unused cover files can be reclaimed safely"; the owner
directed the mechanism and this column is the half of it the schema has to
hold.

| column | type | null | default | notes |
| - | - | - | - | - |
| unreferenced_since | timestamptz | yes | none | when the last reference to this row went, written and cleared by the 11.7 tick; null means referenced, or not yet looked at |

7.19 carries the rule. **What this column exists for is that nothing else in
Dana records when a reference was dropped**, and the reclaim needs exactly that
fact: a cover is destroyed thirty days after it stopped being worn, and a cover
worn again inside the window is kept. The first implementation aged from
`created_at` and was wrong in the direction that loses data — that measures
when the bytes arrived, so a picture uploaded months ago and worn until this
morning was unreferenced *and* old the instant it was replaced, and the next
tick took it with no window at all, which is the one case the window exists
for.

**It is not a reference count and must not become one.** "Referenced" stays a
query over the five foreign keys that name `files(id)`, so there is no second
record of a fact the keys already hold; this column records the *time* an
answer of "no" first held, and the tick re-asks the question every minute,
clearing the mark when the answer changes back.

**No backfill, and none is possible**, because the fact was never recorded.
Every existing row is null, so the first pass after 0014 deploys marks today's
orphans and reclaims nothing, and the oldest of them wait one window from the
mark. That is the safe direction and is the reason no backfill is wanted rather
than merely not run. The partial index `files_unreferenced_since_idx` covers
the marked rows, which are the only ones the delete reads; both it and the
column are in AC-001's catalog.

**Amendment, 2026-09-04, issue #167 (migration 0015). `image` joins the kinds that may stand
outside a folder, and the row above says so.** The 2026-09-03 amendment answered "which
kinds, and why those two" with the sentence a picture's scope matches its page's, and then
listed `image` among the kinds that "hang on something that lives in a folder". Both halves
cannot be true of a shelf page. A shelf is private (4.18) and is not a folder, 4.17 gives a
block exactly one home, and a shelf page's home is the shelf — so an image block there hangs
on nothing that lives in a folder, and the rule that a picture's scope matches its page's
gives it the same folder-less life the cover of that page already had. The owner ruled it on
#167; the fix is the server's and this constraint's, and nothing else in this table moves.

**Who may read one is already written and needed no change**, which is the load-bearing half
again and this time it was load-bearing by not moving. Serving (7.15) answers: a folder-scoped
file is its members'; an **avatar** is readable by any signed-in account; every other
folder-less file is its owner's alone. That last clause is `kind`-blind — it asks who owns the
row, not what kind it is — so a folder-less `image` is its uploader's alone from the moment
one can exist, on the same clause that already held a folder-less `cover`. A predicate that
had instead named `cover` would have failed open here, which is what the 2026-09-03 amendment
records happening once already. **What is narrower than the serving rule is which block may
name one**: a folder page's page-block gate requires the file to be *of that folder* (7.16 as
annotated for issue #107), so one of these can be named only by a block on a shelf page, whose
gate is the serving predicate itself.

**Every existing row passes** — the widening admits rows rather than refusing them — and the
constraint keeps its name and its columns, so AC-001's catalog is unchanged and cannot see
this. AC-413 is the behavioural case that can.

**And it gains a lifetime with the rest**: 7.19's reclaim takes a folder-less `image` that no
column names, thirty days after its `unreferenced_since` mark, exactly as it takes a
folder-less `cover`. A picture dropped from a shelf page would otherwise spend its owner's
gigabyte (10.3) with no route anywhere able to remove it, which is the state #116 was filed
about.
