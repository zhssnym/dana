### 4.18 shelves

A person's shelf: the per-user container whose *membership* remains
`folder_members.label` (unchanged, frozen) and whose page needs a stable key
that a rename cannot move. The API holds label and shelf name in step in one
transaction; the id never changes.

| column | type | null | default | notes |
| - | - | - | - | - |
| id | uuid | no | generated | PK |
| user_id | uuid | no | none | FK users(id) ON DELETE CASCADE |
| name | text | no | none | length 1 to 40; UNIQUE (user_id, name) |
| icon | text | yes | none | server-known key set |
| color | text | yes | none | #RRGGBB |
| cover_file_id | uuid | yes | none | FK files(id) ON DELETE SET NULL |
| cover_preset | text | yes | none | CHECK matches '^[a-z0-9-]{1,40}$'; CHECK (cover_file_id IS NULL OR cover_preset IS NULL), one source at most |
| cover_focal_y | integer | no | 50 | CHECK 0 to 100 |
| description | text | yes | none | length up to 500 |
| created_at | timestamptz | no | now() | none |

Shelves are private by construction (DES-195/196): no member rows, no share.

**In step in all three directions, and the third was added on 2026-09-03
(issue #65).** A rename rewrites the viewer's matching labels and a delete
clears them; and a label written through 7.4 now names a shelf, made in the
same transaction if there is not one already. Until then that direction was
open, and nothing had ever filled this table from the labels that predate it,
so an account whose folder groups were made before 7.16 shipped carried
headings with no shelf behind them: no id, and therefore no `/app/shelves/:id`
to link to and no page to open, which is 9.1's roles table ("each folder and
shelf row: Links") and 9.10's page both unsatisfiable for those rows.
Migration 0011 repairs the labels already stored; the 7.4 write is what keeps
the state unreachable. **Clearing a label leaves the shelf standing**, on 9.1's
own model that a shelf outlives its folders: the shelf is the thing and the
label is its membership.

**Annotation, 2026-09-03, issues #20 and #100 (migration 0012). The two cover rows above are
4.3's, transcribed one object over, and until this date a shelf was the only page kind that
could wear nothing at all.** Imran ruled on #20 that folders, shelves and the built-in pages
get the same cover options; the owner directed the work. `cover_file_id` has been in this
table since migration 0003 and **no route had ever written it** (#100), while the client had
been sending it to 7.16's PATCH since S27 — accepted, discarded, answered 200, because
nothing in `app/src/shared/` is `.strict()`. And with no `cover_preset` column a shelf could
not wear a gradient either.

The one-source rule is 4.3's rather than 4.20's, in admitting no cover at all: a shelf may
wear nothing, and `shelves_cover_file_id_fkey`'s SET NULL produces exactly that state when
the picture is deleted, so a rule demanding one source would refuse a row the schema itself
creates. A shelf being private by construction, its cover is normally a file of the person's
own with no folder (4.16 as amended); a file from a folder they are a member of is admitted
too, which keeps the rule identical to 7.19's for a place page. The three CHECKs are named in
AC-001's catalog. AC-368, AC-369 and AC-372 are the behaviour written down and none of them
is a proof any more: all three lost their test files in the 2026-09-20 cut, the last of them the
one that went at the database directly — which mattered, because AC-001 can see a
constraint's name and never what its expression does.
