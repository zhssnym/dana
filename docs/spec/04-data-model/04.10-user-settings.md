### 4.10 user_settings

| Column | Type | Null | Default | Constraint |
| - | - | - | - | - |
| user_id | uuid | no | none | PK and FK users(id) ON DELETE CASCADE |
| show_important | boolean | no | true | none |
| show_all | boolean | no | true | none |
| show_done | boolean | no | false | Done ships hidden |
| updated_at | timestamptz | no | now() | none |

My Day, Tasks, and Planned have no toggles: they cannot be hidden. Session storage is
stack-dependent and out of the core model; its requirements live in section 10.1.

**Annotation, S29 fold, 2026-08-27. The sentence above is v1's page-visibility model and
v2 does not use it, though every column in the table is untouched and still written.** RFC
0005 replaced three fixed flags with a pin list: which places appear in the sidebar is
9.7's pin list, stored as `pinned_views` on 4.19, and Done, Abandoned and Anytime ship
unpinned. These three columns stay stored, frozen 7.2's `/me/settings` keeps them
untouched, and the pins **derive** from them until the person first writes pins, after
which the new column is the record for the v2 surface. That derivation is RFC 0005 change
control item 6, which took it precisely so that two records of one fact are never both
authoritative for one reader. So: the three columns are not dead and are not the answer to
"can this page be hidden"; 4.19 is. Section 4 is frozen and this is an annotation rather
than an edit.

**Annotation, 2026-09-04, issues #140 and #142, migration 0013. The table
gains `calendar_zoom`: text, NOT NULL, DEFAULT `'month'`, constrained by
`user_settings_calendar_zoom_check CHECK (calendar_zoom IN ('day', 'week',
'month'))`.** Imran ruled on #140 that the calendar's zoom is a durable
account preference and not browser state: "If a person changes the calendar
from Month to Week (or another supported zoom), Dana should remember that
choice instead of resetting it on the next visit. Ideally it should follow the
account across devices, consistent with other durable preferences such as
density, clock format, and task-open surface." He ruled the alternative out by
name in the same breath — "Do not solve this as browser-only state if that
would create another split record" — which is the split the annotation on 4.19
is still working out of the build for `task_open`.

The three values are 9.5's own ("day, week, month zooms") and are the client's
own keys, so nothing maps between the column and the calendar. Year zoom was
cut for v1 by Q3C and the CHECK does not admit it. The default is what a fresh
account has always seen, `PlannedCalendar.tsx` opening at
`useState<Zoom>('month')`; 0010's lesson one column over is that a default
chosen while nothing consumed the column is a behaviour change waiting for the
day something does.

It rides the v2 settings bundle beside the six columns 4.19 lists, rather than
frozen 7.2's `/me/settings`, which keeps its three booleans untouched. Section
4 is frozen and this is an annotation rather than an edit, under the same rule
as the S29 one above: the column is additive, changes no existing column's
type, null or constraint, and records a human ruling rather than a design
choice made here. AC-378 to AC-380 state it — as decisions rather than as proofs, all
three having lost their test files in the 2026-09-20 cut.

**Pointer, 2026-09-04, issue #113: the two annotations above say frozen 7.2's `/me/settings`
keeps these three booleans untouched, and that endpoint is now retired — the columns are
still untouched, but by nothing at all.** Nothing writes `show_important`, `show_all` or
`show_done` any more; they stay stored and are still what `GET /settings` derives
`pinned_views` from while that column is null (7.23), and frozen 7.1's `GET /me` still reads
them. Dropping them is a later contract migration once nothing reads them, and no column,
type, null, default or constraint moves with this note.
