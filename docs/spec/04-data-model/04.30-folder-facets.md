### 4.30 folder_facets

One row is one **facet** of one Folder: a way into it. There are four natives —
Main, Purpose, Consultation and Results, exactly one of each — and the custom
ones a member adds: a **Work** facet, which is a live view of one H1 section of
Main and stores no document of its own; a **shared blank** facet, which has its
own document and is shared by Folder Access; and a **private blank** facet,
which has its own document and is visible only to the person who made it.
Purpose also carries a document of its own. Facet documents live in
`page_blocks` under `facet_id` (4.17); there is no per-facet table. A facet
document is Task-free and Section-free: the facet API refuses `create_task`,
semantic `section` and `folder_ref`.

Columns, constraints and indexes: `app/db/migrations/0027_folder_facets.sql`.
`updated_at` is 7.0's stale-write token; `deleted_at` is Trash, purged by the
11.7 pass at thirty days, as 4.3's is. `position` uses the same fractional-key
domain and regex as `page_blocks.page_position` under `COLLATE "C"`, so the
database's order and the server's are one order on every engine (4.5 explains
why the key is a string).

**Natives are created with the Folder and never lazily**, in the same
transaction as `POST /folders`' owner membership (7.4), and exist for every
Folder, trashed ones included, so they are waiting when a Folder is restored.
Lazy creation would make a `GET` write, race two members on the unique index,
and let a Can-view read answer differently from a Can-edit one.

**The two uniqueness rules are partial in different ways, deliberately.** One
native of each kind per Folder, partial on `kind` and **not** on `deleted_at`:
a native is hidden, never deleted, and a `deleted_at` predicate would admit a
second Main. One live Work facet per H1 block, partial on `deleted_at IS NULL`:
a trashed Work facet must not stop a new one over the same heading, so the
collision is raised on restore.

**No facet's name is a column read straight out.** Main's and Consultation's are
fixed; `display_name` NULL on Purpose and Results is the default name, and Reset
is a write of NULL; the blanks require one; **a Work facet's name is its H1
block's `text` at read time**, so renaming the heading renames the facet.

**The CHECKs pairing a nullable column with `kind` are spelled so no
possibly-null value is compared** (`IS NULL` biconditionals and a `CASE kind`
whose every branch yields a real boolean), for the UNKNOWN hazard 4.24 records.

**Both `users` keys are RESTRICT, not CASCADE**, for 4.28's reason: 8.10 scrubs
rather than deletes a `users` row, so a CASCADE would delete nothing while
looking like cleanup. `created_by` is provenance and never authority.

**`h1_block_id` is CASCADE: deleting the heading destroys its Work facet.**
7.16's `delete_block` is permanent, so a Work facet trashed that way could never
be restored, and an unrestorable Trash row is worse than none. Deleting a Work
facet through its own route is ordinary Trash: it stamps `deleted_at` and touches
no block, Task or Section.

**A private facet does not outlive its owner's membership.** When a membership
ends by any path — removal, leaving, or R-CLEAN at account deletion (8.10) — the
person's private facets in that folder and their `page_blocks` are permanently
deleted in the same transaction, not trashed: a trashed one would be a row nobody
may read, remove or restore. The sweep is a statement, not an `ON DELETE`
clause, since no clause on a `users` key ever fires. **Shared facets are Folder
data and are untouched**, as R-CLEAN unassigns a leaver's Tasks rather than
deleting them (5.3).

**A Work facet stores no name and no document.** Everything it shows is its H1's
blocks and Main's Tasks; it has no page of its own (7.27), and **no column on
`tasks` names a facet**, so a facet can never become another Task database.
