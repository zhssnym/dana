### 4.30 folder_facets

**Added 2026-09-21 by issue #210 (M1-F), on Hassan's technical ruling**
https://github.com/zhssnym/dana/issues/210#issuecomment-5756722756 **(section 1).**
Product authority: #210 as written, plus the Frontend → Backend Handoff of the same day.
Authorization authority: accepted #209 R8A through #228's table.

One row is one **facet** of one Folder: a way into it. There are four natives — Main,
Purpose, Consultation and Results, exactly one of each — and the custom ones a member
adds: a **Work** facet, which is a live view of one H1 section of Main and stores no
document of its own; a **shared blank** facet, which has its own document and is shared by
Folder Access; and a **private blank** facet, which has its own document and is visible
only to the person who made it.

| Column | Type | Null | Default | Constraint |
| - | - | - | - | - |
| id | uuid | no | generated | PK `folder_facets_pkey` |
| folder_id | uuid | no | none | FK folders(id) ON DELETE CASCADE (`folder_facets_folder_id_fkey`) |
| kind | text | no | none | CHECK `folder_facets_kind_check` IN (`main`, `purpose`, `consultation`, `results`, `work`, `shared_blank`, `private_blank`) |
| owner_id | uuid | yes | none | FK users(id) ON DELETE RESTRICT (`folder_facets_owner_id_fkey`); CHECK `folder_facets_owner_kind_check` `((owner_id IS NOT NULL) = (kind = 'private_blank'))` |
| display_name | text | yes | none | CHECK `folder_facets_display_name_kind_check`: NULL on `main`, `consultation` and `work`, NOT NULL on the two blanks, either on `purpose` and `results`; CHECK `folder_facets_display_name_length_check` 1–120 |
| hidden | boolean | no | false | CHECK `folder_facets_hidden_kind_check` `(NOT hidden OR kind IN ('purpose','consultation','results'))` |
| position | text COLLATE "C" | no | none | CHECK `folder_facets_position_format_check` `~ '^[0-9A-Za-z]{2,255}$'` |
| h1_block_id | uuid | yes | none | FK page_blocks(id) ON DELETE **CASCADE** (`folder_facets_h1_block_id_fkey`); CHECK `folder_facets_h1_kind_check` `((h1_block_id IS NOT NULL) = (kind = 'work'))` |
| created_by | uuid | no | none | FK users(id) ON DELETE RESTRICT (`folder_facets_created_by_fkey`) |
| created_at | timestamptz | no | now() | none |
| updated_at | timestamptz | no | now() | none; 7.0's stale-write token, 4.17's rule |
| deleted_at | timestamptz | yes | none | none; Trash, purged by the 11.7 pass at thirty days, 4.3's column and rule verbatim |

Index `folder_facets_folder_id_position_idx` on (`folder_id`, `position`, `id`) WHERE
`deleted_at IS NULL`. Unique index `folder_facets_folder_native_kind_idx` on (`folder_id`,
`kind`) WHERE `kind IN ('main','purpose','consultation','results')`. Unique index
`folder_facets_h1_block_id_idx` on (`h1_block_id`) WHERE `h1_block_id IS NOT NULL AND
deleted_at IS NULL`. Index `folder_facets_owner_id_idx` on (`owner_id`) WHERE `owner_id IS
NOT NULL`.

**Natives are created with the Folder and never lazily**, in the same transaction as
`POST /folders`' owner membership (7.4), and migration 0027 backfilled the four for every
Folder that already existed — **trashed ones included**, a trashed Folder being one that may
still be restored and whose facets must be waiting when it is. Lazy creation means a `GET`
writes, two members race the unique index above, and a Can-view member's read either creates
rows or answers differently from a Can-edit member's. #210's "stable internal identity" is a
fact of the Folder rather than of whoever looked first.

**The two uniqueness rules are partial in different ways and the difference is the design.**
The native one is partial on `kind` and deliberately **not** on `deleted_at`: a native facet
is hidden rather than deleted, so there is no live-versus-trashed distinction to make, and a
partial predicate would admit a second Main the moment somebody wrote a `deleted_at` onto the
first. The H1 one is partial on `deleted_at IS NULL` for 4.28's leave-and-rejoin reason: a
trashed Work facet must not stop somebody making a new one over the same heading, so the
collision is raised on restore rather than pre-empted.

**`display_name` NULL on Purpose and Results is the default name rather than an absence, and
Reset is a write of NULL.** That is why a rename route may write null on those two and is
refused it on a blank facet, whose name is required, and on Main, Consultation and Work,
whose names are not stored at all. **No facet's name is a column that can be read straight
out.** Main's and Consultation's are fixed; Purpose's and Results' are the override or the
default; a **Work facet's is its H1 block's `text` at read time**, so renaming the heading
renames the facet and nothing can disagree with it.

**Both `users` keys are RESTRICT rather than CASCADE, on 4.28's precedent and for its
reason.** 8.10 scrubs a `users` row and never deletes it, so no `ON DELETE` clause on a
`users` key fires at all; a CASCADE here would delete nothing while *looking* like the
cleanup. RESTRICT makes a future hard delete fail loudly instead. `created_by` is provenance
and never authority (#228's authorship rule): nothing reads it to decide anything.

**`h1_block_id` is CASCADE, and that is the one place this contract reads past #210's
words.** #210 says an H1's deletion sends its Work facet to Trash. 7.16's `delete_block` is
permanent, so a Work facet trashed that way could never be restored, and an unrestorable
Trash row is worse than none; the row is therefore destroyed with its heading. Deleting a
Work facet through its own route is the other direction and is ordinary Trash: it stamps
`deleted_at` and touches no block, no Task and no Section. The ruling marks this **(proposed)**
and Imran may overrule it without moving the rest.

#### 2026-09-21 amendment — Ruling 6, a private facet does not outlive its membership

Technical authority: the addendum ruling of 2026-09-21, https://github.com/zhssnym/dana/issues/210#issuecomment-5757696835, taken after the
adversarial review of `backend/210-folder-facets` found the orphan it closes.

**When a membership ends by any path — removal, leaving, or R-CLEAN at account deletion —
the departing person's private facets in that folder, and their `page_blocks`, are
permanently deleted in the same transaction.** Not trashed: `deleted` is the word, and the
reason is what a trashed row here would be. Its owner is no longer a member, so it is
absent from their Trash and from every listing; every other member is refused it by
`facet.read`, which admits no preset at all; and neither can restore it, both routes
needing a membership that has ended. That is a row nobody may read, nobody may remove and
nobody may restore, with a thirty-day clock on it instead of none.

**Shared facets are Folder data and are untouched by a membership ending**, exactly as
5.3's R-CLEAN unassigns a leaver's Tasks rather than deleting them.

`owner_id` stays `ON DELETE RESTRICT` and the sweep is a statement rather than a clause,
which is the same shape 4.28 keeps and for the same reason: 8.10 scrubs the `users` row
rather than deleting it, so no `ON DELETE` clause on a `users` key ever fires, and a table
that keyed its cleanup to one is not cleaned up at all. 8.10 carries the step and
`guard-account-deletion-sweep` now enumerates every `RESTRICT` key on `users(id)` — saying
of each whether its rows are swept or deliberately outlive — so the next one cannot be
silent. AC-846 pins all three paths.

**A Work facet stores a name for nothing and a document for nothing.** Everything it shows is
its H1's blocks and Main's Tasks. It has no page of its own (7.27) and **no column on `tasks`
names a facet** — that absence is #210's "not another Task database" written where it cannot
be edited out.

**Four of the seven CHECKs pair a nullable column with `kind`, and every one is written so
that no possibly-null value is compared until both sides are known.** A CHECK fails only on
FALSE and passes UNKNOWN, so the obvious spelling of a both-or-neither rule admits exactly the
row it was written to refuse; `IS NULL` and `IS NOT NULL` always yield a real boolean, and the
display-name rule is a `CASE kind WHEN … END` whose every branch does. AC-001 asserts
constraints by name and by which columns they mention and can see none of that, so the
behavioural cases that try the bad rows are AC-831, AC-833 and AC-835.

`position` carries **literally the same fractional-key domain and the same regex** as
`page_blocks.page_position` (4.17): base-62 digits under `COLLATE "C"`, so the order the
database sorts by and the order the server computes in are one order on every engine Dana
runs on. 4.5's note on why the key is a string and not an integer governs this column too.
