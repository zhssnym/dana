### 4.24 labels

**Added 2026-09-20 by issue #226, on the technical ruling recorded there** (parent #208).
The M1 Label catalog: the definitions, in two scopes and no third. A **Personal** Label is
owned by one account and private to it; a **Folder** Label belongs to one Folder and is
shared with its members. A Library scope spanning several Folders is M2+, and a Personal
Label applied to a Folder remains a Personal Label rather than becoming a scope of its own.

**Scope is part of identity.** Personal "Research", Folder A "Research" and Folder B
"Research" are three Labels with three ids and are never merged by name.

| Column | Type | Null | Default | Constraint |
| - | - | - | - | - |
| id | uuid | no | generated | PK `labels_pkey` |
| scope | text | no | none | CHECK (`scope IN ('personal','folder')`) as `labels_scope_check` |
| owner_user_id | uuid | yes | none | FK users(id) ON DELETE CASCADE (`labels_owner_user_id_fkey`) |
| folder_id | uuid | yes | none | FK folders(id) ON DELETE CASCADE (`labels_folder_id_fkey`) |
| name | text | no | none | CHECK (`char_length(name) BETWEEN 1 AND 40`) as `labels_name_length_check` |
| color | text | no | none | CHECK (`color ~ '^#[0-9A-Fa-f]{6}$'`) as `labels_color_format_check` |
| description | text | yes | none | CHECK (`char_length(description) <= 100`) as `labels_description_length_check` |
| archived_at | timestamptz | yes | none | none; the archive state, non-destructive |
| created_at | timestamptz | no | now() | none |
| updated_at | timestamptz | no | now() | none |

UNIQUE (`id`, `owner_user_id`) as `labels_id_owner_user_id_key`. UNIQUE (`folder_id`,
`id`) as `labels_folder_id_id_key`. CHECK, as `labels_ownership_check`:

```
(owner_user_id IS NULL) <> (folder_id IS NULL)
AND (scope = 'personal') = (owner_user_id IS NOT NULL)
```

Unique indexes `labels_personal_name_idx` on (`owner_user_id`, `lower(name)`) WHERE
`scope = 'personal'`, and `labels_folder_name_idx` on (`folder_id`, `lower(name)`) WHERE
`scope = 'folder'`.

**The two composite uniques exist to be referenced, not to be queried, and a later reader
would otherwise take them for redundancy over the primary key.** Each is the target of an
assignment table's composite foreign key — `labels(id, owner_user_id)` for the two Personal
relations of 4.25 and 4.26, `labels(folder_id, id)` for 4.27 — and between them they make a
mis-scoped assignment **unrepresentable** rather than merely unwritten by the handlers.
Neither index is there to serve a read, and neither should be dropped on the grounds that
nothing selects through it.

**`labels_ownership_check`'s spelling is load-bearing and the obvious one is wrong.** A
CHECK fails only on FALSE and treats UNKNOWN as good as TRUE, so the natural way to write a
both-or-neither rule — `((owner_user_id IS NULL AND folder_id IS NULL) OR (owner_user_id IS
NOT NULL AND folder_id IS NOT NULL))` inverted for an XOR, or any spelling that compares a
possibly-null value before both sides are known present — admits exactly the row it was
written to refuse. That is issue #27 recurring, and **the reason it recurs is that the
obvious spelling reads correct.** Every operand above is an `IS NULL` or an equality over a
NOT NULL column, both of which always yield a real boolean, so the expression is never
UNKNOWN. This matters twice over because AC-001 asserts constraints by name and by the
columns they mention and never by what the expression does, so a toothless CHECK here would
be green across the whole suite; only a behavioural case that tries the bad row sees it.

**Case-insensitive uniqueness is per catalog and includes archived rows.** Archive is
non-destructive, so an archived "Research" still holds the name and a second cannot be
created beside it; a person who wants the name back restores or renames the Label that has
it. The two indexes are partial rather than plain because the other scope's key column is
NULL on every row of the opposite catalog and NULLs do not conflict — the predicate says
which catalog each index is about instead of leaving that to be inferred.

**The two cascades are the account and Folder lifecycles and nothing else.** A person's
Personal Labels go with their account (8.10), and a Folder's Labels go with the Folder when
it is purged. Soft-deleting a Folder sets `deleted_at` and touches no row here.
