### 4.25 task_personal_labels

**Added 2026-09-20 by issue #226, on the technical ruling recorded there** (parent #208).
The first of the three assignment relations: one of the viewer's own Personal Labels (4.24)
applied to one Task.

| Column | Type | Null | Default | Constraint |
| - | - | - | - | - |
| task_id | uuid | no | none | FK tasks(id) ON DELETE CASCADE (`task_personal_labels_task_id_fkey`) |
| label_id | uuid | no | none | part of the composite FK below |
| owner_user_id | uuid | no | none | part of the composite FK below |
| created_at | timestamptz | no | now() | none |

PK (`task_id`, `label_id`) as `task_personal_labels_pkey`. FK (`label_id`,
`owner_user_id`) against `labels(id, owner_user_id)` ON DELETE CASCADE as
`task_personal_labels_label_scope_fkey`. Index
`task_personal_labels_label_id_idx` on (`label_id`), btree, non-unique and non-partial; the
task side is served by the primary key's leading column.

**`owner_user_id` is stored rather than derived, and the composite foreign key is what makes
it honest.** The pair cannot name a Label somebody else owns, because the referenced unique
is `labels(id, owner_user_id)` and no other row of `labels` carries that pair. And because
the column is NOT NULL here while a Folder Label's `owner_user_id` is NULL (4.24's ownership
CHECK), **a Folder Label cannot be attached through this table at all** — there is no value
of `owner_user_id` that would satisfy the key. That is a scope rule enforced by the schema
rather than by a handler.

The column earns its place twice more. The per-viewer read — a Task carries *your* Personal
Labels and never another member's — is answered from this table alone, and so is the
per-viewer cap of 100 in 10.3, which is counted here without joining `labels`.

**The cascade is the trash rule expressed as foreign-key behaviour.** A soft-deleted Task
keeps its assignments and restores whole; only the permanent delete of 7.13 and the 11.7
purge, which `DELETE FROM tasks`, take them. The same holds of the Label side: archiving a
Label is a column on `labels` and removes nothing here, so every existing assignment stands
while new ones are refused (7.26).

**A retained assignment whose target the owner can no longer reach is deliberate.** When a
Personal Label's owner loses access to the Folder a labelled Task lives in, the row remains,
contributes nothing to any answer the owner can still get, and becomes visible again if
access returns — with no repair step and nothing deleted in between (#208 R8).
