### 4.26 folder_personal_labels

**Added 2026-09-20 by issue #226, on the technical ruling recorded there** (parent #208).
The second assignment relation, and 4.25's shape one target over: one of the viewer's own
Personal Labels (4.24) applied to one Folder.

| Column | Type | Null | Default | Constraint |
| - | - | - | - | - |
| folder_id | uuid | no | none | FK folders(id) ON DELETE CASCADE (`folder_personal_labels_folder_id_fkey`) |
| label_id | uuid | no | none | part of the composite FK below |
| owner_user_id | uuid | no | none | part of the composite FK below |
| created_at | timestamptz | no | now() | none |

PK (`folder_id`, `label_id`) as `folder_personal_labels_pkey`. FK (`label_id`,
`owner_user_id`) against `labels(id, owner_user_id)` ON DELETE CASCADE as
`folder_personal_labels_label_scope_fkey`. Index
`folder_personal_labels_label_id_idx` on (`label_id`), btree, non-unique and non-partial.

**There is no folder_folder_labels, and its absence is the model rather than an omission.** A
Folder Label belongs to one Folder and classifies the **Tasks inside it**; it never
classifies the Folder that owns it (#208 R4). So the only Labels that can be applied to a
Folder are Personal ones, and the NOT NULL `owner_user_id` above is what refuses the other
kind — for the reason 4.25 gives, a Folder Label's `owner_user_id` is NULL and no value
would satisfy the key. A Folder therefore carries exactly one Label projection on the wire,
the viewer's own, and two members reading the same Folder read different arrays, exactly as
they read different `my_shelf` values.

**A Personal Label applied to a Folder is still a Personal Label.** It does not become a
Folder Label, does not become visible to the Folder's other members, and does not acquire a
scope of its own; there are two scopes and no third.

The cascade and the archive behaviour are 4.25's, for the same reasons: a soft-deleted
Folder keeps its rows here and restores whole, only the purge takes them, and archiving a
Label leaves every existing assignment standing.
