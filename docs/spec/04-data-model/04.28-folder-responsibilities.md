### 4.28 folder_responsibilities

**Added 2026-09-21 by issue #230, on the accepted technical ruling**
https://github.com/zhssnym/dana/issues/230#issuecomment-5751322947 **(Ruling 1, section 4).**
Product authority: #209 R5 (one rich, Folder-visible Responsibility document per member),
R7 section O, R10 and the accepted R10B.

One row is one member's **current** Responsibility document in one folder. The document is
rich content in the same storage format 4.17 uses for page blocks, not a list of strings:
R5 asks for something a person writes, with headings, bullets and links in it.

| Column | Type | Null | Default | Constraint |
| - | - | - | - | - |
| id | uuid | no | generated | PK `folder_responsibilities_pkey` |
| folder_id | uuid | no | none | FK folders(id) ON DELETE CASCADE (`folder_responsibilities_folder_id_fkey`) |
| member_id | uuid | no | none | FK users(id) ON DELETE RESTRICT (`folder_responsibilities_member_id_fkey`) |
| content | jsonb | no | none | the rich document, canonical shape per 4.11 |
| content_hash | text | no | none | the canonical hash of `content`; the revision token the API calls `revision` |
| current_revision_no | integer | no | none | CHECK (`current_revision_no > 0`) as `folder_responsibilities_current_revision_no_check` |
| created_at | timestamptz | no | now() | none |
| updated_at | timestamptz | no | now() | none |
| updated_by | uuid | no | none | FK users(id) ON DELETE RESTRICT (`folder_responsibilities_updated_by_fkey`) |
| ended_at | timestamptz | yes | none | none; set when the membership it describes ends |

Unique index `folder_responsibilities_folder_id_member_id_active_idx` on (`folder_id`,
`member_id`) WHERE `ended_at IS NULL`. Index `folder_responsibilities_member_id_idx` on
(`member_id`).

**The uniqueness is partial, and that single index carries the whole leave-and-rejoin
rule.** One *active* document per (folder, member); an ended one sits beside a current one
without colliding with it. Membership ending stamps `ended_at`, which both closes the
standing and frees the slot, so a rejoin writes a new row at revision 1 rather than
reopening the old one. Nothing is deleted on the way, which is R10's "history survives the
membership it describes" expressed as a constraint rather than as a handler's good
intentions.

**There is deliberately no `ended_by` beside `ended_at`.** Who ended a standing is on the
`responsibility_ended` entry in 4.29, which is the record and therefore the authority; a
denormalized copy here would be a second answer to one question and could only ever drift
from the first.

**`content_hash` is the concurrency token and is not decoration.** A commit sends the hash
it read as `base_revision`; a commit whose content already hashes to the current value is a
no-op whatever it sent, and only then is a stale base refused with 409. That order is what
makes a retry after a lost answer safe without a mutation-receipts table, and 7.4 states it
as the route's contract.

**The two `users` keys are RESTRICT rather than CASCADE, and that is a decision rather than
an oversight.** 8.10's account deletion scrubs the `users` row rather than deleting it, so
no `ON DELETE` clause on a `users` key fires at all; a CASCADE here would therefore delete
nothing while *looking* like the cleanup, and the standing would be left open forever. The
sweep closes it explicitly instead, and 8.10 carries the sentence. RESTRICT is what makes a
future hard delete fail loudly rather than quietly taking the folder's record of its own
work with it.
