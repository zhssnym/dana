### 4.27 task_folder_labels

**Added 2026-09-20 by issue #226, on the technical ruling recorded there** (parent #208).
The third assignment relation, and the one worth an extra column: a Folder Label (4.24)
applied to a Task in that same Folder, shared with every member of it.

| Column | Type | Null | Default | Constraint |
| - | - | - | - | - |
| folder_id | uuid | no | none | part of both composite FKs below |
| task_id | uuid | no | none | part of the task-scope FK below |
| label_id | uuid | no | none | part of the label-scope FK below |
| created_at | timestamptz | no | now() | none |

PK (`task_id`, `label_id`) as `task_folder_labels_pkey`. FK (`folder_id`, `task_id`)
against `tasks(folder_id, id)` ON DELETE CASCADE as `task_folder_labels_task_scope_fkey`.
FK (`folder_id`, `label_id`) against `labels(folder_id, id)` ON DELETE CASCADE as
`task_folder_labels_label_scope_fkey`. Index `task_folder_labels_label_idx` on
(`folder_id`, `label_id`), btree, non-unique and non-partial.

**The row carries the Folder, and both keys point at that one column.** The first holds the
Task to that Folder and the second holds the Label to it, so the two ends can only ever
agree. **A Folder A Label on a Folder B Task is therefore not a rule the handlers enforce,
it is a row the database cannot store — direct SQL included**, whichever Folder the
statement claims. Claim Folder A and the task-scope key fails; claim Folder B and the
label-scope key fails. This is the invariant #226 asked for, and putting it in the schema is
what makes it hold for a path nobody thought of.

**The shape is 4.15's `comments_task_scope_fkey`**, which holds a comment to its task's
folder the same way. **Unlike that one it is not deferrable**, and the difference is
deliberate rather than an oversight: 4.15's pair is DEFERRABLE INITIALLY IMMEDIATE since
migration 0007 so that 7.6's move can re-scope a task's conversation inside one transaction,
and nothing here needs to hold a broken pair across two statements. A Task moving to another
Folder does not carry its Folder Labels to a catalog that does not contain them.

**Unlike 4.25 and 4.26 there is no `owner_user_id`, because these assignments are the
Folder's.** Every member sees all of them, so the per-Task cap of 100 in 10.3 is shared
rather than per viewer. **Who may add or remove one is 7.26's `label.apply`** — Can edit
and above across the Folder's work, Can contribute over the Task currently assigned to
them, and nobody below. This sentence read "any member may add or remove one (#208 R5A, the
interim rule until #209 supplies explicit Responsibilities and Authorities)" until
2026-09-20; #209 arrived as #228, supplied exactly that, and issue #274 is the ruling and
the change — the owner's technical ruling of 2026-09-20 authorising this amendment to a
frozen section is
https://github.com/zhssnym/dana/issues/274#issuecomment-5753612375. What the column list
here turns on is unchanged: the cap is shared **because the rows are the Folder's**, which
is a fact about the table rather than about the bar. The two per-Task caps are
counted apart: a Task may carry 100 Folder Labels and, for each viewer independently, 100
Personal ones.

The cascade and the archive behaviour are 4.25's.
