### 9.2 Landing and login

Public page (`app/src/client/pages/LandingPage.tsx`): collaborative to-do lists in
shareable folders, a single "Continue with Google" control, privacy and terms links. It is
one screen: a headline, one sentence, the sign-in control and its disclosure line, a
footer. No product mockups (a picture of the app drifts from the app), no rotating words,
no scroll animation. After callback,
first run lands on Today by way of /app; pending invites, when any exist, gate the application
first (9.8).

A visitor with a session who opens `/` with no query string lands on Today by way of /app
instead (AC-956); any query string, `?signin=failed` included, keeps the page.

**The landing page describes what Dana does, never what it might do.** Every capability
it names must be usable on the day it is read; no copy may promise, imply or preview one
Dana does not ship, and no copy anywhere on it claims AI (section 1). It is stated as a
rule because it is broken by addition, and no assertion about what the page does contain
catches a sentence that should not be there.

Copy and composition are the design record's and live in the component; this section
fixes only the rules copy is written under, because marketing moves and a transcribed
copy would drift silently:

- No capability claimed that Dana does not ship; no AI (AC-159).
- Exactly one "Continue with Google" control on the whole page, a closing block included
  (AC-159).
- Privacy and terms links (AC-159).
- The page says a project is a page and says the product is shared (AC-159).

One string is normative, because it states what Dana takes and its accuracy is a privacy
obligation. Under the sign-in control: "Dana requests only your Google profile and email
for sign-in, sharing, and invitations."

The Privacy page (`app/src/client/pages/LegalPage.tsx`) says the data can be taken away: a section
"Taking your data with you", immediately before "Deleting your data", saying the person
can download everything Dana holds about them at any time as one JSON file from Settings
(7.22, 9.7). It names Settings, not the endpoint. 10.9 records why it is owed: Google's
API terms measure Dana on portability, not only erasure. This is the one sentence on a
public page that claims a capability, so it stands only while the control does (AC-404).

The sign-in control is a link, not a button, although the design renders a button. It
carries the viewer's detected timezone to the authorisation endpoint of section 7, which
is how a first session gets a timezone before any row exists; a link keeps the
destination visible, bookmarkable and reachable without scripting.

Where the page animates a heading, the accessible name is the settled sentence and the
animation is decorative: a heading whose text depends on when it is sampled has no name.

Sign-in refusal pages (`app/src/server/auth/pages.ts`). Both answer 403, establish no
session and create no rows; the callback has these two and no others. Every other sign-in
refusal returns to the landing page with ?signin=failed and 9.1's global failure sentence.

- **Unverified email** (10.1; AC-008): Google reports the email unverified. Heading "We
  can't sign you in yet"; the body says Dana needs Google to confirm the address because
  it uses email for sharing and invites; one action, "Back to Dana".
- **Claimed email** (10.1; AC-346): Google reports a verified email that already belongs to
  a different live account; nothing is joined. Heading "This email already has an
  account"; the body is three sentences in this order — an account already uses this
  email and Dana never joins two accounts; sign in with the Google account used the first
  time; if that fails, write to support and a person will answer. Actions: "Back to Dana",
  and a quieter "Email support" opening a message to `SUPPORT_EMAIL` in
  `app/src/shared/support.ts`.

The claimed-email page names the fact rather than saying only that sign-in failed. That
discloses nothing that can hurt: only someone who completed 11.6's handshake with Google
asserting this verified address is theirs can see it, and they can already read the
mailbox. Against that, with no password to reset and no second factor, a person holding
the wrong Google account has no other way to be told so. A page that says less is the
obvious "safer" edit and is wrong.
