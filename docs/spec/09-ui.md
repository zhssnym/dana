## 9. UI specification

Structure, states, and behavior only; no colors, typography, or spacing. Every page has five possible states unless narrowed: loading (skeleton rows), populated, empty (copy below), error (copy below), plus the global offline banner. Exact copy is normative; design may restyle, not reword, without a spec change.

### 9.1 Global chrome

- Top bar: app name (links to My Day), global search control (keyboard shortcut Ctrl+K or /), avatar menu (Settings, Sign out).
- Sidebar: pages in fixed order My Day, Tasks, Planned, Important, All, Done, each present only if permanent or toggled visible; divider; folder list; "New folder" action; Settings link.
- Folder list: Inbox pinned first with pending-count badge; then per-member label groups (collapsible, labels ascending), each folder showing color dot, name, pending count; unlabeled folders after the labeled groups, name ascending.
- Floating add button: bottom right on every page except Done; opens the task form with the entry-point defaults of 9.3.
- Inline quick-add row: at the bottom of Tasks groups, Planned list, and folder sections; a single title input; enter saves immediately with all other fields at that entry point's defaults; escape clears.
- Offline banner (global, persistent while offline): "You're offline. Dana needs a connection; changes can't be saved right now." Writes attempted offline fail with the toast "Couldn't save. You're offline."
- Global error toast for failed requests: "Something went wrong. Nothing was saved. Try again." 409 conflicts show the state machine copy of 5.1 verbatim.

That criterion requires a page hidden from the sidebar to still render at its URL, which no acceptance test can address and no client can be measured against while the paths exist only inside the router P8 writes. Recording them here rather than there is what keeps the suite reading a specification instead of an implementation, the standing reason the tester session precedes the implementer. Addressing. Every control this section names is reachable by its accessible role and by its normative name, so the copy above is what a screen reader announces and what a test addresses rather than only what is painted. This states what the section already implied, its copy being normative and its icon-only controls already owing a screen reader label. It is stated because the alternative, addressing a control by a class or a test identifier, would make an acceptance criterion depend on markup this section deliberately leaves free, and would put the tester in the business of specifying the implementer's internals.

The names are assigned here because that reaches further for less than anything else available: a description matched loosely is a locator that finds the wrong control on the day a second one resembles it, and every name below is either lifted from this specification's own words or is the shortest thing the control does.

Four of those eight are worth their reason. The floating add button is called "the + button" by Q5's empty state, which is a glyph rather than a name, and "Add task" separates it from the quick-add row beneath it on the same page. That row takes "Add a task", the words the design brief already uses for it. The overflow menus take "More actions" rather than "More options" because 9.3 spends the second on the form's expander, and a page carrying both would otherwise have two different controls answering to one name. And every confirmation offers "Continue" and "Cancel" uniformly, "Continue" being this section's own word in 9.5's un-complete confirm: the destructive verb is already in the normative message the person is reading, so spelling it again on the button buys nothing and costs four more strings to keep in step with four messages.

These are accessible names, which fixes identification and not appearance. An icon-only control still shows an icon, and the name is what a screen reader announces and what a test asks for. Design may restyle and may not rename, exactly as it may restyle and not reword.

Sections, added at the same change control on 2026-08-11 and routed back by the tester return that took the names above. A name identifies a control that appears once on a page, and three of these appear more than once: the quick-add row sits at the bottom of every Tasks group, the Planned list and both open folder sections, "More actions" opens on every task row, and a task row repeats down every page. That was tolerable while every instance behaved identically and stopped being tolerable the moment 9.3 gave a folder page's two quick-add rows different due dates, since the two are one control with one name in two sections and no property of either input tells them apart.

The container is named rather than the control, and the reason is that qualifying the control does not scale. Tasks carries one quick-add row per folder group, so its instances number as many folders as hold undated tasks, and a table of names cannot enumerate a set the data decides. Naming containers costs almost nothing extra, because this section already names most of them.

Every section a page's structure names is a named region, and a control inside one is addressed as that control within that region. The region's name is the heading this section gives it where it gives one, and the datum the section is generated from where it does not:

| Page | Regions and their names |
| - | - |
| Sidebar (9.1) | one per personal label group, named by that label |

| Tasks (9.5) | "Inbox", then one per folder group named by that folder |

| Search overlay (9.9) | "Pending", "Abandoned", "Completed" |

Planned's list and Important carry one section each and need none. Four consequences are worth stating.

A collapsible section is a named region together with a control carrying that same name, and the control's expanded state is what open and collapsed mean. That covers the Completed section of 9.6, the recap of 9.4 and the label groups of 9.1, and it is what makes "collapsed" something a reader and a test observe rather than infer from a visual impression. AC-058's clause reads on that state.

Tasks' Inbox block is a named region with no visible heading, which does not contradict 9.5 calling it ungrouped. A region's name is announced and addressed, not rendered, exactly as a control's is, so the block still reads as a plain list on top with no label above it, and naming it is what separates its rows and its quick-add row from the folder groups beneath.

Where a region's name comes from data rather than from this section, a test addresses it by the text the page rendered rather than by a string fixed here. Done's day groups are the case: the format of a date is the design's and this section has never spelled one.

And one adjacent silence is closed with them, because it sits inside the same table and would otherwise be raised against it: the Inbox block carries a quick-add row like every folder group on that page. 9.1 places the row at the bottom of Tasks groups and 9.5 calls the Inbox block ungrouped, which left the one folder every account has as the only one on that page that could not be quick-added into, on a page whose whole purpose is capture without a date.

The folder page's header and its sharing panel are regions by that same rule, added to the table above at the second P8 change control on 2026-08-11, on the tester session's escalation. 9.6 puts an overflow menu in the folder header, which is a third control answering to "More actions" after the task form's and a task row's, and the table was written against Q7's three body sections so it reached neither the header nor the panel. The escalation offered two answers and the second is taken. Giving the folder's menu a name of its own was declined: the two named menus share "More actions" deliberately, being the same control pointed at different objects, and a third name would assert a difference in kind that is not there, while the sections ruling's own argument applies unchanged, that naming containers scales where qualifying controls does not. Naming the header also reaches further for less, because AC-058's 8.11 ratio is rendered in it, the Share button and the inline rename sit beside the menu, and all four are addressed today by looking anywhere on the page. Both names are 9.6's own words, and "Sharing panel" is the reading the page assembly session had already applied to that section. AC-162's folder case reaches the menu as the first match on the page, which is position, and a tester return owes it this region instead.

Inline state copy, added at the same change control, because three of the states this section gives every page had no words at all. 9.4 writes the error state as "global toast plus inline retry" and this section spells only the toast; section 6 ends its cap rule with "the UI shows a notice" and writes no notice; and 10.2's rule that an inaccessible resource reads as nonexistent reaches a page that then has nothing to say. The copy sits here rather than beside each of those rules because these are page states and page states are this section's, and none of the rules that produce them moves. Normative like the rest of this section's copy:

| State | Copy |
| - | - |
| A read that failed, beside the thing that failed | "Couldn't load this. Nothing was changed.", with the "Try again" control of the table above |
| A resource that answers 404 (10.2) | "Not found. This may have been deleted, or it may never have been yours to see." |
| A response carrying truncated (section 6's cap rule) | "This list is long, so only the first part is shown. Narrow it down to see the rest." |

All three strings are the client's first passes, adopted rather than rewritten, and each is adopted for a reason. The failed read says what was not changed, which is the question a failure raises and which 9.1's own toasts already answer that way. The 404 line states both of 10.2's cases in one sentence without telling a reader which of them they met, which is what that chokepoint exists for. The notice interpolates no number, the flag reporting that rows were dropped and never how many, so a client spelling "1000" would be transcribing a limit of 10.3 the response does not carry and a later release may move. Two of the three are asserted by AC-171; the notice is asserted by nothing, deliberately, because producing it takes a thousand and one rows through section 7 and section 13 item 6 records that the cap is unreachable at v1 scale. It is written down so that it is one string chosen once rather than one per page.

### 9.3 Task form (create and edit are the same artifact)

Always visible: title (required), inline quick-set for due date, inline toggle for important. Behind one "More options" expander: notes, folder, assignee, due time, reminder, repeat, steps.

Dependency graph (disabled means visible but inoperable with helper text; hidden means absent):

| Field | Visible when | Enabled when | On disable, helper |
| - | - | - | - |
| title | always | always | none |
| due date | always | always | none |
| important | always | always | none |
| notes | expanded | always | none |
| folder | expanded | always | none |
| assignee | expanded and target folder has 2 or more members | always when visible | hidden in single-member folders (INV-5) |
| due time | expanded | due date set | "Set a due date first" |
| reminder | expanded | due date set | "Set a due date first" |
| repeat | expanded | due date set | "Set a due date first" |
| steps | expanded | always | none |

Moment of enablement: the instant due date receives a value, in the same render; clearing it disables and clears the three dependents after the 8.4 warning: "Clearing the date also ends the repeat and removes the reminder."

Behavior rules: folder selection re-filters the assignee dropdown to that folder's members plus "Invite by email", which opens the sharing flow with this folder attached and, on send, shows the pending chip; assignee defaults to the viewer; reminder control switches mode with due time (offset picker with due time, time-of-day picker without); repeat control is preset-driven (daily, weekdays, weekly on chosen days, every N days or weeks, monthly on day 1 to 28, yearly) with an optional "Ends on" date, never a raw RRULE box; steps editor: text row, enter appends the next row, per-row check, delete, and up or down reorder controls, cap notice at 50.

Entry-point defaults:

| Opened from | due date | important | folder | other |
| - | - | - | - | - |
| Tasks, All, or bare button | empty | off | Inbox | none |
| My Day | today | off | Inbox | none |
| Planned list | today | off | Inbox | none |
| Planned calendar cell | that cell's date | off | Inbox | none |
| Important | empty | on | Inbox | none |
| Folder page | per that folder's section context | off | that folder | none |

The folder page's section context, closed at the P8 change control on 2026-08-11 because AC-093 asserts all six rows of the table above and this was the one cell stating no value. The two open sections of 9.6 each carry their own quick-add, and each is the context: the Scheduled section's quick-add opens with due date today, the Unscheduled section's opens with it empty. The floating add button sits on the page rather than in a section, and it opens with the due date empty, which is what having no section context means everywhere else in the table. The reason it is empty rather than today is that a folder is not a dated page: My Day, the Planned list and a calendar cell each default to a date because the page the person is standing on is about that date, while Tasks and All default to none because they are not, and a folder holds both kinds of task at once. Defaulting it to today would file a task into the Scheduled section nobody aimed at, and clearing a date that was added for you costs more than adding one that was not.

Validation copy: empty title, "Give it a title"; over-limit fields show "Too long: limit N characters"; the steps editor's cap notice reads "Limit 50 steps"; reminder mode mismatch is impossible in the UI and returns 422 server-side regardless.

Edit mode differences: fields pre-filled; folder change shows, when the assignee would not survive the move, "Moving will unassign Sara; she isn't a member of Home." Delete lives in the form's overflow menu with confirm "Delete this task? This can't be undone."

The assignee dropdown offers no unassignment, ruled at the second P8 change control on 2026-08-11. Section 4 makes assignee_id nullable and this section listed the dropdown's contents without saying whether that null is reachable from it, so the question was asked from the implementation rather than answered by the text. It is not reachable: the dropdown is the target folder's members plus "Invite by email" and nothing else. Three reasons, and one cost stated with them. AC-094 asserts exactly that list, so a "Nobody" option would falsify a criterion that passes, and closing a silence by invalidating a criterion trades the wrong way round. The field is hidden in single-member folders, which is where unassigning is refused by INV-5 with the 409 of AC-032, so nothing is lost at the only place the refusal bites. And this section defaults the assignee to the viewer, so a task written through this form always has someone to answer for it, while the null INV-5 permits in a larger folder arrives from events rather than choices: a move to a folder the assignee is not a member of (7.6), and the R-CLEAN of 5.3 when a member is removed or leaves. The cost is that a task in a multi-member folder can be reassigned from the interface and not unassigned, which is recorded as section 13 item 28 with what changes if evidence arrives.

The reminder is saved like every other field of this form, ruled at the same change control after the co-lead found that it was not. The control implements the two modes above and its dependency on the date; what the two write paths differ over is where it goes. A reminder set while creating rides the reminder arm of frozen 7.6's create body, and a reminder set or changed while editing is frozen 7.9's PUT, whose removal arm is DELETE /tasks/:id/reminder because no task body expresses a removal; 8.6 names all three of those writes. This is stated because it is the one field of the ten above whose write reaches an endpoint the rest of the form does not, which is how it came to be held in the form and dropped at save with every test green: AC-092 reads the form's state and says so itself, AC-146 to AC-150 read the endpoints, and nothing read the two together until AC-169 and AC-170.

### 9.4 My Day

Structure: header with the date; important-only toggle switch; Carried group (heading "Carried over"); Today group (heading "Today"); recap collapsed at bottom (heading "Done today (N)").
Row elements: complete checkbox, title, folder label, due badge (overdue styled when due_date < today), assignee chip when not the viewer, star, pulled marker with un-pull control when inclusion came from an entry ("Remove from My Day"; absent when the row also qualifies automatically), overflow (edit, abandon, delete).

### 9.5 Tasks, Planned, Important, All, Done

- Tasks: ungrouped Inbox block, then folder-headed groups; inline quick-add per group and on the Inbox block, adding into that folder, undated. Each is a named region per 9.1, the Inbox block's name carrying no visible heading.
- Planned: mode toggle list/calendar (persisted per user client-side); list per Q3; calendar per Q3C with day, week, month zooms, previous/next/today controls, all-day banner lane, timed lane when due_time set, ghost styling for virtual instances, click on empty cell opens the form with that date, click on any row opens the task, click on a ghost opens the current occurrence with the banner "Upcoming occurrence of a repeating task"; the month zoom requests the whole weeks overlapping the month, six of them, so one request covers 42 days and the grid keeps its height as the months change.
- Important: single list per Q4; star on each row un-stars it with immediate removal from view; star tooltip points outward as Q4 defines. On every other page the star's name is its own state, "Important" when filled and "Mark as important" when not, which is both its tooltip and its accessible name. That inward copy was a silence closed at the P8 change control on 2026-08-11: AC-099 requires the tooltip to confirm importance off Important and this section spelled no string for it, so the criterion could assert only that the tooltip did not point outward. Two names rather than one because the star is a toggle and icon-only, so each state owes a screen reader something true, and because AC-055's un-star needs a control it can ask for by name.
- All: two labeled sections, "Planned" then "Tasks", each rendered by its home page's rules; section headers are static labels, not links.
- Done: day-grouped infinite scroll per Q6; each row has "Mark as not done", which runs uncomplete and, on the G-SERIES successor branch, first confirms "This removes the next scheduled occurrence (including any edits to it). Continue?"; no add affordance anywhere on this page.
- Abandoned rows on Tasks, Planned, Important, All, and folder pages render faded and struck with an "Abandoned" chip and a "Restore" control.

The month zoom's six weeks, ruled at the P6 mid-package change control on 2026-08-10, the range being the client's to request and Q3C answering whatever range it receives. The count is fixed rather than the four or five weeks a month strictly needs, and the reason is not a test's convenience although it was a test that surfaced it. AC-082's third clause, that ghosts appear only after the current occurrence, is positively observable only on a grid reaching past the month end: for July 2026 the current occurrence is due the 27th and the next instance falls on 2026-08-03, which neither five-week grid reaches and both six-week grids do, on either week start, measured rather than reasoned. A month view stopping at the month end hides the next occurrence of every series whose successor lands in the first days of the following month, which is the case the ghost exists to show, so the criterion and the product want the same grid. Six weeks is 42 days and never approaches Q3C's 62-day refusal. The week the grid starts on changes none of this and is deliberately not decided here: it is the designer's, and it arrives with the 11.13 screens.

### 9.8 People and invites

People screen (reachable from sidebar footer or Settings): roster list with remove control ("Remove connection? You can still see shared folders; you'll just need a fresh invite to share new ones."); bare invite by email, refused when the address is already a connection ("You're already connected to this person. They're in your People list.", the 409 of 7.5 entered by owner ruling on 2026-08-09).
Login surface: when Q12 is non-empty, an invite list renders before anything else: each row "Hassan invited you to Wedding" (or "Hassan invited you to connect"), Accept and Decline buttons; accepting a folder invite lands inside that folder.
Assignment chip: rows and the form show "Invite pending: sara@example.com" while an assignment-invite is outstanding.

Where that list lives, ruled at the second P8 change control on 2026-08-11. This section says it renders before anything else after callback and 9.2 says the callback lands on My Day, which between them fix the first load and say nothing about the second. It is a section of My Day, above everything else on that page, and it is there whenever Q12 is non-empty rather than only on the load that followed a callback; the People screen carries it as well, that being the screen this section gives the rest of this subject. Two readings were rejected. A band above every page would be a piece of global chrome 9.1 does not name, and 9.2 has already decided where a person lands. A surface that appears once and not again would leave anyone who reloads before answering with no invite in front of them, which is the case "before anything else" is written against; the list empties itself as each invite is answered, so the standing reading needs no dismissal and no state of its own. AC-172 asserts it.

The list is a region with no name, which is a decision and not an omission. 9.1's sections rule takes a region's name from the heading this section gives it or from the datum it is generated from, and this list has neither: it is one list rather than one per folder, and this section writes no heading above it. Its rows are addressed the way a task row's controls are addressed, from the row's own sentence, which is what that sentence is for: "Hassan invited you to Wedding" tells a reader and a test which Accept belongs to which invite, and a name invented here would tell neither anything the rows do not already say.
