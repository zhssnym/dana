### 8.8 Folder deletion and member removal

Folder deletion (owner only, never the default folder), one transaction: count open,
completed, abandoned tasks for the confirmation response; set the folder's deleted_at,
which is 7.13's soft delete. The folder leaves every member's sidebar and every query but
the Trash surface at once, and nothing cascades yet. Inside the 30-day window anyone with
access to the folder may restore it, not only whoever deleted it, and it returns with its
membership intact (9.11).

The cascade belongs to the purge, and the purge is 11.7's tick duty: at 30 days the folder
row is deleted, and the database cascades memberships, tasks, and through tasks the steps,
my_day_entries, and reminders; pending invites carrying the folder cascade away; and the
same pass collects the files rows those deletes will cascade away and removes their
objects from the store after the delete commits, because those rows are the only index to
the bytes. Only from that moment is nothing recoverable, and the dialog says so with its
counts and with the window.

**This paragraph read "Nothing is recoverable; the dialog said so with counts" until the
S29 fold of 2026-08-27, and that sentence was v1's.** 7.13 retired the hard delete in
favour of the soft delete and the 30-day purge when RFC 0005 was accepted on 2026-08-24;
the mechanism moved and this section's prose did not, so the specification stated as a
rule the opposite of what it had already agreed to ship. The correction is recorded here
rather than made quietly because a section contradicting another section is worse than a
section merely out of date: a session reading this one would have built the wrong thing
and been right to. RFC 0005 change control item 38 names the contradiction and hands it to
this fold; item 49 is the fold. **What this section still does not carry is the
permanent-delete control** Imran ruled in on 2026-08-26 (change control items 36 and 38),
nor the owner's leave-or-delete question for a shared folder. Those are one frozen 7.13
Replace unit, 9.11's copy and a transaction; they are RFC 0004's S28, and they are absent
here deliberately rather than written ahead of the unit that carries them.

Account deletion is not this path and does not become soft by this fold. 8.10 deletes an
owned folder's row outright, taking the cascades named above in the account's own
transaction, because an account that no longer exists cannot reach a Trash and a folder
waiting thirty days for nobody would be unreachable rather than restorable. That was
already how it behaved; what the fold changes is that 8.10's "cascades per 8.8" now names
which of this section's two acts it means.

Member removal and leave both run R-CLEAN of 5.3: unassign the leaver's tasks in the
folder, delete the leaver's Today entries for the folder's tasks, and, when exactly one
member remains, assign every unassigned task in the folder to that member (INV-5). Removal
never deletes a task [quoting the confirmed rule: removal only unassigns].
