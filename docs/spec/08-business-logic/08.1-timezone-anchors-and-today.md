### 8.1 Timezone anchors and today

Model: floating dates and times everywhere a human plans; UTC instants everywhere the
system records an event.

- Every request that evaluates dates carries tz, the client's current IANA zone. today(V)
  = the current date in tz at the moment of evaluation. The server computes it; the client
  never filters by date itself. Recorded at the P4 merge review of 2026-08-08, because the
  one endpoint that broke this rule broke it by omission rather than by choice: "every
  request" is a requirement on section 7 as much as on the code, so an endpoint that
  stores or filters by a date and takes no tz is an incomplete surface, not an invitation
  to substitute the stored zone below. 7.8's pull was that endpoint and now carries tz. -
  users.timezone exists for one consumer only: reminder fire-instant computation for that
  user as assignee. It auto-syncs at every successful login that carries the 7.1 tz
  parameter, and whenever a session reports a different zone through PATCH /me; a login
  carrying no tz syncs nothing, and a reported zone that is a tzdb alias of the stored one
  is not a different zone: no write, and no 8.6 recompute. There is no manual lock in v1.
  Traveling therefore moves both today and future reminder instants to the new zone. - The
  day boundary is local midnight in tz. DST changes move that instant but never break date
  arithmetic, because comparisons are date against date, never instant against instant. -
  Boundary statement, exact: a task with due_date D is due today when D = today(V),
  overdue when D < today(V), future when D > today(V). Today's automatic clause admits D
  <= today(V).

**Assumption: silent timezone auto-sync is acceptable.** Travel moves today and moves
reminder instants, without asking. If travellers find that wrong, the fix is a per-user
timezone lock: one column and one guard in the sync.
