### 8.3 Concurrency policy

- Reads: no realtime channel in v1. Clients refetch the active view on window focus and
  after each own mutation. Staleness between those points is accepted. - Field writes:
  PATCH sends only changed fields. Two members editing different fields both win; the same
  field is last write wins, and the lost update is accepted and documented. No version
  columns, no ETags in v1. - Status writes: only through the four transition endpoints,
  implemented as guarded updates:

```
rows = execute("update tasks set status='completed', completed_at=now(), completed_by=:actor,
                updated_at=now() where id=:id and status='pending'")
if rows == 1: run_generation_if_recurring(); return task
state = reload(id)                       # lost a race or repeat call
if state.status == 'completed': return task            # idempotent no-op
if state is missing: return 404
return 409                                              # cross-state conflict per 5.1
```

The guard makes recurrence generation exactly-once under any race: only the single winning
transition executes it, inside the same transaction. Operations on deleted rows return 404
and the client drops the row.

Issue #184 adds one narrow exception to the otherwise field-local page writes: mixed page
placement and prose-to-task conversion lock the folder row and complete in one transaction.
Callers name adjacent item identities, never keys. Concurrent placements into one gap may
produce equal fractional keys; the read's final id key makes that one deterministic sequence
without losing either write. Block content and conversion still require the `updated_at`
evidence read by the caller and answer 409 before any write when it is stale.
