### 8.10 Account deletion

One transaction, ordered so the RESTRICT on folders.owner_id can never fire.
Implementation: `deleteAccountData` in `app/src/server/domain/account-deletion.ts` (steps
1 to 6c) and `app/src/server/auth/account.ts` (steps 7 and 8). Step numbers are cited
elsewhere and are not renumbered; there is no step 6b.

- **Step 1.** Invalidate the user's pending sent invites.
- **Step 2.** Transfer ownership (8.9) of each owned non-default project with other members;
  every page of the project goes with it (step 8: people and ownership are the project's).
- **Step 3.** Delete outright every folder the user still owns, the default folder included, taking
  8.8's purge cascades rather than its soft delete: the account is going, so there is no
  Trash for them to wait in.
- **Step 4.** For each remaining membership in others' folders, run R-CLEAN (8.8), which deletes the
  membership.
- **Step 5.** Delete all connection rows containing the user.
- **Step 6.** Delete the user's remaining my_day_entries.
- **Step 6a.** Collect the files rows step 3's cascades drop and every files row the user owns, the
  folderless avatar included; delete the rows in the transaction and remove every
  collected object from the store only after commit, the order 7.15's delete uses. A
  folder transferred away at step 2 keeps its other members' files.
- **Step 6c.** Delete the user's rows in every personal table no real `DELETE` reaches. The list is
  the `DELETE` statements of step 6c in that function, and `USER_CASCADE_DISPOSALS` and
  `USER_RESTRICT_DISPOSALS` beside it carry the argument for every key on `users(id)`.
- **Step 7.** Scrub the user row: google_sub, email, display_name, avatar_url set null; deleted_at =
  now().
- **Step 8.** Destroy all sessions of the user.

**The user row is scrubbed, never deleted, so no `ON DELETE` clause on `users(id)` ever
fires for account deletion.** A table keyed `REFERENCES users(id) ON DELETE CASCADE`
(or `SET NULL`) is therefore not cleaned up by it, silently; every new user-referencing
table needs an explicit disposal here, either swept by a statement or deliberately kept.
The scrub exists so that surviving references (tasks.created_by, tasks.completed_by,
invites.accepted_by) keep resolving; they render as "Deleted user".

This section is what makes the Privacy page's sentence true: "Deleting your account
permanently removes your tasks and your personal data from the running product"
(`app/src/client/pages/LegalPage.tsx`). Weakening a sweep here means moving that copy in
the same change.

Deliberate retentions, each a folder's record rather than the person's data:

- **Responsibility records.** Step 4's R-CLEAN closes the person's standing in each
  folder (`folder_responsibilities.ended_at` set, a `responsibility_ended` entry
  recorded), and the row and its revisions in `folder_responsibility_history` survive,
  readable to the folder's current members, because history survives the membership it
  describes. Their `users` keys are RESTRICT for that reason. Nothing about the person is
  answered as current anywhere.
- **`page_document_receipts`.** They carry no text, and a folder's receipts also mark its
  document as being on the transaction path, so removing a departed member's could change
  how the folder behaves for the people still in it. Step 3 already takes the receipts of
  every folder that dies with the account.
- **`folders.archived_by`.** Archive provenance remains attached to Work that survives an
  actor's account deletion. The Archived work page shows the actor's name only while that
  account is live; the scrubbed row contributes no name. Step 3 removes archived Work that
  belonged only to the departing account.

**A departed member's private facets are deleted** by step 4's R-CLEAN, with their
`page_blocks` — the opposite answer from the Responsibility record, for the same reason
turned around: a private facet is writing no other member may ever read (4.30), so
the folder has no claim on it and nobody would be left who could read, remove or restore
it. Shared facets are Folder data and are untouched.

Dana offers deletion because the product should; no policy binding Dana requires it
(10.9).
