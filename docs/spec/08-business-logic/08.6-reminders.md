### 8.6 Reminders

**Computation** (`computeFireAt` in `app/src/server/time/reminder-time.ts`). The zone is
the users.timezone of the task's assignee, or of the reminder's created_by when the task is
unassigned. An offset reminder (which requires a due_time) fires at the task's due_date and
due_time minus offset_minutes; a time_of_day reminder (date-only task) fires at the task's
due_date at the reminder's time_of_day. That local time converts to a UTC instant under the
zone's IANA rules, which absorb DST: a nonexistent local time in a spring-forward gap
resolves to the first valid instant after the gap, and an ambiguous time in a fall-back
overlap resolves to the earlier instant.

**The state a reminders row is written with is a function of its instant, on every path
that writes one**: scheduled when the instant is in the future; skipped, with fired_at
set, when it is already past; never fired retroactively. The paths are 7.9's PUT, the
reminder arms of 7.6's create and patch, 8.5's copy onto a generated successor, and the
recompute below. Implementation: `app/src/server/time/reminder-recompute.ts`. A path that
wrote a flat 'scheduled' for a past instant would be mailed by the next tick if the
instant were inside the delivery loop's six-hour window, for a deadline that has not
arrived.

**Recompute triggers.** fire_at is recomputed, with the state the new instant earns,
whenever any of these change: due_date, due_time, the reminder's own value or mode,
assignee_id, or the assignee's users.timezone. The reminder row is deleted by: reminder
removal, the 8.4 cascades, task deletion. It survives completion and abandonment
untouched, but delivery requires a pending task, so it silently never fires;
un-completing before the instant lets it fire normally.

- **The timezone trigger recomputes only rows in state scheduled.** The other four
  triggers change the occasion (the deadline, the lead time, or the person owed it), and a
  new occasion deserves a delivery of its own, so they recompute a row in any state. A zone
  change only re-expresses an unchanged occasion on a different wall clock, so reviving a
  sent row would send the same person the same reminder twice.
- Where one of the other four triggers returns a sent or skipped row to scheduled,
  fired_at is cleared with it, so fired_at is non-null exactly when state is not
  scheduled (4.8).
- The creator's zone is a fallback for the computation and not a trigger: an unassigned
  task's reminder is never delivered (the loop skips it) and assignee_id is itself a
  trigger, so following the creator's travels would have no observable effect. The
  fallback exists only because 4.8's NOT NULL fire_at needs an instant.

**Delivery loop** (`createReminderPass` in `app/src/server/scheduler/pass.ts`), the only
background execution in v1, an operational burden named plainly: a scheduler ticks every
minute and takes every scheduled row whose fire_at has passed. A row is skipped (state
skipped, fired_at now) when its task is not pending, when its task is unassigned, when its
fire_at is more than six hours stale (catch-up after an outage), or when the assignee has
no email address; otherwise the REMINDER email goes to the assignee and the row becomes
sent with fired_at now.

Delivery is at-least-once: a crash between send and the state write can duplicate one
email; accepted for v1. The unassigned skip is deliberate: reminders are never broadcast to
a whole folder. The no-address skip should be unreachable (users.email is null only after
8.10's scrub, and R-CLEAN unassigns first); it skips rather than throws so that one bad row
cannot take down the rest of the batch.

**Assumption: one reminder per task is enough.** The source design always spoke of one. If
several are demanded, reminders gets its own id key and PUT becomes POST plus DELETE. The
fire logic per row does not change.
