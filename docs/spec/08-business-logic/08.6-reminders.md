### 8.6 Reminders

**Computation**:

```
def compute_fire_at(task, reminder):
    zone = users.timezone of task.assignee_id, else of reminder.created_by when unassigned
    if reminder.offset_minutes is not null:        # requires task.due_time
        local = datetime(task.due_date, task.due_time) minus offset_minutes
    else:                                          # date-only task
        local = datetime(task.due_date, reminder.time_of_day)
    return to_utc_instant(local, zone)
    # IANA rules absorb DST. A nonexistent local time in a spring-forward gap
    # resolves to the first valid instant after the gap. An ambiguous time in a
    # fall-back overlap resolves to the earlier instant.
```

**Recompute triggers.** fire_at is recomputed, and state reset to scheduled when the new
instant is in the future, whenever any of these change: due_date, due_time, the reminder's
own value or mode, assignee_id, or the assignee's users.timezone. When the recomputed
instant is already past, the row is set state = skipped, never fired retroactively. The
reminder row is deleted by: reminder removal, the clear-date cascade, task deletion. It
survives completion and abandonment untouched, but delivery requires a pending task, so it
silently never fires; un-completing before the instant lets it fire normally.

**The state a reminders row is written with is a function of its instant, on every path
that writes one, and this is the only place that rule is defined.** Scheduled when the
instant is in the future, skipped with fired_at set when it is already past, never fired
retroactively. It was written above as a property of the recompute alone, and that
narrowness produced the same defect twice on the same row: frozen 7.9's PUT bullet said
state resets to scheduled without condition until the owner qualified it on 2026-08-10,
and 8.5's copy arm said state='scheduled' flat until this change control, both of them a
path that computes an instant and then names a state instead of reading the one the
instant earns. Generalizing it here rather than qualifying a fourth path in a fourth
section is the point: the repository's own standing warning is that a rule stated twice
will one day disagree with itself, and this rule had already done so. Five paths write the
column and all five are governed. The three API writes, 7.9's PUT and the reminder arms of
7.6's create and patch bodies, and 8.5's copy onto a generated successor, each compute an
instant for a row that did not have one. The recompute of the five triggers above updates
one that did. Frozen 7.9 keeps its qualifier, which is a client-facing clause consistent
with this rule rather than a second definition of it, and frozen 7.6 needs none, saying
nothing about state and correctly leaving it here.

Why the copy's flat 'scheduled' was a live defect and not a harmless override, recorded
because the implementation's own comment defended it. The delivery loop selects state =
'scheduled' with fire_at <= now() and skips only what is more than six hours stale, so a
row written scheduled with a past instant inside that window is delivered on the very next
tick. The defence, that the loop reaches the same answer one tick later, is true beyond
six hours and exactly inverted inside them, which is the window ordinary values land in:
4.8 admits offsets up to 10080 minutes, so a daily task due 09:00 whose reminder leads by
a day, completed at 10:00, puts the successor's instant an hour in the past and the next
tick mails a reminder for a deadline that has not arrived and was never scheduled for.
AC-168 pins the rule across the paths that create a row.

A reminder already delivered is not revived by a timezone change, ruled at the P7
mid-package change control on 2026-08-10 on the tester session's escalation. The two texts
answered differently: frozen 7.1 scopes PATCH /me's recompute to "scheduled reminders on
tasks assigned to V" and AC-086 says "scheduled fire_at values recompute", while the
trigger sentence above names no state it resets from, so read literally it returns a
delivered row to scheduled and the loop sends the same email a second time. The timezone
trigger takes the narrow reading, recomputing rows in state scheduled and no others, and
no frozen text moves, 7.1 having said so all along where this section merely did not
restate it. What settles it is not that sent is terminal in general, which would be wrong,
but what this one trigger changes. The other four change the occasion the reminder is
about: its deadline through due_date or due_time, its lead time through the reminder's own
value or mode, or the person owed it through assignee_id. A new occasion deserves a
delivery of its own, which is why the reset above names no starting state and why frozen
7.7 scopes its due_date recompute to no state either; a user who pushes a deadline out by
a week and then hears nothing has lost the reminder they can still see configured on the
task. A zone change alters neither the deadline nor the recipient. It re-expresses an
unchanged occasion on a different wall clock, so reviving a row for it sends one person
the same reminder about the same deadline twice, which the at-least-once tolerance below
covers as a crash artifact and never licenses as a designed outcome. Two consequences are
recorded rather than left to be re-derived three times. A skipped row is outside the
timezone trigger too, that being 7.1's scope taken at its word, and the loss is narrow: a
skipped instant is already past, only a large westward move inside the fire window could
carry the same local time back into the future, and the row is recomputed anyway by the
next change to the task's own dates. And where one of the other four triggers returns a
row to scheduled from either of 4.8's two terminal states, sent or skipped, fired_at is
cleared with it, so frozen 4.8's note that fired_at is set when state leaves scheduled
stays true of every row rather than of most of them. That sentence named only the sent
case when this ruling was first written and was widened on 2026-08-10, at the tester
return's routing, before any implementer read it. The narrow wording did not merely omit
the skipped case, it defeated its own reason: a skipped row carries a fired_at like a sent
one, set by the loop below when it skips and required by 4.8's note when a recompute
skips, so reviving it without clearing that column produces a scheduled row holding a
fired_at, which is the single row shape the sentence exists to rule out. Both terminal
states revive by the same four triggers and neither is a delivery that happened, so
nothing distinguishes them here; the distinction this ruling does draw, between the
timezone trigger and the other four, is above and is untouched.

The creator's zone is a fallback for the computation and not a sixth trigger, and the
asymmetry is deliberate rather than an omission from the list above. A reminder on an
unassigned task is computed from its creator's zone because 4.8's NOT NULL fire_at admits
no row without an instant, not because that instant is ever delivered: the loop below
skips an unassigned task at fire time, and assignee_id is itself a trigger, so such a row
either never fires or is recomputed in the new assignee's zone before it does. A creator
who travels therefore moves nothing any user can observe, and following them would add a
write path with no reachable effect. Recorded at the P7 kickoff on 2026-08-10, because the
computation's two arms and the trigger list's one are read by three separate sessions of
that package and could be reconciled three ways.

**Delivery loop**, the only background execution in v1, an operational burden named
plainly: a scheduler ticks every minute.

```
every 60 seconds:
    due = select reminders where state='scheduled' and fire_at <= now()
    for r in due:
        t = task(r.task_id)
        if t.status != 'pending' or t.assignee_id is null: r.state='skipped'; r.fired_at=now(); continue
        if now() minus r.fire_at > 6 hours:          # stale catch-up after an outage
            r.state='skipped'; r.fired_at=now(); continue
        send email to assignee (template REMINDER); r.state='sent'; r.fired_at=now()
```

Delivery is at-least-once: a crash between send and the state write can duplicate one
email; accepted for v1. The unassigned-at-fire-time skip is deliberate: reminders are
never broadcast to a whole folder.

A fourth skip, recorded at the P7 merge review on 2026-08-11 because the pass decides it
and the loop above does not name it: an assignee carrying no email address is skipped
exactly as an unassigned task is. It should be unreachable, and the claim is checked
rather than assumed. 4.1 leaves users.email nullable for one reason, 8.10's scrub at step
7, and R-CLEAN unassigns that user's tasks before the scrub runs, so no row in a tree
where account deletion completed can reach it. It is written anyway because the schema
permits the shape and the loop must decide something, and it resolves to the unassigned
skip for the reason that skip already gives, which is that there is no one person to
deliver to. The alternative, throwing, would take down every other reminder in the same
batch for one row that should not exist. It is recorded here rather than left in the code
because a behavior the implementation performs and this section omits is a deviation
whatever its reachability.

**Assumption: one reminder per task is enough.** The source design always spoke of one. If
several are demanded, reminders gets its own id key and PUT becomes POST plus DELETE. The
fire logic per row does not change.
