### 8.7 Invites and sharing

**V-INV validations on create**, in order: email syntactically valid and lowercased; not
the inviter's own email; folder, when given, accessible to the inviter and not a default
folder; when a folder is given, the email must not belong to a member of it (409 "already
a member"); task, when given, inside that folder; if the email belongs
(case-insensitively) to an active user already connected to the inviter and a folder is
attached, convert to an instant share, subject to the 10.3 member cap (a full folder
refuses 422 and creates nothing, neither membership nor invite row): create the membership
immediately, send the share-grant email, create no invite row; if it belongs to such a
user and no folder is attached, 409 "already connected", the connection the bare invite
exists to create already holding; if a pending invite by this inviter to this email for
this folder exists, 409 pointing at it; rate limits per 10.4.

**Three entry paths, one mechanism**: 1. Direct: enter an email in the sharing panel
(folder attached) or in the People screen (bare). 2. Roster pick: choose a connected
person in the sharing panel; no invite, immediate membership, share-grant email. 3.
Indirect via assignment: assigning a task to someone outside the folder. Connected target:
membership created instantly, then the assignment applies, one transaction. Unconnected
target: an invite is created with folder_id and task_id set; the task's assignee stays
unchanged, and the UI shows the "invite pending" chip derived from that row.

**Acceptance transaction**, in order, all or nothing:

```
def accept(invite, acceptor):
    assert lower(acceptor.email) == invite.email and invite.status == 'pending'
    upsert connection(minmax(invite.inviter_id, acceptor.id))          # INV-9, idempotent
    if invite.folder_id is not null:
        lock folder; refuse 409 folder_deleted if deleted_at is set    # in Trash, whole transaction rolls back
        if acceptor not member:
            refuse 422 if it already holds 25 members                  # 10.3 cap, whole transaction rolls back
            insert folder_members(invite.folder_id, acceptor.id)       # INV-10
    if invite.task_id is not null:
        t = task(invite.task_id)
        if t exists and t.folder_id == invite.folder_id and t.assignee_id is null:
            t.assignee_id = acceptor.id                                # else skip silently
    invite.status='accepted'; invite.accepted_by=acceptor.id; invite.responded_at=now()
```

The 10.3 member cap binds every membership this section grants, ruled at the P5 kickoff on
2026-08-09. The instant-share conversion, with or without a task attached, and the
acceptance transaction each check it the way POST /members does: lock the folder before
counting, so the count and the insert are one decision, and refuse with 422 naming the cap
when the folder already holds 25. Section 5.3 always wrote the guard on its direct-add
row, and the acceptance row's silence was the fourth instance of the defect AC-124 names
rather than an exemption: 10.3 calls the number server-enforced, a cap one path bypasses
is not enforced, and the P3 repair of addMember was accepted partly on the recorded ground
that this package's paths would read its corrected shape. A refused acceptance rolls back
whole, per the all-or-nothing above, so the invite stays pending and can be accepted once
the folder has room, which is also why refusal beats the silent skip the assignment arm
uses: a skipped assignment loses a convenience, while a silently skipped membership would
consume the invite and grant nothing. A refused conversion tells the inviter the folder is
full now, rather than parking an invite whose acceptance the same cap would refuse.

The already-a-member clause above was added to V-INV at the P5 merge, closing a
documentation asymmetry the Adversarial Test role observed while repairing AC-060 and
recorded rather than escalated. Frozen 7.5's bullet has always enumerated that 409, and
5.3's add row and AC-060 both fix the behavior, but this expansion of the same rule
omitted it, so the list read as though a folder invite to a current member fell through to
the conversion arm. Nothing behaves differently and no criterion is invalidated: the
clause is transcribed from the frozen text, in the position frozen 7.5 gives it and the
implementation already checks it, between the folder guards and the task guard. 8.7 is not
frozen and 7.5 is, which is why the fix goes here and why it is one clause rather than a
rewording of either.

The bare invite to an existing connection is refused, ruled by the human owner on
2026-08-09 and entered on frozen 7.5 with its full grounds. The conversion arm above had
named its connected-email condition without naming a folder, while the instant share it
describes creates a membership and only a folder defines one, so a bare invite to a
connected person had no specified outcome. It answers 409 rather than a silent success
because a create on this endpoint either parks an invite with one email sent or is
refused, per 5.2's create row, and because such an invite could only ever accept into an
idempotent no-op: the connection it would create already holds under INV-9. This is the
cap paragraph's principle turned the other way. There an invite against a full folder
still parks, because a member may leave and make it acceptable; here nothing the request
could accomplish is left to accomplish.

**A folder sitting in Trash refuses the acceptance**, ruled by the owner on 2026-09-03
against issue #28 and written into the transaction above and into 5.2's accept row. The
answer is 409 with the code `folder_deleted`, and the whole transaction rolls back, so
the invite is left pending and the connection the first line would have minted is not
written either.

Nothing had specified this and the behaviour was accidental. Folder deletion used to
destroy the folder's pending invites in the same statement, and 5.2's purge row still
carries that cascade; RFC 0005 made deletion soft, so the cascade moved to the 30-day
purge of 8.8 and left a thirty-day window in which the invite is pending and the folder
it names is in Trash. In that window the acceptance succeeded, and what it granted was a
membership on a folder that leaves "every member's sidebar and every query but the Trash
surface at once" (8.8). The acceptor could not open it, could not tell why, and whether
they ever could depended on somebody else restoring it.

Three answers were available and the reason this one was taken is that a restore repairs
it by itself. Refusing leaves the invite pending, so the folder coming back out of Trash
inside its thirty days makes the invite acceptable again with nothing else to do and
nobody to tell. Cancelling the invites at the moment of deletion, which is what account
deletion does to the invites it sent (8.10), is decisive and loses exactly that: a
restored folder would come back with its membership intact per 8.8 and its pending
invites gone, and the inviter would have to notice and send them again. Letting the
acceptance through is the reading the rules had before this paragraph and is the one
nobody would choose on purpose.

Two details follow from the guard being about the folder rather than about the membership.
It is checked even when the acceptor is already a member and the grant would be a no-op,
because the acceptance response carries the folder (7.5) and would otherwise hand a client
a folder it cannot open. And the folder row is locked for the check, the same lock the cap
takes one line later, so that the guard and the grant are one decision: a deletion
committing first is read and refuses, and one arriving later waits and lands after the
grant, which is 8.8's ordinary case of a folder deleted out from under its members.

The refusal is deliberately a different code from the two refusals beside it. An invite
that is not the caller's reads 404 by 7.5's leak rule, an invite already accepted,
declined or cancelled reads 409 `conflict`, and this one reads 409 `folder_deleted`. All
three are refusals of the same request and a person needs a different sentence for each,
which is what a code is for; 7.0 provides for it in the words "409's rule conflicts gain
their specific codes as the section 5 tables land".

**This paragraph is where the rule lives because 8.7 is not frozen and 7.5 is**, the same
reading the already-a-member clause above was entered under. Frozen 7.5's sentence "All
five transition endpoints: 409 when the invite is not pending" enumerates that endpoint's
409 and does not exclude a second one; nothing there is contradicted and no criterion is
invalidated, and a fold into 7.5 is a human decision whenever one is next made. AC-343
asserts the behaviour.

Matching is case-insensitive equality and nothing more; no Gmail dot or plus
normalization. A stranded invite (address variant mismatch) is repaired by the inviter
through the visible pending list with cancel and resend. Multiple pending invites to one
email are all surfaced at login; each acceptance grants only its own folder; the
connection is created once. Creating a new assignment-invite for a task clears task_id on
any earlier pending invite for that task.

**Assumption: invites never expire.** Safe because acceptance is login-gated and the link
carries no secret. Revisit on any report of confusing stale grants; the change is a status
sweep plus an expiry display, with no schema change.
