### 7.23 The settings bundle

*Amendment to frozen section 7, written on 2026-09-04 for issue #152. **This
subsection records an endpoint that has shipped since RFC 0005 rather than
changing one**, which is the human decision the freeze asks for: the owner
ruled on #152 that a pair of routes the client has called from six sites since
RFC 0005, and which section 7 has never named, is a hole in the contract rather
than a new surface, so writing it down is a correction of the record. Nothing
here edits an existing subsection, no status, body or field moves, and no
criterion changes because of it. 7.22 was the last number and this is the next
one.*

The endpoint is `GET /api/v1/settings` and `PATCH /api/v1/settings`, the v2
bundle of 4.19 and 4.10. Until #142 annotated 7.2 on 2026-09-04, the only
description of it anywhere was 4.19's list of columns and the zod schemas in
`app/src/shared/bundle.ts`, and that annotation says in terms that writing the
endpoint up properly is separate work. This is that work.

## Its relationship to 7.2

**They are two endpoints and not two names for one.** Frozen 7.2 is
`/me/settings`, exactly the three v1 page flags `show_important`, `show_all`
and `show_done`, and it is untouched by everything below; AC-119 to AC-123 are
its and stay as written. This is `/settings`, the eight fields of the v2
bundle, and no field of one appears in the other. The two read one row of
`user_settings` and never one column of it — except through the pin derivation
below, which is the single place they meet and is written so that only ever one
of them is the record.

**7.2 is being retired by issue #113**, which folds the three flags into this
bundle and removes `/me/settings`. Nothing here anticipates that: this
subsection states what ships today, and the day #113 lands both this file and
7.2 gain a dated amendment saying so. Until then a v1 client meets only 7.2 and
a v2 client meets only this.

## The document

`GET` answers `200` with the whole object. `PATCH` takes **any subset of the
same eight fields, the empty subset included**, and answers `200` with the same
whole object read fresh afterwards — the fresh-GET convention 7.1 carries on
`PATCH /me`, 7.2 carries on `PATCH /me/settings` and 7.4 carries on each of its
mutations. There is no thinner subset-shaped answer and no `204`. A `PATCH`
carrying none of the eight is a read: it writes nothing, `updated_at` included.

Every field is present on every read. None of the eight is optional in the
answer and none is ever `null`.

## The fields

| Field | Type | Values | A fresh account reads |
| - | - | - | - |
| `theme` | string | `system`, `light`, `dark` | `system` |
| `row_density` | string | `comfortable`, `compact` | `comfortable` |
| `clock` | string | `12h`, `24h` | `12h` |
| `task_open` | string | `dialog`, `panel`, `tab` | `dialog` |
| `calendar_zoom` | string | `day`, `week`, `month` | `month` |
| `pinned_views` | array of string | the nine native view keys `desk`, `today`, `scheduled`, `assignments`, `important`, `all`, `done`, `abandoned`, `anytime`; at most nine entries as sent, duplicates tolerated | derived, see below |
| `sidebar_order` | array of string | uuids, at most 300 | `[]` |
| `arrangements` | object | uuid keys, string values of at most 40 characters | `{}` |

The defaults are the columns' own `DEFAULT`s in 4.10 rather than anything the
server supplies, `pinned_views` alone excepted: provisioning writes the row and
every value above arrives from the database. `task_open` reads `dialog` because
of migration `0010` and `calendar_zoom` reads `month` because of `0013`; both
are recorded in 4.19 and 4.10 and neither is restated as a decision here.

**`calendar_zoom` is read defensively and the other four enumerated fields are
not.** A stored value outside the three, which 4.10's CHECK makes unreachable,
reads back as `month`, on Imran's own ask at #140 that a retired zoom fall back
to the product default rather than stranding somebody on a grid this build
cannot draw. `theme`, `row_density`, `clock` and `task_open` have no such
fallback, deliberately: their values have never moved, nobody has asked, and a
defensive read added everywhere on the strength of one requirement is four more
places for a real wrong value to hide.

**Desk is locked pinned (9.7).** Whatever a write carries, the stored list
keeps `desk`, and a read of a list that somehow lacks it puts it back at the
front, because the place a task goes when you have not said where has to stay
reachable. So a `PATCH` naming `pinned_views: []` answers `["desk"]`, and that
is the endpoint keeping an invariant rather than ignoring the request.

**The cap is on what is sent, so the stored list can be one entry longer than
it, and this is recorded rather than fixed.** Nine is "every native view, and
no more", measured against the array the caller sends; the list is not checked
for duplicates, and `desk` is prepended when absent. A nine-entry list that
repeats a view and omits Desk therefore stores and reads back as ten. Two
reasons for writing it down instead of tightening it. #152 is a ruling to
record an endpoint that ships, and narrowing a write path is a change to one,
which wants its own ruling and its own criterion. And what the wart actually
costs is small: nothing draws a duplicate, the sidebar filtering its own page
list rather than the stored one, so the cost is a stored list that is not a
set. **A future change should dedupe on write** — one line in
`domain/bundle.ts`, where `desk` is already prepended — and when it lands this
paragraph becomes a dated amendment saying the stored list is at most nine.

## The pins before anybody has chosen

4.19 asks for the three v1 flags to become pins with "two records of one fact
are not kept", and names a migration as how. **What ships is a derivation and
not a migration, and the sentence 4.19 was protecting is what survives.**
`user_settings.pinned_views` is nullable and null means *never chosen*
(migration `0004`). While it is null, `GET /settings` derives the list from
9.1's fixed order — `desk`, `today`, `scheduled`, `assignments`, `important`,
`all` — with `important` dropped when `show_important` is false, `all` dropped
when `show_all` is false, and `done` appended when `show_done` is true. So a v1
account arrives with Done pinned and no data migration ran at all. The first
`PATCH` carrying `pinned_views` writes the column, and from then on the column
is the record and the three flags say nothing about this surface. At no moment
are two records authoritative for one reader, which is what 4.19 asked for; the
flags remain the record for 7.2's own three booleans either way, which is what
keeps AC-119 to AC-123 as written.

**This is the one thing in the bundle issue #113 has to carry across.** A fold
of the flags into this bundle that drops the derivation gives every account
that has never opened the Views section a different sidebar on the day it
deploys.

## Refusals

- `401` in the 7.0 envelope, on both methods, when there is no session, or when
  the session's account has been deleted (8.10). Session is the only
  authorization: like 7.22 the endpoint names nothing, the only identifier
  reaching the database is the session's user id, and there is no
  `accessOf(...)` gate because there is no caller-named resource to gate. A
  later field addressing another person's row would owe one.
- `403` in the envelope on `PATCH` with a session and no `X-CSRF-Token` (10.4).
  The session check precedes it, so an unauthenticated caller is never told a
  token was all they lacked.
- `400` in the envelope for a body that is not JSON, that parses to something
  other than an object, or that exceeds 10.3's 3 MB parse limit. AC-118's rule,
  reaching here as it reaches everywhere.
- **`422` in the envelope, `validation_failed`, naming the field**, for a value
  outside an enumeration, of the wrong type, or past a cap: a `theme` of
  `midnight`, a `calendar_zoom` outside the three, a `pinned_views` entry that
  is not one of the nine or a list longer than nine, a `sidebar_order` entry
  that is not a uuid or a list longer than 300, an `arrangements` value over 40
  characters. **Nothing is written**, the whole `PATCH` being one statement.
  This is 7.10's rule for an enumerated parameter applied to a body: absent and
  wrong are different states, and a wrong value is never quietly narrowed to
  the default.
- `429` with `Retry-After` when 10.4's general mutation quota is exceeded.
  `PATCH` is under it; `GET` is under no limit.
- `404` in the envelope for any other method. 7.23 names two.

A `500` is reachable on one path and it is an invariant violation rather than a
refusal: an account with no `user_settings` row breaks INV-14, and the read
says so rather than inventing defaults for a row that should exist.

## Unknown fields

7.0 tolerates a key nobody declared and 11.14 rules that no schema in
`app/src/shared/` becomes strict, so an undeclared key on `PATCH /settings` is
stripped and the request is processed as if it were absent. **It is not dropped
in silence.** Since issue #104 every route reads its body through `parseBody`,
which writes one warn-level `unknown_request_fields` line naming the route and
the undeclared key names and nothing the caller sent, so a client sending
`calender_zoom` is findable in the log rather than answered `200` and forgotten.

That covers a key this contract does not declare. **The loss it does not cover
is a field this file names that the route never reads**, which no strictness
and no unknown-key check can see — the class `app/src/shared/tasks.ts` records
as four packages long. Only a criterion catches that, and the one holding this
file honest is AC-409: **the fields table above, the request schema, the
response schema and the live `GET` body are one list, asserted equal.** A field
added to the bundle with no row here fails it, and a row here naming a field
the bundle does not serve fails it too.
