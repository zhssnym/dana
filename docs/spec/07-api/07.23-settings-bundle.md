### 7.23 The settings bundle

`GET /api/v1/settings` and `PATCH /api/v1/settings`: the person's settings
bundle of 4.19 and 4.10.

## The document

`GET` answers `200` with the whole object. `PATCH` takes **any subset of the
bundle's fields, the empty subset included**, and answers `200` with the whole
object read fresh afterwards — the fresh-GET convention 7.1 carries on
`PATCH /me` and 7.4 on each of its mutations. There is no thinner
subset-shaped answer and no `204`. A `PATCH` carrying none of the fields is a
read: it writes nothing, `updated_at` included.

Every field is present on every read, and none is ever `null`.

Fields, their values and caps: `patchSettingsBody` and `SettingsBundle` in
`app/src/shared/bundle.ts`. The defaults are the columns' own `DEFAULT`s in
4.10 rather than anything the server supplies, `pinned_views` alone excepted
(below).

**`calendar_zoom` is read defensively and the other enumerated fields are
not.** A stored value outside the enumeration, which 4.10's CHECK makes
unreachable, reads back as `month`, so that a retired zoom falls back to the
product default rather than stranding somebody on a grid this build cannot
draw. `theme`, `row_density`, `clock` and `task_open` have no such fallback:
a defensive read added everywhere is more places for a real wrong value to
hide.

**Desk is locked pinned (9.7).** Whatever a write carries, the stored list
keeps `desk`, and a read of a list that somehow lacks it puts it back at the
front, because the place a task goes when you have not said where has to stay
reachable. So a `PATCH` naming `pinned_views: []` answers `["desk"]`, and that
is the endpoint keeping an invariant rather than ignoring the request.

The `pinned_views` cap is on the array as sent, which is not checked for
duplicates, and `desk` is prepended when absent; so the stored list can be one
entry longer than the cap and need not be a set. Nothing draws a duplicate.

## The pins before anybody has chosen

`user_settings.pinned_views` is nullable and null means *never chosen*. While
it is null, `GET /settings` derives the list from 9.1's fixed order — `desk`,
`today`, `scheduled`, `assignments`, `important`, `all` — with `important`
dropped when `show_important` is false, `all` dropped when `show_all` is false,
and `done` appended when `show_done` is true. The first `PATCH` carrying
`pinned_views` writes the column, and from then on the column is the record
and the three flags say nothing about pins. At no moment are two records
authoritative for one reader (4.19). Dropping the derivation would give every
account that has never chosen its pins a different sidebar on the day it
deploys.

## Refusals

- `401` in the 7.0 envelope, on both methods, when there is no session, or when
  the session's account has been deleted (8.10). Session is the only
  authorization: like 7.22 the endpoint names nothing, the only identifier
  reaching the database is the session's user id, and there is no
  `accessOf(...)` gate because there is no caller-named resource to gate. A
  later field addressing another person's row would owe one.
- `403` in the envelope on `PATCH` with a session and no `X-CSRF-Token` (10.4).
  The session check precedes it, so an unauthenticated caller is never told a
  token was all they lacked.
- `400` in the envelope for a body that is not JSON, that parses to something
  other than an object, or that exceeds 10.3's parse limit.
- **`422` in the envelope, `validation_failed`, naming the field**, for a value
  outside an enumeration, of the wrong type, or past a cap. **Nothing is
  written**, the whole `PATCH` being one statement. This is 7.10's rule for an
  enumerated parameter applied to a body: absent and wrong are different
  states, and a wrong value is never quietly narrowed to the default.
- `429` with `Retry-After` when 10.4's general mutation quota is exceeded.
  `PATCH` is under it; `GET` is under no limit.
- `404` in the envelope for any other method.

A `500` is reachable on one path and it is an invariant violation rather than a
refusal: an account with no `user_settings` row breaks INV-14, and the read
says so rather than inventing defaults for a row that should exist.

## Unknown fields

7.0 tolerates a key nobody declared and 11.14 rules that no schema in
`app/src/shared/` becomes strict, so an undeclared key on `PATCH /settings` is
stripped and the request is processed as if it were absent. **It is not dropped
in silence**: `parseBody` writes one warn-level `unknown_request_fields` line
naming the route and the undeclared key names and nothing the caller sent, so a
client sending `calender_zoom` is findable in the log.

A declared field the route never reads is a loss no unknown-key check can see:
every field in `patchSettingsBody` must have a writer in
`app/src/server/domain/bundle.ts` and a reader in the `GET` answer.
