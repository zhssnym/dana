### 7.26 Labels

**Added 2026-09-20 by issue #226, on the technical ruling recorded there** (parent #208).
Thirteen routes over the M1 Label model of 4.24 to 4.27, in four groups: the definition
listing, Personal definition writes, Folder definition writes, and two idempotent assignment
pairs.

Purely additive as a *surface*: no existing endpoint, status or field changes. Two existing
read shapes gain a key each, and those two are named below rather than folded in silently.

**Shared shapes.**

`LabelDefinition` is `{ id, scope, name, color, description, archived, folder_id }` — what a
picker or the manage surface reads. `LabelRef` is `{ id, scope, name, color, archived,
folder_id }`, the compact reference a Task or Folder projection carries once per applied
Label per row; it drops `description` because a dense row renders a chip and never a
sentence, and a description on every chip of every card in a thousand-row list is bytes
nobody reads.

`scope` is `personal` or `folder`, and there is no third. `archived` is a boolean on the
wire where the row holds an instant: the instant is the server's bookkeeping, and exposing it
would invite a client to compute the state from it, which is a second definition of the same
fact. `folder_id` is present on both shapes and **null** for a Personal Label rather than
absent, so that a stable key set is read without narrowing a union. **Neither shape carries
`owner_user_id`**: a Personal definition a viewer can read is by construction their own, so
the field would be a constant, and a constant that happens to be an account id is a discovery
surface rather than information.

**The two projections.** A Task carries `labels: { personal: LabelRef[], folder: LabelRef[] }`
— the viewer's **own** Personal Labels and the Task's Folder Labels, and **never another
member's Personal Labels**, in `GET /tasks/:id` and in every list endpoint alike. A Folder
carries `personal_labels: LabelRef[]`, the viewer's own Personal Labels applied to that
Folder; there is no second array for Folder Labels, because a Folder Label classifies the
Tasks in its Folder and never the Folder itself (4.26). Both arrays are ordered active before
archived, then `lower(name)`, then `id`, in both producers.

**The status grammar, uniform across all thirteen** (5.4, 7.0, 10.2): 401 without a session;
**404 and never 403** for a Label, Task or Folder the viewer cannot see, so existence never
leaks; 422 naming the field for an invalid value; 422 naming the collection for a cap; 409
for a state conflict. Every mutation is CSRF-checked and rate limited as a general mutation.

**#208 left the uniqueness conflict open — "a controlled 409 or a field-addressed 422, choose
one convention and pin it with tests" — and this pins 409**, on all four doors: create and
rename, in both scopes. A name already held is the state of a catalog rather than a bad
value: the same string is valid in the next Folder along and in the viewer's own Personal
catalog, and it will be valid here the moment the Label holding it is renamed. The other 409
on this surface is applying an **archived** Label. Both leave the row untouched.

**Definitions.**

- **GET /labels.** 200 with `{ rows: LabelDefinition[], truncated }`, **capped at 1000 rows**
  — 10.3's standing rule for a list response, applied here because this listing's worst case
  is 500 Personal definitions plus 250 for every Folder the viewer belongs to. One cap across
  the whole response rather than one per scope, which is section 6's per-response reading;
  the kept rows are the first 1000 of the order below, and `truncated` is true exactly when a
  row was dropped, so a full page and a complete one are told apart without counting. The
  spelling is `getPlannedResponse`'s, the existing capped body with one section. Query
  `scope` (`personal` | `folder` | `all`, default `all`), `state` (`active` | `archived` |
  `all`, default `active`), and `folder_id` to narrow the Folder half to one Folder. 422
  naming the field for an invalid value. **404 for a `folder_id` the viewer cannot reach** —
  not 403 and not an empty 200.

  **This read `the bare array` when 7.26 was first written on 2026-09-20 and was amended the
  same day, before any client existed**, on the review finding that `listLabels` had no
  `LIMIT` and no flag while 10.3's table had carried the rule since v1. A bare array has
  nowhere to put a flag, so the cap and the shape are one change rather than two.

- **POST /labels/personal.** Body `{ name, color, description? }`. 201 with the definition.
  The viewer is the owner and there is no field for it, because an owner a caller could name
  is an owner a caller could get wrong. 409 on a duplicate name; 422 at the 500-definition
  cap.

- **PATCH /labels/personal/:labelId.** Any subset of `{ name, color, description }`; an
  absent field is left alone. 200 with the definition. 404 for another account's Label. 409
  on a duplicate name. **Archived state is not in this body** — it moves through the two
  endpoints below, so that "rename" and "retire" are two acts with two audit lines rather
  than one body that can do both by accident. **An archived Label may still be renamed,
  recoloured and described without being restored.**

- **POST /labels/personal/:labelId/archive** and **POST /labels/personal/:labelId/restore.**
  200 with the definition. 404 for another account's Label.

- **POST /folders/:folderId/labels**, **PATCH /folders/:folderId/labels/:labelId**, **POST
  /folders/:folderId/labels/:labelId/archive** and **POST
  /folders/:folderId/labels/:labelId/restore.** The same four over a Folder's catalog, with
  the same bodies, the same statuses and the 250-definition cap. 404 for a Folder the viewer
  is not a member of, and 404 for a Label that is not that Folder's — a Folder-B Label
  patched through Folder A resolves to nothing at all.

**Every current member may create, rename, recolour, describe, archive, restore, apply and
remove a Folder's Labels, with no owner exception.** That is #208's accepted R5A rule and it
is **interim by its own words**: #209 introduces explicit Responsibilities and Authorities
and may then distinguish managing Labels from applying them. Nothing here anticipates that
split, because a guess at it would be a rule to unpick rather than a rule to extend.

**Assignments.** Per-Label `PUT` and `DELETE` rather than a full-set `PATCH`, which #208 asks
for in those words: two members labelling the same Task at the same moment must not erase
each other, and a replacement body cannot carry the Personal assignments of the member who
did not send it without showing them to the one who did. Each is idempotent and each answers
200 with the refreshed Task or Folder.

- **PUT** and **DELETE /tasks/:taskId/labels/:labelId.** The Label may be one of the viewer's
  Personal Labels or one of the Task's Folder's Labels; 422 naming `label_id` otherwise, 404
  for a Task or a Personal Label the viewer cannot see, 409 for an archived Label on a `PUT`,
  422 at either 100-per-Task cap. The two caps are counted apart, and the refusal does not
  say which of them fired, because nothing a caller can do depends on knowing.

- **PUT** and **DELETE /folders/:folderId/labels/:labelId.** Personal Labels only, at the
  100-per-Folder cap.

**One wart, named here so the section carries it rather than leaving it to be rediscovered:
`/folders/:folderId/labels/:labelId` means two different things depending on the verb.**
`PATCH` edits the **Folder** Label with that id. `PUT` attaches the viewer's **Personal**
Label with that id to the Folder. The methods separate them cleanly and each refuses the
other's scope — a Personal id through the `PATCH` is 404, a Folder-Label id through the `PUT`
is 422 naming `label_id` — but `:labelId` does not denote the same thing across the two, and
a reader who assumes a path segment means one thing will be wrong about one of them.

**The one gate no structural sweep can see.** `ac-397` drives every route whose **path**
carries a parameter as a signed-in stranger, and twelve of these thirteen are in its table.
`GET /labels` is not: its Folder selector is in the **query string**, so no structural test
can drive it with a stranger's id. The gate is hand-written, it answers 404 rather than 403
for the reason above, and AC-473 is the only thing in the suite that asserts it. 10.2 records
it as the second standing example of that limit.

**The Shelf wire pair, recorded here because it is this release's other expand half.** 7.4's
`PATCH /folders/:id/my-membership` body and 7.0's Folder object each carry two spellings of
one fact for this release — `shelf` beside `label`, and `my_shelf` beside `my_label` — for
the reason 7.4's annotation gives. **Issue #247 is the contract half** and drops both old
spellings together with `folder_members.label` (4.4), after migration 0022 is live in
production.
