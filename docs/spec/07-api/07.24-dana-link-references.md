### 7.24 Dana Link references

A **Dana Link** is an ordinary internal URL to a Task, a Folder, a Shelf or a supported Facet, persisted
as a rich-content href and resolved live. It is a navigation aid: it is never a
dependency, a permission grant, an Authority grant, a membership grant, a copy or a
workflow relation, and resolving one creates nothing. **No table stores links** — a
Dana Link's durable form is the href a rich-content block already holds, and this
section resolves it rather than recording it.

**Supported targets and their client routes.** Task `/app/tasks/:id`, Folder
`/app/folders/:id`, Shelf `/app/shelves/:id`, and Facet `/app/facets/:id`. The only
Facet kind admitted by the resolver and search is the native **Purpose** facet. Results,
Consultation, private and custom facets, and individual Purpose blocks are not reference
targets. The set is closed. A further kind becomes
referenceable only when it has a stable id and a stable client route, which is the
property this section turns on rather than a matter of taste.

**The reference summary.** Every answer below is one or more objects of exactly `kind`,
`id`, `label` (the target's own title or name, as that target's own read answers it) and
`path` (the canonical internal path), and no others: `referenceSummary` in
`app/src/shared/references.ts`. No folder, assignee, date, status, member count or any
other metadata rides a summary. A chip draws a label and navigates; it is not a
projection of the thing it points at.

- **GET /api/v1/references/:kind/:id.** Resolve one target. Requires a session. A
  `:kind` outside the supported set, an `:id` that is not a uuid, a target that does not
  exist and a target the viewer may not read **all answer 404 `not_found` with an
  identical body**: never 403, and never anything naming the row. A target the viewer
  may read answers 200 with the reference summary. Access resolves through exactly the
  reads that already govern the kind — a Task through its folder's membership, a Folder
  through its membership, a Shelf through its owner, a Purpose facet through its Folder membership — which is what makes "a link grants
  nothing" a property of the code rather than a promise.

- **GET /api/v1/references/search.** The picker's read. Requires a session. Query
  parameters (`referenceSearchQuery`): `q`, required, with 7.10's own length rule
  reused rather than a second one; `folder`, optional, a uuid naming the Folder the
  person is composing in. Answers 200 with `results`, capped at `REFERENCE_SEARCH_LIMIT`
  **across every kind together**. When `folder` is supplied, that Folder's
  matching Tasks lead and matches elsewhere follow: **the context is a priority and not
  a filter.** Matching is on title and name only — a match on a field the picker row
  does not draw reads as a bug. Results never include a target the viewer cannot access.
  A malformed `q`, or a `folder` that is not a uuid, answers 422 `validation_failed`
  naming the field; **a `folder` the viewer is not a member of answers 404 `not_found`**,
  identically to a folder id that names nothing. The endpoint carries 10.4's search
  limit, sharing the bucket with `GET /search`, whose contract (7.10, 7.18) this
  section deliberately does not widen.

**One visibility rule across both doors, and it is the point of the section.** An exact
URL paste and a typed search resolve through the same authorization path and must reach
the same verdict about the same row. An inaccessible target is indistinguishable from a
nonexistent one at both.

**The `folder` query parameter needs its own gate.** It arrives on the query string,
where a sweep over path parameters cannot see it. Without the 404 above nothing leaks
row data — the join returns no rows either way — but a caller would learn the difference
between a folder with no matches and a folder they cannot see, which is the distinction
this section exists to remove.

**Three exclusions, so that a later reader does not read them as oversights.** There is
no cursor and no paging: a picker's answer to "not here" is another keystroke. There is
no `kinds` filter and no `limit` parameter, for no caller needs one. And 10.4 does not move,
because the picker shares the existing search bucket rather than opening a second one.


#### Purpose references

Purpose is the first facet-level Dana Link target. Its **facet id** is the durable target:
renaming Purpose changes the resolved `label` but not the id/path, and hiding Purpose does
not revoke a reference because hide is presentation state rather than access state. Exact
resolution and picker search both require current Folder membership and treat an
inaccessible Purpose exactly like a missing target. Resolving or searching creates no
membership, Access, Authority, dependency, event or relationship row.

Search matches the live resolved Purpose name (`display_name ?? "Purpose"`). A contextual
Folder still prioritizes its matching results without becoming a filter. Individual Purpose
blocks are not referenceable; adding them would require their own stable navigation
contract rather than reusing the facet path.
