### 7.13 Trash

GET /api/v1/trash — the caller's reachable deleted tasks and folders inside
the 30-day window. POST /api/v1/tasks/:id/restore ·
POST /api/v1/folders/:id/restore — access by folder membership, not by who
deleted. DELETE of a task or folder sets deleted_at (soft); purge is the
tick's, at 30 days, permanent.

DELETE /api/v1/trash/tasks/:id · DELETE /api/v1/trash/folders/:id — the
permanent delete (RFC 0005 change control items 36 and 38): destroys a
trashed row now, exactly as the 11.7 purge would at thirty days, through the
purge's own collection rather than a delete beside it. Only a row in Trash
qualifies; a live row is 404, the live delete being the soft one above. The
act is the folder owner's alone, for a task as for a folder: a member who is
not the owner is answered 403, the row being visible to them, and a
non-member 404 (10.2). The cascades fire at once: a folder's tasks,
conversations, page blocks, memberships, events and files rows; a task's
steps, reminders, My Day entries, comments, and the files that hung on its
conversation and on nothing else. Every collected file's bytes leave the
store after the transaction commits, 7.15's order. 204 with no body; a
task's destruction is recorded as a `deleted` event against its folder, a
folder's is not, its events going with it.

**7.16's duplicate line, annotated by the same row.** A task's duplicate
(`POST /api/v1/tasks/:id/duplicate`) carries the title, the notes, the
importance, the section, the steps with every step undone, the due date and
the repeat, and never the conversation, the completion or the assignment;
the copy is assigned to and created by whoever made it. A spent due date
re-anchors on today and a future one keeps, 9.6's rule for a folder read
onto one task. 201 with the new TaskDetail; member access on the source,
404 otherwise.

**7.16's folder duplicate, annotated by the loose-ends row.** POST
/folders/:id/duplicate answers `{ id, name, shifted_days }`: the number of
days the plan moved when its earliest date was spent, 0 when every date
kept. The copy's `duplicated` event carries "dates moved to start today"
exactly when it is positive, which is the fact 9.6's bar reads (ledger
L-055). (Append unit of RFC 0005 change control item 58, E, ruled by
delegation 2026-08-30 and folded here the same day.)

---

**"The act is the folder owner's alone, for a task as for a folder" is false,
and this is the correction (2026-09-20, issue #268).** It has been false since
#228's R8A landed: the two routes were moved onto the Access resolver and this
section was not. A frozen section whose text is false is worse than one that
is merely incomplete, because the freeze exists so that the text can be
trusted.

**Two bullets follow and they rest on different records, which the first
draft of this amendment got wrong and is corrected here.** That draft said
"this is not a new ruling and does not ask for one" of both, and it is true
only of the first: correcting a sentence the accepted model had already
falsified is a transcription, and **putting a new field on a frozen response
shape is a decision somebody has to make.** An amendment that describes its
own authority wrongly is the failure the freeze exists to prevent, whichever
direction it errs in.

- **The first bullet is a transcription**, under the correction 7.4 and 7.14
  already carry and the same two records: Hassan's ruling of 2026-09-20
  requiring the frozen text to be brought into line with the accepted model,
  https://github.com/zhssnym/dana/issues/228#issuecomment-5751449643, and his
  ruling of the same date that made the changes,
  https://github.com/zhssnym/dana/issues/228#issuecomment-5750892771. The
  authority for the rules themselves is **#228's Full-control list**, whose
  stated canonical authority is accepted #209 R8A and R10B, with **governing
  R5** for the custody half.
- **The second is a decision, and it has its own ruling**: the **owner's
  technical ruling on issue #268, 2026-09-20**, which is what admits
  `my_access` to this section's response shape.

- **The two permanent deletes are no longer one rule, and the sentence above
  is wrong to say "for a task as for a folder".** `DELETE
  /api/v1/trash/tasks/:id` is **Full control, with ownership ignored**:
  permanently deleting a Task from Trash is an irreversible administrative
  act, and a Full-control member who owns nothing performs it while an owner
  below Full control does not. `DELETE /api/v1/trash/folders/:id` is **Full
  control *and* the owner together**, governing R5 keeping permanent
  destruction of the whole Folder with custody, so it is strictly the narrower
  of the two. Everything else about both endpoints is unchanged: only a row in
  Trash qualifies, a live row is 404, a non-member is 404 and somebody below
  the bar is 403, the cascades and the file-store ordering stand, and both
  answer 204. (AC-397, AC-790.)
- **A `GET /api/v1/trash` row carries `my_access` beside `is_owner`**, on both
  the task and the folder arrays. Authority: **the owner's technical ruling on
  issue #268, 2026-09-20**. It is the **viewer's own** Access preset for the
  folder the row belongs to, one of R8A's six, **required and non-nullable**,
  and **refused rather than defaulted** on read, every default here being a
  guess about authority. A Trash row exists only for a member — which is what
  the `folder_members` join behind this read means — so there is no row for
  which it is absent. It is the same field the 7.4 Folder object gained under
  Hassan's Ruling 4 and it is here for the same reason: **a trashed folder is
  not in `GET /folders`, so the preset has to travel with the row.** The
  addition is additive — `is_owner` keeps its name, its meaning and its
  place, because `folder.destroy` still reads it — and both fields are needed,
  neither answering alone, which is the whole content of the bullet above.

**The alternatives, considered and declined by the same ruling.** A
server-computed `purgeable` verb on each row; a per-row detail fetch to ask
the question when the screen needs it; and simply not offering purge below the
bar without the screen knowing where the bar is. The first is the one worth
naming a reason for: **7.11 admits "client conveniences with no authority,
each shadowed by a server rule", and that is what this is** — the screen's
answer is drawn from `my_access` and the refusal is still the route's, so
nothing here becomes a rule found only in the client, which 7.11 calls a
specification violation in terms. A per-row verb would have put one
endpoint's answer to one question on the wire, where the next surface asking a
different question of the same folder needs a second. `my_access` is the fact;
`lib/folder-authority.ts` answers the questions, from the same table the
routes resolve against.
