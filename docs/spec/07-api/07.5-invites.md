### 7.5 Invites

- POST /invites. { email, folder_id optional, task_id optional }. Validations V-INV
  (section 8.7): lowercase and syntax-check email (422), reject own email (422), reject
  default folder (409), reject when target of a folder invite is already a member (409
  "already a member"), reject task_id without folder_id or task not in folder (422),
  convert to instant share when the email belongs to a roster connection of V (response
  200 { converted_to_share: true, membership created }), dedupe against INV-11 (409 with
  existing invite id). Rate limits in 10.4. Sends one email. 201 { invite }. - GET
  /invites/sent. V's invites, newest first, any status. - GET /invites/pending. Invites
  addressed to V's email with status pending: [{id, inviter: {display_name, avatar_url},
  folder_name or null, created_at}]. Backs the login surface. - POST /invites/:id/accept.
  Matched recipient only (404 otherwise, not 403, per the leak rule). Runs the acceptance
  transaction (section 8.7). 200 { connection_created, folder or null, assigned_task_id or
  null }. - POST /invites/:id/decline. Matched recipient only. 200. - POST
  /invites/:id/cancel. Inviter or attached folder's owner. 200. - POST
  /invites/:id/resend. Inviter only; 429 within 24 hours of last_sent_at. 200. All five
  transition endpoints: 409 when the invite is not pending. Invariants: INV-9, INV-11.

The bare invite to an existing connection, escalated at P5's mid-package change control
and entered by owner ruling on 2026-08-09: POST /invites answers 409 "already connected"
when the email belongs to a roster connection of V and no folder is attached, and creates
nothing. The conversion clause in the bullet above is therefore folder-conditional, and is
written that way in V-INV; the instant share it describes creates a membership, only a
folder defines one, and the clause had stated its connected-email condition without naming
a folder, so the bare case had no specified outcome at all. This paragraph carries the
rule rather than the bullet being rewritten, the shape 7.2 and 7.4 took for the same
reason: the bullet text that rulings and tests already quote stays byte-identical.

The refusal is symmetrical with the 409 this section already enumerates one clause
earlier, for a folder invite whose target is already a member. Each answers a request
whose whole purpose already holds, membership there and connection here. Two alternatives
were before the owner and were not taken. Answering 200 with nothing created would
introduce a third outcome for this endpoint, where 5.2's create row either parks an invite
with one email sent or refuses, and it is the one answer the inviter cannot read: nothing
enters the pending list that 8.7 makes visible precisely so a stranded invite can be
repaired, and the roster already held the person, so a sent invite and a no-op look
identical. Falling through to the ordinary 201 would park a row whose acceptance is an
idempotent no-op under INV-9, mail "invited you to connect" to somebody already connected,
and surface it through Q12 at their next login. The principle separating this from the
10.3 cap ruled at the same package's kickoff, where an invite against a full folder still
parks: refuse when the request can accomplish nothing, permit when it can accomplish
something later, since a parked invite becomes acceptable the moment a member leaves while
a bare invite to a connected person can never become anything.

The refusal of an acceptance into a folder sitting in Trash, escalated at the work on issue
#28 and entered by owner ruling on 2026-09-03: POST /invites/:id/accept answers 409 with the
code `folder_deleted` when the invite names a folder whose deleted_at is set, and the whole
acceptance transaction rolls back, so the invite stays pending, no membership is granted, and
the connection the transaction's first statement would have minted is not written either.
Restoring the folder inside its thirty days makes the same invite acceptable again with
nothing else repaired and nobody to tell. This paragraph carries the rule rather than the
bullet being rewritten, the shape the bare invite above took and 7.2 and 7.4 before it: the
bullet text that rulings and tests already quote stays byte-identical, and its sentence "All
five transition endpoints: 409 when the invite is not pending" enumerates that endpoint's 409
without excluding a second one.

Nothing had specified this and the behaviour was accidental. Folder deletion used to destroy
the folder's pending invites in the same statement; RFC 0005 made deletion soft, so the
cascade moved to the 30-day purge of 8.8 and left a window in which the invite is pending and
the folder it names is in Trash. In that window the acceptance succeeded and granted a
membership on a folder that leaves every query but the Trash surface at once, which the
acceptor could not open and could not tell why. Refusing is the answer a restore repairs by
itself; cancelling at deletion time, which is what account deletion does to the invites it
sent (8.10), would lose exactly that. The code is its own because a client has three
sentences to say here and only the code tells them apart: 404 for an invite that is not the
caller's, 409 `conflict` for one already settled, and 409 `folder_deleted` for one that is
still good against a folder that is not; 7.0 provides for it in the words "409's rule
conflicts gain their specific codes as the section 5 tables land". The guard is about the
folder rather than about the membership, so it is checked even when the acceptor is already a
member and the grant would be a no-op: the response carries the folder, and would otherwise
hand a client a folder it cannot open. 8.7 carries the whole of the reasoning and the lock
the check takes, and 5.2's accept row carries the state guard. AC-343 states the behaviour,
as a decision rather than as a proof: its test file went in the 2026-09-20 cut.

Response shapes, settled at the P5 shape review and entered by owner ruling on 2026-08-10,
the same way 7.4's four shape sentences were entered at P2. This section names four
objects without enumerating them, and each is settled below against the route that answers
it.

The object inside 201 { invite } and the element of GET /invites/sent are one object: {
id, email, folder_id, folder_name, task_id, status, created_at, last_sent_at, responded_at
}. The rows GET /invites/sent lists are the rows POST /invites creates, and this section's
own "any status" for that list is only meaningful if status is a field of them. It is four
fields wider than 7.4's pending_invites element, which is not a divergence between the
two: the folder detail's list is scoped to one folder and to pending rows, where
folder_id, folder_name, status and responded_at would each be constant. accepted_by is
deliberately absent, being a bare user id this surface offers no person shape to render.

POST /invites/:id/decline, /cancel and /resend each answer that same object in that same
wrapper, { invite }. This section gives each of them "200." and no body, so the convention
decides: a mutation answers what a fresh GET would, as PATCH /me does in 7.1, PATCH
/me/settings in 7.2, and each 7.4 mutation, and the fresh read of a settled invite is the
sent-list element.

The conversion answers 200 { converted_to_share: true, membership }, the membership being
the member element of 7.4, which is what POST /folders/:id/members answers. The conversion
is 8.7's grant and so is that endpoint, so one concept answers one object; the second half
of this section's "membership created" is the effect, and membership is the key that
reports it.

The folder inside the acceptance response is the full Folder object of 7.0, what a fresh
GET would give, and null when no folder was granted. This is 7.4's reading and
deliberately not the {id, name, is_default} stub ruled for 7.10's grouped views on
2026-08-07, and the two rulings do not conflict because they answer different questions.
That one reasoned that a group heading needs what a card's folder label needs, and that
Folder's counts, is_owner, member_count, my_label and my_color are 7.4's business where a
client that wants them already goes. An acceptance is not a heading. It is the moment a
client acquires a folder it did not have, and those five are exactly what it then needs
and has no other way to learn from this response, so the stub would force a second request
for a folder the client learned about one line earlier. Neither reading generalizes to the
other surface.
