### 7.15 Files

POST /api/v1/files (multipart; kind; folder scope; quota- and rate-limited;
images downscaled server-side) · GET /api/v1/files/:id (authenticated
serving) · DELETE /api/v1/files/:id (uploader or folder owner). Avatar: POST
/api/v1/me/avatar updates users.avatar_url to the stored object.

The upload's 201 answers `{ id, bytes, width, height }` (added 2026-09-03 by
issue #27, migration 0009). The downscale is the moment the shape is known, so
it is the moment it is recorded: the numbers are read off the same sharp pass
that performs the re-encode and the 2048px bound, and they describe the object
the store now holds rather than the payload that arrived. Null for every kind
that does not pass through that re-encode — a voice note, a plain attachment —
and never a guess. It is not for the uploader, who is holding the file and
knows. The photo tier's `POST /api/v1/folders/:id/cover/photo` answers the
same four for the same reason and with more force: that caller never held the
bytes at all, the server having fetched them from the upstream's own record,
so the response is the only thing that can tell it what was stored.

Avatar removal (added at the polish round of 2026-08-30, the owner having
waived this section's freeze for that round in his own words): DELETE
/api/v1/me/avatar sets users.avatar_url to null and deletes the caller's
stored avatar row and its bytes with it. 204, no body, idempotent — a second
call on a person who has no picture is the same act and not a 404. Session
and CSRF as the POST, under 10.4's general mutation limit. The file row goes
rather than staying because POST already deletes the picture it replaces, one
avatar being the shape of the feature and the quota's reason (10.3's 1 GB): a
removal that kept the row would spend an account's quota on bytes nothing
points at and leave them on a serving path that still answers. This closes
RFC 0005 change control item 55(f)'s first case, the Settings picture row's
Remove control, which the client drew absent under DES-144 for want of
exactly this route.

The photo tier (added at the polish round of 2026-08-30, the owner having
waived this section's freeze for that round in his own words; the reasoning
is `routes/cover-photos.ts`'s header): GET /api/v1/covers/photos?q= proxies
the Openverse search, each result's thumb rewritten to
GET /api/v1/covers/photos/:id/thumb, which streams that thumbnail from this
origin so 10.8's img-src never widens · POST /api/v1/folders/:id/cover/photo
{ photo_id } fetches the photograph server-side from the upstream's own
record for that uuid — never from a client-supplied URL — and lands it
through the same createFile as an upload: same membership check, same
downscale, same quota and 413. The client then PATCHes cover_file_id exactly
as after an upload, so the stored cover is this origin's file and 10.6's
precache objection does not arise.

**Amendment, 2026-09-03, issues #20 and #100 (migration 0012), on Imran's ruling that every
page kind gets the same cover options and that pictures belong to the person rather than to a
folder; the owner directed the work.** Three changes, and the third is the one with teeth.

**`folder_id` is optional for `kind: cover` and required for every other kind.** A shelf and
a built-in place page are not folders, so a cover has to be storable without one; a page
image, a comment attachment and a voice note keep the folder that is their visibility scope.
The refusal for a missing `folder_id` on those kinds is 422 naming the field, as it was
before, rather than the 404 an unreachable folder gets: an absent part is a malformed
request and not a scope failure. A `cover` that *does* name a folder is unchanged in every
respect, membership check included, and remains the only shape a folder's own shared cover
can take.

**POST /api/v1/covers/photo { photo_id }** is the photo tier's folder-less arm, the same act
as `POST /api/v1/folders/:id/cover/photo` with no folder to name in the URL: the upstream
record is fetched server-side for that uuid, never from a client-supplied URL, and the bytes
go through the same `createFile`, downscale, quota and 413. It answers the same
`{ id, bytes, width, height }`. It carries no `accessOf` gate and that is not an omission —
there is no object whose visibility is in question, the act creating a row owned by the
caller and spending the caller's own quota, which is `POST /me/avatar`'s shape.

**Serving is narrower than it was, and the narrowing is what makes the ruling safe.** GET
/api/v1/files/:id answers a folder-scoped file to its folder's members, an **avatar** to any
signed-in account (unchanged: a member list renders other people's pictures), and **every
other folder-less file to its owner alone**. The old predicate said only "no folder means
everyone", which was true while avatars were the only folder-less rows and fails open the
moment a person can upload a cover of their own; measured before the change, a second
account's request for a folder-less `cover` row answered 200. The same predicate now decides
which `file_id` a cover may name, in 7.16's shelf PATCH and 7.19's place-cover PUT alike, so
a stored cover can never point at bytes its wearer would be refused. **Beside a `kind` in
(`cover`, `image`) clause in each, and the avatar arm above is why that clause is not
decoration**: the predicate alone admits every avatar to every account, so a page gated on it
alone would let a person wear another person's face, and would take a `voice` note's id and
draw it as a broken image. AC-370, AC-371 and AC-374 state all of it, as decisions rather
than as proofs: every one of the three lost its test file in the 2026-09-20 cut.

**Amendment, 2026-09-04, issue #167, on the owner's ruling that a picture on a shelf page is
in the position a cover was before the amendment above: it belongs to the person and to no
folder.** One change, and it is one clause of the 2026-09-03 amendment widened.

**`folder_id` is optional for `kind: image` as well as `kind: cover`, and required for
`file` and `voice`.** The reasoning is the ruling above's, applied to the same page. A shelf
is private (4.18) and is not a folder, so a shelf page's blocks have no folder either — 4.17
gives a block one home and a shelf page's home is the shelf — and an image block there had no
folder to name. The upload answered 422, so a person who chose a picture on a shelf page saw
nothing happen at all. **The reach of that today is narrower than issue #167 says and the
correction is recorded rather than made quietly**: the issue reads "a shelf page's composer
offers Image", and it does not — `screens/shelf-page.tsx` passes its insert line a section
and a paragraph and no image — so the only way in is an image block that already exists,
through its own chooser. That is why nobody has lost a picture, and it is not a reason to
leave the endpoint refusing one: the block, the write and the gate are all in place, and a
composer that offers the tool is a client change against a server that now answers. A
folder-less image is **owned by the uploader**, served to that account alone by the predicate
below (the avatar arm is untouched, and it is `kind`-blind, so no widening was needed there),
and **nameable by a block only where the page's own gate admits it**: 7.16's shelf-homed
clause scopes with that same predicate, while a folder page's clause requires the file to be
*of that folder*, so a folder-homed block cannot name one of these. `file` and `voice` keep
requiring a folder, a comment's attachment and a voice note hanging on a thread that lives in
one, and the 422 for those two names the new rule — "folder_id ... is required for a file or
a voice note" — rather than the old one. Migration 0015 widens
`files_folderless_kind_check` to match, under its own name, so the schema goes on stating the
rule the server enforces. **The lifetime of one of these files is 7.19's**, on the same
sentence as a cover's: unreferenced for thirty days and the tick reclaims it, so an image
dropped from a shelf page does not spend its owner's quota forever. AC-413 states all of it
and is a decision rather than a proof — its test file went in the 2026-09-20 cut, and the reclaim
sweep it belongs to is untested in every one of its five arms (7.19).

**Amendment, 2026-09-04, issue #74, on the owner's ruling: the delete's refusal to a member
who can read the file is 403 and no longer 404.** DELETE /api/v1/files/:id is still "uploader
or folder owner" — **the rule has not moved and nobody who was refused is now admitted, nor
the reverse** — and what has moved is which refusal the caller hears. 10.2 draws the line by
visibility rather than by ownership: inaccessible resources answer 404 to avoid an existence
leak, and permitted-visibility-but-forbidden-action answers 403. A member of the folder reads
the very same bytes at 200 through the GET above, so a 404 was protecting an existence that
the endpoint next door had already disclosed. A caller outside the folder still gets 404,
which is the clause that was always doing real work. `DELETE /api/v1/comments/:id` is the
same shape on the same surface and has always answered 403 for it.

**And it is not only a member of the folder, which is worth saying plainly because the
sentence above would not lead anyone to expect it.** Readability here is the serving
predicate, and that predicate admits **every avatar to every signed-in account** by design,
so `DELETE /api/v1/files/:id` aimed at anybody's avatar now answers 403 to a complete
stranger where it answered 404. That is the same rule applied honestly rather than a second
decision: the caller can fetch those bytes at 200 (AC-371), so a 404 would be denying the
existence of a file the endpoint next door hands over. Nothing new is disclosed and nothing
new is permitted — the avatar's owner is still the only account that can delete it, through
this route or through `DELETE /api/v1/me/avatar`. AC-398 asserts this arm beside the
member's.

**Ruled a correction toward the contract rather than a change to it**, which is why it lands
inside this section's freeze: 7.15 named the actors and never named a status, 10.2 named the
status, and the two disagreed only in the code. It was found by AC-397's authorization sweep,
which drove one caller's `GET` at 200 and `DELETE` at 404 on one file and had no way to call
that anything but a defect. AC-398 asserts the pair directly, and asserts the two permitted
arms with it, because a refusal widened over the uploader and the folder owner would satisfy
the sweep completely.
