### 7.15 Files

POST /api/v1/files (multipart; kind; folder scope; quota- and rate-limited; images
downscaled server-side) · GET /api/v1/files/:id (authenticated serving) · DELETE
/api/v1/files/:id · POST /api/v1/me/avatar · DELETE /api/v1/me/avatar. Response shapes,
the kinds an upload may declare, the folder-less kinds and the MIME allowlists:
`app/src/shared/files.ts`.

**Upload.** The 201 answers the stored object's `bytes`, `width` and `height` beside its id.
The dimensions are read off the same pass that re-encodes and bounds the image, so they
describe what the store now holds rather than the payload that arrived; they are null for
every kind that is not re-encoded, never a guess. A size or MIME failure is 422 naming the
field; the 1 GB quota alone is 413 `quota_exceeded` (10.3).

**`folder_id` is required for `voice` and optional for every other uploadable kind.** A
voice note hangs on a comment thread, and a thread lives in a folder. Every other asset
takes its page's scope, and not every page is a folder: a shelf is private (4.18) and a
built-in place page has none. A missing `folder_id` on a voice note is 422 naming the field,
not 404, an absent part being a malformed request rather than a scope failure. A file that
does name a folder is checked against membership as always. **A folder-less file is its
uploader's alone.** `avatar` is never declared on this route; it has its own. Consequence: a
folder-less `file` cannot then be attached to a comment, which resolves attachments inside a
folder; that is a 422 at attach time, and 7.19's sweep reclaims the file once nothing
references it.

**Audio and video are validated at the container and fail closed.** Each accepts a named
allowlist of types a current browser plays unaided, checked as the declared type against
the list **plus** a container-signature read of the leading bytes, never a filename or
extension. It is container validation, not codec validation: no media-probing subsystem is
used. QuickTime is deliberately absent, playing in some browsers and not others. A payload
off either list is 422, and the sentence says the same bytes upload as `kind=file` and are
offered for download: refusing to preview something is cheap, claiming playback that does
not work is not. `file` accepts any type; its safety is in how it is served.

**Serving scope.** GET /api/v1/files/:id answers a folder-scoped file to its folder's
members, an **avatar** to any signed-in account (a member list renders other people's
pictures), and every other folder-less file to its owner alone. The same predicate
(`readableFileScope` in `app/src/server/domain/files.ts`) decides which `file_id` a cover
may name in 7.16's shelf PATCH and 7.19's place-cover PUT, **together with a clause
requiring `kind` in (`cover`, `image`)**: the predicate alone admits every avatar to every
account, so a page gated on it alone would let a person wear another person's face, or draw
a voice note as a broken image.

**Serving disposition is an allowlist.** `image`, `cover`, `avatar`, `voice`, `audio` and
`video` are served inline, every one validated on the way in. **`file` is served
`Content-Disposition: attachment` with `X-Content-Type-Options: nosniff`, always and for
every type**, which is what makes "Dana never executes an uploaded file" true. An allowlist
rather than a denylist, because a denylist hands any kind added later an inline disposition
on this origin by default. SVG must stay out of the raster set: it decodes like an image and
serves like a document, and a scriptable document on this origin is a session walking out
the door.

**Delete.** DELETE /api/v1/files/:id is the uploader or the folder owner. A caller who can
read the file (by the serving predicate above) and is not permitted is 403; a caller who
cannot read it is 404 (10.2). The 403 reaches every signed-in account for an avatar, which
every account reads: a 404 there would deny the existence of bytes the next endpoint hands
over. Only the avatar's owner can delete it, here or through DELETE /api/v1/me/avatar.

**Avatar.** POST /api/v1/me/avatar stores the picture as a file of kind `avatar`, points
`users.avatar_url` at it, and deletes the picture it replaces: one avatar is the shape of
the feature and the quota's reason. DELETE /api/v1/me/avatar sets `avatar_url` to null and
deletes the avatar row and its bytes; 204, idempotent (a second call on a person with no
picture is the same act, not a 404), session and CSRF as the POST, under 10.4's general
mutation limit. The row goes rather than staying because a kept row would spend quota on
bytes nothing points at, on a serving path that still answers.

**The photo tier.** GET /api/v1/covers/photos?q= proxies the Openverse search, each
result's thumb rewritten to GET /api/v1/covers/photos/:id/thumb, which streams it from this
origin so 10.8's img-src never widens. POST /api/v1/folders/:id/cover/photo { photo_id }
and its folder-less arm POST /api/v1/covers/photo { photo_id } fetch the photograph
server-side from the upstream's own record for that uuid — **never from a client-supplied
URL** — and land it through the same `createFile` as an upload: same downscale, same quota
and 413, same answer shape. The folder arm carries the upload's membership check; the
folder-less arm has no access gate, because it creates a row owned by the caller and spends
the caller's own quota, `POST /me/avatar`'s shape. The client then sets the cover exactly as
after an upload, so a stored cover is always this origin's file and 10.6's precache
objection does not arise. An upstream failure is 502.

The lifetime of a folder-less `cover`, `image`, `file`, `audio` or `video` is 7.19's.
