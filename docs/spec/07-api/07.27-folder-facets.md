### 7.27 Folder facets

**Added 2026-09-21 by issue #210 (M1-F), on Hassan's technical ruling**
https://github.com/zhssnym/dana/issues/210#issuecomment-5756722756 **(section 3).**
Product authority: #210 as written, plus the Frontend → Backend Handoff of the same day.
Authorization authority: accepted #209 R8A through #228's table. **Purely additive**: no
existing endpoint, response, status or refusal moves.

The data model is 4.30 and the document store is 4.17 as amended the same day.

## The refusal order, everywhere on this surface

**404 → 422 → 403 → 409.**

**Existence first** (10.2), so a refusal never confirms that a Folder exists: a person who is
not a member of the Folder is answered 404 whatever their body said. **Then the body**,
because an authority refusal must be able to name what it refused — "you may not create a
Work facet here" and "you may not create a facet at all" are different sentences, and
`facet.create`'s private-facet arm depends on *which kind* was asked for, so the gate cannot
be asked before the body is known. **Then the preset**, which is `mayPerform`'s. **Then
state**, which is meaningful only on a body already valid and an actor already permitted.

## The Facet object

```
Facet = {
  id, kind, name, display_name, hidden, private, owner_id, position,
  h1_block_id, updated_at
}
```

`kind` is one of 4.30's seven. `name` is **server-resolved and never stored**: fixed for Main
and Consultation, `display_name ?? default` for Purpose and Results, **the H1 block's text for
a Work facet**, and `display_name` for a blank. `display_name` is the stored override or null,
and null on Purpose and Results means "the default name" — it is sent beside `name` because it
is the only field that tells a client whether Reset does anything. `private` is a projection of
`owner_id` and the two cannot disagree (4.30's `folder_facets_owner_kind_check`); both are
sent, because a client drawing the privacy treatment should not have to know that equivalence
and a client deciding whether to offer Share needs the id. `updated_at` is 7.0's stale-write
token.

## The routes

**GET /folders/:id/facets** — any member (`folder.read`). `{ facets: Facet[] }` in effective
order: **Main first**, then the natives and shared facets by `position`, with the caller's own
private facets interleaved by theirs. Hidden natives are carried with `hidden: true`, so
Restore can be drawn. A non-member is 404. **Another member's private facets are absent**, by a
clause inside the query's own `FROM`, so the list is not a filtered read that somebody had to
remember to filter.

**POST /folders/:id/facets** — `{ kind, h1_block_id?, display_name?, after_facet_id? }`, 201
Facet. 422 for a native kind, for `h1_block_id` present off `work` or absent on it, for a
missing blank name, and for a block that is not a **depth-1 Section of this Folder's own page**.
403 `facet.create`. **409 when that H1 already carries a live Work facet**, which 4.30's partial
unique index enforces in the same transaction rather than a read followed by a write.
`after_facet_id` places the new facet after a facet the caller can see; absent, it appends.

**PATCH /folders/:id/facets/:facetId** — `{ display_name?, hidden?, updated_at? }`, 200 Facet.
`display_name` is `facet.rename` and `hidden` is `facet.hide`, and a patch carrying both must
satisfy both. `display_name: null` on Purpose or Results is **Reset**; on a blank facet it is
422, its name being required; on Main, Consultation or a Work facet any value is 422. `hidden`
outside the three hideables is 422 — Main can never be hidden, and a custom facet is deleted
rather than hidden. 409 on a stale `updated_at` (7.0), asked last because it is state.

**PUT /folders/:id/facets/order** — `{ order: [facet_id…] }`, `facet.reorder`, 200
`{ facets }`. **The list is complete and is the whole truth**, as 7.16's `set_outline` is:
there is no partial order and no merge. 422 for a repeat, for an id that is not a shared facet
of this Folder, for an omission, for a **private id** — a private facet's place is its owner's
and is written through `my-order` — and for **Main not first**. The write touches no private
facet's key, so one shared-order write changes the order every member reads and changes
nobody's private arrangement.

**PUT /folders/:id/facets/my-order** — `{ placements: [{ facet_id, after_facet_id | null }] }`,
200 `{ facets }`. The caller's own private facets only; **another member's id answers 404**,
which is 10.2's grammar for a row whose existence the caller may not learn.
`after_facet_id: null` means "first among the facets after Main", Main being first for
everybody by the read order above. It is gated on **membership alone**, through
`personal.view_preferences`: #228's personal-actions rule puts a member's own arrangement of
rows only they can see outside Folder Access entirely, and that is also why private order needs
no table of its own — it rewrites `position` on rows nobody else can read.

**POST /folders/:id/facets/:facetId/share** — `{ confirm: true }`, else 422; #210 asks for a
clear confirmation before exposing the content, and a body with nothing in it cannot carry one.
`facet.convert_to_shared` **and** the actor must be the facet's owner: exposing content to the
Folder creates shared Work, so it takes Can edit, and it is somebody's private writing, so it
takes their consent. Neither alone. 200 Facet, **keeping the id, the document and the
position** and clearing `owner_id` with `kind` becoming `shared_blank`; keeping the id is the
point of doing this as a conversion rather than a copy, because every `page_blocks.facet_id`
under it still resolves. 409 when the facet is not private. **There is no inverse**: the same
path in reverse is 409 saying to create a private copy instead, and that copy is out of this
slice.

**DELETE /folders/:id/facets/:facetId** — `facet.delete`, 204. Stamps `deleted_at` and nothing
else. **409 on a native**, which is hidden rather than deleted: the body was fine and the actor
was permitted, and what is wrong is the state of the thing they named. **Deleting a Work facet
changes no block, no Task and no Section.** The other direction is 4.30's foreign key: deleting
the H1 destroys its Work facet rather than trashing it.

**GET /folders/:id/facets/:facetId/page** and **POST …/page/actions** — 7.16's contract
unchanged, and **`document_transaction` only**: 7.16's other six actions are the pre-canvas
vocabulary and three of them are about Tasks, which a facet has none of. The read answers 7.16's
shape, with `task_placements` always empty because no Task row ever belongs to a facet.

Four refusals, all 422 and all naming their field. The first three are the ruling's:
**`create_task`**, because a facet holds no Tasks; a **`section` block**, because a facet
document has no Sections; and a **`folder_ref` block**, because a facet is a view of one Folder
and a reference out of it belongs on Main. The fourth is a **nested list item**:
4.17's `page_blocks_list_parent_kind_check` admits a list parent only where `folder_id IS NOT
NULL`, so a facet document cannot hold one, and the refusal is a named 422 rather than a 500
from the CHECK or a silently dropped nesting. Admitting nested lists in a facet is a later
change to the CHECK and to this refusal together.

The gate is `folder.page.edit` for a shared blank facet — ordinary shared Work, #228's Can-edit
list, the same bar the Folder page asks — and **`facet.read` alone for a private one, which no
preset satisfies**, so Full control and the structural owner are refused by the same line that
refuses everybody else. A shared facet's *read* is any member's (`folder.read`); only its write
takes `folder.page.edit`. **A Work facet has no page route**: it reads and writes
`/folders/:id/page`, and asking for its page is 404 rather than an empty document. "No H1
inside a Work facet" is a **client rule and is not server truth** — the server sees one Folder
document.

## Trash (7.13)

`GET /api/v1/trash` gains a **`facets`** array, whose rows carry `is_owner` and `my_access`
exactly as 7.13's other two do and for the same reason: the permanent delete is not one rule
across the three kinds. Each row carries `id`, the **resolved** `name` — so a Trash row says
what the tab said, a Work facet's included — `kind`, `folder_id`, `folder_name` and
`deleted_at`. A member's trashed private facet is theirs alone to see and to restore.

**POST /api/v1/facets/:id/restore** mirrors `POST /folders/:id/restore`: 200 Facet, access by
membership at read time and never by who deleted. **409 when the facet's Folder is itself
trashed** — the Folder comes back as one entry and its facets ride its fate — and 409 when
restoring a Work facet would collide with one somebody made over the same heading meanwhile,
which 4.30's partial unique index raises in the same transaction. It resolves `facet.delete`:
the ruling names seven actions and no `facet.restore`, and #228's Can-edit list carries restore
beside trash for Tasks, so restoring what you were allowed to trash is the same authority.

**DELETE /api/v1/trash/facets/:id** — 204. **Full control with ownership ignored**, which is
the Task rule of 7.13's 2026-09-20 correction rather than the Folder's custody-and-Full-control
pair: permanently destroying one facet of a Folder that survives it is exactly what destroying
a Task is. It runs through the 11.7 collection rather than a delete written beside it, which is
item 36's requirement on this endpoint. The thirty-day purge takes trashed facets on the same
window and through the same collection.

## Duplication, workflow import and the sample workspace

Every path that creates a Folder creates its four natives in the same transaction, which is
4.30's rule and not this section's; seven modules do (`guard-native-facets-on-every-folder`
enumerates them). Two of those paths need a sentence here because a reader will ask.

**A duplicated Folder and an imported workflow get four fresh natives and none of the
source's custom facets.** #210 is silent and the nearest authority is R10B's rule one table
over: member identities, Access standing and Responsibility documents are not copied by
duplication or by a workflow file, and a copy is a new Folder whose only member is the person
who made it. Copying a facet's *content* is a later slice's decision, and a workflow file
carries no facets at all. Imran may overrule this without moving anything else in 7.27.

## A membership ending (Ruling 6, 2026-09-21)

Technical authority: https://github.com/zhssnym/dana/issues/210#issuecomment-5757696835.

No route on this surface performs it and none has to be called: **when a membership ends by
any path, the departing person's private facets in that folder go with it, permanently and
with their documents**, in the transaction that ends the membership. So
`DELETE /folders/:id/members/:userId`, `DELETE /folders/:id/my-membership` and
`DELETE /me` each take them, and a client that drew a private facet for somebody who has
just left is drawing a row that no longer exists rather than one it may not read. Shared
facets are Folder data and survive all three. 4.30 carries the reasoning and 8.10 the step.

## What this surface does not do

Purpose (#211), Consultation (#212) and Results (#213) internals: this slice gives them a row,
an id, a name, a place and a visibility bit and nothing else. Voting. The
relationship/propagation pass (#214). The private copy of a shared facet. Copying a facet
with its Folder, per the paragraph above. Navigator presentation, docking and auto-hide. Any
Task or view semantics inside a facet.
