### 7.27 Folder facets

The data model is 4.30 and the document store is 4.17.

## The refusal order, everywhere on this surface

**404 → 422 → 403 → 409.**

**Existence first** (10.2), so a refusal never confirms that a Folder exists: a person who is
not a member of the Folder is answered 404 whatever their body said. **Then the body**,
because an authority refusal must be able to name what it refused — "you may not create a
Work facet here" and "you may not create a facet at all" are different sentences, and
`facet.create`'s private-facet arm depends on *which kind* was asked for, so the gate cannot
be asked before the body is known. **Then the preset**, which is `mayPerform`'s. **Then
state**, which is meaningful only on a body already valid and an actor already permitted.

## The Facet object

Wire shapes: `facet` and the request bodies in `app/src/shared/facets.ts`.

`kind` is one of 4.30's kinds. `name` is **server-resolved and never stored**: fixed for Main
("Work") and Consultation ("Discussion"), `display_name ?? default` for Purpose and Results, **the H1 block's text for
a Work facet**, and `display_name` for a blank. `display_name` is the stored override or null,
and null on Purpose and Results means "the default name" — it is sent beside `name` because it
is the only field that tells a client whether Reset does anything. `private` is a projection of
`owner_id` and the two cannot disagree (4.30's `folder_facets_owner_kind_check`); both are
sent, because a client drawing the privacy treatment should not have to know that equivalence
and a client deciding whether to offer Share needs the id. `updated_at` is 7.0's stale-write
token.

## The routes

**GET /folders/:id/facets** — any member (`folder.read`). `facets` in effective
order: the natives and shared facets by `position` (Main may stand anywhere; a Folder nobody
has reordered keeps its creation keys, Main first, which clients draw as the default Purpose ·
Work · Results · Discussion), with the caller's own
private facets interleaved by theirs. Hidden natives are carried with `hidden: true`, so
Restore can be drawn. A non-member is 404. **Another member's private facets are absent**, by a
clause inside the query's own `FROM`, so the list is not a filtered read that somebody had to
remember to filter.

**POST /folders/:id/facets** — 201
Facet. 422 for a native kind, for `h1_block_id` present off `work` or absent on it, for a
missing blank name, and for a block that is not a **depth-1 Section of this Folder's own page**.
403 `facet.create`. **409 when that H1 already carries a live Work facet**, which 4.30's partial
unique index enforces in the same transaction rather than a read followed by a write.
`after_facet_id` places the new facet after a facet the caller can see; absent, it appends.

**PATCH /folders/:id/facets/:facetId** — 200 Facet.
`display_name` is `facet.rename` and `hidden` is `facet.hide`, and a patch carrying both must
satisfy both. `display_name: null` on Purpose or Results is **Reset**; on a blank facet it is
422, its name being required; on Main, Consultation or a Work facet any value is 422. `hidden`
outside the three hideables is 422 — Main can never be hidden, and a custom facet is deleted
rather than hidden. 409 on a stale `updated_at` (7.0), asked last because it is state.

**PUT /folders/:id/facets/order** — `order`, a list of facet ids; `facet.reorder`, 200
with `facets`. **The list is complete and is the whole truth**, as 7.16's `set_outline` is:
there is no partial order and no merge. 422 for a repeat, for an id that is not a shared facet
of this Folder, for an omission, for a **private id** — a private facet's place is its owner's
and is written through `my-order`. Main may stand anywhere. Keys are written from `a1` on, so a
written order is never mistaken for the untouched creation keys. The write touches no private
facet's key, so one shared-order write changes the order every member reads and changes
nobody's private arrangement.

**PUT /folders/:id/facets/my-order** — `placements`, each a `facet_id` and an
`after_facet_id` or null; 200 with `facets`. The caller's own private facets only; **another member's id answers 404**,
which is 10.2's grammar for a row whose existence the caller may not learn.
`after_facet_id: null` means "before the first facet the caller can see", the front of the row. In a Folder nobody has reordered (the built-ins at their creation keys, drawn in the default order), the write first re-keys the built-ins in that drawn order below every other row, so the drop lands where it was made and no member's drawn row changes. It is gated on **membership alone**, through
`personal.view_preferences`: a member's own arrangement of rows only they can see is outside
Folder Access entirely, and that is also why private order needs
no table of its own — it rewrites `position` on rows nobody else can read.

**POST /folders/:id/facets/:facetId/share** — `{ confirm: true }`, else 422: exposing the
content needs a clear confirmation, and a body with nothing in it cannot carry one.
`facet.convert_to_shared` **and** the actor must be the facet's owner: exposing content to the
Folder creates shared Work, so it takes Can edit, and it is somebody's private writing, so it
takes their consent. Neither alone. 200 Facet, **keeping the id, the document and the
position** and clearing `owner_id` with `kind` becoming `shared_blank`; keeping the id is the
point of doing this as a conversion rather than a copy, because every `page_blocks.facet_id`
under it still resolves. 409 when the facet is not private. **There is no inverse**: the same
path in reverse is 409 saying to create a private copy instead.

**DELETE /folders/:id/facets/:facetId** — `facet.delete`, 204. Stamps `deleted_at` and nothing
else. **409 on a native**, which is hidden rather than deleted: the body was fine and the actor
was permitted, and what is wrong is the state of the thing they named. **Deleting a Work facet
changes no block, no Task and no Section.** The other direction is 4.30's foreign key: deleting
the H1 destroys its Work facet rather than trashing it.

**GET /folders/:id/facets/:facetId/page** and **POST …/page/actions** — 7.16's contract
unchanged, and **`document_transaction` only**: 7.16's other six actions are the pre-canvas
vocabulary and three of them are about Tasks, which a facet has none of. The read answers 7.16's
shape, with `task_placements` always empty because no Task row ever belongs to a facet.

The document-bearing kinds are the two blank facets and the native **Purpose** and **Results** facets. Three operational kinds remain refused with 422 naming the field:
**`create_task`**, because a facet holds no Tasks; a semantic **`section` block**, because
facet documents have no Main Work Sections; and a **`folder_ref` block**, because a facet is
a view of one Folder and that block kind remains Main's. `heading1`, `heading2` and
`heading3` are admitted as presentation-only authored headings; they are not `section` and produce
no Task grouping or Work hierarchy.

Nested blocks are admitted in facet documents under 7.16's rule (any block but a Section under
a writing block of this same facet, the parent preceding the child), and the transaction
persists `list_parent_block_id`; the database CHECK admits the relation on every home (0038). A parent id from another facet is 422 and writes nothing.

The gate is `folder.page.edit` for a shared blank facet, **Purpose and Results** — ordinary shared
Folder content, the same bar the Folder page asks — and **`facet.read` alone for a private
one, which no preset satisfies**, so Full control and the structural owner are refused by the
same line that refuses everybody else. A shared facet's *read* is any member's
(`folder.read`); only its write takes `folder.page.edit`. **A Work facet has no page route**:
it reads and writes `/folders/:id/page`, and asking for its page is 404 rather than an empty
document. Consultation is not document-bearing. "No H1 inside a Work facet" is a **client rule and is not server
truth** — the server sees one Folder document.

## Trash (7.13)

`GET /api/v1/trash` carries a **`facets`** array, whose rows carry `is_owner` and `my_access`
exactly as 7.13's other two do and for the same reason: the permanent delete is not one rule
across the three kinds. Each row carries `id`, the **resolved** `name` — so a Trash row says
what the tab said, a Work facet's included — `kind`, `folder_id`, `folder_name` and
`deleted_at`. A member's trashed private facet is theirs alone to see and to restore.

**POST /api/v1/facets/:id/restore** mirrors `POST /folders/:id/restore`: 200 Facet, access by
membership at read time and never by who deleted. **409 when the facet's Folder is itself
trashed** — the Folder comes back as one entry and its facets ride its fate — and 409 when
restoring a Work facet would collide with one somebody made over the same heading meanwhile,
which 4.30's partial unique index raises in the same transaction. It resolves `facet.delete`:
there is no `facet.restore`, because restoring what you were allowed to trash is the same
authority, as it is for Tasks.

**DELETE /api/v1/trash/facets/:id** — 204. **Full control with ownership ignored**, which is
7.13's Task rule rather than the Folder's custody-and-Full-control pair: permanently destroying one facet of a Folder that survives it is exactly what destroying
a Task is. It runs through the 11.7 collection rather than a delete written beside it. The thirty-day purge takes trashed facets on the same
window and through the same collection.

## Duplication, workflow import and the sample workspace

Every path that creates a Folder creates its natives in the same transaction, which is
4.30's rule. Two of those paths need a sentence here.

**A duplicated Folder and an imported workflow get fresh natives and none of the source's
custom facets**, as member identities, Access standing and Responsibility documents are not
copied either: a copy is a new Folder whose only member is the person who made it. A workflow
file carries no facets at all. How Purpose's content travels is 7.16's.

## A membership ending

No route on this surface performs it and none has to be called: **when a membership ends by
any path, the departing person's private facets in that folder go with it, permanently and
with their documents**, in the transaction that ends the membership. So
`DELETE /folders/:id/members/:userId`, `DELETE /folders/:id/my-membership` and
`DELETE /me` each take them, and a client that drew a private facet for somebody who has
just left is drawing a row that no longer exists rather than one it may not read. Shared
facets are Folder data and survive all three. 4.30 carries the reasoning and 8.10 the step.

## What this surface does not do

Consultation internals, voting, the private copy of a shared facet, copying a
custom facet with its Folder, and any Task or view semantics inside a facet.

#### The native Purpose document

There is no Purpose table: the facet-page contract above extends to
`kind = purpose`. Purpose is optional authored shared context: a blank
Purpose is valid, every current Folder member may read it, and writes use
`folder.page.edit`. The document may contain paragraphs, presentation headings, lists,
checklists, quotes, callouts, code and the existing safe media kinds. Authored prose and
checklist ticks create no operational state.

**GET /api/v1/facets/:id/location** is the one navigation-only read added for the stable
Purpose and Results Dana Links. It requires a session and admits only a live native Purpose
or Results facet whose owning Folder the viewer may read. Success is exactly `{ "folder_id": "<uuid>" }`. A
facet of any other kind, a deleted Purpose or Results, a Purpose in a trashed Folder, a missing id and a
Purpose whose Folder the viewer may not read all answer the identical 404 `not_found`.
Hidden state is deliberately irrelevant. The route changes nothing and grants nothing; its
only caller is the `/app/facets/:id` client entry route, which opens the existing Folder
workspace with that facet focused.

Purpose's native facet id is also the stable Dana Link identity defined by 7.24. Rename and
hide do not replace that id. Folder duplication and workflow portability are governed by
7.16; account export carries Purpose under 7.22's shared-facet rule.

#### The native Results document

Results (#213) records what actually happened or was produced — outcomes, findings,
evaluations, partial or unsuccessful results — and is distinct from intended Purpose. Like
Purpose there is no Results route or table: the facet-page contract above extends to
`kind = results` on the same terms, the same admitted block kinds and the same gate
(`folder.read` to read, `folder.page.edit` to write). Task completion writes nothing into
Results, and Results carries no Task state; a Task relates to a Result by Dana Link.

Results' native facet id is a stable Dana Link identity under 7.24. **Folder duplication and
workflow portability do not carry Results**: they are actual outcomes of the source Folder, not
reusable intentions, so a duplicate's native Results starts empty with the default name and a
workflow file has no `results` member. Account export carries Results under 7.22's
shared-facet rule, as it carries every shared facet the person can read.
