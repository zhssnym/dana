### 7.8 My Day membership

- POST /tasks/:id/my-day?tz. Inserts entry (task, V, added_on = today(V)); repeat calls
  are 200 no-ops keeping the original added_on (INV-12). 404 if not accessible. - DELETE
  /tasks/:id/my-day. Removes V's entry; 200 even when absent (idempotent). The task
  remains in My Day when it still qualifies automatically.

Response bodies, settled at the same review and entered by the same ruling: both calls
answer the affected TaskDetail. A My Day entry is no more a resource here than a step is,
and a pull moves pulled, which 7.0 makes a field of the task rather than of the entry, so
the task is again the only object that reports the change. The statuses above are
unchanged, on the repeat no-op and the absent-entry delete alike.

The tz query parameter on the pull, escalated at the P4 merge review and entered by owner
ruling on 2026-08-08. It is an IANA identifier, and an absent or invalid one answers 422
naming tz, the same treatment 7.0 gives the parameter on every view endpoint; the rule is
stated here rather than by widening 7.0's sentence, because this is a mutation and 7.0's
sentence is about views. DELETE gains nothing: it evaluates no date.

Why it was missing and what it cost. This endpoint required added_on = today(V) while
carrying nothing from which today(V) could be computed, and 8.1 defines today(V) as the
current date in tz, the zone the request carries. The only zone an endpoint without tz can
reach is users.timezone, which is what the P3 implementation used, and 8.1 reserves that
column for reminder fire instants alone. The consequence was not theoretical: the pull
dated the entry in the account's zone while My Day grouped it by the request's, so for a
large part of every day a task pulled now appeared under Carried rather than Today, and
the P4 acceptance suite failed on it in CI at 22:00 UTC while passing an hour earlier. The
alternative reading, letting the pull keep the account's zone and saying so, was rejected
because it blesses that defect rather than fixing it: the two zones still disagree, the
row still lands in the wrong group, and the criteria asserting a user-visible behavior
would have had to be weakened to match.

Frozen 4.7 needs no amendment and gets none. Its column note reads "the adder's local date
at pull time", which names neither a zone source nor a mechanism, and once the request
carries the zone that phrase reads correctly and more accurately than before: the adder's
local date is the date where the adder now is, which is what tz reports and what a stored
users.timezone can only approximate, since 8.1 has travel move today. The same holds for
INV-12's "the adder's timezone at insert time". The implementation followed 4.7 rather
than deviating from it, having no other zone within reach.
