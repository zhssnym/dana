### 7.6 Tasks

- POST /tasks. Body { title required, folder_id default V's Inbox, notes, important
  default false, due_date, due_time, recurrence_rule, assignee_id default V, reminder
  {offset_minutes or time_of_day}, steps [titles] }. Guards: member of folder (404), title
  1 to 300 (422), dependency checks (due_time, recurrence_rule, reminder require due_date;
  422), recurrence_rule must parse within the 4.11 subset and gets a fresh series_id,
  assignee must be a member (composite FK, surfaced as 422), single-member folder forces
  assignee to that member ignoring the input (INV-5), steps at most 50 (422). 201
  TaskDetail. - GET /tasks/:id. TaskDetail. 404 if folder not accessible. - PATCH
  /tasks/:id. Any member. Partial body; only present fields change (field-level last write
  wins). Special rules: - folder_id change is a move: V must be member of both source and
  target (404); if the current assignee is not a member of the target, assignee becomes
  null; if the target has exactly one member, assignee becomes that member (INV-5). A move
  carries the task's conversation (4.15) into the target folder (item 60). - due_date set
  to null triggers the clear-date cascade (section 8.4): due_time null, recurrence_rule
  null, reminder row deleted, in the same transaction. - due_date changed (non-null):
  reminder fire_at recomputed; the series anchor moves with it (section 8.5). -
  recurrence_rule set on a task without one: requires due_date (422) and assigns a new
  series_id; changed on a current occurrence: replaces the rule from now on, past rows

  deleted_successor_id or null }. - POST /tasks/:id/order. Any member. Body { after_id:

  the folder's unscheduled list, either being null where the drop had no neighbour on that
  side. Guards: the task is accessible (404); the task is in that list, meaning undated
  and not completed (409, a hand order being the unscheduled list's alone); each named
  neighbour is a different task in the same list (422 naming the field); after_id must
  precede before_id in the list as it stands (422). The call writes the task's 4.5

  they have none, in the order the list already reads, so nothing else moves. 200
  TaskDetail.

Clearing due_time deletes an offset reminder, escalated by the P7 engine session and
entered by owner ruling on 2026-08-10. The PATCH bullets above name a consequence for
due_date in both directions and none for due_time, and one of those edits has no
satisfiable outcome: an offset reminder is computed from the task's due_time (section
8.6), so clearing the time leaves a row 8.6 cannot compute and 4.8 calls an illegal mode
pair. Setting due_time to null therefore deletes the reminder, in the same transaction as
the edit, and section 8.4 carries the rule beside the clear-date cascade it is the smaller
sibling of. The grounds, the owner's and the engine's: 8.4 already deletes the reminder
when the date is cleared, so the two read as one policy rather than two; refusing with 422
would block an edit the user is entitled to make over a row they may have forgotten; and
converting the mode is the only option that silently changes when a reminder fires, by
inventing a time of day nobody chose. A due_time that moves from one time to another
invalidates nothing and is the ordinary recompute of 8.6. The mirror edit deletes
likewise, ruled by the owner on 2026-08-10 on the P7 change control's recommendation:
setting due_time on a date-only task carrying a time_of_day reminder deletes that
reminder, for the same reason and in the same transaction, so this section and 8.4 state
one policy rather than half of one each; that shape does compute, 8.6's date-only arm
reading the reminder's own time_of_day and never the task's, but 4.8 calls the pair
illegal and 9.3 switches the reminder control's mode with due_time, so the surviving row
would render an offset picker over a wall time, a reminder the interface can neither show
nor edit.

The move refusal above was narrowed at the P3 shape review and entered by owner ruling: it
reads 404 where it read "404 or 422". A 422 for a target folder the caller is not a member
of confirms that the folder exists, which is the existence leak this section's own 404
rule and the chokepoint of 10.2 are built to prevent, so the wider text admitted what the
rest of the surface forbids. No response gains or loses a field; one of two admitted

The tz query parameter on the two generating transitions, escalated at the P6 kickoff and
entered by owner ruling on 2026-08-10. POST /tasks/:id/complete and POST
/tasks/:id/abandon take tz, an IANA identifier, validated the way every other zone this
contract accepts is. It is optional in shape and required in effect exactly where a date
is evaluated, which is two rules rather than one. A present value that fails that
validation answers 422 naming tz, always, on either endpoint and whatever the row holds,
because 7.0 refuses a value outside what a parameter admits rather than narrowing it to a
default. An absent one answers 422 naming tz exactly when the transition would run
generation, which is the winning guarded update of 5.1 landing on a pending row that
carries a recurrence_rule; the transaction changes nothing, so the row does not
transition, no successor is created, and the same call retried with a zone gets the
transition it asked for. Every other call these two endpoints serve is untouched, because
a row with no rule evaluates no date and neither do 5.1's no-ops and conflicts: a repeat
complete on a settled row and a complete on an abandoned one answer what they always
answered. POST /tasks/:id/uncomplete and POST /tasks/:id/restore gain nothing, the shape
frozen 7.8's DELETE has, because G-SERIES reads the shape of a series and evaluates no
calendar date.

Why it was missing and what it cost. 8.5 computes the successor from cutoff =
max(t.due_date, current_date(actor.tz)), so these two endpoints decided a calendar date
while carrying nothing from which that date could be computed. The only zone an endpoint
without tz can reach is users.timezone, and 8.1 reserves that column for reminder fire
instants alone. This is 7.8's defect a second time in a different endpoint group, and the
one difference is when it was caught. The pull's cost was measured: an entry dated in the
account's zone while My Day grouped it by the request's, and a P4 acceptance failure in CI
at 22:00 UTC on a suite that had passed an hour earlier. Here nothing is built yet,
because P3 deferred the recurrence_rule arm of the two write bodies above with the
validator it needs, so no row this API can create carries a rule and no implementation has
read a zone here. What it would have cost is the pull's cost compounded one step: a
traveler's completion would place the successor from the zone they left, so the skipped
slot of a late close and the kept alignment of an early one would each land a day out for
part of every UTC day, and AC-072 to AC-075, which pin exactly those relationships, would
have been written against a boundary the request could not state.
