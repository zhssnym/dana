### 7.6 Tasks

Bodies and responses: `app/src/shared/tasks.ts`.

- **POST /tasks.** Body `postTasksBody`; folder_id defaults to V's Inbox, important to
  false, assignee_id to V. Guards: member of the folder (404); title length and step count
  within 10.3 (422); due_time, recurrence_rule and reminder each require due_date (422);
  start_date not later than due_date where both are set (422 naming the field the body
  sent); recurrence_rule must parse within the 4.11 subset and gets a fresh series_id; the
  assignee must be a member (composite FK, surfaced as 422); a single-member folder forces
  the assignee to that member, ignoring the input (INV-5). `steps`, a list of titles, is
  written as unticked checklist items at the end of the task's body (after its notes). 201
  TaskDetail.
- **Subtasks.** A task's subtasks are the checklist items of its body (4.17). TaskDetail's
  `steps` lists them in document order, read-only, and `steps_done` / `steps_total` on
  the card count them. The body's document transaction writes them. Until the contract
  release, 7.7's old calls stay as shims for installed old clients: `POST /tasks/:id/steps`
  (`{ title }`) appends an item, `PATCH /steps/:id` (`{ title?, done? }`) renames or ticks
  one and `DELETE /steps/:id` removes one, by the item's id (0060 kept the steps' ids).
  A tick needs `step.toggle` or `task.edit`, anything else `task.edit`; 404 before 403.
  `position` is ignored; promotion is gone.
- **GET /tasks/:id.** TaskDetail. 404 if the folder is not accessible.
- **PATCH /tasks/:id.** Body `patchTaskBody`. Any member. Only present fields change
  (field-level last write wins). Special rules:
  - folder_id change is a move: V must be a member of both source and target (404, never
    422, since a 422 would confirm the target exists). If the current assignee is not a
    member of the target, the assignee becomes null; if the target has exactly one member,
    the assignee becomes that member (INV-5). A move carries the task's conversation (4.15)
    into the target folder, and the files its document blocks and its comments name (#221):
    a file in the source folder that nothing else names is re-scoped to the target (same
    id); one the source folder still names elsewhere is copied into the target and the
    task's references point at the copy, the copy charged to V's quota like any duplicate
    (413 `quota_exceeded`, nothing written, when it does not fit).
  - due_date set to null triggers the clear-date cascade (8.4): due_time null,
    recurrence_rule null, reminder row deleted, in the same transaction. start_date is not
    part of the cascade, so clearing due_date on a task with a start leaves a start-only
    task.
  - due_date changed (non-null): reminder fire_at recomputed; the series anchor moves with
    it (8.5).
  - due_time set to null deletes an offset reminder, and due_time set on a date-only task
    carrying a time_of_day reminder deletes that reminder, each in the same transaction
    (8.4). An offset reminder cannot be computed without a time, a time_of_day reminder on a
    timed task is a mode pair 4.8 forbids, and converting the mode would invent a firing
    time nobody chose. A due_time moving from one time to another is the ordinary 8.6
    recompute.
  - start_date and due_date are checked against the merged state, since a body setting one
    date is read against whichever the row already holds: start after due is 422.
  - recurrence_rule set on a task without one: requires due_date (422) and assigns a new
    series_id; changed on a current occurrence: replaces the rule from now on, past rows
    untouched; set null: the series ends and the row stays a normal task, keeping its
    series_id.
  - assignee_id: null is refused 409 in single-member folders (INV-5); a non-member is 422
    via the composite FK.
  - status is not accepted here (409 if present): transitions have their own endpoints.

  200 TaskDetail.
  - notes against a Task that has a document (4.17): when the document is still a plain
    mirror of the stored notes (paragraphs only, no rich content, no files, projection equal
    to the stored notes) the write replaces it; otherwise every block is kept and the written
    text is appended as paragraphs, only the part after the stored notes when the write
    extends them. notes then holds the document's projection. A legacy writer can repeat
    text this way and can never drop any.
- **GET /tasks/:id/document.** The Task's document as 7.16's PageView, `task_placements`
  always empty. Any member who can see the Task; 404 otherwise.
- **PUT /tasks/:id/document.** 7.16's `document_transaction` over the Task's blocks, with
  7.16's revision, retry and 409 semantics. Gated on `task.edit`, as a notes PATCH is (404
  before 403); a transaction that only ticks or unticks existing checklist items (the one
  outline unchanged, nothing created or deleted, nothing else about an item changed) needs
  `step.toggle` instead, which Assigned work has on its own task. Refused with 422: `create_task`, a `section` or `folder_ref` block, nesting 7.16
  refuses, and a media file outside the Task's folder. Blocks nest by `list_parent_block_id`. The write
  rewrites notes as the projection. Duplicating a Task or its Folder, and a recurrence
  successor, copy the document with every checklist item unticked.
- **DELETE /tasks/:id.** Any member. 204. Cascades per the 5.1 delete row.
- **POST /tasks/:id/complete, /uncomplete, /abandon, /restore.** Transitions per 5.1 with its
  guards and no-ops; complete and abandon run generation when a rule is present; uncomplete
  and restore apply G-SERIES. 200 `taskTransitionResponse`. Complete and abandon take an
  optional tz query parameter: a present value that is not an IANA identifier is 422 naming
  tz, always; an absent one is 422 naming tz exactly when the transition would run
  generation (a pending row carrying a recurrence_rule), and then nothing changes, so a retry
  with a zone gets the transition asked for. 8.5 places the successor from the actor's today,
  and users.timezone is reserved for reminder fire instants (8.1), so the request must carry
  the zone. Uncomplete and restore take no tz, G-SERIES evaluating no calendar date.
- **POST /tasks/:id/order.** Any member. Body `postTaskOrderBody`: the two rows the task was
  dropped between in the folder's unscheduled list, either null where the drop had no
  neighbour on that side. Guards: the task is accessible (404); the task is in that list,
  meaning undated and not completed (409, a hand order being the unscheduled list's alone);
  each named neighbour is a different task in the same list (422 naming the field);
  after_id precedes before_id in the list as it stands (422). The call writes the task's 4.5
  `position` between its neighbours' and assigns positions to the rest of the list where
  they have none, in the order the list already reads, so nothing else moves. 200 TaskDetail.

A task's Schedule is start_date and due_date together; four states are valid: neither, start
only, due only, and both with start on or before due. Generated recurrence instances (8.5)
carry start_date null, since copying an absolute start forward would put a past start on a
future occurrence. Duplication copies start_date as it stands without re-anchoring it.
