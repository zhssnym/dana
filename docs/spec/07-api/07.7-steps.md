### 7.7 Steps

- POST /tasks/:id/steps. { title, position optional (defaults to max plus 1) }. 422 over
  50. 201. - PATCH /steps/:id. { title, done, position } any subset. 200. - DELETE
  /steps/:id. 204. All require membership of the parent task's folder (404 otherwise). No
  effect on task status ever.

Response bodies, settled at the P3 shape review and entered by owner ruling: POST
/tasks/:id/steps and PATCH /steps/:id each answer the affected TaskDetail, which is what a
fresh GET /tasks/:id would give, the same convention 7.1 carries on PATCH /me and 7.2 and
7.4 carry on each of their mutations. A step is not a resource this contract shapes: 7.0
gives it no object of its own and this section offers no GET for one, while a step
mutation moves steps_done and steps_total as well as the steps array, so the parent task
is the only object that reports what the call did. POST therefore answers 201 with that
task rather than with the step it created, and the created step rides in the steps array
carrying the id and position the server assigned it. DELETE /steps/:id keeps the 204 above
and carries no body.

- POST /tasks/:id/steps/:stepId/promote. The step becomes a pending task titled after it,
  in the parent's folder and under the parent's section, created by V and assigned to
  nobody, and the step is removed in the same transaction. 201 with the new TaskDetail.
  404 when the step is not the named task's or V is not a member of the folder. A task
  never demotes: there is no reverse address. (Append unit of RFC 0005 change control item
  58, C, ruled by delegation 2026-08-30 and folded here the same day; it is item 44's B9
  given an address.)
