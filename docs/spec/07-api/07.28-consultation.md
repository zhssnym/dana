### 7.28 Consultation

A Folder's Consultation is a list of Discussions, and a Discussion is resolved by recording an
Outcome (issue #320, product authority #212 R1, R2, R4). The data model is 4.31 (Discussions)
and 4.32 (Outcomes); the wire shapes and request bodies are `app/src/shared/consultation.ts`;
the action rules are the `discussion.*` rows of `app/src/shared/folder-actions.ts`.

Comments inside a Discussion ride the conversation routes (7.14), and Discussion and Outcome
Dana Link kinds are 7.24's; neither is here.

## The refusal order, everywhere on this surface

**404 → 422 → 403 → 409**: existence first, so nothing about a body is said to a stranger. A `/discussions/:id` route
resolves the Discussion to its Folder and the caller's membership **before** it reads the
body, so a non-member is 404 whatever they sent, and a trashed Discussion is 404 on every
route but the Trash pair. The preset is then asked **under the Discussion's row lock, in the
transaction that writes**, with the actor's Folder facts re-read in that transaction: a
member lowered or removed a moment earlier is decided by their new Access.

## Who may do what

- **Read** (Discussions, Outcomes, history): Can view and above.
- **Start** a Discussion: Can comment and above. The caller becomes `created_by`.
- **Edit** title and context, **resolve**, **reopen**: Can edit and above on any Discussion,
  or its **creator while they hold Can comment or above**. Authorship is provenance and never
  standing authority: a creator lowered below Can comment loses every creator power at once.
- **Move to Trash**: Can edit and above; or the creator at Can comment while the Discussion
  is **unshared** — no comment from anyone else, no Outcome ever (a reopened Discussion's
  previous Outcomes count), and no structured-input response from anyone else (#321).
  Restore follows the same rule.
- **Permanently delete** from Trash: Full control, ownership ignored (7.13's Task rule).
- **The General discussion** (`is_general`, 4.31) is the deployed client's whole Folder
  thread: resolving it freezes that thread's replies and trashing it hides the thread. Until
  the Consultation UI ships, **resolve** and **move to Trash** on it need Full control (the
  `discussion.purge` bar) on top of the rules above, and are 403 otherwise with the row
  unchanged. Edit, reopen and restore follow the ordinary rules.

## State

`state` is exactly `open | resolved`. Edit is refused 409 on a resolved Discussion (reopen
first). Resolve is refused 409 on a resolved one: a changed conclusion is reopen, then resolve
again, which makes a **new** Outcome. Reopen is refused 409 on an open one. Reopening a General discussion, or restoring an open
one, is refused 409 while the Folder already has another open, untrashed General discussion
(a legacy post opened it), because `discussions_one_open_general_key` allows one. Resolve, reopen
and edit each set `last_activity_at` to now.

## The routes

**GET /folders/:id/discussions** — the list. Query: `state` (`open | resolved | all`, default
`all`), `q` (case-insensitive substring of title or context; `%` and `_` are literal),
`limit` (1–100, default 50), `cursor`. Ordered `last_activity_at DESC, id DESC`; trashed
Discussions excluded. Answers `{ discussions, next_cursor }`, `next_cursor` null on the last
page. The cursor is opaque and resumes exactly after the last row at microsecond precision; a
cursor this list did not issue is **422** (`cursor`). Each row also carries the thread
summary (W-C): `post_count`, `last_post` (`author_id`, a plain-text `preview` of at most 140
characters, `created_at`; null with no posts) and `participant_ids` (distinct post authors,
most recent first, at most five), and the viewer's `read_at` (4.34; null when they have
never opened it).

**The Discussion tab lists the project.** `GET /folders/:id/discussions` given any page of a
project lists the discussions of every page of that project the reader is a member of; a
Discussion stays on the page it was started on. `POST /tasks/:id/discussion` ("Discuss") adds
the project's Discussion tab after the last tab when it has none, in the same transaction, for
a caller who may start a discussion, and answers `discussion_tab_id` beside the thread.

**POST /folders/:id/discussions** — 201, the Discussion. Body: `title` (1–200 after
trimming), optional `context` (plain text ≤ 4000; empty is stored as null).

**GET /discussions/:id** — the Discussion, with its current Outcome inline as
`current_outcome` (null when open). Every Discussion answer carries `is_general` (boolean),
so a client can label the Folder's General discussion; a rename does not change it. It
also carries the viewer's `read_at`, as the list does.

**PUT /discussions/:id/read** — 204, no body. The viewer has opened the thread: sets their
`read_at` (4.34) to now and, in the same transaction, marks read their unread notifications
about posts in this Discussion, so opening a thread clears the bell for it. Any member who
can read it may; a stranger, an id naming no Discussion and a trashed Discussion are 404.
Idempotent; it records no event.

**POST /tasks/:id/discussion** — "Discuss" on a task (4.31 `discussion_tasks`). No body.
Answers `{ "discussion": <Discussion>, "discussion_tab_id" }`: **201** when this call made a
Discussion, **200** when it reused the live one (open or resolved) that this route made earlier
for the task in the task's current Folder, so it is safe to repeat. Other Discussions linked to
the task never stop it making one. Any member may be shown an existing one; making one needs
`discussion.create` (Can comment), 403 otherwise with nothing stored. The new one is titled with
the task as it reads now (cut to 200, "Untitled task" when blank), `created_by` the caller, is
linked to the task in the same transaction, and records `started a discussion`. A stranger, an
id naming no task, a trashed task and a task in a trashed Folder are 404. Concurrent calls make
one Discussion: the task row is locked.

**A Discussion may be about many tasks, and a task may have many Discussions.** The link is a
row of `discussion_tasks` (4.31), a reference and not containment. Every Discussion answer
carries `linked_tasks`: `{ id, title, status }` for each linked task that is live and in a Folder
the viewer can read, ordered by title. TaskDetail (7.0) carries `linked_discussions`:
`{ id, title, state }` for each linked Discussion that is live and readable to the viewer, most
recent activity first. A link to a trashed task, a trashed Discussion, or one the viewer cannot
read is left out of both, never leaked; the row itself stays. An unstarted task thread (4.31) is
left out of `GET /folders/:id/discussions` and of `linked_discussions`, and Discuss answers it
(200) rather than making another.

**POST /discussions/:id/tasks** — link a task. Body `{ task_id }`. Answers
`{ created, discussion }`: **201** with `created: true` when this call made the link, **200**
with `created: false` when it was already there. Only while open (409 on a resolved one), and
under the Edit rule above. A new link names a live task of **the Discussion's own Folder**; any
other id — another Folder's task, a stranger's, a trashed one, none — is one **422**
(`task_id`), so the field cannot probe, and the General discussion is 422 too. A link made
earlier stays when its task later moves to another Folder.

**DELETE /discussions/:id/tasks/:taskId** — 204, no body. Removes only that link; the
Discussion and the task are untouched. Only while open (409), under the Edit rule, and 422
(`task_id`) on the General discussion. The task is not looked up, so a link to a task that has
since moved or gone to Trash can still be removed, and a link that is not there is 204 too.

**PATCH /discussions/:id** — 200, the Discussion. Body: `title` and/or `context` (null or
empty clears it) and/or `task_id`. Only while open. `task_id` is kept for older clients and
means exactly `POST /discussions/:id/tasks`: it adds a link, never replaces one, with the same
422s; a link already there is no change.

**POST /discussions/:id/resolve** — 200, the resolved Discussion. Body: `statement` and/or
`source_comment_id`, or `{}` to close the thread without a decision (Wave 2 decision 3): it
resolves with no Outcome row and `current_outcome` null. Otherwise writes a new
`discussion_outcomes` row, makes it current, and resolves, in one transaction, then closes any open input round (#321) in the same transaction. With
`source_comment_id` alone the comment's body, trimmed, is snapshotted as the statement; with
both, `statement` is the snapshot and the comment is provenance. The comment must belong to
**this** Discussion: any other id — another Discussion's comment, a Task's, another
Folder's, none — is one 422 (`source_comment_id`), so the field cannot probe. A comment with
no text and no `statement` is 422 (`statement`). The Outcome never follows later edits of its
source comment.

**POST /discussions/:id/reopen** — 200, the open Discussion. Body `{}`. Clears the current
pointer, `resolved_at` and `resolved_by`; deletes nothing.

**GET /discussions/:id/outcomes** — `{ outcomes }`, every Outcome newest first, each with
`current`.

**GET /outcomes/:id** — an Outcome's stable direct route: `{ outcome, discussion }`, so a
client opens the parent Discussion focused on it. Readable exactly when its Discussion is; an
earlier Outcome answers what it always said, with `current: false`.

**DELETE /discussions/:id** — 204. Moves it to Trash (`trashed_at`); its Outcomes and
conversation are kept.

**POST /discussions/:id/restore** — 200, the Discussion, with its task links as they were. 409
while its Folder is itself in Trash.

**DELETE /trash/discussions/:id** — 204. Only a trashed Discussion. Deletes it with its
Outcomes and its comments (4.15's cascade), collects the uploads that hung only on those
comments, and removes their bytes after the commit (7.15's order). The 11.7 pass purges
Discussions trashed more than 30 days ago through the same collection.

## Trash

`GET /trash` (7.13) carries a fourth array, `discussions`: `id`, `title`, `folder_id`,
`folder_name`, `deleted_at`, `created_by`, `is_owner`, `my_access`. A Discussion of a
trashed Folder rides that Folder's entry and is not listed separately. The client schema
defaults the array to empty, so the field is additive.

## Events

Every act records a Folder event (`subject_kind = 'folder'`) with a detail line — `started a
discussion`, `edited a discussion`, `linked a task to a discussion`, `unlinked a task from a
discussion`, `resolved a discussion`, `reopened a discussion`, `moved a discussion to Trash`,
`restored a discussion from Trash`, `deleted a discussion permanently` — because 7.12's `subject_kind` is a closed set the deployed client parses.
