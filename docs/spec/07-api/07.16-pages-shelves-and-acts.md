### 7.16 Pages, shelves and acts

GET/PUT /api/v1/folders/:id/page — the block list, LWW per block, 409 on stale updated_at.
CRUD /api/v1/shelves and GET/PUT /api/v1/shelves/:id/page. POST
/api/v1/tasks/:id/duplicate · POST /api/v1/folders/:id/duplicate — the DES-198 copy rules
server-side. POST /api/v1/workflows/import?tz — zod-validated structure file, caps per
section 10. It creates folders, their page blocks (sections and paragraphs), and their
tasks, and a task carries its title, notes, star, repeat, reminder and step titles; never
ids, people, due dates or states, a step's tick included. Where a task carries a repeat or
a reminder, the imported task is anchored on the import day in the zone tz names, 4.5 and
8.6 admitting neither without a date; tz is refused as 422 when present and invalid, and
required as 422 exactly when the file carries such a task. POST
/api/v1/folders/:id/transfer-ownership { to: user_id } — owner-only, member target, the
DES-225/8.9 flow.

**Rationale for the workflow file, 2026-09-21, folded from RFC 0005 under the technical
ruling of that date** (https://github.com/zhssnym/dana/issues/280#issuecomment-5754491849,
issue #280). It changes no refusal, no status and no response shape above; only the
reasoning moves.

*Why the file refuses ids, people, due dates and states.* RFC 0005 argued three of the
four, and the three share a shape: what is left out belongs to one run of the work rather
than to the work itself. A due date is a moment in a run, and a template has no run. A
person is an account that may not exist wherever the file is opened. A state — a status, a
step's tick — records what happened rather than what to do, and so does a conversation,
which is where that reasoning reaches a comment; what a workflow file carries is an
allow-list rather than a scrubbing pass, and `app/src/shared/workflows.ts` is where it is
stated for the write side. **Ids are the one the RFC argued nowhere**, and this note invents
no argument for them: the exclusion above is the rule, and the reasoning behind it is not
recorded anywhere this fold could find. What is left in the file is the shape somebody
typing the work into an empty folder would have produced.

*The import-day anchor is a reading rather than a ruling, and it is recorded as one.* The
ruling asked that a repeat and a reminder travel and that dates do not, and those two
sentences cannot both be satisfied literally: 4.5 admits no recurrence without a due date
and 8.6 computes a reminder's instant from one, so a dateless imported task can carry
neither. Anchoring on the import day satisfies the ruling's own reason, which is that a
template holds no moment — the file still carries no date, and the date the task gets is
the day its run began. The two alternatives were to drop the repeat and the reminder, which
contradicts the ruling, and to relax 4.5's check, which would leave the recurrence
generator with no anchor.

A block object carries `width_pct: integer or null` beside its position: the person's
dragged width as a percentage of the column, 25 to 100, null where nobody has dragged it,
and 422 naming the field where it is out of those bounds or set on a block that is not an
image (4.17).

A block read also carries `file_width` and `file_height`, integer or null: the shape of the
picture `file_id` names, 4.16's own columns as issue #27 and migration 0009 added them on
2026-09-03. **They are read-only and the PUT has no place for them**, which is the whole
distinction from `width_pct` above: a width is a decision somebody made about this block and
a PUT carries it; a dimension is a measurement of a file that several blocks may share, so
sending it back would be a second record of one fact. Null means unknown — a block with no
file, or a file stored before 0009, no backfill having been run — and a client must then
draw exactly what it drew before the fields existed. A PUT that echoes a block back, which
7.16's PUT-whole contract makes every client do, therefore cannot carry the shape and must
not lose it.

**Amendment, 2026-09-06, issue #184 (owner ruling recorded on the issue).** A page read now
also carries `items`, the ordered array of `{ kind: 'block' | 'task', id }` references. Its
`blocks` retain their payloads and Q7 retains the only TaskCard payload: the item list is one
ordering contract, not a second task shape. Block reads add nullable `page_position` and
`section_block_id`; the latter is the semantic Section for prose/images and is null for a
Section, shelf block, or loose content. Task cards keep their existing `section_block_id`.

`POST /api/v1/folders/:id/page/actions` is the folder-page mutation boundary. Every body is
one of the following discriminated actions, and every named field is consumed by the server:

- `insert_block`: `block_kind` (`section`, `paragraph`, or `image`), `text`, `file_id`,
  `width_pct`, required nullable `section_block_id`, and required nullable `after`/`before`;
- `update_block`: `block_id`, stale-write `updated_at`, and at least one of `text`, `file_id`,
  or `width_pct`;
- `delete_block`: `block_id`, `updated_at`;
- `insert_task`: `title`, required nullable `section_block_id`, and `after`/`before`;
- `move_item`: a task, paragraph, or image `item`, required nullable
  `section_block_id`, and `after`/`before`; a Section heading is the boundary
  of a semantic span and is not moved as one row;
- `convert_paragraph_to_task`: `block_id`, `updated_at`.

An item reference is `{ kind, id }`; no client sends an index or fractional key. The server
locks the folder, validates both neighbours and the Section within that folder, seeds any
null keys in the sequence it just read, and computes the key between the named neighbours.
A moved task changes `page_position` and its existing `section_block_id` in that transaction.
Conversion reads the persisted paragraph under the same lock, creates a real task at its
exact place and Section, and deletes the paragraph in the same transaction; stale evidence,
an invalid conversion, a deleted/cross-folder neighbour, or an inaccessible file writes
nothing. The existing whole-page PUT remains for shelf pages and compatibility; it re-seeds
the shared keys to the legacy order it was asked to store. No collaborative editing or OT is
introduced.

**Annotation, 2026-09-04, issue #76. Both duplicates take `tz`, and it is a completion of
an incomplete surface rather than a change of contract.** 9.6 says a spent due date
re-anchors on today, and 8.1 defines today as the current date in the request's tz. Until
this date `POST /api/v1/tasks/:id/duplicate` and `POST /api/v1/folders/:id/duplicate` took no
tz at all and re-anchored with SQL `current_date`, which reads in the database session's
zone, so the copy landed on the wrong day for any caller whose local date differed from the
machine's — hours out of every day rather than an instant at midnight. **8.1 forbids that
reasoning by name**: "an endpoint that stores or filters by a date and takes no tz is an
incomplete surface, not an invitation to substitute the stored zone below", recorded at the
P4 merge review of 2026-08-08 after the same mistake had been made once already. 7.8 is the
endpoint completed then, and it is the precedent followed here, as this section's own
`POST /workflows/import?tz` already does.

The rule is that precedent exactly. A tz that is present and is not an IANA identifier is
422 naming tz, whether or not a date would have moved. A tz that is absent is 422 naming tz
**exactly when a date would be re-anchored**, and otherwise the request works unchanged: a
source with no due date, or one whose earliest due date is later than the UTC date plus a
day and so is ahead of today in every zone on earth, needs no zone and is answered as it
always was. That test is deliberately zone-free, the zone being the thing that may be
missing, and it errs towards asking. Where tz is given, the copy re-anchors on `today(tz)`
through the same time module every other date-evaluating route uses, and `shifted_days` on
the folder's answer counts the days it moved in that zone.

**Nothing else about either endpoint changes**, and the shipping client sends the parameter
from the same helper it already uses for 7.6's transitions and 7.8's pull. AC-277 and AC-200
now pin a zone and assert an exact date, which they could not do while the day came from the
database; AC-376 is the refusal shape. The interim fix to AC-277 recorded under issue #46 —
which made the criterion's oracle the database's own clock — is superseded here, and #46's
diagnosis of a "midnight race" was wrong: it was two clocks in two zones. **This does tighten a shipped
endpoint for one window, and that is accepted rather than softened**: a tab left open across
the deploy, or an installed client still on a cached bundle, sends no tz and meets the 422
when duplicating a task or folder whose earliest due date is today or earlier, until 10.6's
next-load activation brings the new bundle down. Softening it would mean substituting the
stored zone, which 8.1 forbids by name; the client half ships in the same merge, so the
window is the service worker's update and nothing longer. A "duplicate answers 422" report
dated to the hours after this deploy is that window and not a defect.

**Annotation, 2026-09-04, issue #107. A block's `file_id` must name a file the page's own
home can reach**, and until this date it named anything at all. `putPage` inserted the id it
was handed with no clause and no composite foreign key underneath it, so a member of folder A
could plant an id from folder B and every member of A learned that a file with that id
exists — and, since #106, what shape the picture is. The bytes were never served: 7.15's
`serveFile` scopes independently, so what leaked was existence rather than content.

The scope is the page's, and it is two predicates because 4.17 gives a block exactly one
home. **A folder page scopes to its folder**, which is 7.14's `AND folder_id = $folder` for a
comment's attachment one object over. **A shelf page scopes with 7.15's own serving
predicate**, because `page_blocks.folder_id` is NULL for a shelf page and a folder clause
there compares against nothing; a shelf being private (4.18), that admits the owner's own
folder-less picture and anything in a folder they are a member of, which is the same rule
this section already applies to a shelf's cover. A block failing either answers 422 naming
the field, the block addressed by its index in the request as a schema failure on the same
block would address it, and a file that does not exist and one the caller cannot reach get
the same sentence (10.2). The PUT stays one unit, so a body refused on one block applies
none of itself.

**A PUT is whole, so this re-gates every `file_id` already stored, not only the ones being
added**, and one consequence follows that a reader meeting it cold would take for a bug. If a
block names a file the page can no longer reach — a shelf page holding a file from a folder
its owner has since left, or whose folder was trashed — then **the whole page becomes
unsaveable, unrelated blocks included**, until that block is removed, which is the answer and
the only one. Removing it is an ordinary edit of the block list. This is latent rather than
live: no client can create such a block today, page images being uploaded into the page's own
folder, so it is reachable through the API alone.

**This is a completion rather than a change of contract, and section 7 is frozen, which is
why it is written as an annotation.** The only requests it newly refuses are requests that
were disclosing another folder's file — or another person's — which 10.2 forbids by name; a
client naming files of the page it is writing sees no difference, and no such client exists
that does otherwise, page images being uploaded into the page's own folder. A composite
foreign key `(file_id, folder_id)` → `files (id, folder_id)` was priced and not taken: it is
a section 4 change needing a unique index on the referenced pair, and it cannot express the
shelf half at all. AC-375 states both homes, as a decision rather than as a proof: its test
file went in the 2026-09-20 cut.

`POST /folders/:id/page/actions` accepts `document_transaction` with UUID
`mutation_id`, opaque `base_revision`, and up to 1000 typed operations, bounded
to 2 MiB. `put_block` names stable UUID, kind, text, rich_content, file_id,
ref_folder_id, width_pct and `checked` (issue #219, 2026-09-20; omitted means
unchecked on a checklist item and none on any other kind). `delete_block` names
a block UUID. `create_task`
names a fresh stable UUID and title, creating one authoritative Dana Task.
Exactly one `set_outline` contains the complete ordered list of block/Task
identities, direct section_block_id and direct `list_parent_block_id` (issue
#219, 2026-09-20; omitted means not nested). **The outline is the whole truth
about both relations**: an omitted list parent flattens the item exactly as an
omitted Section moves it to the page root, so both travel on every item, every
time. There is no partial outline and no merge. Final bounds: 500 blocks, 1000 Tasks,
three heading levels (two until issue #218 amended this sentence on 2026-09-20,
on the technical ruling recorded there), list nesting confined to
`bullet | numbered | checklist` with every list parent preceding its
descendants, sharing their Section and forming no cycle (issue #219,
2026-09-20), contiguous subtrees, no
missing/duplicate/unauthorized identities and no implicit Task detachment. Failure rolls back the whole act.

Page reads and successful actions return revision and task_placements alongside
blocks/items. A document response also includes mutation_id, original
committed_revision, replayed, and created_task_ids. A matching receipt is read
before stale validation; a changed payload for the same identity is 409.
An obsolete base_revision is 409. The client retains its unsaved draft and
reconciles; ambiguous transport retries reuse the exact identity and payload.
Only an acknowledged server response is a save.

Legacy whole-page structural replacements of a document using the new contract
are refused with conflict, as are older structural actions that cannot preserve
its outline. An unchanged plain projection preserves rich content; an older
text edit that would erase rich content conflicts. Task-field edits remain
independent and cannot be replayed by document history.

image dimensions/width, remaps IDs and copies authorized image bytes under the
existing quota/cleanup rules. Account export format version 2 adds rich_content,
section_block_id and page_position. Workflow version 2 optionally carries a
typed document (blocks, complete outline, task_ids aligned with its Task list).
Import creates fresh block/Task IDs, validates the full outline atomically and
copies image bytes only when the importer can read their source file. Legacy
version 1 workflows retain their existing normalization and plain import behavior.

#### Labels across the acts (issue #227, on #208's M1 model)

**The through-line, and every rule below follows from it.** A Personal Label is the
viewer's own and never travels to another person; a Folder Label belongs to its Folder
and is re-created with new ids when the Folder is copied, never pointed at the source's.

**Task duplicate** carries the source's active Folder Label assignments under the **same**
ids — the copy is in the same Folder, so the vocabulary is already the copy's — and the
duplicator's own active Personal assignments. No other member's Personal assignment is
copied, and nothing archived is newly attached on either side: archive withholds the right
to be *newly applied* (#208 R5) and every row a duplicate writes is new.

**Folder duplicate** creates a new Folder-Label scope. The source's **complete** Folder
Label vocabulary is re-created under new ids with its archived state intact, the copied
Tasks' Folder Label assignments are remapped onto those ids, and the duplicator's active
Personal Labels on the source Folder and on its Tasks come across. **"Archived" is read
two ways here and both are intended**: the Folder's own retired definitions are *state
being copied*, because a copy that revived them would widen a taxonomy its owner narrowed
on purpose; the duplicator's archived Personal Labels are *not newly attached*, because
that is a new application. The copy is all-or-nothing with the rest of the duplicate.

**A Task move** removes every source Folder Label assignment in the same transaction as
the `folder_id` change — 0022's `task_folder_labels_task_scope_fkey` would refuse them
standing in any case — and leaves every Personal assignment, whoever owns it, untouched.
**No destination Folder Label is inferred, mapped or merged by name**, however exactly it
matches: scope is part of identity, so one Folder's "Urgent" and another's are two
Labels, and a move that guessed otherwise would assert something nobody said. A Folder
Label is never converted to a Personal one.

**Workflow version 3** optionally carries a Folder's reusable Label vocabulary and each
Task's assignments into it. The vocabulary is the Folder's **active** definitions,
including those no Task currently wears, since an empty category is exactly what a
template exists to set up; archived definitions are excluded, every Label in an imported
Folder being applied to work made in the same transaction. A Task names its Labels by a
**file-local key**, never a database id, and a key no folder of the file declares is
refused 422 rather than dropped. **No Personal Label definition or assignment appears in
a workflow file at any version**: the file is handed to other people and a Personal Label
is the one thing in this model that is never handed to anybody. Import creates new Folder
Label identities inside each imported Folder, remaps the keys onto them, validates name,
colour and description by the same rules a live create uses, merges against nothing by
name, and is atomic with the Folder, Task and page creation. Versions 1 and 2 import
unchanged; a version this build does not know is 422.

**Soft delete, restore and purge** need no Label machinery and have none. A soft delete is
an `UPDATE`, so every definition and assignment stands and a restore reads them back with
no repair step; a purge is a `DELETE`, so 0022's cascades take a Task's assignments, a
Folder's own Labels, its Folder-target Personal assignments and its Tasks' assignments,
while Personal **definitions** survive the purge of any target. Losing membership deletes
nothing: a retained Personal assignment stays stored, is invisible to every read while
access is gone, and reads again if access returns (#208's access-loss rule).

**Account deletion is the one case where a cascade cannot do it**, and 8.10 carries the
statement that does. `labels_owner_user_id_fkey` is `ON DELETE CASCADE`, but 8.10 step 7
*scrubs* the `users` row rather than deleting it, so the cascade never fires; the deletion
transaction deletes the account's Personal Labels explicitly, and their assignments go
with them by 0022's composite keys.

#### 2026-09-20 amendment — #220 files and media blocks

Technical authority: the ruling on issue #220,
https://github.com/zhssnym/dana/issues/220#issuecomment-5750490090, recorded before the code
as this section's freeze requires. 4.17 carries the storage half and 7.15 the upload half;
this is what a client sees.

**`put_block` takes three more `block_kind` values: `file`, `audio` and `video`.** Like
#219's six, **they are writable only through `document_transaction`**: the legacy whole-page
`PUT` keeps `section`, `paragraph`, `image` and `folder_ref`, `insert_block` above keeps
`section`, `paragraph` and `image`, and a read answers every stored kind — so a client that
cannot yet compose one still round-trips a page holding it rather than flattening it.

**A media block names at most one stored file by `file_id` and carries nothing else about
it.** A `file`, `audio` or `video` block must name one — 422 before the first write
otherwise. An `image` block need not, and 4.17 gives the two ways it comes to stand without
one. It does not carry that file's name, its MIME or its byte size, and no write shape offers
a place to send them: the `files` row is the single authority on all three, and a client
reads them from 7.15 rather than from the block. This is the same distinction the `file_width` and
`file_height` paragraph above draws, taken one step further — a measurement of a file several
blocks may share is never echoed back through a block. **A `file`, `audio` or `video` block
carries no text and no rich content of its own either** — the name under the player is the
file's and a caption is a paragraph beside it — and **no media block, `image` included,
carries a `ref_folder_id`**, a folder reference being `folder_ref`'s whole job. Each is 422
refused before any write. The `ref_folder_id` clause is a tightening on `image`, and it is stated
rather than slipped in: `folder_ref` blocks are built by the shelf layout and written through
the whole-page `PUT`, which this schema does not govern, so nothing that composes a folder
page has ever sent one. It gates what a transaction sends and nothing that is merely stored.

**`width_pct` belongs to an image and a video, and to nothing else.** The passage this amends
is the one above that reads "422 naming the field where it is out of those bounds or set on a
block that is not an image (4.17)": the admitted set is now `image` and `video`, the refusal
is otherwise unchanged, and its sentence names both. R1 extends the restrained centred width
to previewable video and stops there — audio keeps its natural compact player width and a
generic file block does not resize in M1 — and no player state is persisted at all. AC-500
and AC-501 assert both arms.

**A block's kind and its file's kind must agree, and that rule is enforced in
`applyDocument` ahead of every write rather than by a database constraint.** A `file` block
must name a `files` row of kind `file`, an `audio` block an `audio` row, a `video` block a
`video` row; an `image` block names an `image` or a `cover` row, the second only because
folder duplication has produced `cover` copies of page pictures since #128 and refusing them
would stop documents that save today from saving. **This is "insertion mode is preserved, not
re-derived"**: the same JPG is an Image block when it was dropped as media and a File block
when it was inserted through the File command, the difference is a decision a person made and
the server validated at upload, and the server never reads it back off a filename or an
extension, which are presentation and never security truth. It fails closed in the direction
that has consequences — a `file` row is untrusted bytes served as an attachment (7.15) and may
never be dressed as previewable media.

**Why not a constraint**, since this is a page-block rule and 4.17 is where such rules
usually land. Two reasons, and either is sufficient. The rule **spans two tables**, so a CHECK
cannot see the far end of the key at all. And the nearest thing a CHECK *could* have said —
that only a media kind may carry a `file_id` — is deliberately not written: `PUT /pages` and
`insert_block` have always accepted a `file_id` on a `section` or a `paragraph`, a CHECK is
validated against every existing row the moment it is added, and migrations here are forward
only with no rollback. 4.17's amendment carries the full argument.

**The refusal is its own answer and is not folded into the scope failure.** Two questions are
asked about a block's file, in this order and they are not the same question. **Scope first
(10.2, and the 2026-09-04 annotation above is unchanged):** the row must be reachable from
the page's own home, and a row that is not and a row that does not exist answer identically,
so nothing is disclosed either way. **Then the treatment, and only for a caller who has
already been told the file is here:** 422 naming the block kind and the kind the bytes were
actually uploaded as, which is the only pair a caller can act on. Folding the two together
would either leak the existence of an unreachable row or leave a legitimate caller guessing
which of the two to change. AC-499 asserts every crossed pairing and every matching one, so
the rule is a rule rather than a ban, and that a refused transaction writes nothing.

**Folder duplication and workflow import copy a page asset's kind along with its bytes.**
Both shared one primitive that wrote `kind = 'cover'` and then rewrote the copy to `image`,
which was right while a page block could only hold a picture and destroys exactly what this
amendment protects: a duplicated MP4 would come out declared an image and a duplicated
generic File would come out declared previewable media. The copy is now an independent file
of the **source's own kind**, with the nullable columns that kind is allowed to carry and no
rewrite afterwards; everything else about either endpoint — the quota charge, the 413, the
remapped identities, the workflow's refusal when the importer cannot read the source — is
unchanged. AC-503 and AC-507 assert both paths.

**And the folder duplicate's 413 is now the whole request for its page assets too, which is
a defect fixed rather than a contract changed.** The paragraph above records the same
correction for the folder's cover on 2026-09-04: the endpoint inserted the copy and then
copied the picture, so a caller at the gigabyte was answered 413 and kept an empty "(copy)"
folder. **The page-asset arm of that fault survived it and is fixed here.** A page asset's
scope is the new folder's id, so its copy cannot be moved ahead of the INSERT the way the
cover's was; and the refusal was a `return` out of the transaction callback, **which resolves
it, so the transaction committed** — measured on this branch before the change, a caller at
10.3's gigabyte got 413 and kept a "(copy)" folder with a membership row, a partial page and
every file row copied before the refusal. It now leaves by the path that rolls back, and the
bytes already written to the object store are removed by the same handler, a `put` not being
transactional and a rollback being unable to un-write one. The answer on the wire is
unchanged: 413 `quota_exceeded` with section 9's sentence. **What changes is that it is now
true of everything the request had begun to do.** The cover arm's half of that sentence —
"no row, no bytes and no folder are stored" — is AC-389, and it is a decision on the record
with no executable form: its test file went in the 2026-09-20 acceptance-suite cut, which is
issue #257's second verdict said plainly rather than left as a citation. The page assets'
half runs. AC-504 asserts it, on the store as much as on the database, so the extension is
the better-defended of the two.
#### 2026-09-21 amendment — #185 the workflow file carries the page

Authority: **the owner's technical ruling on #185, 2026-09-21** —
https://github.com/zhssnym/dana/issues/185#issuecomment-5754130075.
Imran filed the issue; the shape of the file is a technical decision and the owner ruled
it. Section 7 is frozen and this is the dated amendment that releases it.

**The header of this amendment said something else until 2026-09-21, and the correction is
worth more than the fix.** It read "Imran's ruling on issue #185" and quoted *"Format 4
serializes the page document model directly"* as "the issue's own". That sentence was not in
#185 and #185 had no comments: the format below was designed on this branch and then
attributed to a ruling that did not exist. It exists now, it is the owner's rather than
Imran's, and everything this section records was checked against it rather than assumed to
match. Four points, and this amendment carries all four:

1. *"Format 4 serializes the page document model directly"* — verbatim, and the rest of the
   ruling's first point is the four things that means here: positional membership, the
   `section` escape, `list_parent`, `level`, no ids, and the import written through
   `applyDocument`.
2. Media and `folder_ref` **export as `omitted` placeholders and import as nothing**, and
   the export surface reports the count. This is the issue's second option, chosen for M1;
   the ruling says Imran may reopen the first — a portable asset bundle — as a product
   decision, and this amendment is not it.
3. **A file may not claim structure the importer discards.** An undefined kind, a `page`
   beside `tasks`, `blocks`, `document` or `items`, a Task under a list item, and an index
   that resolves to nothing are each 422 naming the field with nothing written; a `page`
   below version 4 is dropped exactly as `labels` below 3 is, **and the picker reports the
   drop**.
4. The writer emits **one** version, formats 1 to 3 stay readable, and `EXPORT_VERSION` is
   a separate number that does not move with this one.

**What was wrong.** The workflow file carried a folder as two collections, `blocks` for its
writing and `tasks` for its work. A collection cannot say that a Task sits **under** a
Section, so it did not: a page composed as `Section A → paragraph → task → image → Section
B` imported as a block sequence and a task list, separately, with the Tasks at the page root
and the image gone without a word. #204's version 2 `document` said all of it and said it in
`uuid`s of the exporting account, which is a row the importing account has no business
resolving. Both are the same defect from opposite ends: a file that cannot describe the page
a person made.

**Workflow version 4 carries `page`, one ordered array, and it is the model 4.17 persists.**
Each entry is a block of writing, a Task, or a placeholder.

- A Section carries `level`, 1 to the three levels #218 admits, and that is the whole of how
  Sections nest in a file: a Section's parent is the open Section one level above it.
- **Every other block belongs to the innermost Section still open above it.** Membership is
  the order, which is what the ruling means by positional; there is no `section` string
  naming an id, and a task field of that shape is not what this amendment adds.
- **`section` is an escape and is written only where the order would be wrong.** This section
  admits content at the page root *after* a Section, and a purely positional file would claim
  that Section. So a block may name an open Section by its position in the same array, or
  `null` for the page root, and the writer emits the key only where the default differs from
  the truth.
- `list_parent` is #219's second parent, by position in the same array, and stays
  independent of the first.
- **A Task is a block of `kind: 'task'`** carrying the portable keys this section has always
  allowed it — title, notes, star, repeat, reminder, step titles, Folder Label keys — at its
  own position. It carries no id, no state, no date, no person: nothing this section
  excluded before is admitted now.
- **Files and media do not travel and the file says which did not.** An `image`, `file`,
  `audio`, `video` or `folder_ref` block names a row of the exporting account, and carrying
  the bytes would be 7.15's upload path inside an import. Each is written as
  `{ kind: 'omitted', was, name? }`, which creates nothing. The placeholder is the
  requirement rather than a courtesy: the file **records what it dropped** instead of
  claiming structure the importer discards.

**No index in a version 4 file is a database id**, which is #185's own requirement, and the
round trip is therefore exact: export, import into another account, export again, and the
bytes are the same less the placeholders — which do not come back, a page with no picture on
it having none to record.

**A version 4 page is refused where it cannot be read, and that is the one place this format
parts company with AC-201's "drop what cannot be a Dana object".** A block kind format 4 does
not define, a folder carrying a page *and* a `tasks`, `blocks`, `document` or `items` key,
and an index that resolves to nothing are each 422 naming the field. A file that says 4 has
said its reader understands this page, so a claim it does not honour is the file
contradicting itself — the same rule an undeclared Label key already meets. **`items` is in
that list because DES-206 wrote it as the name of `blocks`**, and a folder carrying a page
beside one is the same contradiction under the older serialiser's spelling; it is declared on
the request schema for no other purpose than to be refused here, since a key nothing declares
is stripped before any rule can see it (11.14). **Versions 1, 2 and 3 are unchanged and still
import**, and a `page` key in one of them is a foreign arrangement, dropped exactly as a
`labels` key below version 3 is — **and the import picker says so**, on the same terms it
already reports a dropped vocabulary: a file that looks imported and is not is the loss this
whole format exists to end, and it is no better for happening on the older version's side of
the line.

**And a page the schema reads and `applyDocument` refuses names the folder it came from.**
The index arithmetic is the schema's and answers with the block's own path; the structural
rules — contiguous Sections, three heading levels, a nested list item in its list parent's
Section — belong to the document transaction, which is the one implementation of them and
knows nothing about a file. Its refusal reaches the caller as the same 422 addressed from the
root as every other field of this body, `folders.<n>.page`, carrying the transaction's own
sentence. A file with two folders in it is otherwise answered with a rule and no way to tell
which folder broke it.

**`folderToWorkflowFile` writes 4 and nothing else**, and answers a count of the placeholders
it wrote beside the file. The export surface says so before anybody saves — the issue's
"if images are intentionally excluded, the UI/export action clearly communicates that
limitation" — and the count is the writer's answer rather than something the screen
recomputes, so it cannot drift from what was actually dropped.

**A completed Task on the page is left out too, and it is not a placeholder.** 7.16 has never
carried a Task's state, and a template of finished work is not a template, so the writer is
handed the folder's *pending* work and a Task it was not handed is simply not written. It is
not written as `{ kind: 'omitted' }` because a placeholder records a block of the page whose
**bytes** cannot travel — a picture, a file, a sound, a video, a link to another folder — and
a reader is entitled to conclude from one that the page held something there. A finished Task
is content this format excludes by rule at every version, exactly as a due date and an
assignee are, and writing a gap for it would make the file claim the page had a hole in it
where it does not. What a person is owed instead is being told at the moment they save, and
the writer answers that count beside the placeholder one so the export surface can say both.

AC-820 to AC-825 pin the six halves of this: Section membership across an import, a Task
moved between Sections, writing keeping its order and both parents, the placeholder and the
count, the four refusals with the version's own tolerance beside them, and the round trip.

**7.22 is untouched and was checked rather than assumed**: the account export embeds no
workflow file, so `EXPORT_VERSION` stays at 4 and nothing in that section moves. **4.17 is
untouched by this amendment for the same reason** — the one above it is #220's and is a
different change — : no column, kind, constraint or refusal of the block model moves here.
A workflow file now *serializes* that model, which is a statement about section 7.

**And #220's three kinds are already in the list above**, written there before that branch
merged. `file`, `audio` and `video` were named as omitted on the day this was written, so
the merge of #220 cost this format nothing;
`app/tests/guards/guard-workflow-page-covers-every-block-kind.test.ts` is what makes that
claim checkable rather than asserted, and it is what will fail on the next kind nobody
decided about.

The passage this amends is the opening paragraph's "It creates folders, their page blocks
(sections and paragraphs), and their tasks", which describes a version 1 file and is still
true of one. A version 4 file creates a folder and **its page**, the writing and the work in
one sequence. The sentence further down — "Workflow version 2 optionally carries a typed
document (blocks, complete outline, task_ids aligned with its Task list). Import creates
fresh block/Task IDs, validates the full outline atomically and copies image bytes only when
the importer can read their source file. Legacy version 1 workflows retain their existing
normalization and plain import behavior." — also stands as written: version 2 is still read
that way, image bytes included. What has changed is that **nothing writes it any more**.


#### 2026-09-23 amendment — #211 Purpose portability

Product authority: #211 R3. Technical authority: Hassan's ruling
https://github.com/zhssnym/dana/issues/211#issuecomment-5801396721.

**Folder duplication carries the native Purpose document.** The destination Folder first
receives its own four native facets as 4.30 requires. Its fresh Purpose identity then receives
the source Purpose's `display_name` and an independent copy of every Purpose block with fresh
block ids. Authored list parents are remapped within that copied document. Files/media use
the same `copyPageFile` path, quota accounting and rollback cleanup as Folder-page assets,
and one source file copied more than once in the same Folder duplicate is still one copied
file row.

Rich-content Dana Links are rewritten only where the duplicate already has a finite identity
map: the source Folder to the copied Folder, source native Purpose to copied native Purpose,
and a source Task to its copied Task. Every other href remains authored exactly as it was.
This is a copy transform, not a stored relationship graph, and creates no grant.

**Workflow files gain format 5 for Purpose.** Versions 1–4 remain readable unchanged. A v5
folder may carry an optional `purpose` object containing the Purpose display-name override
and one ordered document. Portable Purpose kinds are paragraph, `heading1`, `heading2`,
`heading3`, bullet, numbered, checklist, quote, callout and code. List ancestry is file-local
by position. Image/file/audio/video content is represented by the existing explicit
`{ kind: "omitted", was }` placeholder rather than an exporting-account file id, and counts
toward the export surface's omission notice. Purpose carried blocks count against the same
500-block import ceiling as the Folder page rather than gaining a second cap.

Import uses the native Purpose facet already created with the new Folder, writes the optional
display-name override, mints fresh block ids, reconstructs list parents and preserves safe
rich-content hrefs as authored references. No member, Access, Responsibility or authority
standing travels with the file. A writer that has not loaded/supplied Purpose still emits
format 4; supplying Purpose emits format 5 so an older v4 reader cannot silently strip it.
