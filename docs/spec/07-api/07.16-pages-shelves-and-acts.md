Shapes: the page read, the whole-page PUT and the discrete actions are in
`app/src/shared/pages.ts` (`getPageResponse`, `putPageBody`, `pageActionBody`); the
document transaction and its block kinds in `app/src/shared/page-document.ts`
(`documentTransaction`); shelves in `app/src/shared/shelves.ts`; the duplicate and
transfer answers in `app/src/shared/folders.ts`; the workflow file and its answer in
`app/src/shared/workflows.ts`. The structural rules of a document are enforced by
`applyDocument` in `app/src/server/domain/page-document.ts`.

**Authorization.** Any member reads a folder page; writing it, by PUT or by action, needs
Can edit or better (9.6), a non-member being 404 and a member below the bar 403. A shelf is
private by construction (4.18): every shelf route is scoped to the caller, so somebody
else's shelf is 404 and never 403 (10.2).

#### The folder page

**Reads.** A page read carries `blocks` and `items`, the ordered references to blocks and
tasks: the item list is one ordering contract, not a second task shape, Q7 remaining the
only TaskCard payload. It also carries the page's `revision` and its task placements. A
block's `section_block_id` is its semantic Section and is null for a Section, a shelf
block, or loose content. A block read carries `file_width` and `file_height`, the shape of
the file it names; **they are read-only and no write has a place for them**, because a
dimension is a measurement of a file several blocks may share, and sending it back would be
a second record of one fact. Null means unknown, and a client then draws what it would
without them. A block never carries its file's name, MIME or size either; the `files` row is
the single authority and a client reads them from 7.15.

**`file_reclaimed_at`** (issue #267) is the ISO instant the server deleted the file a media
block (`image`, `file`, `audio`, `video`) named, or null. It is non-null only while the block
still names no file, and it is what separates a picture that was chosen and is gone from one
inserted and never filled — both store a null `file_id`, because `page_blocks.file_id` is
`ON DELETE SET NULL`. Every server path that deletes a file a block may name (7.15's
`DELETE /files/:id`, 8.10's step 6a) stamps it; 7.19's reclaim never deletes a referenced
file and so never needs to. It is read-only and optional on the read, like the dimensions:
a write that keeps the block the same kind with no file preserves it, and a write giving the
block a file or another kind clears it. Blocks emptied before migration 0033 read null; no
record of those deletions exists to recover them from. A cover whose file is deleted is not
affected: its column is set null and the cover reads as having no picture, a state a cover
may legitimately be in, with no empty frame to mistake for an unfilled one.

**`width_pct`** is the person's dragged width as a percentage of the column, null where
nobody has dragged it; it belongs to an `image` or a `video` block and to nothing else, and
is 422 naming the field when out of bounds or set on any other kind. Audio keeps its natural
player width and a generic file block does not resize; no player state is persisted.

**Whole-page PUT.** LWW per block, 409 on a stale `updated_at`. It remains for shelf pages
and compatibility and re-seeds the shared order keys to the order it was asked to store. Its
block vocabulary is the legacy one; a read answers every stored kind, so a client that
cannot compose a kind still round-trips a page holding it. A whole-page structural
replacement of a document written through the transaction contract is refused 409, as is an
older structural action that cannot preserve its outline; an unchanged plain projection
preserves rich content, and an older text edit that would erase rich content conflicts.

**Discrete actions.** `POST /folders/:id/page/actions` takes one discriminated action per
request, every named field consumed. An item reference is `{ kind, id }`; no client sends
an index or a fractional key. The server locks the folder, validates both neighbours and
the Section within that folder, seeds any null keys in the sequence it just read, and
computes the key between the named neighbours. A Section heading bounds a semantic span and
is not moved as one row. A moved task changes its `page_position` and `section_block_id` in
the same transaction. Converting a paragraph reads it under the same lock, creates a real
task at its exact place and Section, and deletes the paragraph in one transaction. Stale
evidence, an invalid conversion, a deleted or cross-folder neighbour, or an unreachable file
writes nothing. No collaborative editing or OT.

**The document transaction** (`action: document_transaction`) carries a UUID
`mutation_id`, an opaque `base_revision`, and typed operations: `put_block` by stable UUID,
`delete_block`, `create_task` with a fresh stable UUID (creating one authoritative task),
and exactly one `set_outline`.

- **The outline is the whole truth about both relations**: it lists every block and task
  identity in order with its direct Section and its direct list parent, and omitting either
  moves the item to the page root or un-nests it. There is no partial outline and no merge.
- Sections are contiguous and nest to three heading levels; list nesting is confined to
  `bullet`, `numbered` and `checklist`, every list parent preceding its descendants, sharing
  their Section and forming no cycle; no identity is missing, duplicated or unauthorized,
  and no task is detached implicitly. `checked` belongs to a checklist item alone and is
  authored content, not a task's status.
- Any failure rolls back the whole act.
- **Idempotency.** A matching receipt for the `mutation_id` is read before stale validation
  and answered as a replay; the same identity with a changed payload is 409, and an
  obsolete `base_revision` is 409. The client keeps its unsaved draft and reconciles;
  ambiguous transport retries reuse the exact identity and payload. Only an acknowledged
  server response is a save. Task-field edits stay independent and are not replayed by
  document history.

**Media blocks.** `file`, `audio` and `video` are writable only through the document
transaction. Each must name one stored file and carries no text and no rich content of its
own (a caption is a paragraph beside it); an `image` may stand empty, since a picture begins
as an empty block. No media block carries a `ref_folder_id`, that being `folder_ref`'s job.
**A block's kind and its file's kind must agree**: a `file` block names a `file` row, an
`audio` block an `audio` row, a `video` block a `video` row, an `image` block an `image` or
`cover` row (folder duplication produces `cover` copies of page pictures). The insertion mode
a person chose is preserved, never re-derived from a filename or extension, and it fails
closed: a `file` row is untrusted bytes served as an attachment and may never be dressed as
previewable media. This is enforced before any write rather than by a constraint, the rule
spanning two tables.

**A block's `file_id` must name a file the page's own home can reach**, asked in this order:

1. **Scope.** A folder page scopes to its folder; a shelf page scopes with 7.15's serving
   predicate, a shelf having no folder. A file that does not exist and one the caller cannot
   reach answer the same 422 naming the field, the block addressed by its index, so nothing
   is disclosed (10.2). A PUT is one unit, so a body refused on one block applies none of
   itself; and because a PUT is whole, it re-gates every stored `file_id`, so a page holding
   a block whose file became unreachable cannot be saved until that block is removed.
2. **Treatment**, only for a caller already told the file is reachable: 422 naming the block
   kind and the kind the bytes were uploaded as, the only pair a caller can act on. Folding
   the two would either leak an unreachable row's existence or leave a legitimate caller
   guessing.

#### Shelves

**PATCH /api/v1/shelves/:id takes the cover**: `cover_file_id`, `cover_preset` and
`cover_focal_y`, behaving as 7.4's three fields do for a folder — one source, so a file
arriving clears the preset and the reverse, and a body naming both is 422 naming the pair.
**The named file must be a picture the caller can reach**, `kind` in (`cover`, `image`) and
readable by 7.15's serving predicate, or 422 naming the field, a missing file and an
unreachable one getting the same sentence (10.2). Setting a cover follows 7.19's lifetime
rules, so the PATCH also answers **413 `quota_exceeded`** where the copy would pass 10.3's
1 GB. A duplicate name is 422.

**The Shelf document (#221).** `GET /shelves/:id/page` answers the Shelf's own `revision`
(the page read's shape, `task_placements` always empty), and
**`POST /api/v1/shelves/:id/page/actions`** takes `documentTransaction` alone — the same body,
`base_revision`, receipts and 409 as the folder page's transaction, answering the page read
plus `mutation`. The content is the Shelf's existing blocks in place: nothing is migrated, and
the stored order is the first revision's. A **Folder row** is a `folder_ref` block, as the
legacy editor stores it; the Folder's membership stays `folder_members.shelf_name`, so a
written `folder_ref` must name a live Folder the owner has **on this Shelf** and at most one
block places any one Folder, or 422 naming `ref_folder_id`. A stored `folder_ref` whose Folder
has left the Shelf is not audited and a reader skips it; an on-Shelf Folder with no block is
drawn after the content. A Shelf holds no Tasks, no Section membership and no nested list
items: `create_task`, a `section_block_id` and a `list_parent_block_id` are 422 naming the
field (a `section` block itself is admitted, flat). Files scope as the whole-page PUT's do,
with #220's kind pairing. Another person's Shelf is 404. Retries are keyed by (Shelf,
`mutation_id`) in `shelf_document_receipts` (migration 0032). **Once a Shelf has a receipt, or
holds a block kind or rich content the legacy editor cannot draw, `PUT /shelves/:id/page` is
refused 409** and writes nothing, since it would delete what it cannot draw; a Shelf the
document path has never written keeps the legacy PUT unchanged.

**POST /api/v1/shelves refuses a cover rather than dropping it** (11.14's `z.never`): a shelf
is made and then dressed, and a field an endpoint does not honour must say so out loud.

**POST /api/v1/shelves/:id/duplicate** answers 201 with the new shelf. The name is marked
`(copy)`, or `(copy 2)` and upward where that is taken, fitted inside 10.3's length by cutting
the base rather than the suffix, 4.18's unique name admitting no second `X (copy)`. Icon,
colour, description, `cover_preset` and `cover_focal_y` copy verbatim; **`cover_file_id`
becomes a file of its own**, copied by 7.19's rule 1, spending the caller's quota and
answering 413 if it will not fit. The shelf's page is not copied. It is one route rather
than a create followed by a PATCH because two calls leave a half-duplicated shelf in the
gap, and one `cover_file_id` shared by two shelves is not independence: deleting that file
would blank both.

#### Duplicates

**Task duplicate** (`POST /tasks/:id/duplicate`) carries the title, the notes, the
importance, the section, the steps with every step undone, the due date and the repeat, and
never the conversation, the completion or the assignment; the copy is assigned to and
created by whoever made it. It carries the source's active Folder Label assignments under
the same ids (the copy is in the same folder) and the duplicator's own active Personal
assignments; no other member's Personal assignment is copied, and nothing archived is newly
attached. 201 with the new TaskDetail; member access on the source, 404 otherwise.

**Folder duplicate** (`POST /folders/:id/duplicate`) answers `{ id, name, shifted_days }`
(`duplicateFolderResponse`): `shifted_days` is how many days the plan moved when its
earliest date was spent, 0 when every date kept, and the copy's `duplicated` event carries
"dates moved to start today" exactly when it is positive, which 9.6's bar reads. The copy:

- carries the folder's cover picture, copied **inside the new folder** and charged to the
  duplicator, beside `cover_preset` and `cover_focal_y`;
- preserves rich runs, direct ancestry, mixed placement and image dimensions and width,
  remaps every id, and copies each page asset's bytes as an independent file **of the
  source's own kind**, so a duplicated video is not declared an image nor a generic file
  previewable media;
- re-creates the source's **complete** Folder Label vocabulary under new ids with its
  archived state intact, remaps the copied tasks' assignments onto them, and brings the
  duplicator's active Personal Labels on the folder and its tasks. A copy that revived
  retired definitions would widen a taxonomy its owner narrowed on purpose;
- carries the native Purpose document: the new folder's own native Purpose receives the
  source's `display_name` and an independent copy of every block with fresh ids and list
  parents remapped, its files copied on the same path, quota and cleanup as page assets, one
  source file copied once per duplicate. Rich-content Dana Links are rewritten only through
  the duplicate's own identity map — source folder to copy, source Purpose to copied
  Purpose, source task to copied task — and every other href stays as authored; this is a
  copy transform, not a stored relationship, and grants nothing;
- does **not** carry the native Results document (#213): Results are the source Folder's
  actual outcomes rather than reusable context, so the copy's native Results starts empty
  under its default name. A Dana Link to the source's Results is left as authored.

**Every refusal writes nothing.** A folder duplicate refused 413 on the cover or on any page
asset rolls back entirely, including the bytes already written to the object store, which
the handler removes because a rollback cannot un-write them; a refused duplicate never
leaves an empty "(copy)" folder counting against 10.3's folder cap. A copy that would pass
that cap is 422.

**Both duplicates take `tz`**, because a spent due date re-anchors on today and 8.1 defines
today in the request's zone; substituting the database's zone is what 8.1 forbids by name. A
`tz` present and not an IANA identifier is 422 naming it. A `tz` absent is 422 naming it
**exactly when a date would be re-anchored**; the test for that is zone-free and errs towards
asking, so a source with no due date, or whose earliest due date is ahead of today in every
zone, needs none. With `tz`, the copy re-anchors on `today(tz)` and `shifted_days` counts in
that zone. A spent due date re-anchors on today and a future one keeps, 9.6's rule.

#### Workflow import

`POST /api/v1/workflows/import?tz` takes a zod-validated structure file under section 10's
caps and creates folders, their pages and their tasks in one transaction; 201 with the
created folders' ids and names. A copy that would pass the folder cap is 422.

**What a file carries is an allow-list, not a scrubbing pass.** A task carries its title,
notes, star, repeat, reminder, step titles and Folder Label keys; never ids, people, due
dates or states, a step's tick included. What is left out belongs to one run of the work
rather than to the work: a due date is a moment in a run, a person is an account that may not
exist where the file is opened, and a state or a conversation records what happened rather
than what to do. **No index in a file is a database id**, and no member, Access,
Responsibility or authority standing travels. **No Personal Label definition or assignment
appears at any version**: the file is handed to other people, and a Personal Label is never
handed to anybody.

**The import-day anchor.** Where a task carries a repeat or a reminder, the imported task is
anchored on the import day in the zone `tz` names, 4.5 and 8.6 admitting neither without a
date. The file still carries no date; the task's date is the day its run began. `tz` is 422
when present and invalid, and required as 422 exactly when the file carries such a task.

**Versions.** The writer emits one version; older ones stay readable and a version this
build does not know is 422. The account export's version is a separate number (7.22).

- Version 1 carries a folder's blocks and tasks as two collections and is normalized as
  before.
- Version 2 optionally carries a typed document with a complete outline; import mints fresh
  block and task ids, validates the outline atomically, and copies image bytes only where the
  importer can read the source file. Nothing writes it any more.
- Version 3 optionally carries a folder's **active** Label vocabulary, including Labels no
  task wears (an empty category is what a template sets up), and each task's assignments by
  a **file-local key**. A key no folder declares is 422. Import creates new Folder Label
  identities, validates them as a live create would, merges against nothing by name, and is
  atomic with the rest.
- **Version 4 carries `page`, one ordered array serializing 4.17's model**, each entry a
  block of writing, a task (`kind: 'task'`), or a placeholder. A Section carries `level`, its
  parent being the open Section one level above; every other entry belongs to the innermost
  Section still open above it, membership being the order. `section` is an escape written
  only where order would be wrong (content at the page root after a Section), naming an open
  Section by position or `null`. `list_parent` is the list parent by position. **Media and
  `folder_ref` do not travel**: each is written as `{ kind: 'omitted', was, name? }`, which
  imports as nothing, and the writer reports how many it wrote so the export surface says so
  before anybody saves. A completed task is left out and is not a placeholder, a placeholder
  meaning the page held something whose bytes could not travel. The round trip is exact less
  the placeholders.
- Version 5 adds an optional `purpose`: the Purpose display-name override and one ordered
  document of the portable Purpose kinds, list ancestry by position, media as the same
  `omitted` placeholder. Its blocks count against the same page block ceiling. Import writes
  into the native Purpose created with the new folder, mints fresh ids and keeps safe hrefs as
  authored. A writer with no Purpose to carry emits version 4, and one carrying Purpose emits
  5, so an older reader cannot silently strip it. No version carries Results (#213), for
  the duplicate's reason: a workflow is reusable intention, and Results are one Folder's outcomes.

**Internal Task dependencies travel; external ones do not (#207).** At any version a task may
carry an optional file-local `key`, unique across the whole file, and `depends_on`, the keys of
the tasks it waits on. The writer emits both only for an edge whose two ends are both in the
file, so a folder with no dependencies writes the same bytes as before and a file without the
keys imports as before. Import recreates every edge whose both keys the file declares, across
its folders, in the same transaction; a key the file does not declare is skipped, being a task
outside the workflow. A duplicated key, a task depending on itself and a cycle of any length
are 422 naming the field, with nothing written, as the live endpoint refuses each. No version
bump: an older reader strips both keys and imports the work without its ordering.

**A file may not claim structure the importer discards.** In a version 4 or later page, an
undefined kind, a `page` beside `tasks`, `blocks`, `document` or `items`, a task under a
list item, and an index that resolves to nothing are each 422 naming the field, with nothing
written. A structural refusal from the document transaction is addressed as
`folders.<n>.page`, so a file with several folders says which one broke. Below its version,
a `page` or `labels` key is dropped, **and the import picker reports the drop**.

#### Transfer of ownership

`POST /api/v1/folders/:id/transfer-ownership { to }` — owner-only; Full control does not
confer it. The target must be a member who currently holds Full control (9.6), or 422 naming
`to`. The default folder cannot change hands, 409. 200 with the new owner's id; 8.9's
direct form.

#### Labels across the other acts

A Personal Label is the viewer's own and never travels to another person; a Folder Label
belongs to its folder and is re-created with new ids when the folder is copied, never
pointed at the source's.

- **A task move** removes every source Folder Label assignment in the same transaction as the
  `folder_id` change and leaves every Personal assignment untouched. **No destination Folder
  Label is inferred, mapped or merged by name**: scope is part of identity. A Folder Label is
  never converted to a Personal one.
- **Soft delete and restore** need no Label machinery: every definition and assignment stands
  and reads back. **A purge** cascades a task's assignments, a folder's own Labels, its
  folder-target Personal assignments and its tasks' assignments, while Personal definitions
  survive the purge of any target. **Losing membership deletes nothing**: a retained Personal
  assignment is invisible while access is gone and reads again if it returns.
- **Account deletion** scrubs the `users` row rather than deleting it, so the cascade from
  Labels to their owner never fires; 8.10 deletes the account's Personal Labels explicitly.
