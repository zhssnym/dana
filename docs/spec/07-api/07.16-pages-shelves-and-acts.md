### 7.16 Pages, shelves and acts

GET/PUT /api/v1/folders/:id/page — the block list, LWW per block, 409 on stale updated_at.
CRUD /api/v1/shelves and GET/PUT /api/v1/shelves/:id/page. POST
/api/v1/tasks/:id/duplicate · POST /api/v1/folders/:id/duplicate — the DES-198 copy rules
server-side. POST /api/v1/workflows/import?tz — zod-validated structure file, caps per
section 10. It creates folders, their page blocks (sections and paragraphs), and their
tasks, and a task carries its title, notes, star, repeat, reminder and step titles; never
ids, people, due dates or states, a step's tick included. Where a task carries a repeat or
a reminder, the imported task is anchored on the import day in the zone tz names, 4.5 and
8.6 admitting neither without a date; tz is refused as 422 when present and invalid, and
required as 422 exactly when the file carries such a task. POST
/api/v1/folders/:id/transfer-ownership { to: user_id } — owner-only, member target, the
DES-225/8.9 flow.

A block object carries `width_pct: integer or null` beside its position: the person's
dragged width as a percentage of the column, 25 to 100, null where nobody has dragged it,
and 422 naming the field where it is out of those bounds or set on a block that is not an
image (4.17).

A block read also carries `file_width` and `file_height`, integer or null: the shape of the
picture `file_id` names, 4.16's own columns as issue #27 and migration 0009 added them on
2026-09-03. **They are read-only and the PUT has no place for them**, which is the whole
distinction from `width_pct` above: a width is a decision somebody made about this block and
a PUT carries it; a dimension is a measurement of a file that several blocks may share, so
sending it back would be a second record of one fact. Null means unknown — a block with no
file, or a file stored before 0009, no backfill having been run — and a client must then
draw exactly what it drew before the fields existed. A PUT that echoes a block back, which
7.16's PUT-whole contract makes every client do, therefore cannot carry the shape and must
not lose it.

**Annotation, 2026-09-04, issue #107. A block's `file_id` must name a file the page's own
home can reach**, and until this date it named anything at all. `putPage` inserted the id it
was handed with no clause and no composite foreign key underneath it, so a member of folder A
could plant an id from folder B and every member of A learned that a file with that id
exists — and, since #106, what shape the picture is. The bytes were never served: 7.15's
`serveFile` scopes independently, so what leaked was existence rather than content.

The scope is the page's, and it is two predicates because 4.17 gives a block exactly one
home. **A folder page scopes to its folder**, which is 7.14's `AND folder_id = $folder` for a
comment's attachment one object over. **A shelf page scopes with 7.15's own serving
predicate**, because `page_blocks.folder_id` is NULL for a shelf page and a folder clause
there compares against nothing; a shelf being private (4.18), that admits the owner's own
folder-less picture and anything in a folder they are a member of, which is the same rule
this section already applies to a shelf's cover. A block failing either answers 422 naming
the field, the block addressed by its index in the request as a schema failure on the same
block would address it, and a file that does not exist and one the caller cannot reach get
the same sentence (10.2). The PUT stays one unit, so a body refused on one block applies
none of itself.

**This is a completion rather than a change of contract, and section 7 is frozen, which is
why it is written as an annotation.** The only requests it newly refuses are requests that
were disclosing another folder's file — or another person's — which 10.2 forbids by name; a
client naming files of the page it is writing sees no difference, and no such client exists
that does otherwise, page images being uploaded into the page's own folder. A composite
foreign key `(file_id, folder_id)` → `files (id, folder_id)` was priced and not taken: it is
a section 4 change needing a unique index on the referenced pair, and it cannot express the
shelf half at all. AC-375 asserts both homes.

**Amendment, 2026-09-03, issues #20 and #100 (migration 0012). PATCH /api/v1/shelves/:id
takes the cover, and until this date it accepted it and threw it away.** Imran ruled on #20
that folders, shelves and the built-in pages get the same cover options; the owner directed
the work. #100 is the defect underneath: `shelves.cover_file_id` has existed since migration
0003, `SHELF_COLUMNS` selected it, the `Shelf` shape carried it and `trash.ts` guarded files
against it, and **no route ever wrote it**, while `client/lib/page-identity.ts` has been
sending it to this endpoint since S27. Nothing in `app/src/shared/` is `.strict()`, so the
field was parsed away and the person was told it worked — 200 with `cover_file_id: null`,
measured on the wire.

The body now takes `cover_file_id` (uuid or null), `cover_preset` (4.20's key alphabet, or
null) and `cover_focal_y` (0 to 100), which are 7.4's three fields for a folder and behave
as they do there: **one source**, so a file arriving clears the preset and a preset arriving
clears the file, and the client never sends the null it means; a body naming both is 422
naming the pair rather than a constraint violation answered as a 500. **The named file must
be a picture the caller can reach** — `kind` in (`cover`, `image`), and readable by 7.15's
own serving predicate — or 422 naming the field, which is 7.4's answer for the same field on
a folder and discloses nothing, a file that does not exist and one the caller cannot reach
getting the same sentence (10.2). A shelf being private (4.18), the file is normally the
caller's own with no folder.

**POST /api/v1/shelves does not take a cover and refuses one rather than dropping it**, as
`z.never(…).optional()` per the #40 ruling (grounds in 11.14): a shelf is made and then
dressed, and this endpoint's whole history is the reason a field it does not honour must say
so out loud. The read shape gains `cover_preset` and `cover_focal_y` beside the existing
`cover_file_id`. AC-368, AC-369 and AC-373 assert it.
