### 7.4 Folders and membership

- GET /folders. All accessible folders as Folder objects. Sort: is_default first, then
  lower(name), id. - POST /folders. { name }. Creates folder with owner = V plus owner
  membership (one transaction). 201 Folder. 422 name length; 422 when V already has 200
  custom folders (limit, section 10.3). - GET /folders/:id. Folder plus members [{user,
  role, joined_at, is_owner}] plus pending invites [{id, email, task_id, created_at,
  last_sent_at}]. 404 if not member. - PATCH /folders/:id. { name }. Owner only (403
  otherwise); works for the default folder too (rename allowed). 200. - DELETE
  /folders/:id. Owner only. 409 if is_default (INV-2). Executes the deletion cascade
  (section 8.8). Response 200 { deleted: {tasks_open, tasks_completed, tasks_abandoned} }
  so the client can confirm what the dialog promised. Invariants: INV-1 via cascade. -
  PATCH /folders/:id/my-membership. { label, color }, either nullable. Any member, own row
  only. 200. - POST /folders/:id/members. { user_id }. Any member; guards per 5.3 row 1:
  409 default folder, 409 already member, 422 no roster connection between V and target,
  422 member cap 25. Sends share-grant email. 201. - DELETE /folders/:id/members/:userId.
  Three legal shapes per 5.3: owner removes another member; non-owner removes self
  (leave); owner removes self, which transfers ownership first when other members exist
  and is 409 "delete the folder instead" when sole member. All run R-CLEAN. 204.
  Invariants: INV-4, INV-5, INV-10.

Response shapes, settled at the P2 shape review and entered by owner ruling: GET /folders
answers the bare array of Folder objects, no wrapper key. The folder detail's invite key
is pending_invites, its elements carrying exactly the five fields above. The user object
inside a members element is {id, display_name, avatar_url}, the person shape TaskCard's
assignee carries, and includes no email. A 7.4 mutation answers what a fresh GET would:
PATCH /folders/:id and PATCH /folders/:id/my-membership answer the Folder object, and POST
/folders/:id/members answers the members element it created.

**PATCH /folders/:id/my-membership makes the shelf its label names** where the
viewer has none of that name, in the same transaction as the label write, and
answers the Folder object exactly as before (amended 2026-09-03, issue #65,
declared against the freeze). 4.18 already required the API to hold a shelf's
name and its members' labels in step and this is the direction that was
missing: a label naming no shelf is a Library heading with no id behind it, so
9.1's "each folder and shelf row: Links" and 9.10's page have nothing to point
at. Nothing else about the endpoint moves — the body, the status, the response
shape, the own-row-only scope and the 10.3 bounds are unchanged, the shelf name
and the personal label sharing one 1-to-40 row there. `{ label: null }` clears
the label and leaves the shelf, a shelf outliving its folders (9.1). The
labels already stored are repaired once by migration 0011.

**Amendment, 2026-09-20, issue #226, on the technical ruling recorded there** (parent #208).
The body of PATCH /folders/:id/my-membership is **`{ shelf, color }`**, and `shelf` is the
field written `label` above: the same field, writing the same column, renamed because that
column was never a classification Label and #208's Label model (7.26) needed the word back.
Nothing about the endpoint's semantics moves — the any-subset presence rule, the null clear,
the own-row-only scope, the 1-to-40 bound and the shelf-making sentence above are all what
they were, with "label" read as "shelf".

**For this release the body accepts `either` spelling, and if both are present `shelf`
wins.** That is expand-and-contract applied to the wire, and it is not politeness toward an
old client: this body is a `z.object`, 7.0 tolerates unknown keys and 11.14 rules that no
shared schema becomes strict, so **a stale tab's `label` would be silently stripped, `shelf`
would then be absent, the handler would read that as "not provided", and the request would
answer 200 having stored nothing** — the person renames their shelf, is told it was
accepted, and loses the edit. One deployable serves the SPA and the API together while a
browser tab keeps its old bundle for as long as somebody leaves it open, so this is not
bounded by the deploy window the way 4.4's column outage is. Declaring the old key is what
makes the deploy safe; `shelf` winning a tie is because a client sending both is a new bundle
and the new name is what a new bundle means.

The response is unchanged in shape and carries the pair 7.0 describes: `my_shelf` and
`my_label`, the same value under both keys. **Issue #247 is the contract half** and drops
`label`, `my_label` and `folder_members.label` in one change, after migration 0022 is live in
production. AC-481 is the criterion that asserts the pair, against the row rather than only
the response; AC-479 is the one that says the terminology move changed nothing else.

The Folder object carries `cover_preset` (text or null) and `cover_focal_y` (0 to 100)
beside `cover_file_id`. PATCH /folders/:id takes `cover_preset` (nullable) and
`cover_focal_y` beside `cover_file_id`, any member as for the rest of the 4.3 identity; a
body naming both a file and a preset is 422, and setting either source clears the other.
(Amend unit of RFC 0005 change control item 58, H, ruled by delegation 2026-08-30 and
folded here the same day; it takes section 13 item 53's first answer, and 4.3 carries the
two columns.)

**A cover file's lifetime is 7.19's, for a folder as for the other two page kinds
(2026-09-04, issues #116 and #128).** Nothing about this endpoint's behaviour moves: the
gate here has always required the named file to be a file *of that folder*, so 7.19's rule 1
finds a cover already in the page's own scope and copies nothing, and a folder-scoped cover
file is out of rule 2's reclaim entirely — it is listed in its folder, its members can delete
it, and 8.8's purge takes it with the folder. Two things do follow. `POST
/folders/:id/duplicate` now carries the cover **picture** and not only the preset and the
crop, copied into the new folder (7.16 as amended, AC-293 unchanged). And a duplicate whose
copy would take the caller past 10.3's 1 GB answers **413 `quota_exceeded`**.

**POST /folders takes `description` beside the name** (added 2026-09-04, issues #21
and #70, declared against the freeze; additive, and the field is the nullable one
4.3 already carries and PATCH /folders/:id already writes). Absent or null is NULL,
which is what every folder made before this carries, so nothing that sent `{ name }`
changes. The 201 answers the same Folder object, its `description` now the sentence
the create was given. On Imran's ruling that a new folder starts with a sentence
rather than an empty line: `defaultFolderDescription(name)` in the client writes one
at both doors that make a folder.

**Why it is on the create rather than a PATCH behind it**, which is the owner's ruling
of the same date. The gesture that makes a folder is one request and has to stay one:
AC-279 reads every mutation the hold writes between the confirm and the API going
quiet and admits `POST /folders` plus one `PATCH /tasks/:id` per task moved and
nothing else, RFC 0005 change control item 44 having priced that gesture as "a
composition of two existing endpoints" that "adds none". A follow-up PATCH is
therefore not a slower spelling of this feature, it is a different act, and it failed
that criterion from every door. It also reports the
wrong failure when it fails: the folder exists and is named, the second call is what
was refused, so the person sees a folder that was made and a message saying something
did not work, and a retry makes a second folder. One request has one outcome.

- **PATCH /folders/:id is Can edit and above, not "Owner only (403
  otherwise)".** Authority: **accepted #209 R8A** — Can edit may "plan/change
  all shared Folder work", Can view is "read only", and a folder's name,
  description, icon, colour and cover are shared Folder work. Ownership is
  neither necessary nor sufficient: a Full-control member who owns nothing
  renames, and an owner holding Can view is refused 403. It still works for the
  default folder. The gate is `folder.profile.edit`; 403 to a member below the
  bar, 404 to a non-member, which is 10.2's order and not this endpoint's
  choice. (AC-011, AC-012, AC-193.)
- **DELETE /folders/:id is Full control, not "Owner only" — and it is no
  longer an owner-only act at all.** Authority: **Hassan's ruling of
  2026-09-20**, and not R8A, which settles it neither way. Ownership is
  *ignored* by this gate rather than being one of two ways in: a Full-control
  member who does not own the folder may trash it, and an owner whose own
  Access has been lowered below Full control may not. The gate is
  `folder.trash`. Everything else about the endpoint is unchanged — 409 if
  `is_default` (INV-2), the 8.8 cascade, and the same 200 body. The two acts
  that *are* custody's are `folder.restore`, where ownership is sufficient, and
  permanent destruction, where it is required. (AC-015.)
- **POST /folders/:id/members is Full control, not "Any member", and its body
  is `{ user_id, access }` rather than `{ user_id }`.** Authority: **accepted
  #209 R8A** — Full control "administer members", and Can edit "cannot
  administer people/Access". `access` is required and has no default, because a
  default would be one person's authority chosen by nobody; it is one of the
  six presets, 422 otherwise, and it is the preset the new membership holds.
  The 5.3 row 1 guards are unchanged (409 default folder, 409 already member,
  422 no roster connection, 422 member cap 25), as is the share-grant email and
  the 201. (AC-024, AC-512.)
- **A members element is `[{user, role, access, joined_at, is_owner}]`.**
  Authority: **accepted #209 R8A** with R9 section 13. `access` is the member's
  current preset and is visible to every member of the folder: knowing what the
  people you work with may do is ordinary Work awareness. It sits *beside*
  `role` rather than replacing it — `role` expressed no authority before this
  change and expresses none after it, and dropping a field from a frozen
  response is a separate decision from adding one. `role` is still exactly
  `'member'`, and ownership is still `is_owner` from `folders.owner_id` (8.9).

**Two further rows of the same paragraph were found false by the verification
that ruling asked for, and are corrected here on the same records.** They were
not in the four the ruling enumerated; each is listed separately so that a
later reader can tell what was ruled row by row from what was found by checking
the text against the code.

- **A pending-invites element is `[{id, email, task_id, access, created_at,
  last_sent_at}]`, and the list is `[]` for every member below Full control.**
  Authority: **Hassan's Ruling 2 of 2026-09-20**, which accepted in terms "the
  7.4 member element gaining `access` while `pending_invites` answers `[]`
  below Full control". A pending invite's address and intended Access are
  member-administration data rather than ordinary Work. The key is always
  present and always an array: a key that appeared and disappeared by authority
  would make "you may not see this" and "there are none" two shapes for the
  client to handle, and the second is the one the panel already renders.
- **DELETE /folders/:id/members/:userId has three legal shapes still, but two
  of the three moved.** Removing *another* member is **Full control's** rather
  than the owner's (accepted #209 R8A, "administer members"), and the folder's
  owner may not be removed by anybody — 403 — because ownership is given up by
  transfer and not taken. An owner removing *themselves* is **409 "transfer
  ownership before leaving"** rather than an automatic transfer to another
  member: authority is **governing #209 R6** section 2, which R8A's supersession
  clause keeps governing for explicit owner succession by name, and there is no
  automatic succession. The sole-member case is unchanged and still answers 409
  "delete the folder instead". A non-owner leave is unchanged except that it is
  refused 409 when it would leave the folder with nobody in Full control. The
  one automatic transfer that survives anywhere is 8.10's account-deletion
  path, which R6 section 3 keeps as a distinct audited recovery. R-CLEAN, the
  204 and INV-4, INV-5 and INV-10 are all unchanged. (AC-016 to AC-020, AC-520,
  AC-521.)

**What this correction does not do is make 7.4 complete.** Ruling 2 also

**The Folder object carries `my_access`** (added 2026-09-20, Hassan's Ruling 4,
https://github.com/zhssnym/dana/issues/228#issuecomment-5751449643; a dated
amendment in the same shape `cover_preset`, `cover_focal_y` and `description`
got theirs). It is **the viewer's own** Access preset, one of R8A's six, never
null, and it is the same value that viewer's own element of `GET
/folders/:id`'s `members` carries. It is not the owner's preset and not the
folder's: two members of one folder at two presets read two different values
from the same row of `GET /folders`, which AC-674 asserts.

**Why it is on the list object rather than left to the detail.** 7.0's Folder
object carried no Access preset for anybody, so the Library rows of 9.1 — built
from `GET /folders` and never from a detail — had nothing to gate on but
`is_owner`, which is now neither necessary nor sufficient for any of the three
acts a row offers. Two defects followed and both were measured: a Full-control
member who is not the owner was offered no Rename, and an owner whose Access
had been lowered was still offered Delete. The three workarounds were rejected
and the reasons are worth keeping, each being the obvious idea: a per-row
detail fetch is up to 200 requests; reading the detail out of the client's
query cache is right for visited folders and wrong for the rest, which is worse
than being consistently wrong; and `member_count === 1` does prove Full control
— the continuity invariant refuses a sole member's self-demotion — but both
defects live on *shared* folders. It costs one column on a query that already
joins the viewer's membership row, and the alternative — dropping Rename and
Delete from the Library row altogether — would make every row a worse
affordance to fix a bug in two of them.

**Amendment, 2026-09-21, issue #230, on the accepted technical ruling**
https://github.com/zhssnym/dana/issues/230#issuecomment-5751322947 **(Ruling 2, section
7).** Five routes are added and **nothing existing changes shape**: no field is removed
from a response above, no status moves, and no body is reinterpreted. Product authority is
#209 R5, R7 section O, R10 and the accepted R10B; the tables are 4.28 and 4.29.

- **GET /folders/:id/members/:userId.** The member-details projection. Any member of the
  folder (`folder.read`), 404 to anybody else. Answers `{ user, is_owner, joined_at,
  access, can_edit_own_responsibilities, responsibility, assigned_open_task_count,
  viewer_may_change_access, viewer_may_change_self_edit_grant,
  viewer_may_edit_responsibility, history: { responsibility_path, access_path } }`. The
  three `viewer_may_*` flags say whether a control is worth rendering and **authorize
  nothing**: every route below asks the question again for itself, which R8A requires by
  name. `responsibility` is the same standing object the next route answers. The
  projection costs a constant number of statements however many members it is asked about,
  which AC-573 asserts by counting them.
- **GET /folders/:id/members/:userId/responsibility.** Any member, 404 to anybody else:
  #209 R5 makes the document Folder-visible in M1, which means visible to the Folder and
  to nobody outside it. Answers `{ member_id, responsibility }`, where the standing
  carries `responsibility_id`, `revision`, `current_revision_id`, `revision_no`,
  `content`, `updated_at`, `updated_by` and `active`. **A member who has written nothing
  and a former member both read the empty standing rather than 404**, deliberately: "there
  is none" and "you may not see it" must not be two answers a prober can tell apart.
- **PUT /folders/:id/members/:userId/responsibility.** `{ content, base_revision }`. Full
  control writes any active member's, including their own; anybody else writes **only
  their own and only when `folder_members.can_edit_own_responsibilities` is set** (4.4).
  200 `{ member_id, committed, responsibility }`; 403 when the resolver refuses; 404 when
  the target is not a member of a folder the caller can see; 422 on content that is not a
  valid document, on an unsafe link or on an unknown document version; **409 when
  `base_revision` is not the current revision**. The order of those last two answers is
  part of the contract: a commit whose content already equals the current content is
  `{ committed: false }` and 200 **whatever `base_revision` said**, and only then is a
  stale base a conflict — which is what makes a retry after a lost answer safe without a
  receipts table. The decision is taken inside the write's own transaction, because it can
  depend on the target's grant and that fact must be read under the lock that authorizes
  the write.
- **GET /folders/:id/members/:userId/responsibility/history.** Any member, 404 to anybody
  else — **a former member is refused their own history**, being no longer in the folder
  rather than because anything hides the subject from themselves. Answers
  `{ entries, truncated }`. Each entry carries `id`, `folder_id`, `member_id`,
  `responsibility_id`, `transition`, `revision_no`, `content`, `actor` and `effective_at`.
  **The entries are newest first, capped at 1000 rows per 10.3, and `truncated` is true
  when the cap cut** — added by a ruling of its own,
  https://github.com/zhssnym/dana/issues/230#issuecomment-5754627068 **(Ruling 3,
  2026-09-21)**, taken after this change's second adversarial review. Ordering it
  oldest-first with a silent cap served a busy folder the first entries of its life and
  reported them as the record, and 10.3's list-response rule is that a short list is never
  silently short. **The cap is 10.3's own row for list responses and not a cap of this
  route's**, which is why 10.3 is not amended here: a second number would be the contract
  decision 10.3 says its table has not taken. `truncated` is true only when a row past the
  cap exists, so a record holding exactly 1000 entries answers whole with `truncated:
  false`, which AC-573 pins as its own case. The flag is a fact about the answer, not a
  capability. **What this is not is a paged read**: a thousand entries each carrying a
  document snapshot is bounded by the 256 KiB content cap and nothing else, and a paged
  read — or a list shape without `content` beside a per-revision body route — is a
  contract decision left to a later issue by the same ruling.
- **PUT /folders/:id/members/:userId/self-edit-grant.** `{ enabled }`. **Full control
  only** (`responsibility.self_edit_grant.manage`), 403 to any member below it, 404 to
  anybody outside the folder, and **403 for the folder's owner as target** — they need no
  grant to write their own, and nobody else administers the owner's standing (R7 section
  M). 200 `{ member_id, can_edit_own_responsibilities, changed }`, with `changed` false
  when the toggle was already where it was asked to be. Both directions are recorded in
  4.29 with the administrator as actor.

**What the grant is not.** It is not a sixth Access preset and it widens nothing else:
`shared/folder-actions.ts` admits it for one action, and only when the member it names is
the actor. A member holding it may neither pass it on nor give themselves one, and it does
not follow them into another folder. AC-563 drives every preset against every action to
pin that exactly one answer moves.

**POST /folders/:id/members and POST /invites may carry `responsibility`**, the initial
document an administrator chooses for the person they are adding. On the instant-share
path the document and its first revision are written with the membership; on the invite
path the content is parked on the invite row (4.9) and becomes a document **at
acceptance**, whose actor is the inviter rather than the person who accepted. An
invitation naming no folder carrying one is 422. Both bodies are unchanged for every
caller that sends no `responsibility`, the key being optional, and AC-569 drives both
paths.
