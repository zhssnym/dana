### 7.19 Place covers

GET /api/v1/place-covers — the caller's own covers, one entry per place they
have chosen one for, each carrying place, file_id, preset and focal_y.
PUT /api/v1/place-covers/:place — body { file_id } or { preset }, exactly one
of the two (422 naming the pair otherwise), plus an optional focal_y of 0 to
100 defaulting to 50; a named file must be one the caller can read (404 by
10.2's rule, never 403). Idempotent, 200 with the entry.
DELETE /api/v1/place-covers/:place — removal, 204, idempotent.
`:place` is 4.20's set and anything else is 404, a place page being furniture
rather than a resource that might exist elsewhere. Covers are the caller's
own throughout: no route reads or writes another person's, and a folder's or
a shelf's cover stays where 7.4 and 7.16 already put it.

**Annotation, 2026-09-03, issues #20 and #100. The clause "a named file must be one the
caller can read" is unchanged as text and narrower in fact, because what it pointed at was
wrong.** The implementation carried its own transcription of 7.15's serving predicate, and
the copy admitted **any** file with no folder to **anybody** — so a person could wear another
person's folder-less picture on their own Today page, measured at 200 on the wire. It is now
one definition, imported. Nothing about this endpoint's shape moves.

**Corrected the same day, before merge: the sentence this annotation carried here — "a
folder-less file is its owner's alone (4.16 as amended)" — was false at this endpoint, and a
false sentence in a frozen section is worse than a missing one.** 7.15's rule has an
exception the restatement dropped: an **avatar** carries no folder and stays readable by
every signed-in account, because a member list renders other people's pictures. So the gate
here is not that serving predicate alone but the predicate **and `kind` in (`cover`,
`image`)** — the clause 7.16 states for a shelf and `patchFolderProfile` has always applied
to a folder, which 7.4 leaves to the implementation — and this endpoint was the only one of
the three to lack it. Without it a person could wear **another
person's avatar** on their own Today page — 200 on the wire, against 422 for the same file
on a shelf — and a `voice` note or a plain attachment could be stored as a cover and drawn
as a broken image with the wrong mime. **Neither is a disclosure**: an avatar's bytes are
already every account's by 7.15's own rule, so what was wrong is that a page could hold a
file it may not draw, and that this annotation claimed a rule the code did not keep. The
refusal stays **404 and one sentence for all three faults** — absent, unreadable, not a
picture — rather than gaining the 422 a shelf answers, a second refusal shape being a change
to this section rather than a correction of it. AC-374 asserts both refusals and the two
arms that must survive them.

**And a place page could always hold a picture, which #20 says it could not.** #20's summary
is that "a place page like Today can have a gradient only. It can never have a picture";
`PUT /place-covers/:place { file_id }` has taken one since this section was written, and
answered 200 for a folder-scoped file before any of this work. What was missing was a picture
to hold that was not some folder's, and a picker offering the tab — the second of which is
client work and not this section's. AC-371 and AC-373 assert the endpoint's half.

**Amendment, 2026-09-04, issues #116 and #128: a cover file's lifetime, which Dana did not
have one of.** Imran ruled it on #116 — "covers stay stable for the user; genuinely unused
cover files can be reclaimed safely" — and on #117 that a duplicated shelf keeps a
same-looking cover while "changing or removing the cover on either shelf must not change the
other"; the owner directed the work and chose the mechanism. It is written here, in the
section whose endpoint has the whole shape of the problem, and 7.4, 7.15 and 7.16 point at
it rather than restating it. Four rules.

**1. Copy at set-time.** When a cover is set on a shelf (7.16), on a built-in place page
(this section) or on a folder (7.4) from a file that is not already a `cover` in that page's
own scope owned by the person setting it, the server copies the file — a new `files` row of
kind `cover` with the dimensions and the bytes of the original — and the page stores the
copy's id. **The copy's scope is the page's**, which is 4.16's rule made true rather than
hoped for: a shelf and a place page get a folder-less copy owned by the setter, and a folder
would get one inside itself, because a folder's cover is one look for every member. After
this a page's cover is always a file its own owner holds outright, so **leaving a folder can
never blank a cover**, which is #116's second half and was true of this endpoint from the day
it was written. `readableFileScope` is unchanged and needed no widening: a copy in the page's
own scope is readable by exactly the people who can see the page.

**In practice the copy fires rarely**, which is the point rather than an accident. A cover
uploaded through `POST /files { kind: cover }` with no folder, or fetched through
`POST /covers/photo`, is already the shape the rule wants and is stored as it stands.
What copies is a picture out of a folder — 7.16's `kind IN ('cover','image')` admits one on
purpose — and a shelf being duplicated. **The same folder-less picture of a person's own
worn on two of their own pages is not copied and reads back the same id on both**, which
AC-373 fixes; rule 2's reference count is what keeps the two independent, and copying there
would buy nothing.

**A folder's cover is the one kind that never copies in practice, and that is not an
exception to rule 1.** 7.4's own gate has always required the named file to be a file *of
that folder*, so a folder cover is already a `cover` or an `image` in the page's scope and
rule 1 finds nothing to normalise. It cannot suffer #116's second half either: you cannot
leave a folder and still be looking at its page. The rule is stated over all three page kinds
anyway, because the day 7.4's gate widens is the day the copy has to be there already.

**2. Reclaim when nothing references it.** A cover file with no folder, of kind `cover`,
that **no** column in the schema names — `folders.cover_file_id`, `shelves.cover_file_id`,
`user_page_covers.file_id`, `page_blocks.file_id`, `comment_files.file_id`, all five foreign
keys that reference `files(id)` — and that is more than **30 days** old is deleted, row and
object, by the 11.7 tick. That is #116's first half: such a file is listed by no surface and
reachable by no route, so a replaced cover used to spend its owner's 1 GB (10.3) forever with
nothing anywhere able to remove it. The count is a query rather than a counter column, so
there is no second record of a fact the foreign keys already hold and no migration.

**Why 30 days and not the moment the last reference goes**, which is what #116 proposes and
what `setAvatar` does for its own one-picture feature. A file this server has stopped
referencing is still a file the *caller* is holding the id of: AC-368 sets a shelf's cover,
replaces it with a gradient, and sets the same picture back, which is what a cover picker
does, and an immediate delete answers that 422.

**The thirty days run from the moment the cover came off, which is `files.unreferenced_since`
(migration 0014), and this paragraph said `created_at` until it was reviewed on the same
day.** The correction is recorded rather than made quietly because the wrong version was
wrong in the direction that destroys data and read as safe: `created_at` measures when the
bytes arrived, so a picture uploaded months ago and worn until this morning was both
unreferenced and old the instant it was replaced, and the next tick took it with no window at
all — the exact case the window was traded for. The tick therefore does three things in one
transaction: it clears the mark on any marked row something references again, marks any
folder-less cover nothing references, and deletes what has carried a mark for thirty days.
**A cover changed this month is reclaimed next month, and a cover put back inside the window
loses its mark and starts over.** Nothing is backfilled and nothing can be, the fact never
having been recorded, so the first pass after 0014 marks today's orphans and reclaims
nothing.

**3. Legacy rows keep working and are not backfilled.** A cover set before this date may name
a file inside a folder, or a file a second page also names. Neither is ever reclaimed: rule 2
takes only folder-less rows that nothing else references, and each of those is one or the
other. A folder-scoped cover file also needs no rescuing — it is listed in its folder, its
members can delete it, and 8.8's purge removes it with the folder. What legacy rows do not
get is rule 1's protection, because nothing re-runs the set; a cover that names a folder's
file goes on being a cover that stops drawing if its wearer leaves that folder, exactly as
before, until the person sets it again.

**4. A copy spends the setter's quota.** 10.3's 1 GB counts every `files` row by `owner_id`,
and a copy is one, so a set or a duplicate that would take an account past the gigabyte is
refused **413 with `quota_exceeded` and section 9's sentence** — `createFile`'s own path,
reused rather than reworded, because a copy that will not fit is the same event to a person
as an upload that will not. A set that copies nothing spends nothing and is never refused on
storage, so a full account can still rearrange pictures it has already paid for.

AC-384 asserts rule 1 and the leaving that used to blank a cover, AC-385 and AC-386 the
reclaim and the sparing, AC-387 and AC-388 the duplicate, AC-389 the quota.
