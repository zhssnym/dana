### 7.22 Data export

The obligation is 10.9's: the Google APIs Terms of Service, section 3(d),
oblige an application storing data obtained through a Google API to enable its
users to export their equivalent data "in a way that's substantially as fast
and easy as exporting such data from Google products and services". Dana takes
the wide reading: a real export of the meaningful data belonging to a person,
in JSON.

## The route

`GET /api/v1/me/export`. Session required, like every other read (10.2). No
query parameters and no body: the endpoint takes no input at all, which is
also its authorization, and the paragraph on it below says why that is a
property to keep rather than an accident.

`200` with `Content-Type: application/json` and

```
Content-Disposition: attachment; filename="dana-export-<YYYY-MM-DD>.json"
```

so a browser saves the answer as a file rather than rendering it. The date is
the UTC day of the document's own `exported_at`, so the header and the body
cannot disagree; it is a label on a file rather than a date anybody reads a
day off, which is why 8.1's viewer-timezone rule does not reach it.

`401` with the 7.0 envelope when there is no session, or when the session's
account has been deleted (8.10), which is 7.1's own answer for the same case.
`429` when the limit below is exceeded.

The whole document is built in memory and sent whole. The caps below are what
makes that safe; there is no streaming and no pagination.

## The document

One JSON object. `format` is the string `dana-export` and `version` is
`EXPORT_VERSION` in `app/src/shared/export.ts`; a reader must refuse a version
it does not know rather than guess at it. **Any added key bumps the version**,
because an older reader's schema would otherwise strip the key in silence and
hand back a document quietly missing something.

Wire shape: `exportDocument` and its parts in `app/src/shared/export.ts`. What
each top-level key holds, and whose:

| Key | What it holds |
| - | - |
| `exported_at` | the instant the document was built |
| `account` | the person's own profile as 7.1's `GET /me` reports it, plus `created_at` |
| `settings` | everything 4.10 holds for them, plus 4.20's place covers and 4.22's place descriptions |
| `folders` | every folder the person **owns**, each with its `my_shelf` and `my_color` (4.4), its `members` as display names, its `tasks`, its page `blocks`, its complete Folder Label vocabulary as `labels`, and the viewer's own Personal Labels on it as `personal_label_ids` |
| `tasks_elsewhere` | tasks in folders they belong to and do not own, kept only where they created the task or are its assignee; each with its steps, `folder: { id, name }`, and `folder_labels`, the definitions of exactly the Folder Labels that task wears |
| `comments` | every comment the person authored, anywhere, each with the metadata of the files attached to it |
| `shelves` | their shelves (4.18), each with its page `blocks` |
| `views` | their saved views (4.19) |
| `files` | metadata of every file they own (4.16), with `url` |
| `personal_labels` | every Personal Label definition the viewer holds, archived included; every `personal_label_ids` entry in the document resolves here |
| `responsibilities` | the person's **own** current Responsibility document (4.28) in each folder they are currently a member of, with its revisions |
| `facets` | every private facet the person owns (7.27) in every folder they are currently in, owned or not, and every shared facet of a folder they own; each with its blocks |
| `truncated` | the collections 10.3's cap cut, by name; empty on an ordinary export |

#### Labels, and the boundary they must not widen

Every task in the document carries `personal_label_ids` and `folder_label_ids`: ids into
definitions the document already holds, rather than definitions inlined per row, so a
Label's archived state is written once and cannot disagree with itself.

An **owned** folder's `labels` is its vocabulary **complete**, archived definitions and
unused ones included: the taxonomy is part of what the folder is. This is deliberately not
the workflow file's rule, which carries the active vocabulary only, because a workflow file
is handed to other people and everything in it is about to be newly applied.

A task exported out of a folder the viewer does **not** own brings only the definitions
that describe **that task**, in its own `folder_labels`. The rest of that folder's
vocabulary describes how somebody else organises their work and is not in this document.
**No other account's Personal Label appears anywhere in it**, by id or by name.

A saved view's `definition` is carried exactly as stored. A criterion naming a Label id
the viewer can no longer reach is **not** dropped — that would silently broaden the view —
and **not** resolved into metadata either, since that would be the disclosure the paragraph
above refuses.

#### Place covers and descriptions

4.22's descriptions are authored text rather than preferences, so an export of everything
Dana holds about someone carries them; 4.20's covers ride beside them as the same kind of
choice about the same pages. Each is carried as its own read answers it: 7.19's covers
sparse, 7.21's descriptions dense.

#### Tasks and files

A task carries its own columns, its `steps`, and its 4.8 `reminder`. Two people appear on
a task, both as a display name alone: `created_by` and `assignee`.

`files[].url` is 7.15's authenticated serving path, `/api/v1/files/:id`, and **the
document carries no bytes**. There are no public URLs in Dana, so an export handed to
somebody else names bytes they cannot fetch; that is intended. Embedding the bytes would
change the `version`.

#### Facets

A private facet is content only its owner can reach (7.27), so leaving it out would hand
somebody a copy of their own data with their own writing missing. `facets` is top-level
rather than nested under `folders` because `folders` holds only owned folders while a
private facet can sit in any folder the person is a member of; each entry names its
`folder_id`, which may or may not appear in `folders`. The `name` is resolved as 7.27
resolves it (a Work facet's from its H1). A Work facet carries no blocks of its own, being
a view of the Folder page. A **shared** facet is carried exactly where the Folder page it
sits beside is, which is under a folder the person owns and not otherwise.

## Trash

7.13 has not deleted anything yet, so an export that dropped trashed rows
would be wrong on the day their owner restores one. **Trashed folders,
tasks and facets the person owns are carried with `trashed: true`** rather than
omitted. A trashed folder the person merely belongs to is its owner's trash
and not theirs, so the tasks in it are out of `tasks_elsewhere` altogether.

## What is absent, and why each one is

- **`notifications`** (4.14) are a delivery record of things that happened to
  other people's rows, each of them a pointer at an event.
- **`events`** (4.13) belong to a folder rather than to a person. An owner's
  history of their own folder is a shared record of what several people did in
  it, and exporting one person's copy would hand them somebody else's activity
  log.
- **`invites`** (4.9) are addressed to email addresses.
- **`connections`** (4.2) are the roster: other people, identified.
- **`my_day_entries`** (4.7) are a fact about one day, stamped `added_on` and
  rewritten every morning. There is nothing in one to port.

**`responsibilities` is the exporting person's own and is deliberately narrow.** A
Responsibility is a folder's record of one person's part in its work, so the document carries the person's own — the text they are answerable for, and the
revisions of it — and never another member's, in a folder they own or in one they do not.
A folder the person has **left** contributes nothing here although its rows survive with
the folder: the standing is closed, and an export is the person's data rather than the
folder's archive. Nor does the export carry the self-edit grant, which is a permission on
a membership rather than data about the person, or the actor of anybody else's revision
beyond the display name the entry already carries.

**No email address but the caller's own appears anywhere in the document.**
Other people enter it as a `display_name` and in no other way. This is the one
rule to check a new field against: an export is a file that leaves Dana, and
an address is the field that would let whoever receives it contact a person
who never agreed to be in it.

## Caps

10.3's "List responses capped at 1000 rows with truncated flag" applies here
**per collection**, and a collection that reached the cap is named in
`truncated` rather than being silently short. The names are the dotted paths
to the collections inside the document, listed in `EXPORT_COLLECTIONS` in
`app/src/shared/export.ts`; one entry stands for every place that collection
was cut, so `folders.tasks` means at least one folder's task list hit the cap,
not which one.

The cap is applied where the rows are read, not where they are written out, so
what an export costs is what it sends: every statement that gathers a nested
collection is restricted to the parents that survived their own cap.

**The bound is per collection and not per document, and that distinction is
the ceiling on this design.** The caps multiply: an account at all of them at
once would build a very large document inside the single production process
(11.1), in the memory every other request is using. **If an account ever approaches it, the answer
is a streamed or paged export**, which is a change of format and a `version`
bump rather than an adjustment to the numbers above.

## Rate limit

**Five per hour per person** (10.4). It is a limit on a read, and the ground
is cost rather than abuse: every other GET answers one page of one surface,
and this one walks most of the schema and builds the whole result in memory
before a byte goes out. Refused
the way 10.4 says every limit is refused, `429` with `Retry-After` and the 7.0
envelope.

## Authorization

**The endpoint's authorization is that it names nothing.** No path parameter,
no query string, no body; the only identifier that reaches the database is the
session's user id, and every statement behind this route is scoped by it
inside its own `FROM` clause, which is 10.2's structural half. There is no
`accessOf(...)` gate because there is no caller-named resource to gate.

That is a property to preserve. A later `?since=`, `?folder_id=` or
`?include=` would make the request name something, and would owe a gate of its
own, and nothing structural would catch its absence (10.2).

## Logging

One line per export, under 10.5's policy: the user id and the byte count, and
nothing of the content.
