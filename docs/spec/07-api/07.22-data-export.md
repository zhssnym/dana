### 7.22 Data export

*Amendment to frozen section 7, written on 2026-09-04 for issue #77. The
freeze's rule is that section 7 moves only on a human decision, and this
subsection carries two: **Imran ruled the product**, on #77, that Dana offers
a real export of the meaningful data belonging to a person — "the safe/wide
interpretation here, not the narrowest possible compliance reading" — and
that JSON is acceptable for the first version; **Hassan ruled the shape**,
the route, the document, the caps, the limiter and the log line. Nothing here
edits an existing subsection. 7.21 was the last number and this is the next
one.*

The obligation is 10.9's, and until this landed it was the one thing that
section recorded Dana as not doing: the Google APIs Terms of Service, section
3(d), oblige an application storing data obtained through a Google API to
enable its users to export their equivalent data "in a way that's
substantially as fast and easy as exporting such data from Google products and
services". 10.9 argued the wide reading and left the work to an issue, on the
ground that an export surface has a shape — a format, an authorization gate, a
rate limit, a size bound — and that inventing one inside a compliance note
would be the wrong way to acquire it. This is that shape.

## The route

`GET /api/v1/me/export`. Session required, like every other read (10.2). No
query parameters and no body: the endpoint takes no input at all, which is
also its authorization, and the paragraph on it below says why that is a
property to keep rather than an accident.

`200` with `Content-Type: application/json` and

```
Content-Disposition: attachment; filename="dana-export-<YYYY-MM-DD>.json"
```

so a browser saves the answer as a file rather than rendering it. The date is
the UTC day of the document's own `exported_at`, so the header and the body
cannot disagree; it is a label on a file rather than a date anybody reads a
day off, which is why 8.1's viewer-timezone rule does not reach it.

`401` with the 7.0 envelope when there is no session, or when the session's
account has been deleted (8.10), which is 7.1's own answer for the same case.
`429` when the limit below is exceeded.

The whole document is built in memory and sent whole. The caps below are what
makes that safe; there is no streaming and no pagination in version 1.

## The document

One JSON object. `format` is the string `dana-export` and `version` is `1`;
a reader must refuse a version it does not know rather than guess at it.

| Key | What it holds |
| - | - |
| `format` | `"dana-export"` |
| `version` | `1` |
| `exported_at` | the ISO instant the document was built |
| `account` | the person's own profile as 7.1's `GET /me` reports it — id, email, display name, avatar url, timezone — plus `created_at` |
| `settings` | everything 4.10 holds for them, which is the v2 bundle `GET /settings` answers together with frozen 7.2's three booleans, plus 4.20's place covers and 4.22's place descriptions |
| `folders` | every folder the person **owns**, each with its own fields, its `my_label` and `my_color` from 4.4, its `members` as display names, its `tasks`, and its page `blocks` |
| `tasks_elsewhere` | tasks in folders they belong to and do not own, kept only where they created the task or are its assignee; each with its steps |
| `comments` | every comment the person authored, anywhere, each with the metadata of the files attached to it |
| `shelves` | their shelves (4.18), each with its page `blocks` |
| `views` | their saved views (4.19) |
| `files` | metadata of every file they own (4.16): id, kind, name, mime, bytes, dimensions, duration, `created_at`, and `url` |
| `truncated` | the collections 10.3's cap cut, by name; empty on an ordinary export |

**The two page tables are an addition to what #77's ruling enumerated, and they are here
on the wide reading rather than despite it.** 4.22 holds a sentence the person wrote under
one of Dana's own pages: that is authored text and not a preference, and an export of
everything Dana holds about someone that dropped it would be wrong in exactly the way the
narrow reading is wrong. 4.20's covers ride beside them because they are the same kind of
choice about the same eight pages, and taking one of the pair and not the other would be
arbitrary. Each is carried as its own read answers it — 7.19's covers sparse, only the
places a person has dressed, and 7.21's descriptions dense, every place with `null` where
nothing was written — rather than being reshaped here into a third thing neither endpoint
serves.

A task carries its own columns, its `steps`, and its 4.8 `reminder` projected
as both columns with exactly one non-null, which is 7.0's TaskDetail rule.
Two people appear on a task and both as a display name alone: `created_by`
and `assignee`. A task in `tasks_elsewhere` additionally carries
`folder: { id, name }`.

`files[].url` is 7.15's authenticated serving path, `/api/v1/files/:id`, and
**version 1 carries no bytes**. There are no public URLs in Dana, so an export
handed to somebody else names bytes they cannot fetch. That is the intended
property rather than a limitation: a person fetches their own files with their
own session, and a version that embeds or archives the bytes changes the
`version` number.

## Trash

7.13 has not deleted anything yet, so an export that dropped trashed rows
would be wrong on the day their owner restores one. **Trashed folders and
trashed tasks the person owns are carried with `trashed: true`** rather than
omitted. A trashed folder the person merely belongs to is its owner's trash
and not theirs, so the tasks in it are out of `tasks_elsewhere` altogether.

## What is absent, and why each one is

- **`notifications`** (4.14) are a delivery record of things that happened to
  other people's rows, each of them a pointer at an event.
- **`events`** (4.13) belong to a folder rather than to a person. An owner's
  history of their own folder is a shared record of what several people did in
  it, and exporting one person's copy would hand them somebody else's activity
  log.
- **`invites`** (4.9) are addressed to email addresses.
- **`connections`** (4.2) are the roster: other people, identified.
- **`my_day_entries`** (4.7) are a fact about one day, stamped `added_on` and
  rewritten every morning. There is nothing in one to port.

**No email address but the caller's own appears anywhere in the document.**
Other people enter it as a `display_name` and in no other way. This is the one
rule to check a new field against: an export is a file that leaves Dana, and
an address is the field that would let whoever receives it contact a person
who never agreed to be in it.

## Caps

10.3's "List responses capped at 1000 rows with truncated flag" applies here
**per collection**, and a collection that reached the cap is named in
`truncated` rather than being silently short. The names are the paths to the
collections inside the document, dotted, and one entry stands for every place
that collection was cut: `folders`, `folders.members`, `folders.tasks`,
`folders.tasks.steps`, `folders.blocks`, `tasks_elsewhere`,
`tasks_elsewhere.steps`, `comments`, `comments.files`, `shelves`,
`shelves.blocks`, `views`, `files`. So `folders.tasks` means at least one
folder's task list hit the cap, not which one.

The cap is applied where the rows are read, not where they are written out, so
what an export costs is what it sends: every statement that gathers a nested
collection is restricted to the parents that survived their own cap.

**The bound is per collection and not per document, and that distinction is
the ceiling on this design.** The caps multiply. An account sitting at all of
them at once — 10.3's 200 custom folders, a thousand tasks in each, ten
thousand characters of notes on every task — would build something on the
order of a gigabyte of JSON inside the single production process (11.1),
which is the same memory every other request is using. No real account is
anywhere near that, and the caps make it a ceiling rather than a surprise,
but a ceiling is not a bound. **If an account ever approaches it, the answer
is a streamed or paged export**, which is a change of format and a `version`
bump rather than an adjustment to the numbers above.

## Rate limit

**Five per hour per person**, added to 10.4 in the same change. It is the
first limit in this API on a read, and the ground is cost rather than abuse:
every other GET answers one page of one surface, and this one walks nine
tables and builds the whole result in memory before a byte goes out. Refused
the way 10.4 says every limit is refused, `429` with `Retry-After` and the 7.0
envelope.

## Authorization

**The endpoint's authorization is that it names nothing.** No path parameter,
no query string, no body; the only identifier that reaches the database is the
session's user id, and every statement behind this route is scoped by it
inside its own `FROM` clause, which is 10.2's structural half. There is no
`accessOf(...)` gate because there is no caller-named resource to gate.

That is a property to preserve. A later `?since=`, `?folder_id=` or
`?include=` would make the request name something, and would owe a gate of its
own; 10.2 records that nothing structural in this repository would catch its
absence.

## Logging

One line per export, under 10.5's policy as amended in the same change: the
user id and the byte count, and nothing of the content.
