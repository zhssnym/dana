### 7.14 Comments

GET /api/v1/folders/:id/comments?task=… · POST same (body, parent_id,
file_id) · PATCH /api/v1/comments/:id · DELETE /api/v1/comments/:id (author
or folder owner) · PUT/DELETE /api/v1/comments/:id/like. Member-only
throughout; one reply level enforced.

Read shape: each comment line carries
`files: { id, name, mime, bytes, width, height }[]`, 4.16's own columns,
ordered as attached; there is no bare-id form. POST's create answer carries
the same. (Replace unit of RFC 0005 change control item 57, B5, ruled by
delegation 2026-08-30 and folded here the same day; it closes section 13 item
54's read half. The write half, one `file_id` per comment, stands. `width` and
`height` added 2026-09-03 by issue #27, migration 0009: the sentence is
unchanged — this shape is 4.16's own columns and 4.16 gained two — and the
addition is what lets a reader who did not attach the picture draw its tile at
the right proportion before the bytes arrive. Both are integer or null, null
meaning unknown: an attachment that is not an image, and anything stored
before 0009, since no backfill has been run.)

**The write half, widened from one file to ten on 2026-09-03.** Imran ruled it
on issue #22 — "People may need to add a few screenshots together, and they
should stay in one comment. Please update Dana to match the existing limit" —
and the owner confirmed it the same day and directed the work, which is what
this section's freeze asks of a change to it: a human decision, recorded, and
folded as text. It is the write half of section 13 item 54, whose read half
closed above; the sentence "The write half, one `file_id` per comment, stands"
above is superseded by this paragraph and is left where it is, because it is
the sentence the ruling answers.

POST takes `file_ids`, an array of up to ten ids in the order they are to be
attached, which is the number 10.3 has said since it was written and this
endpoint had never enforced. `file_id` continues to be accepted and means
exactly `file_ids: [that id]`. It is retained rather than replaced for a
mechanical reason rather than a courteous one: nothing in `app/src/shared/` is
`.strict()`, so a field the server stops reading is accepted, discarded and
answered 201, and the shipping client posts `file_id`. Replacing the field
would have made every attachment made from that client vanish into a success.
The two are never sent together: they have no order between them that a caller
could predict, so the pair is 422 rather than a guess. The same id twice is
422, `comment_files` being keyed on the pair. Every id must name a file of this
folder or the whole comment is refused, which is the single-file rule
unchanged, and it is all or nothing: a comment does not post with the files
that resolved and drop the rest.

No size limit belongs to this endpoint. The bytes are 7.15's: each file is
stored by its own POST before the comment names it, under 10.3's 25 MB per
file and the 1 GB per account, so a comment carrying ten files transfers
nothing and adds no storage. A failed upload is a file the client never
received an id for and therefore never names here, which is what makes partial
failure the client's to retry rather than this endpoint's to define.

"Ordered as attached" in the read shape above is the order of `file_ids`.
Inside one transaction every attachment row would otherwise carry the same
`now()` and the aggregate would have no order to read, so each is stamped one
microsecond after the one before it (`domain/comments.ts`).

PATCH /comments/:id is untouched by this widening. It edits the words and nothing
else, and what a comment carries after it is posted is unspecified here rather than
forbidden; `app/src/shared/comments.ts` records why a `file_ids` sent to it is
accepted and dropped, which is 7.0's tolerance rule rather than this endpoint's
choice.

AC-344 and AC-345 assert it; 10.3's row is unchanged and is now enforced.
