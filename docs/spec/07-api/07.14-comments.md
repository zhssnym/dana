### 7.14 Comments

GET /api/v1/folders/:id/comments?task=… · POST same · PATCH /api/v1/comments/:id · DELETE
/api/v1/comments/:id · PUT/DELETE /api/v1/comments/:id/like. Member-only throughout, a
non-member being 404 and a member below an act's bar 403 (10.2); one reply level enforced.
Request bodies: `postCommentBody` and `patchCommentBody`; read shape: `commentLine`,
`getThreadResponse` and `patchCommentResponse`, all in `app/src/shared/comments.ts`. Each
comment line carries its files as 4.16's own columns, ordered as attached; there is no
bare-id form.

**Who may do what.** Posting and liking need Can comment or better. PATCH is the author's
alone, and only while they still hold Can comment or better: authorship is provenance
rather than standing authority, so a member reduced to Can view keeps their words and loses
the power to change them. No preset lets one member edit another's words. DELETE is the
author (on the same condition) **or** a member holding Full control, whose moderation
ignores ownership: a Full-control member who owns nothing moderates, and an owner below Full
control does not. The bars are `comment.create`, `comment.mutate.own`, `comment.moderate`
and `comment.like` in `app/src/shared/folder-actions.ts`. DELETE answers 204 and takes the
replies with it.

**Attachments on create.** POST names up to 10.3's ten files by `file_ids`, in the order
they are to be attached. `file_id` is still accepted and means exactly `file_ids: [that
id]`: nothing in `app/src/shared/` is `.strict()`, so replacing the field would have made
every attachment from a client that sends it vanish into a 201. The two are never sent
together (422), having no order between them a caller could predict. The same id twice is
422. Every id must name a file of this folder or the whole comment is refused, all or
nothing. A comment carries words, files, or both, never neither.

No size limit belongs to this endpoint. The bytes are 7.15's: each file is stored by its
own POST before the comment names it, so a comment carrying files transfers nothing and
adds no storage, and a failed upload is a file the client never got an id for and so never
names here. "Ordered as attached" is the order of `file_ids`; the server stamps each
attachment distinctly within the transaction so the order survives.

**Attachments on edit.** PATCH takes `file_ids` as **the full new set**, not an addition:
omitted leaves the attachments unchanged, `[]` removes them all, any other list makes the
set exactly those ids in that order. `body` is optional, and an edit names the words, the
attachments, or both. Every id must name a file of the comment's own folder or the whole
edit is refused; a file of another folder and a file of another account answer
identically, 422 naming `file_ids`, so the endpoint is no oracle for which ids exist (10.2).
The same id twice is 422. An edit that would leave neither words nor files is 422 naming
`file_ids`; deleting the comment is the way to remove it. `file_id` is refused by name here
(422, 11.14's `z.never`), there being no client to stay compatible with and a second
spelling being a guaranteed future disagreement.

The PATCH answer is `{ edited: true, comment }`, the comment being the fresh read the
thread would give, files included, because the resolved file rows are something the caller
cannot compute from the ids it sent.
