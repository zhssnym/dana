### 7.0 Conventions

Base path /api/v1. JSON bodies. Authentication: server session established by Google
OAuth; every endpoint below requires it except the auth endpoints themselves. Mutations
require a CSRF token header when cookie sessions are used (section 10.1).

Error envelope: { "error": { "code": string, "message": string } }. Status usage, uniform:
- 400 malformed request: a body that does not parse as JSON, or parses to something other
than an object. On a parsed object, unknown fields are tolerated and wrong types are not:
they are validation failures answering 422 with the field named. This bullet governs
bodies presented as JSON. A request that claims no JSON content type presents nothing to
parse, whatever bytes it carries, so an endpoint needing a body answers 422 for the body
it did not receive rather than 400 for one it could not read. - 401 no valid session. -
403 authenticated, resource visible, action not permitted by the matrix in 5.4. - 404
resource nonexistent, or existent but not accessible to V. Inaccessible always reads as
404, never 403, to avoid existence leaks. - 409 state machine violation or rule conflict
(section 5 tables name each). - 422 validation failure (limits in section 10.3), with
field errors. - 429 rate limited (limits in section 10.4), with Retry-After.

Timezone: every view endpoint takes tz, an IANA identifier, 422 naming the field if it is
invalid or absent. Idempotency: GETs are safe; PUT and DELETE are idempotent; status
transitions are idempotent by the no-op rows of 5.1; POST creations are not idempotent and
clients must disable double submit.

The absent half of that sentence was escalated at the P4 change control and entered by
owner ruling on 2026-08-07; this section had named only the invalid one. A view endpoint
called without tz is missing a required parameter rather than accepting a default: 8.1
makes tz an input of every request that evaluates dates, and the only plausible default,
UTC, would hand most of the world the wrong day with nothing on the wire to say it had
been substituted. 7.1's treatment of the same parameter is the opposite and stays so, an
unparseable zone on GET /auth/google being read as absent rather than refused; that
section records it as a deliberate deviation so a stale zone database cannot lock anyone
out of signing in, and it does not generalize past sign-in.

Shared schemas: - TaskCard: { id, title, status, important, due_date, due_time, folder:
{id, name, is_default}, assignee: {id, display_name, avatar_url} or null, is_recurring:
bool, steps_done: int, steps_total: int, pulled: bool (viewer has a My Day entry),
pending_invite_email: string or null (from invites.task_id), section_block_id: string or
null, created_by: {id, display_name, avatar_url} or null, created_at, updated_at }. -
TaskDetail: TaskCard plus { notes, recurrence_rule, series_id, reminder: {offset_minutes
or time_of_day} or null, steps: [{id, title, done, position}], completed_at, completed_by,
created_by }. - Folder: { id, name, is_default, is_owner: bool, member_count, counts:
{pending, completed}, my_label, my_color }.

Two readings of the shapes above, settled at the P3 shape review and entered by owner
ruling. Floating values ride the wire in the 4.11 formats they are stored in: due_date as
YYYY-MM-DD and due_time as HH:MM, never as instants, because an instant reintroduces the
timezone the floating format exists to remove. TaskDetail's reminder carries both 4.8
columns, offset_minutes and time_of_day, with exactly one of the two non-null:
"{offset_minutes or time_of_day}" above names the 4.8 mode rather than a key list, and a
stable key set is what lets a client read the mode off the values instead of narrowing a
union to learn which keys it holds.
