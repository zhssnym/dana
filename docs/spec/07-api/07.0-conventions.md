### 7.0 Conventions

Base path /api/v1. JSON bodies. Authentication: server session established by Google
OAuth; every endpoint below requires it except the auth endpoints themselves. Mutations
require a CSRF token header when cookie sessions are used (section 10.1).

Error envelope: `errorEnvelope` in `app/src/shared/error-envelope.ts`. Status usage, uniform:

- 400 malformed request: a body that does not parse as JSON, or parses to something other
  than an object. On a parsed object, unknown fields are tolerated and wrong types are not:
  they are validation failures answering 422 with the field named. A request that claims no
  JSON content type presents nothing to parse, whatever bytes it carries, so an endpoint
  needing a body answers 422 for the body it did not receive rather than 400 for one it
  could not read.
- 401 no valid session.
- 403 authenticated, resource visible, action not permitted by the matrix in 5.4.
- 404 resource nonexistent, or existent but not accessible to V. Inaccessible always reads
  as 404, never 403, to avoid existence leaks.
- 409 state machine violation or rule conflict (section 5 tables name each).
- 422 validation failure (limits in section 10.3), with field errors.
- 429 rate limited (limits in section 10.4), with Retry-After.

Timezone: every view endpoint takes tz, an IANA identifier, and answers 422 naming the field
if it is invalid or absent. There is no default: 8.1 makes tz an input of every request that
evaluates dates, and the only plausible default, UTC, would hand most of the world the wrong
day with nothing on the wire to say so. Sign-in is the one exception (7.1).

Idempotency: GETs are safe; PUT and DELETE are idempotent; status transitions are
idempotent by the no-op rows of 5.1; POST creations are not idempotent and clients must
disable double submit.

Shared shapes: TaskCard and TaskDetail are `taskCard` and `taskDetail` in
`app/src/shared/tasks.ts`; the Folder object is `folder` in `app/src/shared/folders.ts`.
Each is key-exact, and no endpoint answers a per-endpoint variant of any of them. What they
mean that the schema cannot say:

- `pulled` is the viewer's own My Day entry, so one task reads differently for two members.
- `labels.personal` is only the viewer's own Personal Labels, never another member's; 7.26
  carries what the two label arrays promise.
- `blocked_by_count` and `blocks_count` count only dependency edges whose other end the
  viewer can read; 7.25 carries what they count.
- A Folder's `my_shelf`, `my_color`, `my_access` and `personal_labels` are the viewer's own
  membership facts, never another member's.
- `is_recurring` says whether the row repeats now; `series_id` says which series it belongs
  to, including one that has ended, so a client never reads repetition off the id.
- Floating values ride the wire in the 4.11 formats they are stored in: due_date and
  start_date as YYYY-MM-DD and due_time as HH:MM, never as instants, because an instant
  reintroduces the timezone the floating format exists to remove.
- TaskDetail's reminder carries both 4.8 columns, offset_minutes and time_of_day, with
  exactly one non-null, so a client reads the mode off the values rather than narrowing a
  union.
