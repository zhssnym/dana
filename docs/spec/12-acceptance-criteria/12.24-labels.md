### 12.24 Labels

Personal and Folder Labels: definitions, assignments, archive, projections, caps, the authority bar, and how duplication, move, the workflow file, export, Trash and membership loss treat them.
A Personal Label never travels to another person; a Folder Label belongs to its Folder and is re-created under new ids when the Folder is copied. The Labels filter axis is 12.8's; Shelf membership is 12.10's.

- AC-1539 Given a Task and its Work filtered by a Label, when the viewer edits its Labels or creates a Task in that Work, then the Task page offers authorized Personal and Work Labels in a searchable fixed row, archived Labels remain assigned without being offered for new assignment, and a new Task receives the active filter Label; the Work filter combines with the other axes and clears with its chip or Clear all (spec 9.3).
- AC-470 Given two accounts sharing two folders, then one account's Personal Label definitions are absent from the other's `GET /labels` and unreachable by id (404, never 403); a Folder Label is listed to every member of its folder and to no one else; a Task read carries the viewer's own Personal Labels and the Task's Folder Labels and never another member's Personal Labels, in `GET /tasks/:id` and in every list endpoint alike; and a Personal Label applied to a Folder is absent from a co-member's Folder projection (spec 5.4, 7.0, 7.4, 10.2).
- AC-471 Given one display name, then Personal "Research", Folder A "Research" and Folder B "Research" are three Labels with three ids and are never merged, each storing and answering its own colour and description; a name differing only by case is refused inside one catalog and admitted in the next; an archived Label still holds its name against a new one; and a Task's Label arrays are ordered active before archived, then lower(name), then id, in both producers (spec 7.0).
- AC-472 Given a name already held in a catalog, then `POST /labels/personal`, `PATCH /labels/personal/:labelId`, `POST /folders/:folderId/labels` and `PATCH /folders/:folderId/labels/:labelId` all answer **409**, and every one of the four leaves the catalog exactly as it was (spec 7.0, 10.3).
- AC-473 Given `GET /labels`, then a `folder_id` naming a folder the viewer cannot reach answers 404 rather than 403 or an empty 200, and each of `scope`, `state` and `folder_id` changes the answer rather than being accepted and dropped; an invalid value is 422 naming the field; and the response is 10.3's capped list, so a viewer holding more definitions than the cap is answered exactly 1000 rows with `truncated` true, and a viewer under it is answered `truncated` false (spec 7.0, 7.26, 10.2, 10.3, 11.14).
- AC-474 Given a folder of three labelled tasks and a folder of twenty-four, then `GET /folders/:id/tasks` issues the same number of statements over both, and `GET /folders` does the same as labelled folders are added: the Label projection is one batched statement per read whatever the row count (spec 6.1, 7.10).
- AC-475 Given an archived Label, then every existing assignment stands, both producers still carry it with `archived: true`, the default definition listing drops it and `state=archived` finds it, a new application is refused 409 with nothing written, an existing assignment may still be removed, and restore re-enables application under the same id; and an archived Label may still be renamed, recoloured and described without being restored (spec 7.0).
- AC-476 Given a Folder Label of Folder A and a Task in Folder B, then the API answers 422 naming `label_id` and writes nothing, and a direct `INSERT` is refused by the database under a named constraint whichever folder it claims — the invariant being the schema's rather than the handler's; a Folder Label applied to a Folder is 422 the same way and refused by the database the same way; and a Personal Label of another account is 404 rather than 422, the two refusals being different facts (spec 4.15, 7.0, 10.2).
- AC-477 Given a Personal Label applied to shared work, when its owner loses access to the folder, then the assignment row remains and is invisible to every read the owner still has, the Label definition stays theirs and discloses no metadata of the target, and restoring access makes the association visible again with no repair step; and purging the target removes the assignment by cascade while the definition survives it (spec 8.8, 10.2).
- AC-478 Given the five caps — 500 Personal definitions per account, 250 Folder definitions per folder, 100 Personal and 100 Folder Labels on one Task, 100 Personal Labels on one Folder — then the boundary is refused 422 naming the collection, a repeat of a Label already applied is admitted at the cap, the two per-Task caps are counted apart, and every refusal leaves the catalog in the state it was (spec 10.3).
- AC-479 Given shelf membership, then all three directions of 4.18 hold membership and shelf name in step — a membership written through 7.4 makes the shelf, a shelf rename rewrites the memberships, a shelf delete clears them and leaves the folders — the contract field is `my_shelf` and the request field is `shelf`, and `folder_members` carries exactly one membership column, `shelf_name`, which every one of those write paths reaches, while the old name is refused by the server (spec 4.4, 4.18, 7.4, 7.16, 11.5, 11.14).
- AC-480 Given a folder member who does not own the folder and holds **Can edit**, then they may create, rename, recolour, describe, archive, restore, apply and remove that folder's Labels, each value stored as well as answered, with no owner exception — ownership being custody and no part of authority over shared Work — and applying and removing a Label are each idempotent; the bar for the other presets is AC-800 (spec 5.4, 7.4).
- AC-750 Given `PATCH /folders/:id/my-membership`, then `label` is an ordinary unknown key — a body sending only `label` answers 200 and changes nothing, on the row, on the card and in the viewer's shelves, and `label: null` does not clear a shelf either — while `shelf` still writes and still clears, a body sending both is accepted rather than refused and stores the `shelf` one, and no producer of the Folder object answers `my_label`: not the PATCH response, not `GET /folders` and not `GET /folders/:id` (spec 4.4, 4.18, 7.0, 7.4, 11.11, 11.14).
- AC-540 Given a Task carrying an active Folder Label and active Personal Labels of two different members, when a member duplicates it, then the copy wears the **same** Folder Label ids — the copy being in the same Folder — and the duplicator's own Personal Labels, and no row of any other member's Personal Label exists on the copy; and a Folder Label the source never wore is not applied (spec 7.16, 7.0, 10.2).
- AC-541 Given a Task wearing an archived Folder Label and an archived Personal Label beside active ones, when it is duplicated, then neither archived assignment is on the copy — a duplicate is a new application and an archived Label may not be newly applied — and both are still on the source, archive being non-destructive (spec 7.16, 7.0).
- AC-542 Given a Folder holding two Folder Labels crossed over two Tasks, when it is duplicated, then the copy holds both definitions with their names, colours and descriptions under **new ids**, none of them the source's; each copied Task wears the copy's own Label and not the other's, so the remap is by row rather than by name or by everything-on-everything; and the source keeps its whole vocabulary (spec 7.16, 4.15).
- AC-543 Given a Folder whose vocabulary holds an archived definition and whose duplicator holds an archived Personal Label, when it is duplicated, then the archived **Folder** definition is copied and arrives archived, and the assignment standing against it comes with it — a copy that revived it would widen a taxonomy its owner narrowed on purpose — while neither the Folder nor its copied Tasks acquires the duplicator's archived **Personal** Label, and the source keeps both of its own (spec 7.16, 7.0).
- AC-544 Given two members who have each privately classified the same shared Task and the shared Folder, when either of them duplicates the Task and then the Folder, then every copy holds exactly the duplicator's own Personal rows and none of the other's; and the other member, reading a copy themselves, sees none of their own on it (spec 7.16, 7.0, 10.2).
- AC-545 Given a Task wearing a source Folder Label and Personal Labels of two members, when it is moved to another Folder, then the Task's `folder_id` is the destination, the source Folder Label assignment is gone, and every Personal assignment stands, the mover's and the co-member's alike; and given a move refused because the caller cannot reach the destination, then the assignments are untouched, the request being one unit (spec 7.6, 4.5).
- AC-546 Given a destination Folder holding a Folder Label identical to the source's in name, case, colour and description, when a Task wearing the source's is moved into it, then the moved Task wears **no** Folder Label: the source's went with the Folder that owns it and the destination's identically-named one is not applied, scope being part of identity; the destination's own Label is unaffected and still applicable by hand; and a round trip does not restore the original either (spec 7.6, 7.0).
- AC-547 Given a Folder with an active vocabulary — one category nothing wears — an archived one, and Tasks wearing them, when a workflow file is written from it and imported **into another account**, then the file says version 3, carries every active definition including the unused one with its colour and description, carries no archived definition, names each Task's Labels by a file-local key, and contains no database id of any Label, Folder or Task; and the imported Folder holds new Label identities, all active, with each Task's assignments remapped onto them, while the source is untouched. Given a Folder with no Folder Labels, then the file is a version 1 file with no `labels` key at all (spec 7.16).
- AC-548 Given a version 1 workflow file and a version 2 one, then each still imports whole — its work, notes, star and step titles arriving as they always did, and no Label vocabulary being invented for a file that carried none; given a file below version 3 that carries a `labels` key in any arrangement, including an array of foreign tag names per task and a null at either level, then the key is dropped and the file imports; given a **version 3** file whose task names a key its folder does not declare, then 422; and given a version this build does not know, then 422 (spec 7.16, 10.3).
- AC-549 Given an author whose own Personal Labels are on the Folder and on every Task, when a workflow file is written, then neither the name, the description, the id, nor the author's account id appears anywhere in its bytes; and given a hand-edited file carrying a top-level personal catalog, a `scope: 'personal'` definition with an `owner_user_id`, and a task naming personal labels, when it is imported, then the importer gains no Personal Label, the author's catalog is unchanged, and every declared definition is created as a **Folder** Label with no owner — `scope` not being a field of this format (spec 7.16, 11.14).
- AC-550 Given an account holding archived and active Personal Labels and an owned Folder whose vocabulary holds an archived definition and one nothing wears, then `GET /me/export` answers a document that validates against the shared contract, says version 4, carries the whole Personal catalog with its archived state, carries the Folder's **complete** vocabulary — unused and archived included — carries the viewer's Personal Labels on the Folder and both Label id arrays on every Task, and every assignment id resolves to a definition the document holds (spec 7.22, 10.9).
- AC-551 Given a Folder the viewer belongs to and does not own, holding one Folder Label on the viewer's own task and another on a task that is not theirs, plus a Personal Label of the owner's on the viewer's task, then the viewer's export carries the first definition on that task and **nowhere in the document** carries the second, its description, or the owner's Personal Label by id or by name; and given a saved View whose definition names a Label id the viewer cannot reach, then the definition comes back exactly as stored and no metadata of that Label enters the document — dropping the criterion would silently broaden the View and resolving it would be the disclosure the first half refuses (spec 7.22, 4.19, 10.2, 10.9).
- AC-552 Given a Task wearing an archived and an active Folder Label and a Personal Label, when it is soft-deleted, then every assignment row stands; when it is restored, then every one reads back with no repair step and the archived one arrives archived. And given a soft-deleted Folder, then its Folder Labels, its Tasks' assignments and the viewer's Personal assignment to it all stand — the cascades hang off a `DELETE` and a soft delete is an `UPDATE` — and a restore reads them back (spec 7.13, 4.3, 4.5).
- AC-553 Given a purged Task, then its assignment rows are gone by cascade and both Label **definitions** survive it; given a purged Folder, then its own Labels, every assignment of them, the owner's Personal assignment to the Folder and a member's Personal assignment to a Task inside it are all gone by cascade while both Personal definitions survive; and given a deleted account, then it holds no Personal Label and its assignments on work that outlives it are gone by 8.10 step 6c's explicit statement rather than by cascade, 8.10 step 7 scrubbing the `users` row rather than deleting it, while another member's Personal Label on that same Task and Folder, and their definition, are untouched (spec 7.13, 8.10, 4.3, 4.5).
- AC-554 Given a member who has privately classified a shared Task and the shared Folder, when they are removed from the Folder, then both rows still exist; the Task is 404 to them, the Folder is absent from their folder list, and `GET /labels?folder_id=` naming it is 404 rather than 403 or an empty 200; their own definition still lists, a definition saying nothing about what wears it; the Folder's own Label is still on the Task for the members who remain; and when they are added back, both assignments read again with no repair step (spec 5.3, 7.4, 10.2).
- AC-780 Given a version 3 workflow file declaring two Folder Labels in one folder whose names collide — identical, differing only in case, or differing only in surrounding space — when it is imported, then 422 naming that folder's own `folders.N.labels` path and saying names are compared without regard to case, and no folder of the file is created, the file being one transaction; the status is 422 rather than the live create's 409 because the file disagrees with itself rather than with an existing catalog; two names that only JavaScript's `toLowerCase()` folds together (`ΦΩΣ` and `φως`) both import; and two different folders of one file may each declare the same name (spec 7.16, 10.3, 4.15).
- AC-781 Given a Folder holding both a canvas page and a Label vocabulary, when it is written and imported into another account, then the file says version 3 and carries the typed `document` beside the `labels`, and the import restores both: the vocabulary with each Task's assignments remapped onto new ids, and the page with its blocks once each, in order, the paragraph still nested under the section under a block id this import minted. The document is not gated by the version; the flat `blocks` key the writer emits beside the document is ignored rather than applied twice (spec 7.16).
- AC-782 Given a hand-written one-folder version 3 file whose `labels` sits at the top level beside its `tasks`, when it is imported, then the vocabulary is created and the task keys join to it, rather than 422 or 201 with the classification silently gone; the version still gates the key through this arrangement, so a version 1 file carrying a top-level foreign tag list imports with nothing invented from it; and the folded vocabulary meets AC-780's and AC-548's refusals under the folded folder's own path (spec 7.16, 10.3).
- AC-800 Given a shared Folder holding one member at each of the six access presets, none of them its owner, then `label.vocabulary.manage` and `label.apply` are resolved through `mayPerform` and not by membership: **Can edit and Full control** create, rename, recolour, describe, archive and restore the Folder's Labels and apply and remove them across its work; **Can contribute** applies and removes an existing Folder Label on the Task currently assigned to them and is refused every vocabulary write and every act on work that is not theirs; **Assigned work, Can comment and Can view** are refused both actions outright, their own current Task included; every refusal is 403 carrying the rule's own sentence rather than 404 and writes nothing; a Label of another Folder is 422 before the 403, and the 403 comes before the 409 an archived Label earns; a contributor whose Task is reassigned away loses `label.apply` on it, the gate reading the current assignee under the row lock; and Personal Labels stay outside the ladder, a Can-view member creating, renaming, applying and removing their own at 200 (spec 5.4, 7.0, 7.4, 10.2).
