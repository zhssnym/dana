### 12.24 Labels

The M1 Label model of issue #208: two scopes and no third, their definitions, their three
assignment relations, the archive lifecycle, the projections a Task and a Folder carry, and
the five technical safety caps. The Labels **filter** axis is 12.8's where it exists.

**The lifecycle integrations are here too, and that is a change of mind worth recording
rather than tidying away.** This paragraph said they "belong to 12.16 and 12.20 and arrive
with issue #227". When #227 arrived they went into the second half of this file instead,
on the ground stated there: each of them is a rule about Labels observed through another
surface, and spreading them over three files would have put the two readings of the word
"archived" on two pages that never have to agree. 12.16 and 12.20 keep the criteria about
duplication and Trash as such — AC-200, AC-277 and AC-014 among them — and #227 changed
none of those.

The Shelf membership this model is often confused with is 12.10's, and the confusion was
literal until issue #226: `folder_members.label` and `Folder.my_label` were Shelf membership
wearing the Label word. The surviving contract field is `my_shelf` and the surviving request
field is `shelf`; the column is `shelf_name`, added beside `label` rather than renamed,
because a rename is refused under hard stop 1 while Render runs the old instance until the
new one is healthy. **The same expand-and-contract reaches the wire**, on the owner's
technical ruling of 2026-09-20: for this release the request body accepts `label` as well and
the Folder object carries `my_label` as well, the same value from the same column. Issue #247
is the contract half and drops the column, the request key and the card key together. AC-479
is what says the terminology move changed nothing else, AC-481 is what says the wire survives
a deploy, and AC-367 in 12.10 is the criterion neither may have broken.

**Hard stop 3 for this surface is spread over four criteria rather than given one of its
own, and where each half lives is worth stating because the failure it guards against is
invisible.** `color` and `description` are declared fields on all four definition-write
bodies, and a declared field no route acts on is stripped, dropped and answered 200. AC-473
carries the three query fields of the listing. The two body fields are carried by the
criteria whose own text already claims the acts: **AC-471** on create in both scopes, three
Labels sharing a name and differing in every other field being the strongest available
statement of "never merged"; **AC-475** on the Personal patch, whose text says an archived
Label may be renamed, recoloured *and described*; and **AC-480** on the Folder create and
patch, whose text names "recolour" and "describe" among the eight acts a member may perform.
Each asserts the value from the response **and** from the row, because a handler that echoes
what it was sent and stores a default passes a response-only check. None of those three
criterion texts moved; what moved is that a 200 stopped being accepted as proof of them.

- AC-470 Given two accounts sharing two folders, then one account's Personal Label definitions are absent from the other's `GET /labels` and unreachable by id (404, never 403); a Folder Label is listed to every member of its folder and to no one else; a Task read carries the viewer's own Personal Labels and the Task's Folder Labels and never another member's Personal Labels, in `GET /tasks/:id` and in every list endpoint alike; and a Personal Label applied to a Folder is absent from a co-member's Folder projection (spec 5.4, 7.0, 7.4, 10.2; issue #226, #208 R4).
- AC-471 Given one display name, then Personal "Research", Folder A "Research" and Folder B "Research" are three Labels with three ids and are never merged; a name differing only by case is refused inside one catalog and admitted in the next; an archived Label still holds its name against a new one; and a Task's Label arrays are ordered active before archived, then lower(name), then id, in both producers (spec 7.0; issue #226, #208 R4, R8).
- AC-472 Given a name already held in a catalog, then `POST /labels/personal`, `PATCH /labels/personal/:labelId`, `POST /folders/:folderId/labels` and `PATCH /folders/:folderId/labels/:labelId` all answer **409**, the convention #208 left open and this build pins, and every one of the four leaves the catalog exactly as it was (spec 7.0, 10.3; issue #226, #208 R8).
- AC-473 Given `GET /labels`, then a `folder_id` naming a folder the viewer cannot reach answers 404 rather than 403 or an empty 200 — the one gate on this surface that `ac-397` cannot see, its id being in the query string — and each of `scope`, `state` and `folder_id` changes the answer rather than being accepted and dropped; an invalid value is 422 naming the field; **and the response is 10.3's capped list, so a viewer holding more definitions than the cap is answered exactly 1000 rows with `truncated` true, and a viewer under it is answered `truncated` false** (spec 7.0, 7.26, 10.2, 10.3, 11.14; issue #226).
- AC-474 Given a folder of three labelled tasks and a folder of twenty-four, then `GET /folders/:id/tasks` issues the same number of statements over both, and `GET /folders` does the same as labelled folders are added: the Label projection is one batched statement per read whatever the row count (spec 6.1, 7.10; issue #226).
- AC-475 Given an archived Label, then every existing assignment stands, both producers still carry it with `archived: true`, the default definition listing drops it and `state=archived` finds it, a new application is refused 409 with nothing written, an existing assignment may still be removed, and restore re-enables application under the same id; and an archived Label may still be renamed, recoloured and described without being restored (spec 7.0; issue #226, #208 R5, R8).
- AC-476 Given a Folder Label of Folder A and a Task in Folder B, then the API answers 422 naming `label_id` and writes nothing, and a direct `INSERT` is refused by the database under a named constraint whichever folder it claims — the invariant being the schema's rather than the handler's; a Folder Label applied to a Folder is 422 the same way and refused by the database the same way; and a Personal Label of another account is 404 rather than 422, the two refusals being different facts (spec 4.15, 7.0, 10.2; issue #226, #208 R4).
- AC-477 Given a Personal Label applied to shared work, when its owner loses access to the folder, then the assignment row remains and is invisible to every read the owner still has, the Label definition stays theirs and discloses no metadata of the target, and restoring access makes the association visible again with no repair step; and purging the target removes the assignment by cascade while the definition survives it (spec 8.8, 10.2; issue #226, #208 R8).
- AC-478 Given the five caps — 500 Personal definitions per account, 250 Folder definitions per folder, 100 Personal and 100 Folder Labels on one Task, 100 Personal Labels on one Folder — then the boundary is refused 422 naming the collection, a repeat of a Label already applied is admitted at the cap, the two per-Task caps are counted apart, and every refusal leaves the catalog in the state it was (spec 10.3; issue #226, #208 R5 clause 10).
- AC-479 Given the Shelf terminology move of issue #226, then all three directions of 4.18 still hold membership and shelf name in step — a membership written through 7.4 makes the shelf, a shelf rename rewrites the memberships, a shelf delete clears them and leaves the folders — the surviving contract field is `my_shelf` and the surviving request field is `shelf`, and **because the database side is the expand half of an expand-and-contract pair, `folder_members.shelf_name` and `folder_members.label` both exist and agree after every one of those write paths**. The contract half is issue #247, which drops `label` after this migration is live; when it lands, this criterion's last clause becomes the assertion that one column remains (spec 4.4, 4.18, 7.4, 7.16, 11.14; issue #226, #247, #208 R9).
- AC-480 Given a folder member who does not own the folder, then they may create, rename, recolour, describe, archive, restore, apply and remove that folder's Labels, with no owner exception — the interim rule until issue #209 supplies explicit Responsibilities and Authorities — and applying and removing a Label are each idempotent (spec 5.4, 7.4; issue #226, #208 R5A, R8).
- AC-481 Given the Shelf wire rename of issue #226 and a browser tab that keeps its old bundle across a deploy, then `PATCH /folders/:id/my-membership` accepts **either** `shelf` or `label`, a body sending only `label` stores the value in `folder_members` rather than answering 200 having stored nothing, a body sending only `shelf` stores it, a body sending both stores the `shelf` one, null clears through either spelling, and the Folder object carries both `my_shelf` and `my_label` with equal values in every producer — the wire half of the expand-and-contract the column already has, because one deployable serves the SPA and the API together while a tab outlives the deploy window without bound (spec 4.4, 4.18, 7.0, 7.4, 11.11, 11.14; issue #226, #247, #208 R9).

## The lifecycle (issue #227)

AC-540 to AC-554 are the Label model met by the acts that already existed: duplication,
move, the workflow file, the account export, the Trash and its purge, and membership loss.
They are here rather than in 12.16 and 12.20 — which 12.24's own header above said they
would be — on one ground: **every one of them is a rule about Labels that happens to be
observed through another surface**, and splitting them across three files would mean the
two readings of the word "archived" below never sit on one page. 12.16 and 12.20 keep the
criteria about duplication and Trash as such, and AC-200, AC-277 and AC-014 are unchanged
by this work.

**These fifteen were AC-520 to AC-534 for about an hour, and the gap at 535 to 539 is
where that is written down.** They were allocated by scanning every ref for the highest
number in use, which was the rule and which was right when it ran; `backend/228` was
concurrently being moved onto 510 to 523 to clear collisions of its own, and that landed
afterwards, putting 520 to 523 in two branches at once under four filenames. The block
was reassigned rather than re-scanned, the five numbers below it are left empty so the
move is legible, and the registry's own entry carries the reasoning and the issue — #252 —
that the near-miss opened. Nothing about any criterion changed; only its number did.

**The one sentence the fifteen come from.** A Personal Label is the viewer's own and never
travels to another person; a Folder Label belongs to its Folder and is re-created with new
ids when the Folder is copied, never pointed at the source's.

**And the one word that means two things.** On a Task duplicate, "archived" withholds the
right to be newly applied, so nothing archived crosses. On a Folder duplicate it is
*state being copied* for the Folder's own taxonomy and *permission withheld* for the
duplicator's Personal Labels, in the same act. AC-541 and AC-543 are the pair that holds
both readings; making either agree with the other loses a rule.

- AC-540 Given a Task carrying an active Folder Label and active Personal Labels of two different members, when a member duplicates it, then the copy wears the **same** Folder Label ids — the copy being in the same Folder, whose vocabulary is already its own — and the duplicator's own Personal Labels, and no row of any other member's Personal Label exists on the copy, asserted over `task_personal_labels` by owner because no read the duplicator has could show one either way; and a Folder Label the source never wore is not applied (spec 7.16, 7.0, 10.2; issue #227 area 1, #208 R4 and R6A).
- AC-541 Given a Task wearing an archived Folder Label and an archived Personal Label beside active ones, when it is duplicated, then neither archived assignment is on the copy — a duplicate is a new application and an archived Label may not be newly applied — and both are still on the source, archive being non-destructive (spec 7.16, 7.0; issue #227 areas 1 and 9, #208 R5).
- AC-542 Given a Folder holding two Folder Labels crossed over two Tasks, when it is duplicated, then the copy holds both definitions with their names, colours and descriptions under **new ids**, none of them the source's; each copied Task wears the copy's own Label and not the other's, so the remap is by row rather than by name or by everything-on-everything; and the source keeps its whole vocabulary (spec 7.16, 4.15; issue #227 area 2, #208 R4 and R6A).
- AC-543 Given a Folder whose vocabulary holds an archived definition and whose duplicator holds an archived Personal Label, when it is duplicated, then the archived **Folder** definition is copied and arrives archived, and the assignment standing against it comes with it — a copy that revived it would widen a taxonomy its owner narrowed on purpose — while neither the Folder nor its copied Tasks acquires the duplicator's archived **Personal** Label, and the source keeps both of its own (spec 7.16, 7.0; issue #227 areas 2 and 9, #208 R5).
- AC-544 Given two members who have each privately classified the same shared Task and the shared Folder, when either of them duplicates the Task and then the Folder, then every copy holds exactly the duplicator's own Personal rows and none of the other's, read over `task_personal_labels` and `folder_personal_labels` by owner; and the other member, reading a copy themselves, sees none of their own on it. Driven from both sides, because a rule keyed on the Folder owner rather than on the caller passes one direction and fails the other (spec 7.16, 7.0, 10.2; issue #227 areas 1, 2 and 5, #208 R4).
- AC-545 Given a Task wearing a source Folder Label and Personal Labels of two members, when it is moved to another Folder, then the Task's `folder_id` is the destination — a wrong ordering of the DELETE and the UPDATE presents as a refused move rather than a stale row — the source Folder Label assignment is gone, and every Personal assignment stands, the mover's and the co-member's alike; and given a move refused because the caller cannot reach the destination, then the assignments are untouched, the request being one unit (spec 7.6, 4.5; issue #227 area 3, #208 R6A).
- AC-546 Given a destination Folder holding a Folder Label identical to the source's in name, case, colour and description, when a Task wearing the source's is moved into it, then the moved Task wears **no** Folder Label: the source's went with the Folder that owns it and the destination's identically-named one is not applied, scope being part of identity; the destination's own Label is unaffected and still applicable by hand; and a round trip does not restore the original either (spec 7.6, 7.0; issue #227 area 3, #208 R4 and R6A).
- AC-547 Given a Folder with an active vocabulary — one category nothing wears — an archived one, and Tasks wearing them, when a workflow file is written from it and imported **into another account**, then the file says version 3, carries every active definition including the unused one with its colour and description, carries no archived definition, names each Task's Labels by a file-local key, and contains no database id of any Label, Folder or Task; and the imported Folder holds new Label identities, all active, with each Task's assignments remapped onto them, while the source is untouched. Given a Folder with no Folder Labels, then the file is the version 1 file this build wrote before #227, with no `labels` key at all (spec 7.16; issue #227 area 4, #208 R4).
- AC-548 Given a version 1 workflow file and a version 2 one, then each still imports whole — its work, notes, star and step titles arriving as they always did, and no Label vocabulary being invented for a file that carried none; given a file below version 3 that carries a `labels` key in any arrangement, including an array of foreign tag names per task and a null at either level, then the key is dropped and the file imports, a file declaring no vocabulary being unable to contradict one; given a **version 3** file whose task names a key its folder does not declare, then 422, the tolerance being scoped by the version rather than removed; and given a version this build does not know, then 422, because a schema that accepted any number would put back the silent strip the bump exists to prevent (spec 7.16, 10.3; issue #227 area 4).
- AC-549 Given an author whose own Personal Labels are on the Folder and on every Task, when a workflow file is written, then neither the name, the description, the id, nor the author's account id appears anywhere in its bytes; and given a hand-edited file carrying a top-level personal catalog, a `scope: 'personal'` definition with an `owner_user_id`, and a task naming personal labels, when it is imported, then the importer gains no Personal Label, the author's catalog is unchanged, and every declared definition is created as a **Folder** Label with no owner — `scope` not being a field of this format, so naming one changes nothing rather than choosing one (spec 7.16, 11.14; issue #227 areas 4 and 5, #208 R4).
- AC-550 Given an account holding archived and active Personal Labels and an owned Folder whose vocabulary holds an archived definition and one nothing wears, then `GET /me/export` answers a document that validates against the shared contract, says version 4, carries the whole Personal catalog with its archived state, carries the Folder's **complete** vocabulary — unused and archived included — carries the viewer's Personal Labels on the Folder and both Label id arrays on every Task, and every assignment id resolves to a definition the document holds (spec 7.22, 10.9; issue #227 area 5, #208 R4 and R5).
- AC-551 Given a Folder the viewer belongs to and does not own, holding one Folder Label on the viewer's own task and another on a task that is not theirs, plus a Personal Label of the owner's on the viewer's task, then the viewer's export carries the first definition on that task and **nowhere in the document** carries the second, its description, or the owner's Personal Label by id or by name; and given a saved View whose definition names a Label id the viewer cannot reach, then the definition comes back exactly as stored and no metadata of that Label enters the document — dropping the criterion would silently broaden the View and resolving it would be the disclosure the first half refuses (spec 7.22, 4.19, 10.2, 10.9; issue #227 areas 5 and 6, #208 R4).
- AC-552 Given a Task wearing an archived and an active Folder Label and a Personal Label, when it is soft-deleted, then every assignment row stands; when it is restored, then every one reads back with no repair step and the archived one arrives archived. And given a soft-deleted Folder, then its Folder Labels, its Tasks' assignments and the viewer's Personal assignment to it all stand — 0022's cascades hang off a `DELETE` and a soft delete is an `UPDATE` — and a restore reads them back (spec 7.13, 4.3, 4.5; issue #227 areas 7 and 9).
- AC-553 Given a purged Task, then its assignment rows are gone by cascade and both Label **definitions** survive it; given a purged Folder, then its own Labels, every assignment of them, the owner's Personal assignment to the Folder and a member's Personal assignment to a Task inside it are all gone by cascade while both Personal definitions survive; and given a deleted account, then it holds no Personal Label and its assignments on work that outlives it are gone — **not by cascade**, 8.10 step 7 scrubbing the `users` row rather than deleting it, but by 8.10 step 6c's explicit statement, without which they would persist indefinitely — **while another member's Personal Label on that same Task and Folder, and their definition, are untouched**, step 6c being scoped to the leaving account and a statement over every Personal Label in the product satisfying the first half of this criterion exactly (spec 7.13, 8.10, 4.3, 4.5; issue #227 area 7, #208 R4).
- AC-554 Given a member who has privately classified a shared Task and the shared Folder, when they are removed from the Folder, then both rows still exist; the Task is 404 to them, the Folder is absent from their folder list, and `GET /labels?folder_id=` naming it is 404 rather than 403 or an empty 200 — the one Label gate `ac-397` cannot see, its id being in the query string; their own definition still lists, a definition saying nothing about what wears it; the Folder's own Label is still on the Task for the members who remain; and when they are added back, both assignments read again with no repair step (spec 5.3, 7.4, 10.2; issue #227 area 8, #208 R4).
