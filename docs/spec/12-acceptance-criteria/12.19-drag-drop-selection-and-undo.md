### 12.19 Drag, drop, selection and undo

Every gesture that writes: the hand order, the board drop, the Library drag,
multi-select, and undo.

- AC-221 Given a board on Today grouped by folder, when a task is captured in a column, then it lands in that column's folder and appears on Today; given board view, then no floating add button renders.
- AC-225 Given a completion, when Ctrl+Z is pressed within five seconds, then the task is pending again through an ordinary mutation, and the wire never held the completion back.
- AC-227 Given the Library's one ordered column, when a folder row is dragged onto a closed group, then the group is not sprung open, the carried row names the container it would land in as "Into {group}", and on release the folder is in that group and still in it after a reload; and when that folder is dragged back out of every group, then it is in the ungrouped list and still there after a reload.

**What AC-227 asserts and what it deliberately leaves alone.** 9.1 gives the Library "one
ordered list", "the order is the viewer's own, seeded alphabetically and rearranged by
dragging", and two limits on the gesture: a closed group is never sprung open by a drag
hovering it, and the drop names the container it would land in. The membership half of that is
durable server state, `folder_members.shelf_name` through 7.4's my-membership (that column
was written `label` here until issue #226 renamed it; #247 stops every write to the old one
and drops it a release later, and 4.4 carries the argument), which is why both
halves of this criterion survive a reload and are asserted across one. The *sequence* half is
not asserted, because the design register carries DES-171 as approved with persistence marked
Lane 2 and no store for a directory sequence exists that can hold it: `sidebar_order` is an
array of uuids, and a group in the Library is a label with no id, so an ordering that includes
group entries cannot be written down. A criterion asserting a sequence nothing can persist
would be asserting the client's memory of the last five seconds.

**"Into {group}" is read off the carried row while the pointer is still down**, because that
is the only moment the sentence exists. It is the proposal, not the outcome: DES-171's reason
for `onOver` is that a list holding a gap open for a row that is going somewhere else is lying
about what a release will do, so the criterion reads the promise first and then the release,
and a client that moves the folder correctly while showing the wrong proposal fails the half
that was the design decision.

- AC-228 Given a board grouped by folder, when a card is dragged from one column and released in another, then the carried card names the column it would land in as "Into {column}", the task's folder is that column's folder on the wire, and the card is in that column after a reload; and given a column that is a relation rather than a value, then a release there writes nothing.
- AC-417 Given an existing task on a composed folder page, when it is dragged between prose/images or across a Section boundary, then one page action names the mixed neighbours and the destination `section_block_id`, the task's mixed position and semantic Section change together, and both exact placement and membership survive refresh; two concurrent drops into one gap retain both tasks and produce one deterministic read order (4.5, 7.16, 8.3, 9.6; issue #184). Multi-selected task drag remains #186.
- AC-266 Given a folder holding several undated open tasks and no hand order, then its unscheduled section reads exactly in Q2's row order as it always has; and when one of those tasks is placed through the order endpoint between two named neighbours, then the section reads with that task between exactly those two and every other task in the order it already had, that sequence survives a fresh request, and the same call repeated leaves the sequence unchanged; and given a task placed with no neighbour above it, then it reads first, the top of an arranged list being reachable.
- AC-267 Given a task carrying a due date, or a completed one, when the order endpoint is called for it, then 409 and no row's position changes, a hand order belonging to the unscheduled list alone; and given a neighbour id that is a task in another folder, one that does not exist, or the moved task itself, then 422 naming the field and nothing is written; and given a task in a folder the caller is not a member of, then the 10.2 not-found shape rather than 403.
- AC-268 Given two members of one folder placing two different tasks into the same gap of its unscheduled list at the same time, then both placements survive, the section lists every task exactly once, and two separate reads of the section answer the identical sequence, ties in the stored order being broken to one answer by the id key section 6's preamble ends every order with.
- AC-269 Given a folder whose unscheduled list has been arranged by hand, then Q2's own page, Q3, Q4, Q5, Q6, Q8 and the folder's own scheduled and completed sections each answer exactly the sequence they answered before the arrangement; and given an arranged folder holding a task that is then abandoned, then that task keeps its hand place rather than sorting below the pending ones, which is the one ordering change of item 44 and is confined to that section.

**AC-269 asserts an absence**, and it is the one of these most likely to be broken by
accident: the hand order changes no query but the one item 44 permits, and an implementation
breaks it by widening an ORDER BY it did not have to touch.

**The order endpoint's criteria name neighbours and never a stored key.** `tasks.position` is
a fractional index and the value it holds is the server's business; a criterion that asserted
a key would pin the contract to an algorithm and would go red the day the midpoint changed.
What the criteria read is the sequence the list answers, which is what section 6 promises
anybody.

- AC-278 Given a folder with no filter or sort applied, when a task row is dragged to another place in the composed page and released, then the client writes the folder page action naming the real task and the two page items it now sits between and the page reads back in that exact order after a reload; and given a view, or the same folder with a filter applied, when the same gesture is made, then nothing is written and the row returns to where section 6 puts it.
- AC-279 Given a list of tasks, when one row is carried onto another and held still there for the dwell, then the list proposes a folder of the two and, on release, opens its naming panel; and when the panel is confirmed with a name, then exactly one `POST /folders` is written with that name, both tasks are moved into it with `PATCH /tasks/:id`, and no other endpoint is called.
- AC-280 Given a list of tasks, when a row is pressed and held without moving, then the list enters selection with that row selected and its bar says how many are selected, and a tap on another row adds it; when the bar's "Mark complete" is pressed, then every selected task is completed through 7.6's transition and the bar leaves; when "Move to a folder" names a folder, then every selected task is moved with `PATCH /tasks/:id`; and when "Delete" is pressed, then 9.3's confirmation is asked once, in the plural, and each task is deleted through 7.6 on Continue. The bar offers no Duplicate.
- AC-340 Given Scheduled in calendar view, when an open task is dragged from its day to another, then 7.6 hears a PATCH of its due date and the task reads that day; and the month opens with today's cell in view (spec 9.5, 7.6).
