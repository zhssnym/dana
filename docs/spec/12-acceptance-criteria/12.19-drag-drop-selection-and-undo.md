### 12.19 Drag, drop, selection and undo

Every gesture that writes: the hand order, the Library drag,
multi-select, and undo.

- AC-225 Given a completion, then the undo bar shows at the bottom centre of the window; and when Ctrl+Z is pressed within five seconds, then the task is pending again through an ordinary mutation, and the wire never held the completion back (spec 9.1).
- AC-227 Given the Library's one ordered column, when a folder row is dragged onto a closed group, then the group is not sprung open, the carried row names the container it would land in as "Into {group}" while the pointer is still down, and on release the folder is in that group and still in it after a reload; and when that folder is dragged back out of every group, then it is in the ungrouped list and still there after a reload (group membership is durable; the Library's drag sequence itself has no store).
- AC-417 Given an existing task on a composed folder page, when it is dragged between prose/images or across a Section boundary, then one page action names the mixed neighbours and the destination `section_block_id`, the task's mixed position and semantic Section change together, and both exact placement and membership survive refresh; two concurrent drops into one gap retain both tasks and produce one deterministic read order (4.5, 7.16, 8.3, 9.6).
- AC-266 Given a folder holding several undated open tasks and no hand order, then its unscheduled section reads exactly in Q2's row order; and when one of those tasks is placed through the order endpoint between two named neighbours, then the section reads with that task between exactly those two and every other task in the order it already had, that sequence survives a fresh request, and the same call repeated leaves the sequence unchanged; and given a task placed with no neighbour above it, then it reads first.
- AC-267 Given a task carrying a due date, or a completed one, when the order endpoint is called for it, then 409 and no row's position changes, a hand order belonging to the unscheduled list alone; and given a neighbour id that is a task in another folder, one that does not exist, or the moved task itself, then 422 naming the field and nothing is written; and given a task in a folder the caller is not a member of, then the 10.2 not-found shape rather than 403.
- AC-268 Given two members of one folder placing two different tasks into the same gap of its unscheduled list at the same time, then both placements survive, the section lists every task exactly once, and two separate reads of the section answer the identical sequence, ties in the stored order being broken by the id key section 6's preamble ends every order with.
- AC-269 Given a folder whose unscheduled list has been arranged by hand, then Q2's own page, Q3, Q4, Q5, Q6, Q8 and the folder's own scheduled and completed sections each answer exactly the sequence they answered before the arrangement; and given an arranged folder holding a task that is then abandoned, then that task keeps its hand place rather than sorting below the pending ones, which is the one ordering change the hand order makes and is confined to that section.
- AC-278 Given a folder with no filter or sort applied, when a task row is dragged to another place in the composed page and released, then the client writes the folder page action naming the real task and the two page items it now sits between and the page reads back in that exact order after a reload; and given a view, or the same folder with a filter applied, when the same gesture is made, then nothing is written and the row returns to where section 6 puts it.
- AC-279 Given a list of tasks, when one row is carried onto another and held still there for the dwell, then the list proposes a folder of the two and, on release, opens its naming panel; and when the panel is confirmed with a name, then exactly one `POST /folders` is written with that name, both tasks are moved into it with `PATCH /tasks/:id`, and no other endpoint is called.
- AC-280 Given a list of tasks, when a row is pressed and held without moving, then the list enters selection with that row selected and its bar says how many are selected, and a tap on another row adds it; when the bar's "Mark complete" is pressed, then every selected task is completed through 7.6's transition and the bar leaves; when "Move to a folder" names a folder, then every selected task is moved with `PATCH /tasks/:id`; and when "Delete" is pressed, then 9.3's confirmation is asked once, in the plural, and each task is deleted through 7.6 on Continue. The bar offers no Duplicate.
- AC-340 Given Scheduled in calendar view, when an open task is dragged from its day to another, then 7.6 hears a PATCH of its due date and the task reads that day; and the month opens with today's cell in view (spec 9.5, 7.6).
