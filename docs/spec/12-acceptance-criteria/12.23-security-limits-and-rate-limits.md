### 12.23 Security, limits and rate limits

The envelope, the parser, the caps under concurrency, the route sweep, the rate limits,
the response headers, and what the browser reports back through them.

- AC-101 Given a sixth invite within one minute or a twenty-first within a day, then 429 with Retry-After.
- AC-102 Given a fetch of an existing task in an inaccessible folder, then the response is indistinguishable from a nonexistent id (404).
- AC-103 Given the logs after a full suite run, then no task title, note, step title, email address in invite events, or token appears in them.
- AC-104 Given /api/health, then 200 with the build version, and a deliberately thrown test error reaches the error tracker.
- AC-117 Given any request the mounted surface answers with a 4xx status, when the body is inspected, then it carries the 7.0 envelope with error.code and error.message both non-empty strings.
- AC-118 Given a body presented as JSON that does not parse, parses to something other than an object, or exceeds the parse limit, when any endpoint receives it, then 400 in the envelope and no side effects; given a parsed object carrying a wrong-typed field, then 422 naming the field; given unknown fields beside valid ones, then they are ignored and the request is processed as if they were absent.
- AC-124 Given two concurrent requests that would each take a 10.3 count from its limit to one past it, a 26th member, a 201st custom folder, then exactly one succeeds, the other is refused 422, and the stored count equals the limit.
- AC-236 Structural: every mutating route on the mounted application answers 401 with no session and 403 with a session but no X-CSRF-Token, enumerated over the router rather than sampled; two are exempt by name and each carries its reason, the development login, which precedes any session and is absent from production builds, and `POST /api/csp-report`, which a browser sends of its own accord with no cookie and no token this application could ask it to add (10.8), and an exemption naming a route that is mounted and does answer 401 fails.
- AC-238 Given any response, then it carries Content-Security-Policy with default-src 'self' and frame-ancestors 'none', and an img-src admitting `https://*.googleusercontent.com` where account pictures are stored, and Referrer-Policy: strict-origin-when-cross-origin, and no Strict-Transport-Security, HSTS being the edge's alone (10.8).
- AC-392 Given a signed-in person, when they call GET /api/v1/me/export a sixth time within one hour, then 429 with Retry-After and the `rate_limited` envelope, the first five having answered 200; and a second account's first call answers 200 against the same running application, the quota being per user (spec 7.22, 10.4).
- AC-394 Given an HTML response from this application, then its Content-Security-Policy names the violation endpoint through both `report-uri` and `report-to`, and the response carries a `Reporting-Endpoints` header naming the same path, and every directive 10.8 fixed before it is unchanged.
- AC-395 Given a violation report posted from this deployment's own origin, in the `report-uri` shape or the Reporting API shape, then the endpoint answers 204 and writes exactly one warn-level `csp_violation` line carrying the effective directive, the blocked URI and the document path, with no script sample and no query string anywhere in it, and hands Sentry one message whose fingerprint, text and tags are built from those same whitelisted values and never from the report; a second report with that fingerprint inside the ten-minute window is logged again and captured no second time, a report with a different fingerprint is captured, and past 20 events in a window a report is logged, is not captured, and one message says the budget is spent.
- AC-396 Given a violation report about another origin, one whose blocked URI is a browser-extension scheme, or a body over the 16 KB cap, then nothing is logged and nothing reaches Sentry, and a dropped report is answered 204 exactly as a kept one is; a `data:` URL refused under `style-src` is dropped while the same URL refused under `script-src` is kept; and given more than 10.4's row allows in a minute, the next is refused 429 with Retry-After.
- AC-397 Structural: every route on the mounted application whose path carries a parameter is enumerated over the router rather than sampled, and driven as a signed-in person with no membership, no authorship and no connection to the row that id names; each answers 404, or 403 where 5.4 or 7.15 grants visibility and withholds the act, and where the matrix distinguishes a member from an owner the member variant is asserted beside it; an id-bearing route with no expected status fails, and a route whose parameter names no row of ours carries its reason, as 10.2's public reads do.
- AC-399 Structural: no file under `app/src/server` parses `req.body` other than through `parseBody`, in either the checked or the throwing spelling, the helper itself being the one exception (spec 7.0, 11.14, 11.15).
- AC-400 Given a signed-in person who sends a request body carrying a top-level key its schema does not declare, when the mounted application answers, then the status and the body are unchanged — 7.0's tolerance holds and the key is still stripped — and exactly one warn-level `unknown_request_fields` line is written, naming the route as its method and mounted path template and the undeclared key names and nothing else, with no value the caller sent and no row id from the URL anywhere in it; and given a body every key of which is declared, or a body refused 422 with its fields named, then no such line is written at all (spec 10.5, 11.14).
- AC-402 Given the document this application actually serves, at `/` and at `/app`, then every inline script in the body of that response is named by a sha256 hash-source inside the `script-src` directive of that same response's Content-Security-Policy, and the response carries `Reporting-Endpoints` naming the path `report-uri` names (spec 10.8, 11.11).
- AC-414 Given an application built with an APP_ORIGIN, when a request arrives carrying any other host, then a GET or HEAD is answered 301 with a Location naming the same path and query on the canonical origin, every other method is answered 404 in the 7.0 envelope, `/api/health` is answered whatever host it arrives on, and a request already on the canonical host reaches whatever it would have reached, in any casing; given an application built without one, then nothing redirects and no method is refused by host (spec 10.1, 11.11).
- AC-421 Given any application response, then its `frame-src` is exactly `https://www.youtube-nocookie.com https://player.vimeo.com`, with no wildcard or caller-selected origin, and its `media-src` gains no remote host because direct media remains a link (10.8).
- AC-410 Given the mounted application, then it trusts exactly one proxy hop and not the whole `X-Forwarded-For` header; given a request carrying one forwarded address, then `req.ip` reads that address; given two, then it reads the last, the hop the proxy appended, and never the first, which the caller writes; given none, then it reads the socket peer; and given a per-address limit of 10.4, then two clients with different forwarded addresses spend separate buckets, one exhausting its own without refusing the other (spec 10.4, 11.11).
- AC-412 Given more sign-in begins in a minute than 10.4's row allows, all carrying one forwarded address, then the next is refused 429 with Retry-After and the `rate_limited` envelope; given a different forwarded address, then it is not refused, the limit being per client rather than per deployment; and given the callback, then it carries a counter of its own, so a spent begin quota does not refuse a person who is being redirected back and forth (spec 10.4, 11.6, 11.11).
