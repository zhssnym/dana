### 12.23 Security, limits and rate limits

The envelope, the parser, the caps under concurrency, the route sweep, the rate limits,
and the response headers.

- AC-101 Given a sixth invite within one minute or a twenty-first within a day, then 429 with Retry-After.
- AC-102 Given a fetch of an existing task in an inaccessible folder, then the response is indistinguishable from a nonexistent id (404).
- AC-103 Given the logs after a full suite run, then no task title, note, step title, email address in invite events, or token appears in them.
- AC-104 Given /api/health, then 200 with the build version, and a deliberately thrown test error reaches the error tracker.
- AC-117 Given any request the mounted surface answers with a 4xx status, when the body is inspected, then it carries the 7.0 envelope with error.code and error.message both non-empty strings.
- AC-118 Given a body presented as JSON that does not parse, parses to something other than an object, or exceeds the parse limit, when any endpoint receives it, then 400 in the envelope and no side effects; given a parsed object carrying a wrong-typed field, then 422 naming the field; given unknown fields beside valid ones, then they are ignored and the request is processed as if they were absent.
- AC-124 Given two concurrent requests that would each take a 10.3 count from its limit to one past it, a 51st step, a 26th member, a 201st custom folder, then exactly one succeeds, the other is refused 422, and the stored count equals the limit.

**One reading AC-124 rests on**, recorded because the test's shape turns on it: on a
single-connection backend the interleaving that produces the breach is likely but not
guaranteed, so the criterion asserts the outcome rather than asserting that a breach was
attempted. A run in which the two requests serialize completely satisfies it for the same
reason an interleaved run does, that the limit held and one caller was refused.

- AC-236 Structural: every mutating route on the mounted application answers 401 with no session and 403 with a session but no X-CSRF-Token, enumerated over the router rather than sampled; the development login alone is exempt, preceding any session and absent from production builds.
- AC-238 Given any response, then it carries Content-Security-Policy with default-src 'self' and frame-ancestors 'none', and Referrer-Policy: strict-origin-when-cross-origin, and no Strict-Transport-Security, HSTS being the edge's alone (10.8). (Amended at the polish round of 2026-08-30, avatars F3: and its img-src admits the host 7.2's account picture is stored on, `https://*.googleusercontent.com`, which the policy had silently refused since 4.1 — the criterion gains the arm because a directive narrower than what the client loads is the same defect as one wider, and only one of the two announces itself.)
- AC-397 Structural: every route on the mounted application whose path carries a parameter is enumerated over the router rather than sampled, and driven as a signed-in person with no membership, no authorship and no connection to the row that id names; each answers 404, or 403 where 5.4 or 7.15 grants visibility and withholds the act, and where the matrix distinguishes a member from an owner the member variant is asserted beside it. The table of expected statuses is hand-written and asserted against the enumeration in both directions, so an id-bearing route with no entry fails rather than passing in silence; the four routes whose parameter names no row of ours each carry an entry giving the reason, as 10.2's public reads do.

**One finding stands open under AC-397 and the criterion records it rather than excusing it.**
`DELETE /api/v1/files/:id` answers **404** to a folder member who is neither the uploader nor
the folder owner, and that same member reads the same bytes at 200 through
`GET /api/v1/files/:id`. 7.15's rule is enforced correctly — the delete is the uploader's or
the folder owner's — and it is 10.2's grammar that is not: visibility is permitted, so the
forbidden act is 403. `DELETE /api/v1/comments/:id` is the identical shape one router over
and answers 403. The status sits on a frozen section 7 endpoint, so it is the owner's to
move; until then the variant is held in the criterion's `test.fails` block at the status the
rule requires, which is green only while the defect stands and goes red the day it is fixed.
