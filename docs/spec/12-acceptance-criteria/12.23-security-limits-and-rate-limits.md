### 12.23 Security, limits and rate limits

The envelope, the parser, the caps under concurrency, the route sweep, the rate limits,
the response headers, and what the browser reports back through them.

- AC-101 Given a sixth invite within one minute or a twenty-first within a day, then 429 with Retry-After.
- AC-102 Given a fetch of an existing task in an inaccessible folder, then the response is indistinguishable from a nonexistent id (404).
- AC-103 Given the logs after a full suite run, then no task title, note, step title, email address in invite events, or token appears in them.
- AC-104 Given /api/health, then 200 with the build version, and a deliberately thrown test error reaches the error tracker.
- AC-117 Given any request the mounted surface answers with a 4xx status, when the body is inspected, then it carries the 7.0 envelope with error.code and error.message both non-empty strings.
- AC-118 Given a body presented as JSON that does not parse, parses to something other than an object, or exceeds the parse limit, when any endpoint receives it, then 400 in the envelope and no side effects; given a parsed object carrying a wrong-typed field, then 422 naming the field; given unknown fields beside valid ones, then they are ignored and the request is processed as if they were absent.
- AC-124 Given two concurrent requests that would each take a 10.3 count from its limit to one past it, a 51st step, a 26th member, a 201st custom folder, then exactly one succeeds, the other is refused 422, and the stored count equals the limit.

**One reading AC-124 rests on**, recorded because the test's shape turns on it: on a
single-connection backend the interleaving that produces the breach is likely but not
guaranteed, so the criterion asserts the outcome rather than asserting that a breach was
attempted. A run in which the two requests serialize completely satisfies it for the same
reason an interleaved run does, that the limit held and one caller was refused.

- AC-236 Structural: every mutating route on the mounted application answers 401 with no session and 403 with a session but no X-CSRF-Token, enumerated over the router rather than sampled; two are exempt by name and each carries its reason, the development login, which precedes any session and is absent from production builds, and `POST /api/csp-report`, which a browser sends of its own accord with no cookie and no token this application could ask it to add (10.8), and an exemption naming a route that is mounted and does answer 401 fails.
- AC-238 Given any response, then it carries Content-Security-Policy with default-src 'self' and frame-ancestors 'none', and Referrer-Policy: strict-origin-when-cross-origin, and no Strict-Transport-Security, HSTS being the edge's alone (10.8). (Amended at the polish round of 2026-08-30, avatars F3: and its img-src admits the host 7.2's account picture is stored on, `https://*.googleusercontent.com`, which the policy had silently refused since 4.1 — the criterion gains the arm because a directive narrower than what the client loads is the same defect as one wider, and only one of the two announces itself.)
- AC-392 Given a signed-in person, when they call GET /api/v1/me/export a sixth time within one hour, then 429 with Retry-After and the `rate_limited` envelope, the first five having answered 200; and a second account's first call answers 200 against the same running application, the quota being per user (spec 7.22, 10.4; issue #77).
- AC-394 Given an HTML response from this application, then its Content-Security-Policy names the violation endpoint through both `report-uri` and `report-to`, and the response carries a `Reporting-Endpoints` header naming the same path, and every directive 10.8 fixed before it is unchanged. (Both generations, because browsers are split across them: `report-uri` is implemented everywhere and deprecated in Chromium, `report-to` is its replacement and not yet universal, so either alone loses reports — one today and one on a day nothing will announce. An HTML response and not only an API one, because the document is the response class a refusal happens on.)
- AC-395 Given a violation report posted from this deployment's own origin, in the `report-uri` shape or the Reporting API shape, then the endpoint answers 204 and writes exactly one warn-level `csp_violation` line carrying the effective directive, the blocked URI and the document path, with no script sample and no query string anywhere in it, and hands Sentry one message whose fingerprint, text and tags are built from those same whitelisted values and never from the report; a second report with that fingerprint inside the ten-minute window is logged again and captured no second time, a report with a different fingerprint is captured, and past 20 events in a window a report is logged, is not captured, and one message says the budget is spent. (Three rules, because none of them bounds anything alone: grouping is not a quota, Sentry counting events and not issues; dedupe is not a bound when the key contains a stranger's string; and a budget that went quiet without saying so would reproduce the silence this endpoint exists to end. The log is the record and is throttled by none of them.)
- AC-396 Given a violation report about another origin, one whose blocked URI is a browser-extension scheme, or a body over the 16 KB cap, then nothing is logged and nothing reaches Sentry, and a dropped report is answered 204 exactly as a kept one is; and given more than 10.4's row allows in a minute, the next is refused 429 with Retry-After. (With the two the endpoint must *not* drop asserted beside them: a `data:` URL refused under `style-src` is extension noise and goes, the same URL refused under `script-src` is a script assembled at runtime and stays.)
- AC-397 Structural: every route on the mounted application whose path carries a parameter is enumerated over the router rather than sampled, and driven as a signed-in person with no membership, no authorship and no connection to the row that id names; each answers 404, or 403 where 5.4 or 7.15 grants visibility and withholds the act, and where the matrix distinguishes a member from an owner the member variant is asserted beside it. The table of expected statuses is hand-written and asserted against the enumeration in both directions, so an id-bearing route with no entry fails rather than passing in silence; the four routes whose parameter names no row of ours each carry an entry giving the reason, as 10.2's public reads do.
- AC-399 Structural: no file under `app/src/server` parses `req.body` other than through `parseBody`, in either the checked or the throwing spelling, with an allowlist of exactly one — the helper itself — and the helper's call sites and the modules holding them counted to equality, so a body-taking route cannot join or leave the application without the number moving in the same change (spec 7.0, 11.14, 11.15; issue #104). (A source sweep rather than a runtime one, and the file says so: it proves the spelling and not the path a request takes, because the runtime form needs a minimal valid body, valid ids and satisfied preconditions for twenty-nine routes including a multipart upload and one that fetches from an external host. What it does catch is how this is actually lost — the next route written by copying an older one, carrying the two lines that were the convention before the helper existed — and AC-400 drives the mounted application for the rest.)
- AC-400 Given a signed-in person who sends a request body carrying a top-level key its schema does not declare, when the mounted application answers, then the status and the body are exactly what they were before this line existed — 7.0's tolerance is untouched and the key is still stripped — and exactly one warn-level `unknown_request_fields` line is written, naming the route as its method and mounted path template and the undeclared key names and nothing else, with no value the caller sent and no row id from the URL anywhere in it; and given a body every key of which is declared, or a body refused 422 with its fields named, then no such line is written at all (spec 10.5, 11.14; issue #104). (The absence is half of it. A line on every request would be a line nobody reads, and the search 11.14 asked for would be worthless the day it was needed.)
- AC-402 Given the document this application actually serves, at `/` and at `/app`, then every inline script in the body of that response is named by a sha256 hash-source inside the `script-src` directive of that same response's Content-Security-Policy, and the response carries `Reporting-Endpoints` naming the path `report-uri` names (spec 10.8, 11.11; issue #96). (A browser-leg criterion because it is the only place the build has already run: `.github/workflows/ci.yml` reaches both vitest legs before the build step, `dist/` is gitignored and `actions/checkout` cleans it, so AC-238's arm always takes its source-document fallback in CI and cannot see a script only the build produces — set `injectRegister: 'inline'` in `vite.config.ts` and vite-plugin-pwa injects a second one, the service worker is refused in production, offline stops working, and the whole vitest suite stays green. Measured against the header of the same response rather than against a constant, which is what makes it independent of `src/server/index.ts` and AC-238 worth keeping beside it; and read on both paths, `/` being answered by `express.static` and `/app` by the SPA fallback, two code paths that have diverged before.)
- AC-414 Given an application built with an APP_ORIGIN, when a request arrives carrying any other host, then a GET or HEAD is answered 301 with a Location naming the same path and query on the canonical origin, every other method is answered 404 in the 7.0 envelope, `/api/health` is answered whatever host it arrives on, and a request already on the canonical host reaches whatever it would have reached, in any casing; given an application built without one, then nothing redirects and no method is refused by host (spec 10.1, 11.11; issue #6). (The pass-through arm asserts a 401 from a mutation on the canonical host rather than the absence of a Location, which a middleware that refused everything would satisfy just as well: reaching the router and being refused for want of a session is what passing through looks like, and the same request on the other host is 404 before any router sees it. The criterion drives `createApp`'s `appOrigin` option rather than the environment, so both halves are two applications in one process and no file races another's `process.env`; the middleware declines to read the environment for the same reason, AC-109's harness setting APP_ORIGIN to its own ephemeral origin and then crafting Host headers, which a redirect reading the environment would answer with a 301 before an auth endpoint saw one. What it cannot see is the cause: every criterion here drives one origin, so a second address serving identical bytes is invisible to all of them, and how many addresses a platform has pointed at this service is a fact 11.11 carries and the boot logs once.)

**One reading AC-392 rests on, and it is the difference between this criterion and AC-101.**
AC-101 measures the invite limiters in isolation, driving `createRateLimits` through a bare
Express application, which proves the policy and cannot prove the wiring: a limiter that is
defined, exported and never attached to a route passes every one of its cases. AC-392 drives
the real route on the mounted application instead, and for it to be able to, 7.22's limit is
the one limit `createApp` does **not** raise under test. That has a cost the next person
writing against this endpoint should know about rather than discover: a test file making a
sixth export call for one person gets a 429 that reads as a defect in the export. The three
files that do call it ration themselves and each says so.


**AC-397 found one defect on its first run, and it is fixed rather than recorded.**
`DELETE /api/v1/files/:id` answered **404** to a folder member who is neither the uploader nor
the folder owner, while that same member read the same bytes at 200 through
`GET /api/v1/files/:id`. 7.15's rule was enforced correctly — the delete is the uploader's or
the folder owner's — and it was 10.2's grammar that was not: visibility is permitted, so the
forbidden act is 403. `DELETE /api/v1/comments/:id` is the identical shape one router over and
has always answered 403. The status sat on a frozen section 7 endpoint and the owner ruled it
in on 2026-09-04 as a correction toward the contract rather than a change to it, 7.15 having
named the actors and never a status. The dated amendment is 7.15's and **AC-398 is the direct
case**, asserting the pair and the two arms 7.15 permits — the sweep alone would be satisfied
by a refusal widened over everybody, since it only ever looks at refusals.

**The mechanism that held the finding while it was open is still in the file and is worth
knowing about**, because the next one may not be a branch's to fix: a variant may carry a
`known` note, which moves it out of the pass that would fail and into a register asserting
that the finding is *still open*, at the status the rule requires rather than the one
observed. Promoting one is deleting one field. The register is empty as of 2026-09-04.

- AC-410 Given the mounted application, then it trusts exactly one proxy hop and not the whole `X-Forwarded-For` header; given a request carrying one forwarded address, then `req.ip` reads that address; given two, then it reads the last, the hop the proxy appended, and never the first, which the caller writes; given none, then it reads the socket peer, so nothing moves in development or under test; and given the one per-address limit 10.4 carries, then two clients with different forwarded addresses spend separate buckets, one exhausting its own without refusing the other (spec 10.4, 11.11; issue #153).

**Two things about AC-410 that a green run does not say, and both are the reason it exists
at all rather than a limitation of it.** Before this landed, `trust proxy` was set nowhere
and every per-address limit was one bucket for the whole deployment behind the edge of
11.11 — and **no existing case could ever have caught it**, because under test and in
development the socket peer *is* the real client, so every criterion that drove a limiter
measured the fixed behaviour on the broken code. That is why this one writes the header by
hand instead of asking a limiter to disagree with itself. And it drives
`POST /api/csp-report`, which as of 2026-09-04 carries the **only** per-address limit this
API has, every other limiter keying on the session's user id; issue #153 named the sign-in
and upload limits and they are per user, so what the criterion protects most is the limits
not yet written, each of which is per client now because of one line and would have been
per deployment without it.

- AC-412 Given more sign-in begins in a minute than 10.4's row allows, all carrying one forwarded address, then the next is refused 429 with Retry-After and the `rate_limited` envelope; given a different forwarded address, then it is not refused, the limit being per client rather than per deployment; and given the callback, then it carries a counter of its own, so a spent begin quota does not refuse a person who is being redirected back and forth (spec 10.4, 11.6, 11.11; issue #168).

**Why AC-412 could not have been written before AC-410, which is the point of it sitting
here.** `GET /api/v1/auth/google` and its callback carried no limiter at all until
2026-09-04, and that gap is older than every limit in 10.4: `createRateLimits` keys on the
session's user id, both routes precede any session by definition, and both are GETs, so even
the general mutation quota would have skipped them. There was nothing to key on but the
address — and an address-keyed limit was worthless until issue #153 gave this process one
trusted proxy hop, because behind the edge of 11.11 every visitor shared the edge's address.
Twenty begins a minute for the whole world is not a limit, it is an outage. **The second
clause above is the arm that would have failed on the old behaviour**, and it is why these
two criteria are neighbours rather than one of them being a detail of the other. The
callback is the route that mattered most: it performs a token exchange against Google, which
makes it the only route in this API that spends an outbound request to a third party on an
unauthenticated caller's say-so.
