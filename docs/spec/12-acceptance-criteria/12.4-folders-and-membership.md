### 12.4 Folders and membership

Who may rename, delete, join and leave a folder, and the identity every member reads.
What a deletion does is 12.20; what a folder page draws is 12.9.

- AC-011 Given a member holding Can view, when they rename the folder or set its icon, colour, cover or description, then 403 to each, and the folder's identity is unchanged for every member; given a non-member, then 404 rather than 403. (**Rewritten 2026-09-20.** It read "given a non-owner member, when renaming the folder, then 403", which made the name the owner's and left the dressing to every member, Can view included. **Accepted #209 R8A** contradicts both halves directly — Can edit may "plan/change all shared Folder work" and Can view is "read only" — and a folder's name and dressing are shared Folder work. Hassan's ruling of 2026-09-20, https://github.com/zhssnym/dana/issues/228#issuecomment-5750892771.)
- AC-012 Given a member holding Can edit or above — the owner, and equally a member holding Full control who is not the owner — when renaming, then 200 and every member reads the new name. (**Rewritten 2026-09-20.** It read "given the owner, when renaming, then 200 and every member reads the new name", which passed for the wrong reason once the rule moved: its actor held custody rather than Access, so it could not tell the old rule from the new one. Authority and ruling as AC-011: **accepted #209 R8A**, https://github.com/zhssnym/dana/issues/228#issuecomment-5750892771.)
- AC-013 Given the owner of a default folder, when deleting it, then 409.
- AC-015 Given a member below Full control, Can edit included, when moving the folder to Trash, then 403 and nothing is deleted; given a member holding Full control who is not the owner, then it proceeds; given a non-member, then 404 rather than 403. (**Rewritten 2026-09-20.** It read "given a non-owner member, when deleting the folder, then 403", which made the act custody's. Authority is **Hassan's ruling of 2026-09-20**, https://github.com/zhssnym/dana/issues/228#issuecomment-5750892771, and **not R8A, which does not settle this**: "Can edit may change all shared Folder work" can be read either way for trashing the whole folder. The narrower reading was chosen because the recoverable direction of a wrong call is the restrictive one — widening later is a decision, while narrowing later takes away something people already had. Nothing in the suite moved: the actor this criterion refuses holds Can edit, which is below Full control under either reading.)
- AC-016 Given the owner removes a member holding assigned tasks, then those tasks are unassigned, the member's My Day entries for the folder's tasks are deleted, and their access ends.
- AC-017 Given a removal leaves exactly one member, then every unassigned task in the folder is assigned to the remaining member (INV-5).
- AC-018 Given a non-owner member leaves, then the same cleanup as removal runs.
- AC-019 Given the owner leaves a folder with other members, then 409 telling them to transfer ownership first, nobody is promoted, and every membership survives; the owner transfers ownership explicitly to an active member who currently holds Full control, and only then may leave. There is no automatic succession. (**Rewritten 2026-09-20.** It read "then ownership transfers to the earliest-joined member (tie: lower user id) and the leave proceeds". Authority is **governing #209 R6** section 2, which R8A's supersession clause keeps governing for "explicit owner succession" by name: joining first is not evidence that anybody intended you to hold custody. Hassan's ruling of 2026-09-20, https://github.com/zhssnym/dana/issues/228#issuecomment-5750892771. The one automatic transfer that survives is 8.10's account-deletion path, which R6 section 3 keeps as a distinct audited recovery rather than ordinary succession.)
- AC-020 Given the owner is the sole member, when leaving, then 409 with the delete-instead message.
- AC-021 Given two members race to add the same person, when both POST, then one 201 and one 409 (INV-10).
- AC-022 Given a member adds someone they hold no roster connection with, when POST members, then 422.
- AC-023 Given a member sets a personal label and color, then another member's view of the folder shows no label change.
- AC-173 Given folders in the sidebar whose 4.3 identity colours differ and one with no colour set, then each row is painted with its own folder's colour and not with another's, a row for an uncoloured folder still renders its name and its pending count, and two folders carrying different colours do not render the same paint. (Reworked at S17a; the text it replaces read the personal column 9.6 retired, and the reasoning sits with S17a's criteria at the foot of this section.)

**AC-173 asserts the dot as identification rather than as a colour value**, for the reason the
tokens file itself gives: the swatch is always beside a name, so what a test can hold the
client to is that the dot is present, that it carries the folder's own colour rather than one
colour for every row, and that a folder with no colour set still renders a row rather than a
gap.

- AC-181 Given the "New folder" action of 9.1, then it opens a dialog taking a name and creating the folder.
- AC-193 Given a member holding Full control who is not the owner, then the folder's name and its icon, colour, cover and description are all theirs to change and every member reads the same identity; given a member holding Can view, then each of the five is refused 403. (**Rewritten 2026-09-20.** It read "given a non-owner member, when they rename the folder, then 403; when they set its icon, colour, cover, or description, then success" — the DES-225 split, which **accepted #209 R8A** replaces with one rule: a folder's identity is ordinary shared Folder work, changed by Can edit and above and by nobody below. Hassan's ruling of 2026-09-20, https://github.com/zhssnym/dana/issues/228#issuecomment-5750892771. **It has carried no test file of its own since the 2026-09-20 suite reduction**, which deleted `ac-193-identity-is-any-members.test.ts`; both halves are asserted deliberately by AC-011's file, whose actor holds Can view, and AC-012's, whose actor holds Full control without owning anything.)
- AC-202 Given an owner and another member who currently holds Full control, when ownership is transferred to that member, then owner_id changes and the previous owner may leave; given a transfer aimed at a member who does not hold Full control, then 422 naming the field and owner_id does not move. There is no default successor. (**The succession clause rewritten 2026-09-20.** It read "the default successor is the longest-standing member per 8.9". Authority is **governing #209 R6** sections 2 and 3; Hassan's ruling of 2026-09-20, https://github.com/zhssnym/dana/issues/228#issuecomment-5750892771. The first clause is unchanged in substance and is now **stated** rather than true by accident: it held only because the transfer target in every exercise of it happened to hold Full control. Like AC-193 it has carried no test file of its own since the 2026-09-20 reduction deleted `ac-202-ownership-transfer.test.ts`; AC-521 asserts both arms.)
- AC-217 Given a folder shared with the viewer, then its menu offers "Leave folder…" and neither Rename nor Delete folder, and its page title is not editable; given an owned folder, then the reverse.
- AC-243 Given a folder whose icon and colour are set once from its own page's mark, then the same glyph and the same colour are drawn on that folder's sidebar row, on the folder chip of a task in it wherever that task's row is listed, and on that folder's entry in the tab strip's "New tab" menu; and given a second folder wearing a different glyph, then no two of those surfaces draw the first folder's glyph for the second.
- AC-246 Given one folder the viewer owns, then the acts its menu offers in the sidebar's Library and the acts its own page's menu offers come from one declared contract: both menus offer History, Rename, Move to shelf, Copy link, Duplicate, Save as workflow and "Delete folder…", those acts stand in the same relative order in both, and every other item either menu carries is one of the four that belong to a surface rather than to the folder, the sidebar's "Add task", "New folder group" and "Open in a new tab" and the page's "Transfer ownership"; and given a folder the viewer is only a member of, then both menus offer "Leave folder…" in Delete folder's place and neither offers Rename or Delete folder, which is AC-217's rule read on both surfaces rather than on one.
- AC-377 Given a description in the body of POST /folders, then the 201 Folder object carries it and a fresh read of the folder gives back the same sentence; given a create body naming only a name, then the folder's description is null, as every folder made before 7.4's paragraph of 2026-09-04 is; and given a description over 500 characters, then 422 naming the field, and the folder is not created. The whole of it is one request: nothing here is written by a PATCH behind the POST, which is what AC-279 refuses on the wire.

**AC-510 to AC-523 are the Folder Access model of issue #228, and they are filed here
because every one of them is about who a folder's members are and what their membership
lets them do.** The product authority is accepted #209 R8A (the six presets), governing R5
and R6 (ownership as custody, and explicit succession), R9 (the append-only Access record)
and R10B, which accepted R9 and R10.

**Six earlier criteria stated decisions those records supersede, and all six were rewritten
on 2026-09-20 rather than deleted or weakened**: AC-011, AC-012, AC-015, AC-019 and AC-193
above, AC-202's succession clause above, and AC-024 in 12.5. Each bullet carries what it
said, what it says now, the record that authorises the change and the ruling's date and
link, which is hard stop 7's requirement that the decision be named in the same commit as
the criterion.

**The authority is not R7, and an earlier draft of this branch said it was.** #228's
request for a ruling grounded AC-011, AC-012, AC-015, AC-193 and AC-024 in "R7 §C / §L /
§N" and called them #209's accepted records. R7 is marked "(PROPOSED, not accepted)" in
#209 and **R8A explicitly supersedes it** — "R8A supersedes the five-level recommendation
in R7 and earlier R4 matrices where they conflict" — so it is authority for nothing, and a
citation pointing at a superseded record is worse than none because it reads as
authoritative. The correction and the ruling are Hassan's, 2026-09-20,
https://github.com/zhssnym/dana/issues/228#issuecomment-5750892771. What actually
authorises each of the six:

| Criterion | Record | What it turns on |
| - | - | - |
| AC-011, AC-012, AC-193 | **accepted R8A** | Can edit may "plan/change all shared Folder work"; Can view is "read only". A folder's name and dressing are shared Folder work. |
| AC-024 | **accepted R8A** | Full control "administer members"; Can edit "cannot administer people/Access". |
| AC-019, AC-202's succession clause | **governing R6** | R8A's supersession clause keeps R5/R6 governing for a named list including "explicit owner succession". |
| AC-015 | **Hassan's ruling of 2026-09-20** | R8A settles it neither way, and the ruling says so rather than pretending otherwise. |

**The numbers are 510 upward and the gap below them is deliberate.** This block was written
as AC-480 to AC-493 and renumbered on 2026-09-20 when two sibling branches were found
holding AC-481 and AC-490 to AC-492 inside it: `backend/226-label-core-domain` spending 470
upward and `backend/220-files-and-media-blocks` running to 507. 494 to 509 are left free and
unclaimed so that this renumber reads as one rather than as an ordinary allocation.

- AC-510 Given memberships carrying no Access decision, when migration 0023 initializes them, then the folder's owner holds Full control and every other member holds Can edit, and each membership gains exactly one baseline history transition whose previous Access is null, whose actor is null and whose kind is migration initialization rather than a grant somebody made; and given any other transition kind, then a null actor is refused, as is a transition from nothing to nothing and a folder invite carrying no intended Access.
- AC-511 Given a folder whose structural owner holds Can view and whose Full-control member owns nothing, then the owner is refused ordinary Work and the Full-control member performs it, and Full control confers no ownership; given a Task its author assigned to somebody else, then the author may not edit it; given an assignment held by a Can-view member, then it authorizes nothing; and given the newest member at the highest preset and the oldest at the lowest, then the newest administers the oldest.
- AC-512 Given Can edit, then adding a member, changing a member's Access, removing a member and inviting into the folder are each refused 403 while every ordinary Work act succeeds; given Full control, then each succeeds and the preset the add named is the preset the membership holds; given an add naming no preset, then 422 and no membership; and given a pending invite, then Full control reads its address and its intended Access while every lower preset reads the empty list.
- AC-513 Given Can edit, then the folder's name, description, icon and colour, its page, its Sections, and every Task in it including another member's are all theirs to change; and given the same member, then trashing the folder, permanently deleting a Task and transferring ownership are each refused.
- AC-514 Given Can contribute, then they originate a Task and choose its initial assignee — themselves, another member, or nobody — and they fully plan and manage the Task currently assigned to them; given another member's existing Task, then every edit, completion and Step write is refused; given a Task they created and handed to somebody else, then they may neither edit it nor take it back; and given their own current Task, then trashing it, editing the folder, creating a Section, creating a dependency and administering members are each refused.
- AC-515 Given Assigned work on the Task currently assigned to them, then they complete it, uncomplete it, tick an existing Step, set and clear its reminder and comment on it; and given the same Task, then every title, notes, date, importance and recurrence edit, every reassignment, abandon, restore and trash, and every Step create, rename, reorder, delete and promote are refused, as is completing a Task assigned to anybody else.
- AC-516 Given a member who read a Task as theirs and a reassignment that commits before their next request, then the mutation is refused and writes nothing, while the current assignee performs it; given a reassignment and a completion in flight together, then whichever the database ordered first is the one that acted and the other was refused, with the status moving only in the first case; and given a Step, then its authorization is its parent Task's locked assignee.
- AC-517 Given Can comment, then they comment, reply, like, and edit and delete their own comment, and every shared Work mutation is refused; given Can view, then commenting, liking, deleting another member's comment and every shared Work mutation are refused while every read succeeds; and given somebody outside the folder, then each answers 404 rather than 403.
- AC-518 Given a member downgraded to Can view, then the comment they wrote is still theirs to read and no longer theirs to edit or delete, the file they uploaded is still theirs to read and no longer theirs to delete, and the Task they created is still theirs to read and no longer theirs to edit; and given a Can-edit member who uploaded a folder's file, then deleting it is refused and Full control deletes it.
- AC-519 Given any preset down to Can view, then putting a Task they may read on their own My Day, setting their own label and colour for the folder, and keeping their own saved views and settings all succeed; given a Task in a folder they are not in, then the personal act answers 404; and given Can view, then shared Work is still refused.
- AC-520 Given a folder with one Full-control member, then demoting them, removing them and their leaving are each refused 409 and write nothing, and the owner may lower their own Access only once another member holds Full control; given a folder with two, then an ordinary leave and an ordinary demotion both succeed; and given two custodians stepping down at once, then exactly one succeeds and the folder keeps a custodian.
- AC-521 Given a structural owner holding any preset, then owner recovery restores Full control and records it as a custody recovery with the owner as actor, and no other member may perform it; given any member, then raising their own Access is refused; given an owner leaving a shared folder, then 409 rather than a silent succession, and nobody is promoted; given a removal aimed at the owner, then 403; given a transfer to a member without Full control, then 422 naming the field, and to one with it, then 200; and given the transfer followed by a step-down, then the previous owner leaves.
- AC-522 Given any Access change, then one append-only transition records the exact from, to, actor, kind and time, a refused change records nothing, and a self-demotion is distinguished from a grant somebody made; given a leave and a removal, then each records the preset to null with the right actor and the record outlives the membership; given a rejoin, then a new explicit grant rather than the old one restored; given an invitation accepted, then the inviter is the actor and not the recipient; given an ownership transfer that changes nobody's Access, then no transition at all; and given the history routes, then every current member reads them and nobody else does.
- AC-523 Given the mounted application, then every mutating route is named either by the Folder action that governs it or by an explicit classification as personal, account or system state, in both directions, so a route with no decision beside it fails and a decision naming no route fails; given the resolver's own table, then every action's answers are monotonic in the ladder and the current-assignee clause never admits a preset on work that is not theirs; and given the Folder Label actions, then Full control and Can edit manage the vocabulary, Can contribute applies existing Labels only to work they may self-manage, and Assigned work, Can comment and Can view modify no shared Label.
