### 12.4 Folders and membership

Who may rename, delete, join and leave a folder, the Access presets, Responsibilities and
facets, and the identity every member reads. What a deletion does is 12.20; what a folder
page draws is 12.9.

- AC-011 Given a member holding Can view, when they rename the folder or set its icon, colour, cover or description, then 403 to each and the folder's identity is unchanged for every member; given a non-member, then 404 rather than 403.
- AC-012 Given a member holding Can edit or above — the owner, and equally a Full-control member who is not the owner — when renaming, then 200 and every member reads the new name.
- AC-013 Given the owner of a default folder, when deleting it, then 409.
- AC-015 Given a member below Full control, Can edit included, when moving the folder to Trash, then 403 and nothing is deleted; given a Full-control member who is not the owner, then it proceeds; given a non-member, then 404 rather than 403. The restrictive reading is chosen because widening later is a decision while narrowing later takes away something people already had.
- AC-016 Given the owner removes a member holding assigned tasks, then those tasks are unassigned, the member's My Day entries for the folder's tasks are deleted, and their access ends.
- AC-017 Given a removal leaves exactly one member, then every unassigned task in the folder is assigned to the remaining member (INV-5).
- AC-018 Given a non-owner member leaves, then the same cleanup as removal runs.
- AC-019 Given the owner leaves a folder with other members, then 409 telling them to transfer ownership first, nobody is promoted, and every membership survives; the owner transfers ownership explicitly to an active member holding Full control, and only then may leave. There is no automatic succession; 8.10's account deletion is the one automatic transfer.
- AC-020 Given the owner is the sole member, when leaving, then 409 with the delete-instead message.
- AC-021 Given two Full-control members race to add the same person, when both POST, then one 201 and one 409 (INV-10).
- AC-022 Given a member adds someone they hold no roster connection with, when POST members, then 422.
- AC-023 Given a member sets a personal label and color, then another member's view of the folder shows no label change.
- AC-173 Given sidebar folders whose 4.3 identity colours differ and one with no colour, then each row is painted with its own folder's colour, an uncoloured folder's row still renders its name and pending count, and two folders with different colours do not render the same paint.
- AC-193 Given a Full-control member who is not the owner, then the folder's name, icon, colour, cover and description are all theirs to change and every member reads the same identity; given a member holding Can view, then each of the five is refused 403.
- AC-202 Given an owner and another member holding Full control, when ownership is transferred to that member, then owner_id changes and the previous owner may leave; given a transfer to a member without Full control, then 422 naming the field and owner_id does not move. There is no default successor.
- AC-217 Given a folder the viewer holds Can view in, then its menu offers "Leave page…" and neither Rename nor "Delete page", and its title, icon, colour, cover and description are not editable; given Can edit, then Rename is offered and the title is editable, and "Delete page" is not; given Full control, owner or not, then Rename and "Delete page" are both offered; and given the owner, then "Leave page…" is replaced by "Transfer ownership" while the folder has other members.
- AC-243 Given a folder whose icon and colour are set from its own page's mark, then the same glyph and colour are drawn on its sidebar row, on the folder chip of its tasks wherever listed, and on its entry in search's results; and given a second folder with a different glyph, then no surface draws the first folder's glyph for the second.
- AC-246 Given a folder the viewer holds Full control in, then the sidebar Library menu and the folder page menu both come from one contract (`app/src/client/lib/object-acts.ts`, gated by `app/src/client/lib/folder-authority.ts`): the sidebar row's menu offers exactly Rename, Copy link, Duplicate and "Delete page" in that order (a right-click on the row opens the same menu), and the folder page's menu offers exactly History, Copy link, Duplicate, "Import as sub-page…", "Export as template" and "Delete page" in that order, leaving Rename to the title, with "Transfer ownership…" before Delete where the viewer owns a shared folder; neither offers a move, a page moving by dragging its sidebar row; and given Can view, then both offer "Leave page…" in Delete's place and neither offers Rename or "Delete page".
- AC-377 Given a description in the body of POST /folders, then the 201 Folder carries it and a fresh read gives back the same sentence; given a create body naming only a name, then the description is null; and given a description over 500 characters, then 422 naming the field and no folder is created; the whole is one request, with no PATCH behind the POST.
- AC-510 Given memberships carrying no Access decision, when migration 0023 initializes them, then the owner holds Full control and every other member Can edit, each membership gains exactly one baseline transition with null previous Access, null actor and kind migration initialization; and given any other transition kind, then a null actor is refused, as are a transition from nothing to nothing and a folder invite carrying no intended Access.
- AC-511 Given a folder whose structural owner holds Can view and whose Full-control member owns nothing, then the owner is refused ordinary Work and the Full-control member performs it, Full control conferring no ownership; given a Task its author assigned to somebody else, then the author may not edit it; given an assignment held by a Can-view member, then it authorizes nothing; and given the newest member at the highest preset and the oldest at the lowest, then the newest administers the oldest.
- AC-512 Given Can edit, then adding a member, changing Access, removing a member and inviting into the folder are each refused 403 while ordinary Work succeeds; given Full control, then each succeeds and the added membership holds the preset the add named; given an add naming no preset, then 422 and no membership; and given a pending invite, then Full control reads its address and intended Access while every lower preset reads the empty list.
- AC-513 Given Can edit, then the folder's name, description, icon and colour, its page, its Sections, and every Task in it including another member's are theirs to change; and trashing the folder, permanently deleting a Task and transferring ownership are each refused.
- AC-514 Given Can contribute, then they originate a Task and choose its initial assignee — themselves, another member, or nobody — and fully manage the Task currently assigned to them; given another member's Task, then every edit, completion and Step write is refused; given a Task they created and handed to somebody else, then they may neither edit it nor take it back; and trashing their own Task, editing the folder, creating a Section, creating a dependency and administering members are each refused.
- AC-515 Given Assigned work on the Task currently assigned to them, then they complete and uncomplete it, tick an existing Step, set and clear its reminder and comment on it; and every title, notes, date, importance and recurrence edit, reassignment, abandon, restore and trash, every Step create, rename, reorder, delete and promote, and completing a Task assigned to anybody else are refused.
- AC-516 Given a member who read a Task as theirs and a reassignment that commits before their next request, then the mutation is refused and writes nothing while the current assignee performs it; given a reassignment and a completion in flight together, then whichever the database ordered first acted and the other was refused; and given a Step, then its authorization is its parent Task's locked assignee.
- AC-517 Given Can comment, then they comment, reply, like, and edit and delete their own comment, and every shared Work mutation is refused; given Can view, then commenting, liking, deleting another's comment and every shared Work mutation are refused while every read succeeds; and given somebody outside the folder, then each answers 404 rather than 403.
- AC-518 Given a member downgraded to Can view, then their comment, uploaded file and created Task are still theirs to read and no longer theirs to edit or delete; and given a Can-edit member who uploaded a folder's file, then deleting it is refused and Full control deletes it.
- AC-519 Given any preset down to Can view, then putting a readable Task on their own My Day, setting their own label and colour for the folder, and keeping their own saved views and settings all succeed; given a Task in a folder they are not in, then the personal act answers 404; and given Can view, then shared Work is still refused.
- AC-520 Given a folder with one Full-control member, then demoting, removing and their leaving are each refused 409 and write nothing, and the owner may lower their own Access only once another member holds Full control; given two, then an ordinary leave and demotion both succeed; and given two custodians stepping down at once, then exactly one succeeds and the folder keeps a custodian.
- AC-521 Given a structural owner at any preset, then owner recovery restores Full control, recorded as a custody recovery with the owner as actor, and no other member may perform it; given any member, then raising their own Access is refused; given an owner leaving a shared folder, then 409 and nobody is promoted; given a removal aimed at the owner, then 403; given a transfer to a member without Full control, then 422 naming the field, and with it, then 200; and after the transfer and a step-down, the previous owner leaves.
- AC-522 Given any Access change, then one append-only transition records from, to, actor, kind and time, a refused change records nothing, and a self-demotion is distinguished from a grant; given a leave and a removal, then each records the preset to null with the right actor and the record outlives the membership; given a rejoin, then a new explicit grant rather than the old one restored; given an accepted invitation, then the inviter is the actor; given an ownership transfer that changes nobody's Access, then no transition; and given the history routes, then every current member reads them and nobody else does.
- AC-523 Given the mounted application, then every mutating route is named either by the Folder action that governs it or by an explicit personal, account or system classification, in both directions; given the resolver's table, then every action's answers are monotonic in the ladder and the current-assignee clause never admits a preset on work that is not theirs; and given the Folder Label actions, then Full control and Can edit manage the vocabulary, Can contribute applies existing Labels only to work they may self-manage, and Assigned work, Can comment and Can view modify no shared Label.
- AC-560 Given the Responsibility record, then an entry carrying content must carry a revision number and a hash and be a creation or an update, one without content carries none of the three, an entry with a revision number names a document, and an undeclared transition is refused; given one document, then two entries cannot hold the same revision number, and one membership cannot hold two active documents while it can hold an ended one beside a current one; and given an invite naming no folder, then initial Responsibility content on it is refused.
- AC-561 Given a member who has written nothing, then their Responsibility reads as absent, no row or entry exists, and a save of the empty document writes and records nothing, the empty document being the canonical payload of no document; given a deliberately cleared document, then the row, the history and an empty document are all still there; and given a document with headings, bullets, bold, italic, a web link and an internal link, then commit, fresh read and stored row reconstruct it exactly, while an unsafe link, an unknown key inside a block and an unknown document version are each 422 and write nothing.
- AC-562 Given Full control, then creating and editing any active member's Responsibility succeeds, their own included; given Can edit, then writing another's or their own is refused 403; given each preset below Full control, then the write is refused and both reads succeed; and every refusal writes no document and no entry.
- AC-563 Given a member added at any preset, then their self-edit grant is off; given Can view without the grant, then writing their own Responsibility is refused, and with it, it succeeds; with the grant, another member's is still refused and the grant does not follow the person into a second folder; across the fixed vocabulary at every preset, the grant changes exactly one answer; a holder may neither pass it on nor grant themselves; after revocation the next write is refused, both directions recorded with the administrator as actor; and the grant is refused for the structural owner.
- AC-564 Given a Can-view member whose Responsibility claims in the model's own vocabulary that they hold full control, then their preset and grant are unmoved and renaming the folder, adding a member, changing Access, granting self-edit, editing another's Task and creating one are each still refused; and editing a Responsibility from either side moves neither preset nor grant.
- AC-565 Given five distinct committed states, then five revisions numbered without gap or duplicate, the first a creation and the rest updates, behind exactly one current document; given two different committers, then each revision names its committer and instant while the subject is the member throughout; given a commit the resolver refuses, then no document or entry is left behind; and after five further commits, the first revision's id, content, hash, actor and time are unchanged.
- AC-566 Given the same document sent twice, then one revision and an answer saying nothing was committed; given a replay carrying the caller's pre-commit base, then 200 and no second revision rather than a conflict, a commit whose content already is the current content being a no-op whatever its base, checked before staleness; given the same document with reordered keys and an omitted optional, then it is the same document, sameness being equality of canonical payloads, and the stored hash is unmoved; and given a different document at the same base, then it commits.
- AC-567 Given two administrators reading one version and both saving, then the first commits and the second is refused 409 having overwritten nothing; given the refused writer reading the current version, then their save succeeds; given two commits fired together from one base, then exactly one commits; and given a base this document never had, then 409.
- AC-568 Given three committed states, then every prior revision read through the history route reconstructs the document as committed and names its actor; given an authorized member restoring the oldest content, then a new revision carrying it, committed by the restorer, the old one neither returning nor rewritten; and neither shape of an ordinary revision delete is mounted.
- AC-569 Given a member added with initial Responsibility content, then the document and its first revision exist naming the administrator who chose it; given a parked invite carrying content, then no document exists until acceptance, which records the inviter; given the instant share that writes no invite row, then the same; given no content or an explicitly empty document, then no document on any path; and given an invite naming no folder, then content on it is 422.
- AC-570 Given a member removed, then their active standing is closed in the same operation, the ending recorded, and the document and every revision retained with the folder; given a member leaving, then the same with the leaver as actor; given that former member, then the Responsibility, history and member-details reads all answer 404; given a rejoin, then no old content or grant returns, while a deliberate reuse by Full control is a new document at revision one beside the ended one; and given an account deleted while a member of another's folder, then the standing closes, the revisions survive, and their actor is still the writer.
- AC-571 Given three Access changes, an ownership transfer and an owner custody recovery, then every Responsibility document and entry is unchanged and none of the acts records a Responsibility entry; given an Access change against a self-edit grant holder, then the grant is unmoved; and assigning and unassigning a Task changes nothing about a Responsibility.
- AC-572 Given a duplicated folder, then its only member is the duplicator with no self-edit grant, no Responsibility document or record and no other member's Access, the source unchanged; given a workflow file naming members, presets and Responsibilities, then it imports as a folder with one member and no Responsibility; given two members each holding one, then each account's export carries only its own; given a folder the exporter has left, then it is absent from their export; and given a folder trashed then permanently destroyed, then Trash preserves the documents and the purge removes them with the record.
- AC-573 Given the member-details read, then it carries identity, the owner marker, joined time, current preset, the self-edit grant, the current document with revision id, updated time and updating actor, a count of the member's open assigned Tasks in the folder, and the two history routes; given the projection for one member and for six, then it issues the same three statements; given a grant, a write, a self-edit and a membership ending, then History's four sentences are built from actor, subject and transition alone; given a viewer who may not administer, then the projection says so and the route refuses them; given more entries than 10.3's cap, then the newest 1000 with `truncated` true; and given exactly 1000, then all with `truncated` false (spec 7.4).
- AC-674 Given one shared folder whose structural owner holds Can view, whose administrator holds Full control and owns nothing, and whose third member holds Can comment, when each reads GET /folders, then each reads their own preset as `my_access`; `is_owner` and `my_access` disagree in both directions on one row; the detail's `my_access` equals that reader's own members element; a non-member finds the folder absent from their list and the detail 404; and the resolver's answer for renaming and trashing at the listed preset is the route's answer (spec 7.4).
- AC-830 Given a Folder created after migration 0027, then it holds exactly four native facets — Main, Purpose, Consultation and Results — with stable ids written in the same transaction as the Folder and its owner membership; given a Folder that existed before 0027, trashed ones included, then it holds the same four at the same positions, the keys `initialKeys(4)` produces (spec 4.30, 7.4, 7.27).
- AC-831 Given a native facet, when it is created a second time, deleted, or converted to shared, then 422, 409 and 409 respectively and the row is unmoved; given Main hidden, then 422; and given a direct write of a second Main, then the database refuses it by name (spec 4.30, 7.27).
- AC-832 Given Purpose and Results renamed, then every member reads the new name and the id is unchanged; when `display_name` is written null, then each reads its default name with the same id; and given Main, Consultation or a Work facet, then any `display_name` is 422 (spec 4.30, 7.27).
- AC-833 Given a Work facet over an H1, then its name is that heading's text and follows a heading rename with no write to the facet; and a rename sent to the facet is 422 with the heading unchanged (spec 4.30, 7.27, 4.17).
- AC-834 Given an H1 already carrying a live Work facet, when a second is created over it, then 409; given two creates fired together, then one 201 and one 409; and given the first facet trashed, then a new one over the same heading is admitted (spec 4.30, 7.27).
- AC-835 Given an H1 deleted from Main, then its Work facet is gone from the listing and from Trash alike, destroyed rather than trashed because 7.16's block delete is permanent, and no other facet, block or Task moved (spec 4.30, 7.16, 7.27).
- AC-836 Given a Work facet deleted through its own route, then every block of its H1 section, every Task under it and every Section on the Folder page is unchanged, and Main reads the same document (spec 7.27, 4.17).
- AC-837 Given a blank facet with writing, then every block carries `facet_id` and a null `folder_id`, the Folder page holds none of them, and no `tasks` row names the facet; and given a block written with two homes at once, then the database refuses it (spec 4.17, 4.30, 7.27).
- AC-838 Given a private facet, then it is absent from the listing every other member reads, Full control and the structural owner included, and its document is refused to each with the same answer a stranger gets (spec 7.27, 10.2).
- AC-839 Given a private facet with writing at a known position, when its owner shares it, then id, blocks and position are unchanged, `owner_id` is null and `kind` is `shared_blank`; given the same request from a non-owner, then refused; and given a shared facet, when sharing is asked again, then 409 saying to create a private copy instead (spec 7.27).
- AC-840 Given a shared order written by one member, then every member reads it; given a list omitting a shared facet, naming one twice, carrying a private id or not beginning with Main, then 422 and nothing moved; and given one member's private-order write, then only their own arrangement changes (spec 7.27).
- AC-841 Given a signed-in non-member, then every one of 7.27's routes answers 404 and never 403; and given a member below each route's bar — Can view against create, rename, hide, reorder and delete, Can edit against the permanent delete — then 403 with the reason and the row unchanged (spec 7.27, 10.2, 5.4).
- AC-842 Given a native facet hidden, then it is still listed with `hidden: true`, its id unchanged and no content deleted; and when restored, then the same facet returns with the same id and document (spec 4.30, 7.27).
- AC-843 Given a facet deleted, then it leaves the listing and appears in `GET /trash`'s `facets` with its resolved name, `is_owner` and `my_access`; restored, it returns with its document; with its Folder trashed, restoring the facet alone is 409; below Full control the permanent delete is 403, and a Full-control non-owner is admitted; and a facet trashed over thirty days ago is destroyed with its blocks by the 11.7 pass (spec 7.13, 7.27, 11.7).
- AC-844 Given a facet document transaction carrying `create_task`, a semantic `section` block or a `folder_ref` block, then each is 422 naming its field and nothing is written; and given ordinary authored writing including a nested list item, then it commits with the list parent and every block inside the same facet document (spec 7.27, 7.16, 4.17).
- AC-845 Given a person with a private facet, when a facet document transaction names a `page_blocks` row that facet does not hold — a heading of a Folder they are not in, of one where they hold Can view, or a block of someone else's shelf page — by `put_block` alone or with `delete_block`, then 422 and the named row, its Work facet and the caller's facet are unchanged; and given `delete_block` alone naming a block the document does not hold, then 404, disclosing nothing about whether the id exists (spec 7.27, 7.16, 4.17, 10.2).
- AC-846 Given a member holding a private facet with writing and a shared facet beside it, when their membership ends by removal, leaving or account deletion, then the private facet and its blocks are destroyed rather than trashed and the shared facet is untouched; and another member's private facet in the same Folder survives, the sweep being scoped to one membership (spec 4.30, 7.27, 8.10).
- AC-860 Given a Folder holding one-off Tasks that are completed, pending, abandoned and trashed, and a recurring series with a completed and a pending occurrence, some of them in a Section, then the Folder's `progress` counts one-off completed over one-off pending-or-completed with the pending recurring occurrence reported apart as `recurring_active`, GET /folders/:id's `section_progress` gives the same three counts per Section with an empty Section at zero, and `counts` keeps its pending and completed tallies (spec 7.4).
- AC-875 Given a Folder's native Results facet, then any member reads its document and a member with `folder.page.edit` writes it as facet-homed `page_blocks`, a Can-view member's write is 403, a non-member's read, write and Dana Link resolution are each 404 disclosing nothing, and no refused write leaves a row; a member resolving the link receives the live name, `Results` by default (spec 7.27, 7.24, 10.2).
- AC-876 Given a Folder whose native Results holds writing, when it is duplicated or exported as a workflow, then the duplicate's Results is empty under its default name and the workflow file carries no Results (spec 7.16, 7.27).
- AC-852 Given Folders with Folder-level comments, Folders with only Task comments and Folders with none, when migration 0029 runs, then each Folder with Folder-level comments gains exactly one open "General discussion" with `is_general` true and the others gain none, every Folder-level comment points at its own Folder's discussion while Task comments keep a null `discussion_id`, and every comment's content, author, timestamps, likes and files are unchanged (spec 4.31).
- AC-853 Given the 0029 schema, then a comment that is both Task- and Discussion-scoped is refused by `comments_one_scope_check`, a comment naming another Folder's Discussion is refused by `comments_discussion_scope_fkey`, an open Discussion naming a current Outcome or a resolved one without `resolved_at` is refused by `discussions_resolution_check` (since 0040 a resolved one may have no Outcome, and a current Outcome of another Discussion is refused by `discussions_current_outcome_fkey`), and a second open, untrashed General discussion in one Folder is refused by `discussions_one_open_general_key` while a trashed one or an ordinary Discussion carrying the title is not (spec 4.31, 4.32).
- AC-854 Given a Discussion resolved, reopened and resolved again, then both Outcomes remain; deleting an Outcome's source comment keeps its statement; and purging the Folder removes its Discussions, Outcomes and comments even while its current Outcome names a live source comment (spec 4.32).
- AC-910 Given a Folder with a Discussion started by a Can-comment member, then a non-member is 404 on its read, edit, resolve and on starting a Discussion there, a Can-view member reads it and is 403 on start, edit and resolve, the creator edits, resolves and reopens it while holding Can comment and is 403 on each the moment their Access drops to Can view, a former member is 404, and a Can-edit member resolves it; no refused act leaves a Discussion or Outcome row or changes the stored one (spec 7.28, 10.2).
- AC-911 Given Discussions in a Folder, then the Can-comment creator moves their own to Trash and restores it while only they have commented, is 403 once another member has commented or once it has ever had an Outcome, a Can-edit member trashes a shared one keeping its comments and it appears in `GET /trash` and is 404 on the ordinary read, the Can-edit member's permanent delete is 403 and Full control's removes the Discussion and its comments; a Can-edit member is 403 on resolving or trashing the Folder's General discussion with the row and its Outcomes unchanged while Full control may, and reopening or restoring a General discussion beside another open one is 409 with the row unchanged; and purging a Discussion, or its Folder, succeeds while its current Outcome names a live source comment (spec 7.28, 7.13).
- AC-912 Given an open Discussion, when it is resolved with a statement, then one Outcome row holds that statement and actor and is current; a second resolve is 409 and an edit is 409; reopen clears the pointer and keeps the Outcome; `Use as outcome` naming another Discussion's comment is 422 and changes nothing, naming its own comment snapshots the trimmed body as a new current Outcome that a later edit of the comment does not change; the earlier Outcome's direct route still answers its statement with `current: false`, and the history lists both newest first (spec 7.28).
- AC-913 Given a Folder's Discussions, then the list pages at `limit` in most-recent-activity order with a cursor that visits every Discussion exactly once, `state=resolved` answers only resolved ones, `q` searches title and context with `%` and `_` literal, and a cursor the list did not issue — malformed, or naming an impossible instant — is 422 rather than 500 (spec 7.28).
- AC-935 Given a Discussion's input rounds, then a non-member is 404 on every route and writes nothing; Can view reads rounds and responses and is 403 opening a round or responding; Can comment responds; the Discussion's creator with Can comment opens and closes a round and a non-creator with Can comment may not open one; a creator or participant lowered to Can view loses those powers at once with the rows unchanged; and Can edit+ closes any round, recorded as `close_reason: closed` with `closed_by` (spec 7.29, 10.2).
- AC-936 Given a Discussion with an open input round, when a second is opened, then 409, and a direct insert is refused with SQLSTATE 23505 on `discussion_input_rounds_one_open_key`; a closed round does not close again (409); and once the first is closed a new round opens (spec 4.33, 7.29).

- AC-1015 Given a Folder nobody has reordered, when a member drags their own private tab to just after Purpose, then the tab row draws it there rather than after the built-ins, `after_facet_id: null` puts it at the front of the row, every other member's drawn row is unchanged, and a later `PUT /facets/order` draws the shared tabs exactly in the written order without moving the private one (spec 7.27).
