### 12.12 Reminders

The stored instant, every trigger that recomputes it, the two DST policy rules, and the scheduler pass. The reminder email is 12.21.

- AC-083 Given due 2026-07-28 15:00, offset 30, assignee timezone Asia/Karachi, then fire_at is the UTC instant of 2026-07-28 14:30 Karachi time.
- AC-084 Given a date-only task with time_of_day 09:00, then it fires at 09:00 in the assignee's zone on the due date.
- AC-085 Given the due date moves, then fire_at is recomputed; given it recomputes into the past, then the reminder is skipped, never sent.
- AC-086 Given the assignee's timezone changes via login sync, then scheduled fire_at values recompute.
- AC-087 Given the task is completed before the instant, then the scheduler records skipped and sends nothing.
- AC-088 Given the task is unassigned at fire time, then skipped and logged, no broadcast.
- AC-089 Given the scheduler was down across fire_at and restarts within 6 hours, then it sends; beyond 6 hours, it skips.
- AC-090 Given PUT reminder with offset_minutes on a task without due_time, then 422; given a valid reminder in a single-member folder, then the recipient is that member.
- AC-144 Given a reminder whose local fire time falls inside a spring-forward gap, then fire_at is the first valid instant after the gap, not the instant raw Luxon answers by advancing the gap's length.
- AC-145 Given a reminder whose local fire time falls inside a fall-back overlap, then fire_at is the earlier of the two instants.
- AC-146 Given DELETE /tasks/:id/reminder, then 204 with no body, the row is gone, the task is otherwise unchanged, and a repeat call answers 204 again.
- AC-147 Given PUT /tasks/:id/reminder against a task with no due_date, or with a body carrying the wrong mode, both modes, neither mode, or an offset outside 4.8's range, then 422 naming the field and no row is written or changed.
- AC-148 Given a second PUT /tasks/:id/reminder over an existing row whose new instant is in the future, then the single row carries the new value with fire_at recomputed, state returns to scheduled from sent or skipped, and the response is the affected TaskDetail.
- AC-149 Given POST /tasks carrying a reminder, then the row is created with the 8.6 instant under the same guards as the PUT, a refused body creates no task, and the two write paths agree on the instant.
- AC-150 Given a recurring occurrence carrying a reminder, when it generates a successor, then the successor carries a reminder of the same mode and value with fire_at recomputed for its own due date and state scheduled, and the closing row's reminder is untouched.
- AC-151 Given the due_time moves on a task carrying an offset reminder, then fire_at is recomputed from the new time.
- AC-152 Given assignee_id changes, then fire_at is recomputed in the new assignee's zone, an unassigned task falls back to the reminder creator's zone, and a creator who travels moves nothing.
- AC-153 Given a reminder the pass has already settled, then a later pass sends nothing more for it, while a reminder that becomes due between the two passes is sent by the second.
- AC-154 Given the assignee's timezone changes, then a reminder already sent is untouched (state, fire_at and fired_at), while a scheduled reminder is recomputed by the same sync.
- AC-164 Given a PATCH clearing due_time on a task with an offset reminder, then the reminder row is deleted in the same transaction and the response reports reminder null; a PATCH setting due_time on a date-only task with a time_of_day reminder deletes that reminder the same way; and a due_time moving between two non-null values deletes nothing and recomputes fire_at.
- AC-168 Given a write that computes a fire instant already past, whether 8.5's copy onto a successor or 7.9's PUT, then the row is written skipped with fired_at set and the next pass sends nothing; given an instant in the future, then it is written scheduled with fired_at null and sent when the instant arrives.
- AC-169 Given a reminder set in the task form while a task is created, then the task is stored carrying that reminder in the mode the form offered, and a fresh read reports it.
- AC-170 Given a reminder set, changed or cleared on 9.3's task surface for an existing task, then the stored reminder matches the surface in each case, clearing leaves none, and a reload shows what was stored.
- AC-212 Given a task with a due date and no due time, when a reminder is set for 17:45, then it stores time_of_day mode and the 11.7 pass fires it on the due date at 17:45 in the viewer's timezone.
