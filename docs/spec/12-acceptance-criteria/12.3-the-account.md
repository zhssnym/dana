### 12.3 The account: profile, settings, deletion

GET and PATCH /me, the settings bundle and the Settings page, account export, and the whole
of DELETE /me. The folders a deletion touches are 12.4; the invites and connections it
invalidates are 12.5.

- AC-009 Given DELETE /me without the literal confirm string, when called, then 422 and no change.
- AC-116 Given GET /me or PATCH /me answers 200, when the body is inspected, then it is exactly the 7.1 object: the same keys and shapes, nothing extra, nothing missing.
- AC-119 Given a fresh account, when GET /api/v1/settings, then `pinned_views` is Desk, Today, Scheduled, Assignments, Important, All, derived from the three 4.10 defaults, and every other field is its column default; and given the three v1 flags set directly in the table, then the pins move with them (spec 7.23, 4.19, 4.10).
- AC-120 Given PATCH /api/v1/settings with any subset of the 7.23 fields, the empty subset included, then 200, present fields take the sent values, absent fields keep theirs, the answer is the GET /settings object read fresh, and an empty body writes nothing, `updated_at` included; and given two concurrent disjoint single-field PATCHes, then both persist (spec 7.23, 7.0).
- AC-121 Given PATCH /api/v1/settings carrying a value outside a field's enumeration, of the wrong type, past a cap, or null, then 422 naming the field and nothing written; given one valid field beside a refused one, then the valid one does not land either; and given an admitted value, then it lands (spec 7.23, 7.0, 7.10, 10.3).
- AC-133 Given a user with pending sent invites, bare and folder alike, when DELETE /me completes, then each is invalidated and gone from its recipient's pending list, while the user's already-terminal invites and invites merely addressed to their email are untouched.
- AC-134 Given DELETE /me by the owner of shared folders, then each survives under the remaining member with the earliest join, ties to the lower user id, the new owner's membership row otherwise unchanged, and the deleted owner's membership and assignments in it are gone.
- AC-135 Given DELETE /me, then the default folder and every owned folder without other members are deleted with the full 8.8 cascade: their tasks of all statuses, steps, My Day entries, reminders, and pending invites carrying them are gone.
- AC-136 Given DELETE /me by a member of others' folders, then each membership is removed through R-CLEAN: their assigned tasks in the folder unassigned, their My Day entries for its tasks deleted, and a folder left with exactly one member has every task in it assigned to that member.
- AC-137 Given DELETE /me, then no connection row contains the user and both former rosters drop them, no My Day entry of theirs remains anywhere, and connections between other users are untouched.
- AC-138 Given DELETE /me, then the user row survives scrubbed, google_sub, email, display_name, and avatar_url null with deleted_at set, and surviving tasks keep created_by and completed_by pointing at it, readable by remaining members with the assignee cleared; an accepted invite keeps its accepted_by.
- AC-208 Given the v2 settings fields written and re-read, then they round trip; given a v1 account with show_done true, when the migration runs, then Done is pinned for it.
- AC-241 Given the Settings page, then it carries no view-pin switches, the sidebar having no pinnable views; its sections are Account, Preferences, People and Data, in that order (spec 9.7).
- AC-250 Given the creator's account deleted under 8.10, then `created_by` is null on every card and detail that task appears on, while `tasks.created_by` still points at the scrubbed row and a live creator's own tasks in the same folder still name them.
- AC-261 Given the Settings page, then its Preferences section offers the theme and the clock; and when a theme and a clock are chosen, then the application draws in that theme and writes timed rows on that clock, both still in force after a full reload (spec 4.19).
- AC-281 Given an account whose theme is Dark, when the application is opened again on a device that has drawn it before, then the document's theme attribute is `dark` from its first value rather than after the settings bundle answers, with no Content-Security-Policy refusal of the inline script that sets it; given System chosen, then the device keeps `system` rather than the resolved value; and given a sign-out, then the device keeps nothing.
- AC-339 Given Settings, then the Time section offers a searchable Timezone picker written through PATCH /me and read back; a People section carries the roster, /app/people redirecting to /app/settings#people; and the Account section carries "Sign out", its one home (spec 9.7, 9.8, 7.1).
- AC-365 Given an account provisioned after migration 0046, then `task_open` reads `dialog` through the settings bundle and the column's DEFAULT is `dialog`, both asserted; and Settings offers no "Open tasks in", because a task always opens as its one page (spec 4.19, 7.23, 9.3, 9.7).
- AC-378 Given an account provisioned after migration 0013, then the settings bundle reads `calendar_zoom` as `month`, 9.5's default zoom, and the column's DEFAULT is `month` too, both asserted (spec 4.10, 7.23, 9.5).
- AC-379 Given `calendar_zoom` written through PATCH on the settings bundle, then the response and a fresh read both carry it, a second session on the same account reads the same value, and another account's stored zoom is untouched (spec 4.10, 7.23).
- AC-390 Given a person who owns a folder with a task, step, page paragraph, description and a comment carrying a file, who has a shelf and a saved view, and who belongs to another's folder holding a task they wrote, one assigned to them and one neither, when they GET /api/v1/me/export, then the body is 7.22's document: `format` "dana-export", `version` 1, an ISO `exported_at`, their `account` and `settings`, owned `folders` with tasks, steps, page blocks and members as display names, `tasks_elsewhere` holding the two tasks that are their own work and not the third, `comments`, `shelves`, `views`, `files` with 7.15's URLs, an empty `truncated`, no `notifications` or `events` key, and no email address but the caller's own anywhere (spec 7.22, 10.9).
- AC-391 Given no session, when GET /api/v1/me/export, then 401 in the 7.0 envelope; given two people each with their own data, then neither export carries any row of the other's, measured over the whole response text; and given another person's comment and file inside a folder the viewer owns, then neither is in the viewer's export, `comments` being keyed by author and `files` by owner, while the viewer's own comment and file are (spec 7.22, 10.2).
- AC-393 Given GET /api/v1/me/export answers 200, then it carries `Content-Type: application/json` and `Content-Disposition: attachment; filename="dana-export-<YYYY-MM-DD>.json"` for the day `exported_at` names; and given a folder holding one task more than 10.3's 1000-row cap, then its `tasks` list is exactly 1000 long and `truncated` names `folders.tasks` (spec 7.22, 10.3).
- AC-404 Given the Settings page, then its Data section carries a "Download my data" row described "Everything Dana holds about you, as one JSON file", whose control is an anchor with `href` exactly `/api/v1/me/export` and the `download` attribute; and given no session, when `/privacy` is read, then it carries "You can download everything Dana holds about you at any time, as a single JSON file, from your Settings page." (spec 9.7, 9.2, 7.22, 10.9).
- AC-409 Structural: the fields 7.23's table names, the keys the settings bundle's request schema and response schema declare in `app/src/shared/bundle.ts`, and the keys `GET /api/v1/settings` answers on the mounted application are one set, equal in both directions (spec 7.23, 4.19).
- AC-620 Given an account holding a row in each of 8.10 step 6c's nine tables — a comment they reacted to, a Personal Label with a description, a notification, a sample-workspace mark, a shelf with a description, a page cover, a page description, its settings and a saved View — when DELETE /me completes, then none of the nine holds a row for it, the Personal Label's assignments are gone with it, and the users row is still there, scrubbed (spec 8.10, 4.1).
- AC-621 Given a second account holding the identical fixture and a Folder Label on a folder both belong to, when the first account is deleted, then every one of the second account's rows is unchanged, the comment both reacted to carries exactly the survivor's reaction, and the Folder Label and its assignment are untouched (spec 8.10, 4.15).
- AC-622 Given a departing account that left a page-document receipt on a folder that outlives it and another on a folder it owned alone, when DELETE /me completes, then the first survives naming the scrubbed row, the second is gone with its folder, and a bystander's receipt on the surviving folder is untouched (spec 8.10, 4.17).
- AC-851 Given an owned project with a Purpose tab holding heading, list and checklist structure, when the account export is produced, then `folders` carries the tab with its id, `project_id`, `kind` and `tab_position` and its 4.17 blocks including list ancestry and checklist state, and `facets` is empty (spec 7.22).
