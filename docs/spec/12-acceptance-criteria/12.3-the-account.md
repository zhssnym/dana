### 12.3 The account: profile, settings, deletion

GET and PATCH /me, the settings bundle and the Settings page, and the whole of DELETE
/me. The folders a deletion touches are 12.4; the invites and connections it invalidates
are 12.5.

- AC-009 Given DELETE /me without the literal confirm string, when called, then 422 and no change.
- AC-116 Given GET /me or PATCH /me answers 200, when the body is inspected, then it is exactly the 7.1 object: the same keys and shapes, nothing extra, nothing missing.
- AC-119 **Rewritten 2026-09-04 (issue #113)**, frozen 7.2 having been retired. Given a fresh account, when GET /api/v1/settings, then `pinned_views` is 9.1's six — Desk, Today, Scheduled, Assignments, Important, All — which is exactly what the three 4.10 defaults derive to, and every other field of the bundle is its own column default; and given the three v1 flags set directly in the table, then the pins move with them, so a build answering a constant instead of reading the row fails (spec 7.23, 4.19, 4.10, 9.1). (It read GET /me/settings and asserted the three booleans at their defaults. That endpoint is gone; the defaults are not, `pinned_views` being derived from those columns until somebody first chooses pins, so the fact is still observable — in one place now rather than two.)
- AC-120 **Rewritten 2026-09-04 (issue #113).** Given PATCH /api/v1/settings with any subset of the eight 7.23 fields, the empty subset included, then 200, present fields take the sent values, absent fields keep theirs, the answer is the GET /settings object read fresh, and a body carrying nothing writes nothing at all, `updated_at` included; and given two concurrent disjoint single-field PATCHes, then both persist, because a conforming implementation never writes an absent field and a read-merge-write one loses a side (spec 7.23, 7.0). (The rule is 7.23's word for word, and nothing asserted it there: AC-379 pins one field's round trip and AC-409 the document against the schemas, and neither sees a PATCH that rewrote a field it was not sent. The old clause about the settings key of GET /me is dropped: 7.1 still answers the three v1 booleans and this endpoint no longer touches them, so the two have nothing left to agree about.)
- AC-121 **Rewritten 2026-09-04 (issue #113).** Given PATCH /api/v1/settings carrying a value outside a field's enumeration, of the wrong type, past a cap, or null — null included since 4.10 admits no null state for any of these columns — then 422 in the envelope naming the field and nothing written; and given a body carrying one valid field beside a refused one, then the valid one does not land either, the whole PATCH being one statement; and given a value the enumeration does admit, then it lands, so the refusals are not blanket (spec 7.23, 7.0, 7.10, 10.3). (AC-380 pins this for `calendar_zoom` beside migration 0013's CHECK; this is the general case over all eight fields.)
- AC-122 **Retired 2026-09-04 (issue #113); the number is spent and is never reused.** It read: given two users, when one PATCHes their settings, then the other's stored settings and GET bodies are unchanged — of frozen 7.2's `/me/settings`, which is retired. It is not rewritten because the behaviour is already asserted on the surviving endpoint and by name: AC-379's third clause reads another account's stored zoom after a bundle write, and its own text cites "AC-122's reason" for doing so — an UPDATE that lost its WHERE passes every single-account clause. A second criterion saying the same thing about a different column of the same statement would be a duplicate rather than coverage.
- AC-123 **Retired 2026-09-04 (issue #113); the number is spent and is never reused.** It read: given tasks of every status with steps, My Day entries and reminders in the viewer's folders, when the viewer PATCHes any of the three toggles, then no row outside user_settings changes. The sentence under test was frozen 7.2's "hidden pages are a navigation preference only; no data changes", and the defect it forbade was the helpful handler that clears importance flags when Important is hidden. **It is unreachable rather than merely untested**: no route in this application writes those three columns any more, so there is no toggle write for a helpful handler to hang off. It is not rewritten against the bundle because the bundle's fields are not page-visibility toggles and no reading of 7.23 makes one of them a licence to touch another table; a criterion asserting that a theme change does not archive tasks would be asserting the absence of a defect nobody has a reason to write.

**Two readings that AC-119 to AC-123 rested on when they were frozen 7.2's**, both grounded
in the ratified any-subset reading of section 7's PATCH conventions, and **both carried into
7.23 by issue #113's rewrites** — the paragraph is kept because it is where the reasoning was
first recorded and because 7.23 states the conclusions without restating the argument. The empty subset is a subset: a body
carrying none of the three fields answers 200 and changes nothing, and an implementation
refusing it with an at-least-one-field rule is refusing a body the frozen sentence admits.
Null is a wrong-typed value here rather than a clear: 4.10's three columns are NOT NULL
booleans with defaults, so there is nothing to clear back to, unlike the label and color of
7.4's my-membership, which the frozen text itself marks nullable. The frozen sentence is
unchanged in both cases; the reading is the record.

- AC-133 Given a user with pending sent invites, bare and folder alike, when DELETE /me completes, then each is invalidated and gone from its recipient's pending list, while the user's already-terminal invites and invites merely addressed to their email are untouched.
- AC-134 Given DELETE /me by the owner of shared folders, then each survives under the remaining member with the earliest join, ties to the lower user id, the new owner's membership row otherwise unchanged, and the deleted owner's membership and assignments in it are gone.
- AC-135 Given DELETE /me, then the default folder and every owned folder without other members are deleted with the full 8.8 cascade: their tasks of all statuses, steps, My Day entries, reminders, and pending invites carrying them are gone.
- AC-136 Given DELETE /me by a member of others' folders, then each membership is removed through R-CLEAN: their assigned tasks in the folder unassigned, their My Day entries for its tasks deleted, and a folder left with exactly one member has every task in it assigned to that member.
- AC-137 Given DELETE /me, then no connection row contains the user and both former rosters drop them, no My Day entry of theirs remains anywhere, and connections between other users are untouched.
- AC-138 Given DELETE /me, then the user row survives scrubbed, google_sub, email, display_name, and avatar_url null with deleted_at set, and surviving tasks keep created_by and completed_by pointing at it, readable by remaining members with the assignee cleared; an accepted invite keeps its accepted_by.

**Two distinctions the account deletion criteria pin as pairs**, recorded because an
implementation can satisfy either half alone. A pending invite whose folder survives by
transfer is invalidated and keeps its row, which is AC-133's outcome, while one whose folder
dies at step 3 is removed by the FK cascade of 5.2's folder-deleted row, which is AC-135's;
invalidation is for rows that survive. And step 4 is not new machinery but 5.3's R-CLEAN,
which AC-016 and AC-018 already pin for removal and leave, so what AC-136 adds is the caller:
an implementation that revokes the memberships without the cleanup, or sweeps My Day entries
by user rather than by the folder's tasks, passes both of those and corrupts here.

- AC-404 Given the Settings page, then its Account section carries a "Download my data" row under the line "Everything Dana holds about you, as one JSON file.", whose control is an anchor whose `href` is exactly `/api/v1/me/export` and which carries the `download` attribute, so the session cookie rides a navigation and 7.22's `Content-Disposition` names the saved file, a button calling the client's fetch layer being the build this refuses; and given no session, when `/privacy` is read, then it carries the sentence "You can download everything Dana holds about you at any time, as a single JSON file, from your Settings page." The two clauses are one criterion because 9.2 admits that sentence only while Dana ships the control, so a page carrying it with nothing behind it is the failure, and no response is downloaded here: what is asserted is the address and the attribute, the bytes being AC-390's and AC-393's (spec 9.7 as amended, 9.2 as amended, 7.22, 10.9; issue #162).

**One reading AC-390 to AC-393 rest on, and it is why three of them sit here rather than in
12.15 or 12.20.** An export is one act on the whole of a person's own data, which is what
this group is about: it is the same kind of thing as DELETE /me, taking the account as its
subject rather than any one of the surfaces it reads. The files it names are not 12.15's
subject, the trashed rows it flags are not 12.20's, and splitting the four across four
groups would have left no file able to say what the document is. The limiter is the one
that honestly belongs elsewhere and is AC-392, in 12.23 beside AC-101.

**AC-404 sits here for the same reading and is the client half of it**, added 2026-09-04 for
issue #162. The four above assert what the endpoint answers; this asserts that a person can
find it, which 10.9 records as the half still owed on the day 7.22 landed: "the clause is met
by an endpoint a person can be given the URL of rather than by something they can find". Its
Privacy clause is 12.22's subject by topic and is deliberately not filed there, on this
group's own rule that a criterion has one home: the sentence and the control are one promise,
and split across two files neither half could fail for the other's absence.

- AC-409 Structural: the fields 7.23's table names, the keys the settings bundle's request schema declares, the keys its response schema declares, and the keys of the body `GET /api/v1/settings` answers on the mounted application are one set, asserted equal in both directions at every join, with 7.23 read as markdown text the way AC-315 reads `routes.ts` — so a field added to `app/src/shared/bundle.ts` and served without a row in 7.23 fails, and a row in 7.23 naming a field the bundle does not carry fails too (spec 7.23, 4.19; issue #152).

**One thing AC-409 is for, and one place it is, both worth saying because neither is
obvious from the line above.** Section 7 described this endpoint nowhere for the whole of
RFC 0005 and four fields were added to it in that time, so the failure this guards against
is not hypothetical: it is exactly what happened, and a subsection written once and left
would go stale the same way with nobody able to tell. It is written as the equality of four
lists rather than of two because the pairs that can drift are different — schema against
document is a contract going stale, and schema against wire is 11.15's first loss class,
a declared field the route never serves. **The test is `app/src/server/http/bundle-contract.test.ts`
and not a file under `app/tests/` named for the number**, which this section's README asks
for. That file is the one that already boots the real application and binds the shared
schemas to what the wire answers, which is the whole of this criterion, and AC-101 is the
standing precedent for a criterion living beside the code it measures. The exception is
recorded here rather than taken quietly.
