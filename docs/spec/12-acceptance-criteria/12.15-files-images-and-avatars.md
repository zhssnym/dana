### 12.15 Files, images and avatars

Upload, quota, what is served back and under which headers, and what a deletion takes
with it.

- AC-194 Given an upload within the 10.3 caps, then a files row exists and the uploader's quota is spent; given an account at quota, then 413; given a mime that does not match the declared kind, then 422 naming the field.
- AC-195 Given a stored file in a shared folder, when a non-member requests it, then the 10.2 not-found shape; when a member requests it, then the bytes.
- AC-196 Given an avatar upload, then users.avatar_url resolves to the stored object.
- AC-230 Given a stored file, when its address is requested with no session, then 401, never the bytes and never 404: the not-found shape is for the signed-in and unentitled, and an unauthenticated request is refused at the door.
- AC-231 Given an upload declaring an image kind with mime image/svg+xml, then 422; and given a raster upload whose bytes carry an HTML tail behind a valid image, then what is served back is re-encoded with no tail surviving, so no stored object can serve as a scriptable document on Dana's origin.
- AC-232 Given a served file of kind file, then the response carries X-Content-Type-Options: nosniff and Content-Disposition: attachment; given a served image, then nosniff and inline.
- AC-233 Given an account at its 1 GB storage quota, when it uploads another file, then 413 with section 9's copy and no files row is created.
- AC-234 Given a deleted account (8.10), then its avatar answers 404 to a signed-in account that held the id, and no files row owned by the deleted account remains.
- AC-235 Given a folder in Trash past 30 days holding stored files, when the 11.7 pass purges it, then the files rows are gone and their objects are absent from the store.
- AC-360 Given an account whose avatar has been uploaded, when `DELETE /api/v1/me/avatar` is called, then 204 with no body, `GET /me` answers `avatar_url` null, no files row of kind avatar owned by that account remains, and the stored object stops being served at the id the upload published; and when it is called a second time, then 204 again, the removal being idempotent (spec 7.15, 4.1, 4.16, 9.7).
- AC-361 Given an image upload, then the `files` row and the 201 answer carry the width and height of the object that was stored, read off the re-encode 7.15 already performs; and given an image longer than the 2048px edge, then what is recorded is the downscaled shape and not the shape that arrived, the columns describing what is served rather than what was sent (spec 4.16 as amended by migration 0009, 7.15; issue #27).
- AC-362 Given an upload of a kind that carries no picture, a voice note or a plain attachment, then its width and height are null on the answer and in the row; given a control image in the same run, then its shape is recorded, so the null is a kind rule and not a broken write; and given a row claiming a dimension for such a kind, or half a pair, or a zero or negative edge, then the database refuses it by the name of the CHECK that caught it (spec 4.16 as amended by migration 0009; issue #27).
- AC-370 Given POST /api/v1/files, when kind is cover and no folder_id is sent, then the picture stores, belongs to the caller, passes the same downscale and records the same dimensions; and when a kind that takes its visibility from a folder omits folder_id — `voice`, and it alone — then 422 naming the field. (`image` was among those refused until 2026-09-04, when issue #167 gave a shelf page's picture the folder-less life a cover has; the criterion follows the contract, and AC-413 asserts the line where it now runs.) (`file` was among them too until 2026-09-20, when issue #220 gave a composer asset that same folder-less life on #167's own reasoning one object over — a block's home is its page, 4.17 gives it exactly one, and not every page is a folder — which leaves `voice` as the only kind this clause still refuses, a voice note hanging on a comment thread and a thread living in a folder; `audio` and `video` arrived folder-less on that day and were never among them. The criterion follows the contract again: AC-496 asserts the folder-less arm for all three new kinds and AC-494 the one refusal that stands. **Nothing went red at the widening**, `ac-370-*.test.ts` having been deleted in the 2026-09-20 suite cut, so this sentence was silently false rather than failing — which is why it is corrected by reading the contract rather than by a run.) (spec 4.16 as amended 2026-09-20, 7.15 as amended 2026-09-20, 10.3, migrations 0012, 0015 and 0024).
- AC-371 Given a picture stored with no folder, then its owner is served the bytes and every other signed-in account meets the 10.2 not-found shape, a folder in common included; an avatar, also folder-less, still serves to any signed-in account; a folder-scoped file is still its members'; and the same predicate decides which file id a cover may name, so another person's picture cannot be worn (spec 4.16, 7.15, 7.19, 10.2).
- AC-398 Given a file stored in a shared folder, when a member who is neither its uploader nor the folder's owner reads it and then tries to delete it, then the read answers 200 and the delete answers 403 carrying the forbidden code, and the bytes survive the refusal; when someone outside the folder tries the same delete, then 404, the existence being theirs to not learn; and the uploader and the folder owner each still delete at 204, so the corrected refusal has not been widened over the two actors 7.15 permits; and given anybody's avatar, which every signed-in account reads at 200, then a stranger's delete of it is likewise 403 and removes nothing, the rule reaching past folder membership because the readability it turns on does (spec 7.15 as amended 2026-09-04, 10.2, 4.16; issue #74).

- AC-490 Given POST /api/v1/files with kind `file`, when a payload of an unknown extension, of no extension at all, of a double extension, or of an extension that contradicts its own declared type is uploaded, then each is stored as a `file` row keeping the name it arrived under and the declared MIME verbatim, none of the four reclassified from what its filename happens to say; and given one byte past 10.3's 25 MiB, then 422, the cap being unchanged by this issue (spec 4.16 as amended 2026-09-20, 7.15 as amended 2026-09-20, 10.2, 10.3; issue #220).
- AC-491 Given one physical file uploaded twice under the same name and the same declared type, once as previewable media and once through the File command, then two independent rows are stored and each keeps the kind it was **declared** with rather than one derived from its extension — a PNG, an MP3 and an MP4 each staying an `image`, an `audio` and a `video` on one arm and a `file` on the other; and when the two are served, then the media one carries `Content-Disposition: inline` and the File one `attachment`, with `nosniff` unconditional on both, so insertion mode is what the file does rather than a label on a row (spec 4.16 as amended 2026-09-20, 7.15 as amended 2026-09-20; issue #220).
- AC-492 Given kind `audio`, then `audio/mpeg`, `audio/mp4`, `audio/ogg`, `audio/wav` and `audio/webm` over bytes of the container each names are stored as `audio`; and given a type absent from that list, a type that is not audio in any reading, or an allowlisted label over the bytes of another container, then 422 for each; and given those same three refused payloads re-sent as kind `file`, then each is stored as a `file`, the generic path staying available as R1 requires. The check is the declared type against the list plus a container-signature read of the leading bytes, and it is container validation and never codec validation (spec 4.16 as amended 2026-09-20, 7.15 as amended 2026-09-20, 10.3; issue #220).
- AC-493 Given kind `video`, then `video/mp4`, `video/webm` and `video/ogg` over bytes of the container each names are stored as `video`; and given QuickTime, which is deliberately absent, a type absent from the list, an audio type declared as video, or an allowlisted label over the bytes of another container, then 422 for each, on the same two-part check AC-492 states (spec 4.16 as amended 2026-09-20, 7.15 as amended 2026-09-20, 10.3; issue #220).
- AC-494 Given kind `voice`, then #220 leaves every rule it had: `audio/ogg;codecs=opus`, which the browser's own recorder sends and which the new allowlist does not carry, still stores as a `voice`; a type that is not audio is still 422; an upload naming no folder is still 422, `voice` being the one kind that still requires one; and a note past 10.3's ten minutes is still 422. Narrowing it to the new allowlist would refuse recordings that work today, which nothing in this issue asked for (spec 4.16 as amended 2026-09-20, 7.14, 7.15 as amended 2026-09-20, 10.3, migration 0024; issue #220).
- AC-495 Given a stored `file` read by its uploader, then 200 carrying `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, whatever MIME the uploader declared — asserted on the worst case deliberately, a `text/html` payload under a `.png` name — so that nothing in the serving path can be decided from an extension and no browser may sniff a scriptable document out of the declared type and run it on this application's own origin (spec 4.16 as amended 2026-09-20, 7.15 as amended 2026-09-20, 10.2; issue #220).
- AC-496 Given a `file`, an `audio` or a `video` uploaded with no `folder_id` part at all, then it stores and the row is its uploader's alone: they read it at 200 and a second account meets the 10.2 not-found shape, and that second account is not a stranger but a person who shares a folder with them, so a scope leaking through membership rather than through ownership would still fail here. The serving predicate names `avatar` and then falls through to ownership, so the three became owner-private the moment migration 0024 let them stand outside a folder and no predicate changed to make it true; it is asserted rather than reasoned about because a predicate later rewritten to enumerate kinds would disclose every private composer asset in Dana for the cost of guessing a uuid (spec 4.16 as amended 2026-09-20, 4.18, 7.15 as amended 2026-09-20, 10.2, migration 0024; issue #220).
- AC-497 Given a `file`, an `audio` or a `video` scoped to a folder, then it follows that folder's boundary exactly and in both directions: a non-member meets the not-found shape, the same account reads the bytes at 200 once it is added as a member, and meets the not-found shape again once it is removed, access ending with membership rather than having been granted once (spec 4.3, 4.16 as amended 2026-09-20, 7.15, 10.2; issue #220).
