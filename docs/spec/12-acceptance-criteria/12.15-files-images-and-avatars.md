### 12.15 Files, images and avatars

Upload, quota, what is served back and under which headers, and what a deletion takes
with it.

- AC-194 Given an upload within the 10.3 caps, then a files row exists and the uploader's quota is spent; given an account at quota, then 413; given a mime that does not match the declared kind, then 422 naming the field.
- AC-195 Given a stored file in a shared folder, when a non-member requests it, then the 10.2 not-found shape; when a member requests it, then the bytes.
- AC-196 Given an avatar upload, then users.avatar_url resolves to the stored object.
- AC-230 Given a stored file, when its address is requested with no session, then 401, never the bytes and never 404: the not-found shape is for the signed-in and unentitled, and an unauthenticated request is refused at the door.
- AC-231 Given an upload declaring an image kind with mime image/svg+xml, then 422; and given a raster upload whose bytes carry an HTML tail behind a valid image, then what is served back is re-encoded with no tail surviving, so no stored object can serve as a scriptable document on Dana's origin.
- AC-232 Given a served file of kind file, then the response carries X-Content-Type-Options: nosniff and Content-Disposition: attachment; given a served image, then nosniff and inline.
- AC-233 Given an account at its 1 GB storage quota, when it uploads another file, then 413 with section 9's copy and no files row is created.
- AC-234 Given a deleted account (8.10), then its avatar answers 404 to a signed-in account that held the id, and no files row owned by the deleted account remains.
- AC-235 Given a folder in Trash past 30 days holding stored files, when the 11.7 pass purges it, then the files rows are gone and their objects are absent from the store.
- AC-360 Given an account whose avatar has been uploaded, when `DELETE /api/v1/me/avatar` is called, then 204 with no body, `GET /me` answers `avatar_url` null, no files row of kind avatar owned by that account remains, and the stored object stops being served at the id the upload published; and when it is called a second time, then 204 again, the removal being idempotent (spec 7.15, 4.1, 4.16, 9.7).
