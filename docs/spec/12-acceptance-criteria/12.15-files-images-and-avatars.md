### 12.15 Files, images and avatars

Upload, quota, what is served back and under which headers, and what a deletion takes
with it.

- AC-194 Given an upload within the 10.3 caps, then a files row exists and the uploader's quota is spent; given an account at quota, then 413; given a mime that does not match the declared kind, then 422 naming the field.
- AC-195 Given a stored file in a shared folder, when a non-member requests it, then the 10.2 not-found shape; when a member requests it, then the bytes.
- AC-196 Given an avatar upload, then users.avatar_url resolves to the stored object.
- AC-230 Given a stored file, when its address is requested with no session, then 401, never the bytes and never 404: the not-found shape is for the signed-in and unentitled, and an unauthenticated request is refused at the door.
- AC-231 Given an upload declaring an image kind with mime image/svg+xml, then 422; and given a raster upload whose bytes carry an HTML tail behind a valid image, then what is served back is re-encoded with no tail surviving, so no stored object can serve as a scriptable document on Dana's origin.
- AC-232 Given a served file of kind file, then the response carries X-Content-Type-Options: nosniff and Content-Disposition: attachment; given a served image, then nosniff and inline.
- AC-233 Given an account at its 1 GB storage quota, when it uploads another file, then 413 with section 9's copy and no files row is created.
- AC-234 Given a deleted account (8.10), then its avatar answers 404 to a signed-in account that held the id, and no files row owned by the deleted account remains.
- AC-235 Given a folder in Trash past 30 days holding stored files, when the 11.7 pass purges it, then the files rows are gone and their objects are absent from the store.
- AC-360 Given an account whose avatar has been uploaded, when `DELETE /api/v1/me/avatar` is called, then 204 with no body, `GET /me` answers `avatar_url` null, no files row of kind avatar owned by that account remains, and the stored object stops being served at the id the upload published; and when it is called a second time, then 204 again, the removal being idempotent (spec 7.15, 4.1, 4.16, 9.7).
- AC-361 Given an image upload, then the `files` row and the 201 answer carry the width and height of the object that was stored, read off the re-encode 7.15 already performs; and given an image longer than the 2048px edge, then what is recorded is the downscaled shape and not the shape that arrived, the columns describing what is served rather than what was sent (spec 4.16 as amended by migration 0009, 7.15; issue #27).
- AC-362 Given an upload of a kind that carries no picture, a voice note or a plain attachment, then its width and height are null on the answer and in the row; given a control image in the same run, then its shape is recorded, so the null is a kind rule and not a broken write; and given a row claiming a dimension for such a kind, or half a pair, or a zero or negative edge, then the database refuses it by the name of the CHECK that caught it (spec 4.16 as amended by migration 0009; issue #27).
- AC-370 Given POST /api/v1/files, when kind is cover and no folder_id is sent, then the picture stores, belongs to the caller, passes the same downscale and records the same dimensions; and when a kind that takes its visibility from a folder omits folder_id — `file` or `voice` — then 422 naming the field. (`image` was among those refused until 2026-09-04, when issue #167 gave a shelf page's picture the folder-less life a cover has; the criterion follows the contract, and AC-413 asserts the line where it now runs.) (spec 4.16, 7.15 as amended 2026-09-04, 10.3, migrations 0012 and 0015).
- AC-371 Given a picture stored with no folder, then its owner is served the bytes and every other signed-in account meets the 10.2 not-found shape, a folder in common included; an avatar, also folder-less, still serves to any signed-in account; a folder-scoped file is still its members'; and the same predicate decides which file id a cover may name, so another person's picture cannot be worn (spec 4.16, 7.15, 7.19, 10.2).
- AC-398 Given a file stored in a shared folder, when a member who is neither its uploader nor the folder's owner reads it and then tries to delete it, then the read answers 200 and the delete answers 403 carrying the forbidden code, and the bytes survive the refusal; when someone outside the folder tries the same delete, then 404, the existence being theirs to not learn; and the uploader and the folder owner each still delete at 204, so the corrected refusal has not been widened over the two actors 7.15 permits; and given anybody's avatar, which every signed-in account reads at 200, then a stranger's delete of it is likewise 403 and removes nothing, the rule reaching past folder membership because the readability it turns on does (spec 7.15 as amended 2026-09-04, 10.2, 4.16; issue #74).
