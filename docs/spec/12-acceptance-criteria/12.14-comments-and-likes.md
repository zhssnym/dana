### 12.14 Comments and likes

Threads, their permissions, likes, and the files hung on a comment. The file itself is
12.15.

- AC-204 Given a reply to a reply, then 422; comment threads hold one level.
- AC-205 Given a comment in a folder, when a non-member reads or writes its thread, then the 10.2 not-found shape; when the author or the folder owner deletes it, then success; when another member tries, then 403.
- AC-206 Given the same user liking a comment twice, then one like exists; unliking removes it.
- AC-207 Given a comment in a thread with participants, then each participant except the actor gains a notification.
- AC-290 Given a comment carrying a file, when the thread is read, then that comment's `files` carries the file's id, name, mime and bytes as 4.16 stores them and no bare-id form rides beside it; and the create answer carries the same (spec 7.14 as amended by item 57, B5).
- AC-344 Given a comment posted with several file ids, then one comment is created carrying all of them and the thread reads them back in the order they were sent, not the order they were uploaded; given the one-file `file_id` spelling, then its file is attached and not dropped; given one id naming a file of another folder, then 422 and no comment is created.
- AC-345 Given a comment naming ten files, then 201, all ten are attached, and the thread reads them back in the order they were sent rather than in any order the files or their ids carry; given eleven, then 422 naming `file_ids`; given the same id twice, or `file_ids` sent beside `file_id`, then 422; and in every refusal no comment exists afterwards.
- AC-364 Given a comment carrying an image, then both the create answer and the thread read carry that picture's width and height beside 4.16's other columns, so a reader who did not attach it draws the tile at the right proportion before the bytes arrive; and given a comment carrying a document, then both are null on both shapes (spec 7.14 as amended, 4.16 as amended by migration 0009; issue #27).
- AC-381 Given a comment carrying attachments, when PATCH /comments/:id sends `file_ids`, then the set becomes exactly those ids in the order sent and the thread reads them back, the words being untouched and 4.15's edited stamp set; given the field omitted, then the attachments are unchanged, absent not being empty; given a wordless comment, then its attachments are editable at all, which a required `body` would have made impossible; and the answer carries the fresh comment, files included, beside the `edited` flag the shipping client already parses (spec 7.14 as annotated 2026-09-04, 4.15, 4.16; issue #94).
- AC-382 Given a comment carrying words and attachments, when `file_ids: []` is sent, then every attachment is removed on the wire and in `comment_files` while the words stay; and given a wordless comment, then the same empty list is 422 naming `file_ids` and removes nothing, because a comment carrying neither words nor files is the row the create half refuses — deleting it being what that person means and DELETE being what does it (spec 7.14 as annotated, 4.15; issue #94).
- AC-383 Given an attachment edit naming a file the comment's folder does not hold, one from another folder of the author's own or one belonging to another account, then 422 naming `file_ids` with the same message for both so the endpoint is no oracle for which ids exist, and the attachments are unchanged; given eleven ids, or the same id twice, or the create half's `file_id` spelling, then 422 naming the field, while exactly ten is admitted; and given a member of the folder who is not the author, then 403 and nothing moves, attachment editing widening nobody's grant (spec 7.14 as annotated, 10.2, 10.3, 11.14; issue #94).
- AC-790 Given another member's comment in a shared folder, when the viewer holds Full control and owns nothing, then both conversation surfaces offer Delete and `DELETE /comments/:id` answers 204 with the row actually gone; and given the folder's owner whose Access has been lowered to Can comment, then neither surface offers Delete and the same request answers 403 with the words intact and `folders.owner_id` unchanged; and given each of R8A's six presets, then moderation is Full control's at every one of them whether or not the viewer owns the folder, while the viewer's own comment stays deletable under `comment.mutate.own` — the screen's gate being `folderGates(...).moderate` over `shared/folder-actions.ts`, the same table the route resolves against, so the two cannot disagree (spec 7.14 as amended 2026-09-20, 10.2; #228's Full-control list and its authorship rule; issue #268).
