### 12.14 Comments and likes

Threads, their permissions, likes, and the files hung on a comment. The file itself is 12.15.

- AC-204 Given a reply to a reply, then 422; comment threads hold one level.
- AC-205 Given a comment in a folder, when a non-member reads or writes its thread, then the 10.2 not-found shape; when the author or the folder owner deletes it, then success; when another member tries, then 403.
- AC-206 Given the same user liking a comment twice, then one like exists; unliking removes it.
- AC-207 Given a comment in a thread with participants, then each participant except the actor gains a notification.
- AC-290 Given a comment carrying a file, when the thread is read, then that comment's `files` carries the file's id, name, mime and bytes as 4.16 stores them with no bare-id form beside it, and the create answer carries the same (spec 7.14).
- AC-344 Given a comment posted with several file ids, then one comment carries all of them and the thread reads them back in the order sent; the one-file `file_id` spelling attaches its file; and one id naming a file of another folder is 422 with no comment created.
- AC-345 Given a comment naming ten files, then 201 with all ten attached in the order sent; eleven is 422 naming `file_ids`; the same id twice, or `file_ids` beside `file_id`, is 422; and no refusal leaves a comment.
- AC-364 Given a comment carrying an image, then the create answer and the thread read carry its width and height beside 4.16's other columns; for a document both are null on both shapes (spec 7.14, 4.16).
- AC-381 Given a comment carrying attachments, when PATCH /comments/:id sends `file_ids`, then the set becomes exactly those ids in that order, the words untouched and 4.15's edited stamp set; an omitted field leaves attachments unchanged; a wordless comment's attachments are editable; and the answer carries the fresh comment with files and the `edited` flag (spec 7.14, 4.15, 4.16).
- AC-382 Given a comment with words and attachments, when `file_ids: []` is sent, then every attachment is removed and the words stay; given a wordless comment, then the empty list is 422 naming `file_ids` and removes nothing, a comment with neither words nor files being one only DELETE produces (spec 7.14, 4.15).
- AC-383 Given an attachment edit naming a file outside the comment's folder, whether the author's own or another account's, then 422 naming `file_ids` with one message for both and attachments unchanged; eleven ids, a repeated id, or the `file_id` spelling is 422 while ten is admitted; and a folder member who is not the author gets 403 (spec 7.14, 10.2, 10.3, 11.14).
- AC-790 Given another member's comment in a shared folder, then a Full-control member who owns nothing is offered Delete on both conversation surfaces and `DELETE /comments/:id` answers 204; the folder owner lowered to Can comment is offered no Delete and gets 403; a member at Can view is offered no Edit, Delete, like or Reply on any comment, their own included, with the composer shown disabled carrying the sentence saying what commenting needs; at every access preset moderation belongs to Full control and changing one's own comment to Can comment, the screen and the route both resolving through `app/src/shared/folder-actions.ts`; and at Trash a Full-control non-owner may permanently delete a trashed task (204) but not a trashed folder (403, custody required), the demoted owner may do neither, and `GET /trash` carries `my_access` beside `is_owner` (spec 7.13, 7.14, 10.2).
- AC-920 Given a Discussion in a Folder, then `GET` and `POST /discussions/:id/comments` answer 404 to a signed-in person outside the Folder and to an id naming no Discussion, a Can view member reads the conversation and is refused a new comment with 403, and nothing is written (spec 7.14, 10.2).
- AC-921 Given two Discussions in one Folder, when a comment and a reply are posted to one, then both are stored with its `discussion_id`, its `last_activity_at` moves in the same transaction, its read answers exactly its own comments in order, a reply naming a parent of the other Discussion is 422 naming `parent_id`, and neither appears on the legacy Folder thread (spec 7.14, 4.15, 4.31).
- AC-922 Given a resolved Discussion, then a new comment, a reply, an edit, a like and a delete of its comment all answer 409 `discussion_frozen` and the stored comment, its likes and the Discussion's comment count are unchanged; a trashed Discussion refuses a delete the same way and still reads (spec 7.14, 4.31).
- AC-923 Given a Folder with no Discussion, when the deployed client posts to `/folders/:id/comments`, then one open "General discussion" created by the Folder owner is made and the comment is stored under it; a later post files any Folder-level comment no Discussion holds under it too; a legacy reply lands in its parent's Discussion; the legacy read answers the General discussion and never another Discussion's comments; renaming the General discussion keeps later legacy posts in it without forking a second, and a Discussion created with the title "General discussion" (`is_general` false) stays off the legacy read; and `?task=` on either verb answers 410 and stores nothing (spec 7.14, 4.15, 4.31).
- AC-924 Given a resolved General discussion, then a legacy top-level post opens a fresh open General discussion rather than being refused, a legacy reply to a comment of the resolved one answers 409, and the legacy read shows both Discussions' comments in time order (spec 7.14, 4.31).
- AC-925 Given the sample workspace is made, then every Folder-level comment it writes is stored under a Discussion, and removing the sample removes those Discussions with their Folders (spec 7.20, 4.31).
- AC-1170 Given a post in a Discussion and another member's reply to it, when the post's author deletes the post, then the post's row is gone and the reply's row is still stored in that Discussion with `parent_id` null, its author and its body unchanged (spec 4.15, 7.14).
- AC-1171 Given a Discussion shared by two members where one member's post has notified the other, when the other sends `PUT /discussions/:id/read`, then a `discussion_reads` row is stored for that member alone, their list row and `GET /discussions/:id` carry a non-null `read_at` while the poster's list row still carries null, and their notification for that post has `read_at` set; a stranger is 404 (spec 4.34, 7.28).
- AC-1511 Given a task in a Folder, when a Can comment member sends `POST /tasks/:id/discussion`, then it answers 201 with the new Discussion carrying `task` and one Discussion is stored with that `task_id`, the task's title and the caller as `created_by`; a second call answers 200 with the same id and still one row; a Can view member is shown the existing one but is 403 with nothing stored when there is none; a stranger and a trashed task are 404 with nothing stored; `GET /tasks/:id` carries its `discussion_id`; and a post in it notifies the task's creator (spec 7.28, 4.31, 4.14).
- AC-1512 Given an open Discussion and a task in its Folder, when `PATCH /discussions/:id` sends `task_id`, then the stored row carries it and both the Discussion's `task` and the task's `discussion_id` name the other; a task of another Folder or a stranger's is 422 and a second Discussion linking the same task is 409, each leaving the row unlinked (spec 7.28, 4.31, 10.2).
- AC-1513 Given a task with a Discussion holding a post, when the task moves to another Folder, then the Discussion's `folder_id` and its comments' `folder_id` are the new Folder's (spec 7.6, 4.31, 4.15).
