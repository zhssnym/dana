### 12.6 Tasks, steps and the task surface

Creating, moving, assigning and transitioning a task, its steps, and the surface that
opens it, and task dependencies: one directed relation, `dependent depends on blocking`,
with `blocks` the same row read from the other end. Deleting a task is 12.20; where it is
listed is 12.8; recurrence is 12.11.

- AC-025 Given creation with only a title, then the task lands in the caller's Desk, assigned to the caller, pending, undated.
- AC-026 Given creation in a single-member folder with assignee_id null in the body, then the stored assignee is that member.
- AC-027 Given creation with due_time and no due_date, then 422.
- AC-028 Given a PATCH clearing due_date on a task with due_time, a rule, and a reminder, then all three are cleared or deleted in the same transaction.
- AC-029 Given a move whose target folder the caller is not a member of, then the request fails and nothing changes.
- AC-030 Given a move where the assignee is not a member of the target, then the task arrives unassigned.
- AC-031 Given a move into a single-member folder, then the task arrives assigned to that member.
- AC-032 Given a PATCH setting assignee to null in a single-member folder, then 409.
- AC-033 Given a PATCH setting assignee to a non-member, then 422.
- AC-034 Given a PATCH containing a status field, then 409.
- AC-035 Given two concurrent PATCHes touching different fields, then both changes persist.
- AC-036 Given complete on a pending task, then completed_at and completed_by are set to the acting time and user.
- AC-037 Given complete on an already completed task, then 200, and completed_by is unchanged.
- AC-038 Given complete on an abandoned task, then 409.
- AC-039 Given abandon on a pending task, then it leaves My Day, appears faded in its home, and never appears in Done.
- AC-040 Given restore on an abandoned non-recurring task, then it is pending with every date and the reminder configuration untouched.
- AC-041 Given uncomplete on a completed non-recurring task, then it is pending and completed_at and completed_by are null.
- AC-043 Given a create carrying 51 steps, then 422.
- AC-092 Given the form holds a rule and reminder, when the date is cleared, then the warning copy shows and, on confirm, the three dependents are disabled and empty.
- AC-093 Given the capture points of 9.3's entry table, when a task is created from each, then it carries exactly that row's defaults: Desk and undated from the bare control; a Today membership and today's date from Today; tomorrow's date from Upcoming's list; the cell's date from a calendar cell; assigned to the viewer from Assignments; and the folder and the section the thread's last line ends from a page's thread.
- AC-094 Given the assignee control in a multi-member folder, then its choices are that folder's members, Invite by email, and Unassigned; given a single-member folder, then the control is hidden and the server still enforces INV-5.
- AC-097 Given an abandoned row, then it renders faded and struck with a Restore control, and restoring an overdue assigned task returns it to My Day immediately.
- AC-157 Given a mutation the server refuses with 409, then the page shows the state machine copy of 5.1 verbatim rather than the general error toast.
- AC-161 Given 9.3's task surface, then an empty title shows "Give it a title", an over-limit field shows "Too long: limit N characters", and the subtasks editor shows "Limit 50 subtasks" at fifty and appends no more rows.
- AC-166 Given a list page (Today, Upcoming, Assigned), then its list ends in an inline text box named "New task"; pressing N or C while not typing focuses it; a title committed there with Enter saves immediately with every other field at that page's entry-point defaults per 9.3, the box empties and keeps focus for the next; and no dialog opens (spec 9.1, 9.3).

- AC-178 Given a saved task opened, then its timeline carries who created it and when, and who completed it and when where it is complete, as events that offer no action, and the page has no History item and no "Created by" or "Completed by" line; given either of those users deleted, then that name renders as "Deleted user" (spec 9.3).
- AC-179 Given an open task opened for edit, then the panel's Status row set to Done completes it and set back un-completes it, each producing the same stored state as the equivalent control on a task row, and the panel's "More actions" menu offers neither "Complete task" nor "Mark as not done"; and given the un-complete would take a G-SERIES successor, then it first confirms with 9.5's copy and does nothing if declined.
- AC-199 Given a task assigned to a section block, when that section is deleted, then the task survives with section_block_id null.
- AC-219 Given the due picker on an existing dated task, then its one time-of-day control edits the due time (4.11's due_time), the time the Date row shows; given the reminder picker on a dated task, then it offers a time on that day, at or before the due time where there is one.
- AC-220 Given the assignee menu in a multi-member folder, then it lists that folder's members, Invite by email, and Unassigned last; choosing Unassigned clears the assignment.
- AC-248 Given a task placed under a section of its folder's page, then `section_block_id` names that block on the folder read and carries the same value on every other 7.10 body the task appears in and on its TaskDetail; given a task under no section, then it is null on all of them; and when the task is moved to another section and then out of every section, then all of them follow.

- AC-249 Given a task read by a member who did not create it, then its TaskCard `created_by` is the creator's { id, display_name, avatar_url } stub, equal to the object `assignee` carries for that same person, identical on the folder read, on a 7.10 view body and on the TaskDetail, per row rather than per folder, and never null while the account is live.
- AC-352 Given a task with steps in a folder of its own, when its row is clicked, then the side panel opens beside the list (the list still visible) and draws the task's own checklist rather than titles invented from a count, and names that folder rather than the Desk fallback (spec 9.3, 9.6).
- AC-353 Given the "New task" box holding typed words, when Escape is pressed, then focus leaves the box, and a row is made only by Enter, with one `POST /tasks` (spec 9.1, 9.3, 7.6).
- AC-354 Given `/app/tasks/:id` opened, then it is the task's one page inside the app's shell and sidebar on a desktop and on a phone alike — the title a field, the properties block with Status, the task's document, then one timeline of its posts and events — with no dialog, no peek and no Work or Discussion tabs (spec 9.3, 7.17).
- AC-356 Given a dated task's due picker, then the day grid stands open with no "Custom date…" control, "Next week" is offered above it, and a Time field under the day writes the task's `due_time` with what was typed, carrying an existing reminder in the same `PATCH /tasks/:id` in the mode the task now takes (spec 4.8, 4.11, 7.6, 8.4, 9.3).

- AC-423 Given the Task Schedule of 7.6, then `start_date` is carried end to end through create, read and PATCH in all four valid states — neither date, start only, due only, and both — read back from the response and from the row rather than inferred from a 200; a create or a PATCH leaving a start later than the due date is refused 422 naming the field the body sent, in both directions and with nothing written, rather than surfacing as a constraint violation; clearing either date leaves the other standing; a generated recurrence instance starts undated, 8.5 moving a recurring task forward from its due date alone; and a duplicated task and a duplicated folder each carry the Schedule with both ends moving together by one delta (spec 4.5, 7.6, 8.5).

- AC-440 Given two tasks a member can read, when one is given the other as a blocker, then the relation is created once, answered 201, and read from both ends as `depends_on` of the dependent and `blocks` of the blocker; a second identical create writes nothing and answers 200 with the edge already there; and one task carries as many blockers as it is given, uniqueness being of the pair.
- AC-441 Given tasks already related, when a dependency is asked for that would make a task wait on itself directly, through one other, or through any number of others, then it is refused 422 naming `blocking_task_id` and nothing is written.
- AC-442 Given a dependency, when the blocking task is completed, reopened, abandoned or restored, then the relation's state follows — pending is active, completed is satisfied, abandoned is unresolved and never satisfied — with no write to the relation and no new row; and a dependency write alters no task's status, dates, assignment or membership.
- AC-443 Given two folders, when a person who is a member of both relates a task in each, then it is allowed; and a viewer who can read only one end sees the edge with the far task withheld whole and its state `unknown`, and naming an unreadable task as a blocker is refused with the same 404 and the same body as naming a task that does not exist.
- AC-444 Given a task with dependencies, when it is trashed, then every relation it is part of is kept and reads as an unreadable far end, and a restore brings them back by identity; and when it is deleted permanently, then the relations that named it are gone.
- AC-445 Given a folder whose tasks depend on each other and on a task elsewhere, when the folder is duplicated, then relations with both ends inside the copied set are remade between the copies, the relation with one end outside it does not travel, and no copied task names an original; and a single task duplicate carries no relation, one end not having travelled.
- AC-446 Given a page that links to, mentions and pastes the URL of another task, then no dependency exists; and given a folder exported to a workflow file and imported again, then the file names no database id and carries only dependencies whose two ends are both in the file, by file-local key (AC-870).
- AC-447 Given a dependency, when either end asks for its removal, then it is removed and answered 204; a second removal is 404, which is this repository's ordinary delete grammar; and an edge that does not touch the task in the path cannot be removed through it.
- AC-865 Given a task with pending, abandoned and completed blockers, a blocker and a dependent in a folder the viewer cannot read, and a completed task that blocks another, then every list row and the task's detail carry `blocked_by_count` counting the pending and abandoned readable blockers only and `blocks_count` counting readable dependents only while the task is not completed; and once the viewer can read the far folder, the same stored edges are counted (spec 7.0, 7.25).
- AC-880 Given Tasks with non-empty notes, when migration 0031 runs, then each gets paragraph blocks whose texts joined with a line break equal its notes exactly (a single line over 4000 characters is cut with no character lost), notes itself is untouched, empty notes get no document, and running the backfill again writes nothing. (spec 4.17)
- AC-881 Given a Task whose notes were written by a client that knows nothing of documents, when its document is first read, then the notes become its document once, and a second read returns the same revision and blocks. (spec 4.17, 7.6)
- AC-882 Given a Task, when a non-member reads or writes its document, then both are 404, and a Can-view member reads it and is refused the write with 403; no stored block or note changes. (spec 7.6, 10.2)
- AC-883 Given a Task document, when it is written, then notes holds its projection, checklist items left out; when the deployed client writes notes over a plain-paragraph mirror, then the document is replaced by the new text; and over a document with any other content, then every block is kept (ticks included) and only the new text is appended; Task rows, Sections and a block nested under a divider are refused with 422, while a block nested under a toggle heading is stored with its parent and the heading's `toggleable`. (spec 4.17, 7.6)
- AC-884 Given a Task with a document, when it is duplicated or its owner exports their data, then the copy holds its own copy of every block in order, checklist items unticked, and the export carries the blocks under the task's `document`. (spec 7.6, 7.22)
- AC-885 Given a Task with a document, when it is trashed, then the document is kept and unreadable until restore; when the Task row is purged, then its blocks are gone. (spec 4.17, 7.13)
- AC-950 Given a folder whose tasks depend on one another, on a task in another folder the member can read, on a task in a folder they cannot, and on a trashed task, when a member reads `GET /folders/:id/dependencies`, then only the edge whose two ends are both live tasks of that folder is answered and no other folder's task id reaches the wire; and a non-member is answered 404 (spec 7.25, 10.2).
- AC-955 Given a Task whose document names a picture in its Folder, when the Task is moved to another Folder and the old Folder is purged, then the picture's file row still exists and the block still names it, a member of only the new Folder can open it, and a picture the old Folder's page also names is copied for the Task while the page keeps the original. (spec 7.6, 7.15; issue #221)
- AC-996 Given a Task document holding every kind a Task admits (paragraph with line breaks, heading1-3 with bold, bullet, numbered, quote, code, image with width, file, callout), when the Task composer opens it, then the projection it would save names every block with its kind, text, style runs, file and width, and opening without typing writes no block. (spec 7.6, 7.16; issue #221)
- AC-997 Given the Task composer, when a bullet is turned into text, then the save writes a paragraph, and when a block is indented under another, then it is written nested under the block above it (its `list_parent_block_id`), with every word kept, and reopens nested there. (spec 7.6; issue #221; migration 0038)
- AC-998 Given a Task edited in two tabs, when the second tab's save is refused as stale and its writing is merged back into the latest copy, then every block from both tabs is present, a block both changed appears in both versions, and the merged copy sits right after the block it rewrote. (spec 7.16; issue #221)
- AC-1504 Given a task, when it is opened from its page's thread, from Today and from search, then each lands on `/app/tasks/:id`, Back returns to where it was opened, and Settings offers no "Open tasks in" (spec 9.3, 9.7).
- AC-1505 Given a task's page, when a post is written and then "Mark done" pressed, then the post and the done event stand in its one timeline in that order; "Mark done ▾" holds Drop, a finished task offers "Reopen", and a dropped task never draws the done check (spec 9.3).
- AC-1506 Given any screen, then a task's state is named To do, Done or Dropped, and no client copy says "Not started", "Abandon" or "Abandoned"; the stored status `abandoned` is unchanged (spec 9.3, 2).
- AC-1516 Given steps on tasks, when migration 0060 runs, then each step is a checklist item of its task's body with the same id, text and tick, in (position, id) order, after the task's last block; a task's lazy notes are materialized first; and no other block, key or notes value changes. (spec 4.6, 4.17)
- AC-1517 Given a task whose checklist has ticked items, when it is duplicated or its next occurrence is generated, then the copy holds the same items in order, unticked, and the source keeps its ticks. (spec 7.16, 8.5)
- AC-1518 Given Assigned work on the task assigned to them, when they tick or untick a checklist item of its body, then it is stored; when they add, rename or remove one, then 403 and nothing is stored. (spec 5.4, 7.6)
- AC-1531 Given a task page, when `/Blocked by` is chosen in its body and a blocker picked, then the relation is created, the body's stored blocks are exactly what the person wrote (the slash text gone, and its line when that was all it held), the relation shows as a "Blocked by" line under the properties and as a "marked this blocked by" entry in History, and nothing about it is drawn in the body. (spec 9.3, 7.25)
- AC-1536 Given a task assigned to one member, when its owner adds another assignee, then both assignments are stored and shown, the second assignee sees it in Today and may complete it under Assigned work access, and removing the first member keeps the second assigned (spec 4.5, 7.6, 9.3).
