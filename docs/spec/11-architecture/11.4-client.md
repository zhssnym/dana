### 11.4 Client

- Vite 8, React, React Router 7 in library mode only: no loaders, no actions, no framework
  mode. Data fetching belongs to the query layer alone. - TanStack Query 5 implements the
  8.3 policy: refetch on window focus and after each own mutation; no other invalidation
  strategy exists. - Forms with react-hook-form 7 plus the shared zod schemas via
  @hookform/resolvers. The client departs from this and the departure is recorded as
  section 13 item 31 with what it costs; the sentence does not move, because a rule is not
  rewritten to match what was built. - Styling with Tailwind CSS 4 (CSS-first
  configuration through @tailwindcss/vite; there is no tailwind.config.js) and shadcn/ui
  components copied into `app/src/client/components/ui/`, composed with
  class-variance-authority, clsx and tailwind-merge, which are the three packages that
  distribution composes its class strings with, and animated with tw-animate-css. The
  behaviour under those components is @base-ui/react, pinned, which is the primitive
  library the shadcn distribution in use is built on; the `shadcn` package itself is a
  copy-in generator and is never a runtime dependency. Icons are lucide-react, imported
  per icon. The sans family is Inter, self-hosted through @fontsource-variable/inter, a
  third-party font link being an origin the service worker of 10.6 cannot precache. Design
  tokens live in exactly one file, `app/src/client/styles/tokens.css`, as Tailwind @theme
  variables; it is the only place raw color, type, spacing, and radius values may appear,
  and it has one owner (the Component and Design System role). What that rule governs is
  the values the design fixes, ruled at the P8 merge on 2026-08-12 and recorded because
  the sidebar's folder dot reads like an exception and is not one. A folder's colour is a
  person's runtime choice carried on 7.4's my_color, per member and free-form under 4.4's
  #RRGGBB check, so it is data on the wire rather than a design value; the sidebar writes
  no colour at all, taking the fill from the response, while the dot's size and shape stay
  in tokens.css where the rule puts them. Reading the rule to cover this value would
  require mapping a free-form hex onto the ten swatches that file carries, which would
  paint a folder a colour its owner did not pick, and the hazard the rule exists to
  prevent, a design that cannot be changed in one place, is untouched: changing tokens.css
  must never change what colour somebody's own folder is. - Calendar: the grid is Dana's
  own, a fixed six-week month of day cells with week and day zooms, built from the
  designer's prototype. Virtual instances from /views/planned/calendar render as
  ghost-classed rows and the Q3C cell order, banners then timed then ghosts, is the order
  the cell renders them in. A day cell shows what fits and reveals the rest through 9.5's
  "+N more" control. - PWA: vite-plugin-pwa with the prompt-for-update registration flow
  (virtual:pwa-register with onNeedRefresh), satisfying 10.6's non-forcing update rule.
  Fallback if the plugin fights the 10.6 contract: a hand-written service worker under a
  hundred lines implementing precache, network-only API, and navigation fallback.

FullCalendar 7 is removed, amended at the RFC 0002 change control on 2026-08-13 by the
owner's ruling. This bullet named FullCalendar 7's standard plugins through the
@fullcalendar/react entrypoints, with a custom eventOrder comparator for the Q3C order and
a per-cell overlay as the fallback if the comparator could not express it. The designer's
prototype builds the grid itself, so the choice is between two working implementations
rather than between a library and nothing, and three things decide it. The visible order
is the contract and the mechanism never was, which this bullet said in as many words; a
grid whose cells we render orders them by rendering them in order, and the comparator and
its fallback both disappear. 9.5 fixes a constant six-week height and a "+N more"
overflow, which is a layout the library has opinions about and ours has none. And the
dependency leaves with it, which matters more here than its size: 11.15 lists this
library's v7 plugin entrypoints as a hazard precisely because recall of them is wrong, and
a hazard that no longer has a subject is one fewer thing every future session must read
before its first line of code. What is given up is the library's own accessibility and
keyboard handling in the grid, which is now ours to hold and is why 9.1's roles table
fixes the grid cell.

The virtual:pwa-register parenthesis names the flow rather than the import, read that way
at the second P8 change control on 2026-08-11, on the Frontend Architect session's
escalation, and recorded here so that a client not importing that module is not read later
as a deviation. What the bullet obliges is 10.6's non-forcing update: a worker that
installs while another controls the page is announced and never applied without a click.
The parenthesis identifies which of the plugin's registration flows satisfies that,
prompt-for-update rather than autoUpdate, and a module specifier is how the plugin's own
documentation names that flow rather than a requirement to import it. The plugin still
builds the worker and the manifest; the client registers the generated worker directly and
implements the same flow against it. Nothing here forbids the import to a later session,
and the swap is one file. This is a reading of 11.4 rather than a change to it, the shape
11.9 took for UNTIL's spelling at P6.
