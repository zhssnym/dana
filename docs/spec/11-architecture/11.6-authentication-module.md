### 11.6 Authentication module

Hand-rolled Google OIDC on openid-client, implementing sections 7.1 and 10.1 exactly, with
no auth framework. The available libraries are gone or unfit (11.14): Auth.js is in
maintenance mode, Lucia and Arctic are deprecated, and Better Auth would own the users
table shape and the provisioning transaction boundary that section 4 and AC-005/AC-006 fix.
The scope that makes hand-rolling defensible: Google-only authorization code flow, no
passwords, no resets, no MFA.

Requirements, each pinned by an acceptance criterion (AC-105 to AC-115):

- Authorization requests carry state, nonce, and a PKCE S256 challenge; the callback
  validates all three, single-use, and rejects on any mismatch. The pending-authorization
  record also carries the tz reported on GET /auth/google (7.1); tz never rides
  redirect_uri and is never composed into a redirect target.
- Sessions are rows in a sessions table (outside the section 4 core model; observable
  contract in 10.1), referenced by an opaque identifier in an httpOnly, Secure,
  SameSite=Lax cookie, with 30-day rolling expiry. Secure is set unconditionally, never
  derived from the request's own transport: TLS terminates ahead of the process (11.11),
  so the process always speaks plain HTTP and a derived flag would never be set. A fresh
  identifier is issued at every sign-in; no pre-authentication session identifier is ever
  promoted.
- CSRF uses the double-submit pattern so the section 7 surface is untouched: a token bound
  to the session is set in a second, non-httpOnly cookie at sign-in, and every mutation
  must echo it in the X-CSRF-Token header; missing or mismatched answers 403 with no side
  effects.
- The session cookie is `dana_session` and the CSRF cookie is `dana_csrf`. The names are
  fixed here because the client must read the second one and cannot import the server's
  constant; each side transcribes this one specified name, and the client never guesses
  or falls back to another readable cookie. The short-lived pending-authorization cookie
  is deliberately unnamed: nothing outside the auth module reads it.
- Auth endpoints never redirect off the application origin, whatever the request carries
  in parameters or Host headers.
- No Google access, refresh, or ID token is persisted once the callback transaction
  completes.
- The development-only login endpoint (DANA_DEV_LOGIN) must be absent from production
  builds, regardless of environment variables. Absent means excluded from the compiled
  output at build time, never a runtime guard (mechanism hazard in 11.15), and the flag is
  read at createApp() call time, never at module load. The endpoint provisions through the
  same transaction as the callback and takes an optional timezone field with the 7.1 tz
  parameter's semantics, absent meaning UTC.
- Expired session rows are pruned opportunistically by the scheduler pass (11.7). Pruning
  is hygiene, not revocation; revocation never waits for it.
