### 11.12 Observability

- Sentry (free tier) receives server and client errors; AC-104 proves the wiring. - Better
  Stack (free tier): an uptime monitor on /api/health, and a heartbeat the scheduler pass
  pings after each successful cycle; heartbeat silence beyond 10 minutes alerts.
  /api/health also reports seconds since the last completed pass. - Dana's privacy-policy
  logger continues to write its structured application events to stdout, which leaves
  Render's deploy diagnostics and seven-day Hobby log explorer intact. When both
  `AXIOM_DATASET` and an ingest-only `AXIOM_TOKEN` are present, the same Pino records are
  also sent directly over HTTPS to that Axiom dataset, whose retention is at least 30
  days; with neither setting the external destination is disabled, and an incomplete pair
  records only the missing variable name and remains stdout-only. Only the closed,
  whitelisted logging surface of 10.5 reaches Axiom. Render platform and build logs are
  not copied and retain Render's own plan period. This direct destination is v1's accepted
  substitute for a Render workspace log stream because the free Axiom plan does not
  include its Secure Syslog endpoint and the free Better Stack Logs plan does not meet
  10.5's retention period.

Added 2026-09-04 (issue #99). **A Sentry event whose volume is proportional to page
loads carries a fingerprint, and 10.8's CSP violation report is the first of them.**
Every kept report sends one warning-level message fingerprinted on the pair
`('csp-violation', effective directive, blocked URI)`, so a policy that refuses the
theme script on every cold load for everybody is one issue with a count on it rather
than one issue per load. Without that this destination is worse than none: the
hundred-and-first identical issue is the one nobody reads, the quota it spends is the
free tier's, and the next real error arrives underneath it. The rule generalises past
this endpoint — **any event a browser can produce once per page view is fingerprinted on
what makes two of them the same event, and the fingerprint is the caller's to choose,
because only the caller knows.**

**And the fingerprint is not enough on its own, which is the half worth writing down.**
It groups issues; the quota counts events, so a hundred grouped events still spend a
hundred. Nor is per-fingerprint dedupe enough, because a fingerprint built from a
caller's string has a key space the caller chooses. So an unauthenticated path takes
three rules together, and the CSP endpoint is the first to carry them. **Every value that
reaches this destination has passed 10.5's whitelist** — the fingerprint, the message text
and the tags are built from the same sanitised fields as the log line and never from the
report, so the closed logging surface bounds what Sentry sees exactly as it bounds what
stdout sees. A given fingerprint sends at most once per ten-minute window, held in process
against 11.1's single instance over a map bounded at a few hundred entries. And an
absolute budget of twenty events per window sits over both, with **exactly one message
when it is spent**, because a channel that simply went quiet under load is
indistinguishable from a deployment with nothing wrong. All three are the caller's and
none is the tracker's — a tracker that silently dropped what it was handed would be lying
to every other caller — and **the 10.5 log line is written every time regardless**, so the
log stays the record and Sentry is the alert. The message carries the same two values the log line
does and nothing else (10.5), so it is subject to the same whitelist; `beforeSend`
already strips request, user and context off every event this process sends.
