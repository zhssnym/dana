### 11.7 Reminder scheduler

The 8.6 delivery loop runs in-process: a 60-second interval in the server, guarded against
overlapping passes, executing the poll-classify-send-mark cycle in a transaction that
claims due rows with SELECT ... FOR UPDATE SKIP LOCKED. Consequences, each intended:

- A missed tick self-heals: the poll is over fire_at <= now(), so the next pass picks up
  anything a missed one would have sent, inside the 6-hour stale window. - The deploy
  overlap window can run two instances for about ninety seconds; SKIP LOCKED makes
  concurrent ticks contend safely instead of double-sending. A crash between send and mark
  can duplicate at most one batch; 8.6 accepts duplicates. - Tick liveness is monitored
  separately from process liveness (11.12), because a dead interval inside a live server
  is invisible to an uptime check. - The same pass prunes expired session rows, purges
  Trash rows whose deleted_at is older than 30 days and events older than 90 (RFC 0005),
  so 8.6's statement that the reminder loop is the only background execution stays true:
  one scheduled process, five duties. **The fifth was added 2026-09-04 (issue #116): a
  folder-less cover file that no column in the schema names and that is more than 30 days
  old is deleted with its object.** It is here rather than in the act that stops wearing one
  because there is no such act to put it in — a cover with no folder is listed by no surface
  and reachable by no route, so once nothing references it, nothing in section 7 could ever
  remove it, and it spends its owner's 1 GB (10.3) forever. Deleting it the instant a page
  stops naming it was refused for a reason worth keeping: the caller is still holding that
  id, and setting the same picture back a moment later is what a cover picker does. The rule
  in full, the reference count and the 30 days are 7.19's; the statement is
  `reclaimUnwornCovers` in `app/src/server/domain/files.ts`. **The count reached five once
  before and wrongly, and the correction of 2026-09-01 is kept because the wrong fifth is
  not this one**: it named notification fan-out, which had moved to the 10.2 chokepoint so
  that an act and its notification commit in one transaction, and
  `app/src/server/domain/events.ts:9` and `app/src/server/scheduler/pass.ts` both record the
  move. From that date the pass returned four results; the reclaim above is a real fifth and
  makes it five. The Trash purge collects the files
  rows its folder deletes will cascade away and removes their objects from the store after
  the delete commits, because those rows are the only index to the bytes and a purge that
  drops them without the objects grows the disk without bound (change control item 18,
  2026-08-25). Each added duty claims its rows the way the reminder duty always has, SKIP
  LOCKED in its own transaction, and each is idempotent, so the missed-tick and overlap
  properties above hold for every one of them unchanged. This is also three more reasons the
  single-instance rule of 11.2 must be flagged before it ever changes, and none of these
  duties may migrate into request handlers.

The pass is a plain callable function and must stay one: if hosting ever moves somewhere
without an always-on process, the replacement is an external per-minute trigger (Google
Cloud Scheduler or equivalent) hitting an authenticated endpoint that runs one pass.

That callable is the acceptance suite's only way in, ratified here at the P7 mid-package
change control on 2026-08-10 rather than left assumed, the way 11.10 ratified
options.notifications when the same need appeared for sends. Everything else the suite
reaches, it reaches over HTTP through the 11.10 seam, and frozen section 7 offers no
endpoint that runs a pass, so without this the delivery criteria could not be written at
all. `app/src/server/scheduler/index.ts` exports the pass as `createReminderPass(deps)` or
as `runReminderPass(deps)`, either name, with deps of { dbClient, notifications } reusing
11.10's own option names for the same two things. The tolerance over the name is
deliberate and costs nothing: the harness accepts both, so the choice is the implementing
session's and no drift is possible in the suite. What is fixed is only what the suite must
know in advance, the module path and the two dependencies, both already determined by
11.10 and by the scheduler directory this section's implementer owns; the pass's
internals, its transaction shape and its return value are untouched by this and stay that
session's. Two things it is not. It is not an HTTP endpoint, adding one being a change to
frozen section 7 that the paragraph above contemplates only if hosting moves. And it is
not a second export path for production, which composes the same callable at boot as it
always did.
