### 11.11 Hosting and delivery

- Render: one Starter web service plus one Render Postgres instance (cheapest paid tier),
  same region, deployed from GitHub on push to main. Production is exactly one instance
  (11.1). Combined cost as of 2026-07: about 13 to 14 USD per month. - Render Postgres is
  paid from day one because the free tier expires after 30 days and has no recovery
  capability. The paid tier's point-in-time recovery (3-day window on the Hobby workspace)
  is the primary backup. The runbook's quarterly drill restores into a scratch instance,
  runs the constraint catalog test against it, and destroys it; a monthly pg_dump kept
  off-platform guards against account-level failure. - CI is GitHub Actions: npm ci, lint,
  typecheck, test on a real Postgres 18, build, Playwright. Six steps in
  that order, seven until the PGlite leg was struck out by the 2026-09-20 amendment below.
  The set and the order are normative and move only by amendment here; where
  the job runs, and where its Postgres comes from, are job configuration rather than steps
  and move without touching either, exactly as the service container always was
  configuration rather than a step. Two forms are admitted, the second ruled 2026-08-11
  after hosted runs stopped starting on an account billing failure and the owner chose not
  to buy hosted minutes: a GitHub-hosted runner with a postgres:18 service container, and
  a self-hosted runner with the host machine's own Postgres 18 cluster, whose test
  database 11.10 fixes. A self-hosted runner is still GitHub Actions, the workflow, the
  triggering events, the checks and the run history being unchanged and only the executing
  machine moving, so the opening clause of this bullet is unamended. Three consequences
  are load-bearing. A self-hosted runner executes whatever a workflow on any pushed branch
  tells it to, on a machine holding the owner's own data, which is acceptable exactly
  while this repository is private and every writer is the owner or a session he runs;
  making it public, or admitting an outside collaborator, revokes that and is the revisit
  trigger. CI then exists only while that machine is powered and the runner service is up,
  and a job queued against an absent runner waits rather than failing, so a pushed branch
  has no verdict until the machine is available: a cost the release ritual pays, not a
  defect to debug. And on the self-hosted form the Playwright step may drop `--with-deps`,
  which installs Linux system packages and has nothing to do on Windows; the step itself
  does not move. - Merges to main require green CI. This project enforces that through the
  Integration Steward rather than through a protected branch: checked 2026-08-11, the
  repository is private on a plan that offers neither branch protection nor rulesets, so
  the rule has always been the protocol's rather than the platform's, and a red or absent
  CI run blocks a merge because the definition of done says so. - Environments: production
  and local only, no standing staging. The release ritual is CI green, deploy, then the
  production smoke subset (health, auth round trip, one CRUD cycle). A throwaway Render
  service restored from point-in-time recovery substitutes for staging when a release
  warrants a rehearsal. - Secrets: Render environment variables in production, GitHub
  Actions secrets for anything a hosted runner must reach, a gitignored .env locally, and
  an `.env.example` naming every variable. One rule is stated positively because its
  violation is silent: a credential for a resource GitHub cannot reach is never stored at
  GitHub. The self-hosted runner's TEST_DATABASE_URL is the first of these and lives in
  the runner installation's own `.env` file, outside the repository and outside every
  working tree, which the runner reads into each job's environment. A repository secret
  was rejected for it, and the reasoning is worth keeping because it inverts the usual
  answer: every workflow on every branch can read a repository secret, workflow files are
  code the sessions of this build edit and push, and the string describes a database on
  the owner's own machine that GitHub has no route to, so storing it there widens exposure
  and buys nothing. A machine-wide environment variable was rejected for the same
  plaintext at a wider blast radius, every process on the machine rather than the runner's
  jobs, and a service restart to rotate. The role that string authenticates is never the
  superuser: a dedicated `dana_ci` login role with CREATEDB owns `dana_test`, which is all
  the migrations need, pg_trgm having been a trusted extension since Postgres 13 and so
  installable by a database owner. The workflow never echoes the variable, and anything
  that must print it masks it first.

**Added 2026-09-04 (issue #180, the owner's ruling): the seven steps stay normative and stop
being the property of one machine.** They remain exactly as the bullet above fixes them — npm
ci, lint, typecheck, test on PGlite, test on a real Postgres 18, build, Playwright, in that
order — and **GitHub Actions runs all seven on every push to `main`**, which is the run that
measures what was merged and the run this section's order is normative for. What changes is
where they run **before** a merge: **a pull request carries the same seven steps as a gate
record produced on the author's own machine**, printed by `npm run gate` in `app/`, naming the
head sha, whether the working tree was dirty, the machine, the clock, and the tally each step
reported. **A pull request exists only when that record is green on its head commit**, which
is the definition of done this section's "merges to main require green CI" bullet has always
carried, now met before review rather than after it. GitHub Actions on a pull request is
reduced to a light job — the branch name, npm ci, lint, typecheck, build — and that job is
**not** one of the seven and does not stand in for any of them; it exists to catch a pull
request opened without a gate run and to build the merge result the author never built. Two
facts about the runner decided it, both recorded in `CLAUDE.md` with their measurements: a
job of the seven steps holds about half this machine's memory, so it cannot share the machine
with the agents doing the work, and one self-hosted runner serves both people, so every
branch queues behind every other. **A record missing a step is `incomplete` rather than green
and does not open a pull request**: the gate prints three verdicts, `green` requires all
seven, and a run whose real-Postgres leg was skipped because the machine had no
`TEST_DATABASE_URL` has not answered for that leg — it exits non-zero and says so in those
words. That is a one-time setup rather than an exemption, 11.10's `CREATE DATABASE` statement
being the same on every machine, and it is what keeps the next sentence true rather than
aspirational. **Which machine prints the record is job configuration in this section's own
terms and moves without amending it; that all seven steps are answered for before a merge is
not.**

*(That block enumerates seven steps because seven is what it amended. The set is six since
the 2026-09-20 amendment immediately below; everything else it rules — the gate on the
author's machine, the light pull-request job, `incomplete` rather than green for a record
missing a step — is unchanged and still governs.)*

**Added 2026-09-20 (the owner's ruling): the PGlite leg is struck out, and the set is six.**
The steps are npm ci, lint, typecheck, **test on a real Postgres 18**, build, Playwright, in
that order. Until this amendment the suite ran twice, once on each engine, and the second run
was duplication for every file whose behaviour does not depend on which engine answers it —
which is nearly all of them. **The leg removed is the one production does not run**, and on
the machine this section describes it was also the slower of the two: 291 seconds against 94
at the 2026-09-03 measurement, the PGlite leg being the expensive half of a pair that existed
to catch disagreement between them.

**What that gives up is stated rather than waved at.** Cross-engine defects are now caught by
the one leg that runs rather than by two legs disagreeing, and `CLAUDE.md` records a real
instance of the class: a criterion that read the process clock at UTC while `duplicateTask`
re-anchored on SQL `current_date` in the database session's zone was false for one to two
hours every evening, and forcing the zone is what separated it from a midnight race. That
class is now a Postgres-leg defect like any other. 11.10's two locale checks, which prove the
test database orders text as the application expects, run inside the surviving leg and are
unaffected.

**PGlite remains the fallback and never the gate.** A machine with no `TEST_DATABASE_URL`
runs the suite on PGlite rather than running nothing, because a gate that silently skips its
only test step is worse than a slow one. That run is **`incomplete` rather than green** and
does not open a pull request, on exactly the rule the block above fixes: a record that did not
answer for the engine that serves users has not answered. The CI guard on the Postgres step is
load-bearing in one more way for the same reason — there is no second leg left to notice a
silent fallback.

**Added 2026-09-04 (issue #153): exactly one proxy hop stands in front of the process, and
the application now says so.** Render's edge terminates TLS and opens its own socket to the
service, so without Express's `trust proxy` the address every request appears to come from
is the edge's, and every rate limit keyed on an address is one bucket for the whole
deployment rather than one per visitor. `createApp` sets `trust proxy` to `1` — one hop, and
never `true`, which would trust a header the client writes. **The count is a claim about
this hosting and it moves when the hosting does**: a CDN or a second proxy in front of
Render makes it `2`, and putting one there without moving the number silently restores the
defect in a subtler form, with the edge's address trusted and the CDN's read as the client.
Anyone changing what stands in front of this service owes that number an edit. 10.4 carries
what the limits mean under it and AC-410 measures the three cases.

**What was checked about the header, and what could not be**, recorded because the issue
that raised this assumed the answer and asked for it to be read rather than assumed. Every
one of the 205 pages in Render's own documentation index was fetched and searched on
2026-09-04 for `X-Forwarded-For`, for "forwarded", and for the phrases a platform uses to
tell you how to find a caller's address. **No page states that Render's edge sets the
header.** What was found is one piece of indirect evidence and it is a good one: Render sets
`FORWARDED_ALLOW_IPS=*` by default on every Python service, a variable whose only purpose is
to make gunicorn honour `X-Forwarded-*` from the proxy ahead of it, which no platform
defaults to `*` for a proxy that sends nothing. So the header is near-certain and it is
**not documented**, and this paragraph says so rather than citing a page that does not exist.

**If that near-certainty is wrong, this setting fails permissively**, and the first draft of
this paragraph got that backwards by reasoning about the wrong half. It argued from the
request carrying no `X-Forwarded-For`, where one trusted hop does change nothing and the
address stays the socket peer; that is the case AC-410 asserts and it is not the case that
decides anything. **The case that decides it is the request carrying the header because the
caller wrote it.** If Render's edge appends nothing, nothing overwrites what a caller sends,
and one trusted hop makes `req.ip` a string of their choosing: a stranger rotating the
header meets no per-address limit at all, where before they met an over-strict shared one.
The failure direction is **from too strict to absent**, not from working to neutral. The
cost is bounded but real — log volume and the CPU of parsing reports, with 10.8's
20-per-window budget still capping what reaches Sentry — and it is the direction that does
not announce itself, an endpoint that has stopped refusing anything looking exactly like an
endpoint nobody is abusing.

**So the production check is what closes this, rather than tidying after it.** Read `req.ip`
once against the deployed service — one security log line carrying the address, or an
equivalent one-off — and see whether it is a Render edge address or a visitor's. It is left
undone here because 10.5 keeps the caller's address out of the log deliberately, and putting
it in even for a single measurement is a change to that policy rather than an aside to this
one. Until it is run, the honest statement is that the evidence is strong, indirect, and
that the downside of its being wrong is a limiter that does not limit.

**Added 2026-09-04 (issue #6): this deployment answers on exactly one host, and every other
one is redirected to it.** APP_ORIGIN names the canonical host, `https://dana.so`, and the
Google callback, the CSP reporting endpoint and every link in an 11.8 email are built from
that value rather than from the request. Render's own address for the same service,
`https://dana-iuax.onrender.com`, served the whole application beside it and pointed at
nothing. **Session cookies are host-only (10.1) — no Domain attribute is set and none should
be — so two addresses were two cookie jars.** A sign-in begun on either one ends on the
canonical host, the callback coming from configuration and never from the request (11.6), so
that is where the cookie lands; open the Render address afterwards, from a bookmark or from
history, and there is no session on it at all. Sign in again, land on `dana.so` again, and a
few days of that reads exactly as "every visit needs a fresh sign-in", which is how issue #6
was reported and why it was investigated twice as a cookie defect. Nothing in the cookie code
was wrong.

So, when APP_ORIGIN is set: a request whose host is not its hostname, compared
case-insensitively against the trust-proxy-aware `req.hostname`, is answered ahead of
everything else this application does — **301 to the same path and query on the canonical
origin for GET and HEAD**, permanent because it is permanent and so that a stale bookmark
heals itself, and **404 in the 7.0 envelope for every other method**, a mutation aimed at the
wrong host having carried no cookie for that host anyway and 301 being no way to move a body.
**Exactly one path is exempt, `/api/health`**: Render's own health check reaches this service
by its Render hostname, which is the non-canonical one by definition, so a redirect there
fails the check and with it every deploy. **Nothing is logged per request** (10.5); the boot
writes one line naming the host it is enforcing, and the absence of that line means
APP_ORIGIN was unset, which is development and which `assertSignInIsPossible` already refuses
to start production without. Unset, nothing redirects at all.

**It compares hosts and not origins**, because the rule is about cookie jars and those are
keyed by host: a request on the right host over the wrong scheme is left to the edge that
terminates TLS, the same ground 10.8 gives it HSTS on. And **no test in this repository can
see the cause** — every criterion drives one origin, so a second address serving identical
bytes is invisible to all of them, and how many addresses a platform has pointed at this
service is a fact that lives in this paragraph and in that one boot line. AC-414 measures
everything else.
