### 11.5 Database and migrations

- Postgres 18 in production, and the same major everywhere tests run: PGlite embeds
  Postgres 18 and CI pins the postgres:18 image. Section 4's reference dialect (Postgres
  16) remains valid; nothing in the schema requires more than Postgres 15. - Drizzle ORM
  is the query client. The twelve queries of section 6 are written as SQL through
  Drizzle's sql template so their ORDER BY clauses can be compared to the spec textually;
  CRUD may use the query builder. - Migrations are hand-authored SQL files in
  `app/db/migrations/`, forward-only, with every constraint and index explicitly named
  (AC-001 asserts them by name). The Drizzle programmatic migrator applies pending
  migrations at server boot, before the health endpoint reports ready, and wraps each run
  in one transaction: all pending files commit or roll back together, which is strictly
  stronger than per-file atomicity (verified in the installed migrator; section 13 item
  16). - Deploy interplay: the host's zero-downtime deploy keeps the old instance serving
  until the new one passes its health check. Postgres DDL is transactional, so a failed
  migration rolls back, boot fails, the deploy is canceled, and the old version keeps
  running. Destructive changes (drops, renames) must be split expand-and-contract across
  two releases, because the old code runs against the new schema during the overlap window
  (roughly ninety seconds).
