### 11.5 Database and migrations

- Postgres 18 in production, and the same major everywhere tests run: PGlite embeds
  Postgres 18 and CI pins the postgres:18 image. Section 4's reference dialect (Postgres
  16) remains valid; nothing in the schema requires more than Postgres 15. - Drizzle ORM
  is the query client. The twelve queries of section 6 are written as SQL through
  Drizzle's sql template so their ORDER BY clauses can be compared to the spec textually;
  CRUD may use the query builder. - Migrations are hand-authored SQL files in
  `app/db/migrations/`, forward-only, with every constraint and index explicitly named
  (AC-001 asserts them by name). The Drizzle programmatic migrator applies pending
  migrations at server boot, before the health endpoint reports ready, and wraps each run
  in one transaction: all pending files commit or roll back together, which is strictly
  stronger than per-file atomicity (verified in the installed migrator; section 13 item
  16). - Deploy interplay: the host's zero-downtime deploy keeps the old instance serving
  until the new one passes its health check. Postgres DDL is transactional, so a failed
  migration rolls back, boot fails, the deploy is canceled, and the old version keeps
  running. Destructive changes (drops, renames) must be split expand-and-contract across
  two releases, because the old code runs against the new schema during the overlap window
  (roughly ninety seconds).

**The seam that chooses the engine announces itself in production, added 2026-09-04 for
issue #80.** `app/db/client.ts` selects PGlite in `./.data` when it is handed no connection
string. That default is what lets the whole suite run with no Docker and no setup, and it is
exactly wrong for a production boot, where an unset or empty `DATABASE_URL` is a silent
downgrade to a database living inside the container; on a host whose filesystem does not
survive a spin-down, every spin-down then destroys every row, and what a person reports is
that they have to sign in again (#6). The boot already logged
`{"event":"migrations_applied","database":"pglite"}`, which reads as neutral information and
is why nobody was looking at it.

A production boot that has fallen back therefore does three things and **does not refuse to
start**: it writes one error-level line with its own event name,
`database_fallback_pglite`, carrying a sentence saying what is at stake; it reports the same
sentence through the error tracker of 11.12 so alerting can see a condition that is not an
exception; and it declares the engine to `GET /api/health`, which answers
`database: "postgres" | "pglite"`. Refusing the boot was considered and rejected: it could
take production down to prevent a data-loss bug that instance may not have. **When
`DATABASE_URL` is guaranteed, the refusal becomes the right thing** and this paragraph is
the record of why it was not done first.
