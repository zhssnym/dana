### 11.10 Testing infrastructure

- Vitest 4 runs unit and acceptance tests. The acceptance suite exercises section 7 over
  HTTP against the real Express app in-process. - The suite reaches that application
  through one construction seam: createApp(options?) in app/src/server/index.ts,
  Platform's file. It is synchronous, performs no I/O, and opens no database.
  options.dbClient injects the app/db/client.ts handle, the only way a test's in-memory
  PGlite database can arrive; the boot path always passes its own. options.auth injects {
  issuerUrl, clientId, clientSecret, appOrigin, allowInsecureRequests } and wins over the
  environment variables that remain the production path (GOOGLE_CLIENT_ID,
  GOOGLE_CLIENT_SECRET, GOOGLE_ISSUER_URL, APP_ORIGIN, OIDC_ALLOW_INSECURE); the issuer is
  injectable because a module that hardcodes accounts.google.com cannot be tested at all.
  options.notifications injects a sink { send(message) }: when present, the 11.8
  notification module delivers each outbound message to it instead of logging, which is
  what makes a send observable under test at all, since 11.8 forbids real sending there
  and 10.5 keeps recipient addresses out of the logs. Each delivered message identifies
  its template and its recipient; the remaining keys are the module's own. Absent the
  sink, 11.8 stands unchanged: log in development and tests, send in production. Routes
  that touch the database require options.dbClient and fail only when called without it,
  which lets database-free surfaces (health, route-presence probes) construct the
  application bare. - The database under test is selected by one seam in
  `app/db/client.ts`: PGlite (embedded Postgres 18, in-process, no Docker, runs on
  Windows) by default, or any real Postgres via TEST_DATABASE_URL, which since 2026-09-03
  names the **base** database of that leg rather than the database the tests run in; the
  per-worker bullet below carries what is derived from it. The variable is scoped
  to test and database-script processes: a server entrypoint passes its connection string
  explicitly (DATABASE_URL) and clears TEST_DATABASE_URL from its environment before
  opening the seam. CI ran the full suite both ways — PGlite for parity with local runs,
  and a real Postgres 18 server as the second leg — **until 11.11's 2026-09-20 amendment
  struck the PGlite leg out. There is one leg now and it is Postgres; PGlite survives as
  the seam's default and as the fallback for a machine with no `TEST_DATABASE_URL`, whose
  gate record is `incomplete` rather than green.** Everything this section fixes about
  that leg — the locale its database is created with, the two checks that prove the
  ordering, the connection-loss listener — is unchanged and now applies to the only leg
  there is. Where the text below says "the second leg" or "both legs", read it as the
  Postgres leg and the PGlite fallback: the properties it is distinguishing between are
  the two engines', and those have not moved.
  That leg's vehicle belongs to the
  runner rather than to this sentence: a postgres:18 service container on a GitHub-hosted
  runner, and the runner host's own Postgres 18 cluster on a self-hosted one (11.11). What
  the leg is an authority for is the engine rather than the operating system around it: a
  real client and server across a socket, a pool holding several sessions so that a second
  concurrent transaction is expressible where 11.15 records PGlite cannot hold one, the
  real planner, and the packaged pg_trgm rather than the contrib build. It was called the
  production-fidelity authority until 2026-08-11, and that name over-claimed in exactly
  one place, which the bullet below fixes. PGlite's pg_trgm ships in its main package
  (contrib import). PGlite is alpha-badged; the named fallback behind the same seam is the
  embedded-postgres npm package (real Postgres binaries, Windows x64, no Docker or admin
  rights). - **The text ordering the suite runs on is fixed by the test database's own
  locale, never inherited from whatever cluster hosts it.** Ruled 2026-08-11 at the
  local-CI change control. Section 6's preamble asks its orderings to make any two agents
  produce byte-identical result sequences, and neither the migrations nor the query
  modules write COLLATE, so every ordering over a text column takes the database default:
  7.4 and Q2 over lower(folder name), and 7.3's roster over display_name, which is not
  case-folded. The second leg's database is therefore created explicitly, and this
  statement is its normative form:

  ```sql
  CREATE DATABASE dana_test OWNER dana_ci TEMPLATE template0 ENCODING 'UTF8'
    LOCALE_PROVIDER builtin BUILTIN_LOCALE 'C.UTF-8' LC_COLLATE 'C' LC_CTYPE 'C';
  ```

  **Added 2026-09-20 (issue #235): that statement is normative for the gate machine, and
  a server too old to parse it falls back rather than being unable to run the leg.**
  `LOCALE_PROVIDER builtin` arrived in Postgres 17; the gate host runs 18 and takes the
  statement above unchanged. Below 17 the clause does not parse — a 16 server answers
  SQLSTATE 42601, `option "builtin_locale" not recognized` — so the leg creates its
  per-worker databases with libc `LC_COLLATE 'C' LC_CTYPE 'C.UTF-8'` instead. This exists
  because the one-leg gate of #229 left exactly one machine able to produce a green
  record, and #231 and #232 are what that cost: a branch merged unverified on Postgres and
  a stale test found three days late.

  **The ctype in that fallback is `C.UTF-8` and not `C`, and the difference is the whole
  of what this amendment had to get right.** The sentence below is that the statement
  fixes how the database sorts **and folds** text, and those are two settings rather than
  one: sorting is LC_COLLATE, where `C` is byte order under either provider, and folding
  is LC_CTYPE, which is what `lower()`, `upper()` and `ILIKE` read. `C` folds ASCII only.
  Measured 2026-09-20 on a 16.13 server, one database against another differing in ctype
  alone: `lower('ÉCOLE')` answers `école` under `C.UTF-8` and `École` under `C`, and
  `'CAFÉ' ILIKE 'café'` is true under the first and false under the second. **Both order
  identically**, which is why the first draft of this amendment took `C` and why nothing
  in the suite went red on it. What it would have cost is section 7: Q2's folder order is
  `ORDER BY lower(name)` and Q8 searches with ILIKE, so two legs would have answered
  different result sequences over accented names while both read green — the property the
  preamble above exists to hold, broken in the one way no ordering probe can see. PGlite
  reports datcollate `C` with datctype `C.UTF-8`, and 18's builtin `C.UTF-8` folds the
  same way, so `C.UTF-8` is the value that agrees with both legs and collate-C-with-ctype-C
  is the one combination agreeing with neither.

  **What is required of every server is therefore both halves, and
  `guard-postgres-leg-isolation.test.ts` now asserts them separately**: an ordering probe
  and a folding probe, both unconditional and both run on the PGlite leg too, with the
  provider that produced them asserted per version beside them. The fallback remains the
  weaker of the two forms and is confined to servers which cannot express the stronger
  one, the builtin provider's point being that neither setting depends on the host's libc
  at all.

  **That statement fixes how the database sorts and folds text and nothing about the
  language the server writes its messages in, and since 2026-09-03 the suite depends on
  the first and not the second.** The message language is the separate `lc_messages` GUC,
  inherited from the cluster and superuser-context, so a database owner cannot set it; on
  the machine this leg first ran on, that cluster is French. From 2026-08-11 to 2026-09-03
  a second statement stood beside the first as equally normative, `ALTER DATABASE dana_test
  SET lc_messages = 'C'`, because one acceptance assertion read the server's message prose
  rather than an identifier: AC-001's adversarial NOT NULL case asserted that the rejection
  contained the English sentence naming the column, deliberately, since the bare column
  name also appears in the statement it sent and a fragment satisfiable by the statement
  text would prove nothing. It was the only one of the suite's nine such assertions to fail
  on that cluster, the other eight naming constraints and indexes, which appear verbatim
  in a translated message. **Issue #92 retired the assertion rather than the privilege.**
  A PostgreSQL ErrorResponse carries the SQLSTATE and the schema, table, column and
  constraint names as fields of their own (protocol fields C, s, t, c and n), written by
  the server from the object that failed and translated by no locale; only the message,
  the detail and the severity are prose. The case now asserts SQLSTATE 23502 with table
  `tasks` and column `folder_id`, read from those fields, which answers the statement-text
  concern more strongly than the prose did: a field the server wrote cannot be satisfied
  by anything the client sent, where a fragment of a sentence at least in principle could.
  Measured against both drivers before it was relied on: node-postgres 8.22.0 against a
  created database answering in French, and PGlite 0.5.4 against its own, each surface
  every one of those fields on the error drizzle nests under `cause`, and the French
  message beside them read `une valeur NULL viole la contrainte NOT NULL de la colonne
  « folder_id »` with even the severity translated. `tests/support/helpers.ts` reads the fields
  (`serverErrorFields`, `expectRejectedWith`), and `tests/guards/guard-postgres-leg-isolation.test.ts`
  fails any test file that grows an assertion on server prose, so the dependency cannot
  return unannounced. The ALTER DATABASE is therefore harmless where it exists and required
  nowhere; a rebuild of `dana_test` that omits it changes nothing the suite reads.

  Postgres 18's builtin provider is the only one Postgres itself guarantees identical on
  every platform and every version, being code point order over Postgres's own Unicode
  tables rather than an operating system's collation library, and it is already what
  PGlite does. Measured on 2026-08-11 against the installed PGlite (server 18.3): its
  database reports LC_COLLATE C with a UTF-8 ctype, its default ordering is byte-identical
  to the builtin pg_c_utf8 collation over a probe carrying case, accents, punctuation and
  digits, and its case mapping is full Unicode, which the builtin C.UTF-8 locale also
  provides, so Q8's ILIKE and its trigram search fold the same way on both legs. Pinning
  the second leg the same way means a disagreement between the two legs can only be an
  engine difference, which is the only thing that leg exists to find. It also puts the
  database under the same ordering as the acceptance suite's own oracle, JavaScript's <
  over strings being UTF-16 code unit order, which is what AC-069 sorts with to assert
  7.3's roster order; under a linguistic collation that criterion agreed with the database
  only for as long as its fixture avoided case, accent and punctuation differences.

  Verify rather than assume. Two checks, both runnable with TEST_DATABASE_URL set, and
  since 2026-09-03 both run on every Postgres leg from
  `app/tests/guards/guard-postgres-leg-isolation.test.ts` rather than waiting for someone to type them
  into psql, against the per-worker database the leg created a moment earlier, which is
  the database whose locale nobody chose by hand. There was a third, `SHOW lc_messages`
  against the base database, for as long as a criterion read a message; nothing does now,
  and what stands in its place is the same file's scan of every test source for the
  fragments a server writes in prose.

  ```sql
  SELECT datlocprovider, datlocale, pg_encoding_to_char(encoding)
    FROM pg_database WHERE datname = current_database();  -- must answer b, C.UTF-8, UTF8

  SELECT string_agg(v, '|' ORDER BY v) FROM (VALUES
    ('Zebra'),('apple'),('Apple'),('a-b'),('ab'),('coté'),('côte'),('_x')) AS s(v);
  -- must answer Apple|Zebra|_x|a-b|ab|apple|coté|côte, on this leg and on PGlite alike
  ```

  What the ruling gives up is section 13 item 29: no leg any longer runs a linguistic
  collation, so the ordering a production Render Postgres serves is checked by nothing. It
  was checked by nothing before either, PGlite having been LC_COLLATE C since P0 while the
  container leg was glibc en_US.utf8 by the image's own LANG, which is proof that no
  criterion could ever have distinguished the two and stayed green on both. - **The second
  leg gives each Vitest worker a database of its own, and no two test files ever share one.
  Amended 2026-09-03 at issue #32.** Until then this section described one `dana_test` and
  the leg used one: all 282 files wrote into it at once and could see each other's rows.
  The fingerprint was a count that climbed across successive tests, `expected 2 to be 1`,
  then 3, then 4, where a logic error gives one constant wrong number; it was measured on
  the first two CI runs this repository ever had, on `ac-153` and `ac-251`, both of which
  passed alone in 2.4 seconds. What that costs is not tidiness: a check that goes red for
  reasons unrelated to the change teaches everyone to ignore it, and the person on the other
  half of this project cannot tell a flake from a defect at all. **The unit of isolation is
  Vitest's pool slot rather than the file**, because `VITEST_POOL_ID` is an integer between
  1 and maxWorkers that the pool allocates from a free set and returns when a file finishes,
  so the files running at any one instant hold distinct ids by construction. Each slot's
  database is named `<base>_r<run>_w<slot>`, created from `template0` with the statement
  above and migrated, and emptied of every `public` table before each file that uses it, so
  a file cannot start on top of the rows of the file that shared its slot earlier either.
  It is created rather than copied from a pre-migrated template because creating and
  migrating was measured faster (about 200 ms and 150 ms against about 700 ms for a copy
  under eleven-way parallelism) and has no staleness to invalidate when a migration lands.
  **A run is identified by a Postgres advisory lock it holds for its whole length**, which
  is what makes this safe to kill and safe to overlap: the next run drops the databases of
  every run whose lock it can take, because a lock it can take belongs to a process that has
  exited, and leaves alone every one it cannot. Nothing is dropped on a timer and nothing is
  dropped by name, so two runs on one cluster cannot delete each other's databases. **The
  one property of a created database this role cannot set is `lc_messages`, and since
  issue #92 nothing depends on it.** It is a superuser-context GUC, so the role that
  creates these databases cannot set it on them, at session level, through the startup
  packet, with ALTER DATABASE, or by inheriting it from a TEMPLATE, `pg_db_role_setting`
  being a shared catalog keyed by the database's own oid; all four were measured on
  2026-09-03 rather than assumed. A created database therefore answers in the cluster's
  language, which on this machine is French, and for the hours between #32 and #92 that
  mattered: AC-001 read server prose, so that file alone was routed to the base database,
  which a superuser had set `lc_messages = C` on. **That routing was the last place on this
  leg where two runs, and worse two branches, could still interfere, and it did within
  hours.** Migrations are forward-only and the base database is never dropped, so a branch
  that ran AC-001 there left its migrations behind for every other branch; a branch behind
  `main` then failed AC-001 on this leg with assertions naming tables and constraints its
  own catalog had never heard of, and would have gone on failing until it rebased. The
  assertion now reads the server's structured error fields (above), the routing is gone,
  and no test file runs against the base database at all: it is where the run's advisory
  lock lives and what the per-worker names are derived from, and nothing else. A schema
  one branch leaves in it reaches nobody, and two runs overlapping on one cluster share
  nothing a test can see. - The AC-001 constraint catalog test asserts structured facts
  from pg_constraint and pg_index (constraint type, columns, on-delete targets, partial
  predicates, names), never deparsed SQL text, and its behavioural probes read the
  structured fields of a rejection rather than its message, so the same test passes on
  every Postgres the suite runs against, whatever language it answers in. - **A pool this
  seam opens carries an error listener on both of the windows where a dead socket would
  otherwise end the process, and that is a requirement of the seam rather than a test
  convenience.** node-postgres re-emits an **idle** pooled connection's socket error on
  the pool itself, and a connection **checked out** by pool.connect(), which is every
  transaction and every migration run, emits its own; an EventEmitter 'error' with no
  listener throws, so a single reset connection ends the process with an uncaught error
  naming no frame of this repository. A query run through pool.query() is the one window
  the driver already covers. Measured 2026-09-04 at issue #174 with a TCP proxy resetting
  a real pooled socket on demand, and it is what the second leg had been losing a whole
  file to about once a run: a socket message rather than a Postgres one, no assertion
  failing, a different file each time, and every one of them green alone. Each listener
  writes one line and lets the pool discard the connection; a query in flight still
  rejects with the same error, so nothing a caller would have seen is swallowed. The same
  seam is the production boot's, where a reset idle connection is the ordinary fate of a
  long-lived pool and the single instance would otherwise die of one. - **The connection
  arithmetic, recorded because it is not the cause and the next reader should not have to
  measure it again.** This leg's pool is the driver's default: max 10, idle timeout 10
  seconds, no connection timeout. Twelve workers could therefore in principle ask for 120
  connections, plus the run's registry connection and the admin connections a worker opens
  to create or empty its database, against the 97 a non-superuser role can hold on a
  cluster whose max_connections is 100 with 3 reserved. **The measured peak across a whole
  parallel leg is 17 and 18 on the two runs it was sampled on**, every 500 ms on
  2026-09-04, because the requests inside a test file are serial; the ceiling is real, has never been approached, and the pool stays
  at its default until a measurement says otherwise. Anything that makes many files issue
  concurrent requests at once should measure it again. - Playwright
  drives end-to-end tests on Windows and in CI, using the seed dataset and the development
  login endpoint for sessions.

**Assumption: the browser leg runs against PGlite alone, where the vitest suite runs
against both engines.** Every case in that leg is a rendering, a copy string, a route, a
control's presence, or a request the client did or did not send, and the engine underneath
is reached through section 7 by code the vitest suite already exercises on both. A
divergence a real Postgres would catch and PGlite would not is a divergence in SQL
behaviour, which the other leg is the authority for.

What it costs: a client defect and an engine defect arriving together would appear as one
red with nothing separating them. Revisit on any browser case failing while its server
half passes on both vitest legs, which is the shape that would mean the engine rather than
the page. The change is one environment variable on the CI step and the same on the
runner, with that leg's database then needing its migrations run before the seed.
