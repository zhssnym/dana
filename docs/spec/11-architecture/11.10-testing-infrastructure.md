### 11.10 Testing infrastructure

- Vitest 4 runs unit and acceptance tests. The acceptance suite exercises section 7 over HTTP against the real Express app in-process.
- The suite reaches that application through one construction seam: createApp(options?) in app/src/server/index.ts, Platform's file. It is synchronous, performs no I/O, and opens no database. options.dbClient injects the app/db/client.ts handle, the only way a test's in-memory PGlite database can arrive; the boot path always passes its own. options.auth injects { issuerUrl, clientId, clientSecret, appOrigin, allowInsecureRequests } and wins over the environment variables that remain the production path (GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_ISSUER_URL, APP_ORIGIN, OIDC_ALLOW_INSECURE); the issuer is injectable because a module that hardcodes accounts.google.com cannot be tested at all. options.notifications injects a sink { send(message) }: when present, the 11.8 notification module delivers each outbound message to it instead of logging, which is what makes a send observable under test at all, since 11.8 forbids real sending there and 10.5 keeps recipient addresses out of the logs. Each delivered message identifies its template and its recipient; the remaining keys are the module's own. Absent the sink, 11.8 stands unchanged: log in development and tests, send in production. Routes that touch the database require options.dbClient and fail only when called without it, which lets database-free surfaces (health, route-presence probes) construct the application bare.
- The database under test is selected by one seam in `app/db/client.ts`: PGlite (embedded Postgres 18, in-process, no Docker, runs on Windows) by default, or any real Postgres via TEST_DATABASE_URL. The variable is scoped to test and database-script processes: a server entrypoint passes its connection string explicitly (DATABASE_URL) and clears TEST_DATABASE_URL from its environment before opening the seam. CI runs the full suite both ways: PGlite for parity with local runs, and a real Postgres 18 server as the second leg. That leg's vehicle belongs to the runner rather than to this sentence: a postgres:18 service container on a GitHub-hosted runner, and the runner host's own Postgres 18 cluster on a self-hosted one (11.11). What the leg is an authority for is the engine rather than the operating system around it: a real client and server across a socket, a pool holding several sessions so that a second concurrent transaction is expressible where 11.15 records PGlite cannot hold one, the real planner, and the packaged pg_trgm rather than the contrib build. It was called the production-fidelity authority until 2026-08-11, and that name over-claimed in exactly one place, which the bullet below fixes. PGlite's pg_trgm ships in its main package (contrib import). PGlite is alpha-badged; the named fallback behind the same seam is the embedded-postgres npm package (real Postgres binaries, Windows x64, no Docker or admin rights).
- **The text ordering the suite runs on is fixed by the test database's own locale, never inherited from whatever cluster hosts it.** Ruled 2026-08-11 at the local-CI change control. Section 6's preamble asks its orderings to make any two agents produce byte-identical result sequences, and neither the migrations nor the query modules write COLLATE, so every ordering over a text column takes the database default: 7.4 and Q2 over lower(folder name), and 7.3's roster over display_name, which is not case-folded. The second leg's database is therefore created explicitly, and this statement is its normative form:

  ```sql
  CREATE DATABASE dana_test OWNER dana_ci TEMPLATE template0 ENCODING 'UTF8'
    LOCALE_PROVIDER builtin BUILTIN_LOCALE 'C.UTF-8' LC_COLLATE 'C' LC_CTYPE 'C';

  ALTER DATABASE dana_test SET lc_messages = 'C';
  ```

  **Both statements are normative, and the second was learned the hard way.** Amended 2026-08-11 at the local-CI merge review, after the first execution of this leg turned it up. The locale a database is created with fixes how it sorts and folds text; it does not fix the language the server writes its error messages in, which is the separate lc_messages GUC, inherited from the cluster and superuser-context so a database owner cannot set it. On the machine this leg first ran on that cluster is French, and one acceptance assertion reads the server's own message prose rather than an identifier: AC-001's adversarial NOT NULL case asserts that the rejection contains `null value in column "folder_id"`, deliberately, because the bare column name also appears in the statement it sent and a fragment satisfiable by the statement text would prove nothing. It was the only one of the suite's nine such assertions to fail, the other eight naming constraints and indexes, which appear verbatim in a translated message. The second statement therefore belongs beside the first: a test database whose locale is pinned in one dimension and inherited in another is pinned in neither, and a rebuild of `dana_test` that omits this line reintroduces exactly the red it was written to close.

  Postgres 18's builtin provider is the only one Postgres itself guarantees identical on every platform and every version, being code point order over Postgres's own Unicode tables rather than an operating system's collation library, and it is already what PGlite does. Measured on 2026-08-11 against the installed PGlite (server 18.3): its database reports LC_COLLATE C with a UTF-8 ctype, its default ordering is byte-identical to the builtin pg_c_utf8 collation over a probe carrying case, accents, punctuation and digits, and its case mapping is full Unicode, which the builtin C.UTF-8 locale also provides, so Q8's ILIKE and its trigram search fold the same way on both legs. Pinning the second leg the same way means a disagreement between the two legs can only be an engine difference, which is the only thing that leg exists to find. It also puts the database under the same ordering as the acceptance suite's own oracle, JavaScript's < over strings being UTF-16 code unit order, which is what AC-069 sorts with to assert 7.3's roster order; under a linguistic collation that criterion agreed with the database only for as long as its fixture avoided case, accent and punctuation differences.

  Verify rather than assume. Three checks, all runnable with TEST_DATABASE_URL set:

  ```sql
  SELECT datlocprovider, datlocale, pg_encoding_to_char(encoding)
    FROM pg_database WHERE datname = current_database();  -- must answer b, C.UTF-8, UTF8

  SELECT string_agg(v, '|' ORDER BY v) FROM (VALUES
    ('Zebra'),('apple'),('Apple'),('a-b'),('ab'),('coté'),('côte'),('_x')) AS s(v);
  -- must answer Apple|Zebra|_x|a-b|ab|apple|coté|côte, on this leg and on PGlite alike

  SHOW lc_messages;  -- must answer C, never a language name
  ```

  What the ruling gives up is section 13 item 29: no leg any longer runs a linguistic collation, so the ordering a production Render Postgres serves is checked by nothing. It was checked by nothing before either, PGlite having been LC_COLLATE C since P0 while the container leg was glibc en_US.utf8 by the image's own LANG, which is proof that no criterion could ever have distinguished the two and stayed green on both.
- The AC-001 constraint catalog test asserts structured facts from pg_constraint and pg_index (constraint type, columns, on-delete targets, partial predicates, names), never deparsed SQL text, so the same test passes on every Postgres the suite runs against.
- Playwright drives end-to-end tests on Windows and in CI, using the seed dataset and the development login endpoint for sessions.

**Assumption: the browser leg runs against PGlite alone, where the vitest suite runs against
both engines.** Every case in that leg is a rendering, a copy string, a route, a control's
presence, or a request the client did or did not send, and the engine underneath is reached
through section 7 by code the vitest suite already exercises on both. A divergence a real
Postgres would catch and PGlite would not is a divergence in SQL behaviour, which the other
leg is the authority for.

What it costs: a client defect and an engine defect arriving together would appear as one red
with nothing separating them. Revisit on any browser case failing while its server half
passes on both vitest legs, which is the shape that would mean the engine rather than the
page. The change is one environment variable on the CI step and the same on the runner, with
that leg's database then needing its migrations run before the seed.
