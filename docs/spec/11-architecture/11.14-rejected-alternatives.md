### 11.14 Rejected alternatives

Recorded so future work argues with a decision instead of rediscovering it. Verification
date for the external facts: 2026-07-29. The five product rows at the foot of the table
are v2's own rejections, decided 2026-08-24 to 2026-08-30 and folded here from RFC 0005
when `docs/rfcs/` was retired; they carry their own dates rather than that one.

| Alternative | Rejected because |
| - | - |
| Next.js (App Router) | Server actions and RSC data paths are a second door past the section 7 contract and the 10.2 chokepoint; the framework is mid-churn (Turbopack default, middleware renamed proxy, async params), which is where agents invent; SSR has no consumer in a login-gated PWA |
| Vercel hosting | No always-on process for the 8.6 tick (Hobby cron is daily-only and the plan is non-commercial; Pro adds 20 USD/month); ephemeral instances break 10.4's in-memory rate limiting; honest total cost about triple Render, across three vendors |
| Railway | Close second: always-on and cheaper, but snapshot backups only, no point-in-time recovery |
| Fly.io | No free allowance for new accounts; managed Postgres from 38 USD/month; the cheap path is self-operated Postgres, which the project constraints exclude |
| Supabase | Free tier pauses after 7 idle days and has no automated backups; its native pattern (client-side data access behind RLS) is what 10.2 forbids; Pro costs more than this entire stack |
| Neon | Scale-to-zero is defeated by the one-minute poll, so its pricing works against exactly this workload |
| Auth.js (NextAuth) | Maintenance mode by its own 2025-09-26 announcement; v5 never left beta |
| Better Auth | Would own the users table shape and the provisioning transaction that section 4 and AC-005/AC-006 fix; weekly release cadence outruns agent training data; it is the designated fallback if hand-rolled auth is ever vetoed |
| Lucia, Arctic | Both deprecated by their author |
| Prisma | Schema DSL far from section 4's SQL; heavier runtime; worse fit for constraint-exact migration work |
| rrule.js at runtime | Unmaintained; its reinterpreted-UTC result model collides with floating dates; kept as a test oracle only |
| Serwist | Coupled to Next.js, which was rejected |
| GitHub Actions as the reminder trigger | Documented 5-minute floor, plus documented delays and dropped runs under load |
| Buying GitHub-hosted CI minutes after the 2026-08-11 billing failure | The owner's decision, recorded so the self-hosted runner reads as a choice rather than an accident. Hosted runners stay admitted by 11.11 and cost nothing to return to, the workflow differing only in `runs-on` and in where the postgres leg's database comes from |
| Matching the postgres:18 image's libc locale on the self-hosted runner | Windows has no glibc, so naming en-US there selects the Windows NLS implementation rather than the image's; the orderings would still differ, with nothing able to say by how much, which is fidelity claimed and not held (11.10) |
| ICU as the test database's locale provider | Deterministic across operating systems only within one ICU major version, and nothing here pins Debian's or the Windows build's; it would also be a third ordering, agreeing with neither PGlite nor a glibc production database, so it buys a linguistic collation at the cost of the byte-identical results section 6 asks for |
| Standing staging environment | Doubles hosting cost to serve zero users; CI against postgres:18 plus the production smoke subset covers it |

| Per-viewer folder identity | Lost to folder-owned identity at v2, 2026-08-24. A collaboration product where every member sees a different page is two products, and the per-member table also doubles the sharing system |
| CRDTs for page blocks | Lost to last-write-wins plus 409. Dana's concurrency is two people occasionally rather than documents-as-a-service, and 8.3 already had the conflict vocabulary |
| Real-time push for comments | Lost to refetch-and-poll: no new architecture, and the single instance 11.1 assumes stays intact. Deferred by name rather than denied |
| A reminders redesign | Lost to the existing `time_of_day` mode. The schema already answered day-level reminders, so a new column would have been a worse copy of 4.8 |
| Trash as its own table | Lost to `deleted_at` columns. Users already soft-delete this way, so it is one pattern and restore is an UPDATE |

**Why `.strict()` is rejected, at length, because this keeps being reopened.** Issue #40
asked for it and issue #94 is one instance of what prompts the asking: a request field the
server does not read is accepted, thrown away, and answered 200, with nothing on the wire
to separate that from a request that never carried it. The complaint is real. The remedy is
the wrong one, on four measurements taken 2026-09-03 against the shipping tree.

**It does not address the incident it is argued from.** The reminder loss recorded in
`app/src/shared/tasks.ts`, four packages of a silently dropped field and the reason AC-149
exists, was a field the schema **declared** and the route did not act on. Strictness reads
only the keys a schema does not declare, so it would have been silent through all four
packages. There are two failure classes here and only one of them is about unknown fields
at all; 11.15 now names both, because conflating them is what makes this argument
recur.

**It would break `POST /workflows/import` against Dana's own normaliser.** 7.16's import
accepts the arrangements a real file arrives in and folds them, and the fold copies rather
than moves: normalising a DES-206 shaped file leaves `exported_at` on the file, `colour`
and `items` on the folder, `priority` on the task and `note` on the step, five keys the
canonical schema does not declare and one of which — `items` — the normaliser created the
leftover of itself. Those five sit at four levels of the object, so a strict canonical
schema refuses the file outright — on the endpoint most deliberately widened to be
forgiving about the shape a file arrives in.

**Its refusal cannot be phrased.** zod 4 raises an unrecognized key as an issue with an
**empty path** and the code `unrecognized_keys`, and `sendValidationError` filters
empty-path issues out and then looks for a `custom` one. A strict schema in this tree today
therefore answers `422 validation_failed` with the message **"A JSON object body is
required."** for a request that supplied a perfectly good object. That names no field,
contradicts 7.0's own "422 with the field named", and tells the caller something untrue. A
sweep would have violated 7.0 in the act of enforcing it.

**That ground is spent as of 2026-09-04, and the ruling is not.** Issue #105 taught
`sendValidationError` to expand an `unrecognized_keys` issue into one named field per key,
so a strict schema can now phrase its refusal within 7.0. The measurement above stands as a
measurement of 2026-09-03 and is kept because it is why the formatter was fixed. The other
three grounds — that strictness is blind to the failure class it is always argued from, that
it breaks `POST /workflows/import` against Dana's own normaliser, and that 10.6's version
skew makes a dropped field an old client degrading rather than failing — are untouched by
it, and the answer for an endpoint that means to refuse a field is still to declare it.

**And 7.0's tolerance has a live reason, which 7.0 does not state and which is recorded
here rather than in a frozen section.** 10.6 lets an installed client outlive a deploy on
purpose: new versions "activate on next load", a mid-session update is an unobtrusive
affordance, and there is **no forced reload**. One deployable removes every other source of
version skew, so this is the only one left — and the specification chose to leave it open.
A field dropped from a request schema is, under tolerance, an old client degrading quietly;
under strictness it is that person's writes failing until they reload.

**What is done instead**, none of it a change to section 7:

- **An endpoint that deliberately refuses a field declares it and refuses it**, rather than
  making the whole object strict: `field: z.never({ error: … }).optional()` answers 422 with
  the field named and its own sentence, leaves every other unknown key tolerated, and needs
  no change to `sendValidationError`. This is the ruling for #94, whose `file_ids` on
  `PATCH /comments/:id` is exactly a field the contract closes rather than an accident.
- **A field a request schema declares is read in the same change.** That is the rule
  `app/src/shared/` exists to carry, it is the only answer to the second failure class, and
  a criterion is what proves it, as AC-149 does.
- **Observing unknown fields, rather than refusing them,** was the open half of this ruling
  and is **delivered, 2026-09-04, issue #104**. Logging a request that carried a key its
  schema did not declare turns the silent case into a searchable one without moving a single
  status code, and that is what shipped: `parseBody` in
  `app/src/server/http/parse-body.ts` is now how every route reads a body, parsing exactly
  as `safeParse` did — same statuses, same `sendValidationError`, 7.0's tolerance untouched
  — and writing one warn-level `unknown_request_fields` line naming the route template and
  the key names, and no value of any of them (10.5).

  **It was built with the guard rather than without it**, which is why this entry called it
  a unit of work rather than a line in this table. The helper went to all 29
  `safeParse(req.body)` sites across 11 modules — 28 when this issue was written, and 29 by
  the time it landed the same day — and **AC-399** fails any file under `src/server` that
  parses `req.body` without it, with an allowlist of one entry, the helper, and both counts
  pinned to equality the way AC-236's are. A helper a new route can simply forget has
  exactly the failure shape of the 10.2 gates. **AC-400** is the behaviour: the line's
  contents, the route template rather than the concrete URL, and its absence for a body
  every key of which is declared.

  Two limits, recorded here rather than left to be discovered. The observation is **top
  level only**: a key nested inside a declared object or an array element is dropped as
  silently as before. And AC-399 is a **source sweep rather than a runtime one** — it
  proves the spelling and not the path a request takes, the runtime form needing a minimal
  valid body for twenty-nine routes including a multipart upload; the file says so in its
  header and AC-400 buys back what could be bought cheaply.

  **What this does not do is anything about the other failure class**, and that is the
  point this entry has made from the beginning: the reminder loss it is always argued from
  was a field the schema **declared**, so `parseBody` is as blind to it as `.strict()`
  would have been. 11.15 names both classes; only a criterion catches that one.
