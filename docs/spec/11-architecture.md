## 11. Architecture

**This section is normative.** It records the implementation stack, the constraint each choice imposes, and the alternatives rejected with their reasons, so a future change is an argument with a recorded decision rather than a silent replacement. Agents implement against it exactly as against every other section; changes go through an RFC. External facts cited here (platform limits, versions, prices) were verified on 2026-07-29; prices are context, never contract.

### 11.1 Shape

One deployable: a single Node process runs the Express API, serves the static landing page, and serves the built client. One origin serves everything, so there is no CORS surface. The client is a Vite-built React single-page application; the server renders nothing but the landing page and JSON.

Three structural rules, each load-bearing:

- **Single instance.** Exactly one instance runs in production. Rate limiting (10.4) is in-memory, the reminder tick (11.7) is in-process, the boot-time migration run (11.5) takes no lock, and the auth module's pending-authorization records (11.6) live in process memory; all four assume it. A second instance requires moving rate limits to a shared store, electing a single tick owner, serializing the migration run, and relocating the pending-authorization records beside the rate limits, and must be flagged before it happens, never discovered after.
- **The API of section 7 is the only mutation path.** All client data access is fetch calls to /api/v1. No server-side rendering of application data exists, and no code path touches the database without passing the 10.2 chokepoint middleware. This is why the SPA-plus-API shape was chosen: it makes the single chokepoint architectural rather than merely mandated.
- **Forward-only migrations** (11.5). There is no down migration; recovery from a bad migration is a fix-forward migration or a restore.

### 11.2 Runtime, language, repository

- Node 24 (Active LTS until 2028-04-30), pinned in `.nvmrc` and the package.json engines field. npm is the package manager. ESM throughout.
- TypeScript in strict mode plus noUncheckedIndexedAccess. No JavaScript source files.
- A single package rooted at `app/`; no workspaces. Ownership boundaries are directories: `app/src/server/**`, `app/src/client/**`, `app/src/shared/**` (zod schemas and API types used by both sides), `app/db/**` (schema, migrations, seed), `app/tests/**` (the acceptance suite, owned by the Adversarial Test role).

### 11.3 Server

- Express 5. Route modules mirror section 7's resource groups. Every data route passes, in order: session resolution, CSRF verification (mutations only), rate limiting, then the handler, which resolves membership scope per 10.2 before touching rows.
- Validation with zod 4; the schemas live in `app/src/shared/` and produce the 422 field errors of 10.3. The client reuses them as convenience validation only (7.11).
- Rate limiting with express-rate-limit, in-memory, keyed by authenticated user id, limits per 10.4. Counters reset on deploy; accepted.
- Logging with pino to stdout. All log emission goes through one policy module that whitelists fields, making the 10.5 never-log list (task titles, notes, step titles, invite email addresses, tokens, session identifiers) structurally absent rather than filtered.

### 11.4 Client

- Vite 8, React, React Router 7 in library mode only: no loaders, no actions, no framework mode. Data fetching belongs to the query layer alone.
- TanStack Query 5 implements the 8.3 policy: refetch on window focus and after each own mutation; no other invalidation strategy exists.
- Forms with react-hook-form 7 plus the shared zod schemas via @hookform/resolvers. The P8 client departs from this and from the shadcn/ui sentence below; both departures are recorded as section 13 items 31 and 30 with what each costs, and neither sentence moves, because a rule is not rewritten to match what was built.
- Styling with Tailwind CSS 4 (CSS-first configuration through @tailwindcss/vite; there is no tailwind.config.js) and shadcn/ui components copied into `app/src/client/components/ui/`. Design tokens live in exactly one file, `app/src/client/styles/tokens.css`, as Tailwind @theme variables; it is the only place raw color, type, spacing, and radius values may appear, and it has one owner (the Component and Design System role). What that rule governs is the values the design fixes, ruled at the P8 merge on 2026-08-12 and recorded because the sidebar's folder dot reads like an exception and is not one. A folder's colour is a person's runtime choice carried on 7.4's my_color, per member and free-form under 4.4's #RRGGBB check, so it is data on the wire rather than a design value; the sidebar writes no colour at all, taking the fill from the response, while the dot's size and shape stay in tokens.css where the rule puts them. Reading the rule to cover this value would require mapping a free-form hex onto the ten swatches that file carries, which would paint a folder a colour its owner did not pick, and the hazard the rule exists to prevent, a design that cannot be changed in one place, is untouched: changing tokens.css must never change what colour somebody's own folder is.
- Calendar: FullCalendar 7 standard plugins (MIT) through the @fullcalendar/react entrypoints. v7 consolidated standard plugins into the framework package: dayGrid and timeGrid are imported from @fullcalendar/react subpaths, never from the standalone @fullcalendar/daygrid package, which is frozen at v6. Virtual instances from /views/planned/calendar render as ghost-classed events; the Q3C cell order (banners, then timed, then ghosts) is implemented with a custom eventOrder comparator. If the comparator cannot express the order exactly, the fallback is rendering ghosts in a separate per-cell overlay: the visible order is the contract, the mechanism is not.
- PWA: vite-plugin-pwa with the prompt-for-update registration flow (virtual:pwa-register with onNeedRefresh), satisfying 10.6's non-forcing update rule. Fallback if the plugin fights the 10.6 contract: a hand-written service worker under a hundred lines implementing precache, network-only API, and navigation fallback.

The virtual:pwa-register parenthesis names the flow rather than the import, read that way at the second P8 change control on 2026-08-11, on the Frontend Architect session's escalation, and recorded here so that a client not importing that module is not read later as a deviation. What the bullet obliges is 10.6's non-forcing update: a worker that installs while another controls the page is announced and never applied without a click. The parenthesis identifies which of the plugin's registration flows satisfies that, prompt-for-update rather than autoUpdate, and a module specifier is how the plugin's own documentation names that flow rather than a requirement to import it. The plugin still builds the worker and the manifest; the client registers the generated worker directly and implements the same flow against it. The reading is preferred to the import for a reason measured on this repository rather than argued: the virtual module exists only while the plugin is configured, so a static import of it fails the build outright, and this package's client had to be green on a tree where vite.config.ts was not yet wired. Nothing here forbids the import to a later session, and the swap is one file. This is a reading of 11.4 rather than a change to it, the shape 11.9 took for UNTIL's spelling at P6.

### 11.5 Database and migrations

- Postgres 18 in production, and the same major everywhere tests run: PGlite embeds Postgres 18 and CI pins the postgres:18 image. Section 4's reference dialect (Postgres 16) remains valid; nothing in the schema requires more than Postgres 15.
- Drizzle ORM is the query client. The twelve queries of section 6 are written as SQL through Drizzle's sql template so their ORDER BY clauses can be compared to the spec textually; CRUD may use the query builder.
- Migrations are hand-authored SQL files in `app/db/migrations/`, forward-only, with every constraint and index explicitly named (AC-001 asserts them by name). The Drizzle programmatic migrator applies pending migrations at server boot, before the health endpoint reports ready, and wraps each run in one transaction: all pending files commit or roll back together, which is strictly stronger than per-file atomicity (verified in the installed migrator; section 13 item 16).
- Deploy interplay: the host's zero-downtime deploy keeps the old instance serving until the new one passes its health check. Postgres DDL is transactional, so a failed migration rolls back, boot fails, the deploy is canceled, and the old version keeps running. Destructive changes (drops, renames) must be split expand-and-contract across two releases, because the old code runs against the new schema during the overlap window (roughly ninety seconds).

### 11.6 Authentication module

Hand-rolled Google OIDC on openid-client 6, implementing sections 7.1 and 10.1 exactly, with no auth framework. The reason is recorded: the libraries available when this section was first drafted are gone or unfit (Auth.js is in maintenance mode by its own 2025-09-26 announcement and v5 never left beta; Lucia and Arctic are deprecated by their author; Better Auth would own the users table shape and the provisioning transaction boundary that section 4 and AC-005/AC-006 fix). The scope that makes hand-rolling defensible: Google-only authorization code flow, no passwords, no resets, no MFA.

Requirements, each pinned by an acceptance criterion (AC-105 to AC-115):

- Authorization requests carry state, nonce, and a PKCE S256 challenge; the callback validates all three, single-use, and rejects on any mismatch. The pending-authorization record also carries the tz reported on GET /auth/google (7.1); tz never rides redirect_uri and is never composed into a redirect target.
- Sessions are rows in a sessions table (outside the section 4 core model; observable contract in 10.1), referenced by an opaque identifier in an httpOnly, Secure, SameSite=Lax cookie, with 30-day rolling expiry. Secure is set unconditionally, never derived from the request's own transport: TLS terminates ahead of the process (11.11), so the process always speaks plain HTTP and a derived flag would never be set. A fresh identifier is issued at every sign-in; no pre-authentication session identifier is ever promoted.
- CSRF uses the double-submit pattern so the frozen section 7 surface is untouched: a token bound to the session is set in a second, non-httpOnly cookie at sign-in, and every mutation must echo it in the X-CSRF-Token header; missing or mismatched answers 403 with no side effects.
- Auth endpoints never redirect off the application origin, whatever the request carries in parameters or Host headers.
- No Google access, refresh, or ID token is persisted once the callback transaction completes.
- The development-only login endpoint (DANA_DEV_LOGIN) must be absent from production builds, regardless of environment variables. Absent means excluded from the compiled output at build time, never a runtime guard (mechanism hazard in 11.15), and the flag is read at createApp() call time, never at module load. The endpoint provisions through the same transaction as the callback and takes an optional timezone field with the 7.1 tz parameter's semantics, absent meaning UTC.
- Expired session rows are pruned opportunistically by the scheduler pass (11.7). Pruning is hygiene, not revocation; revocation never waits for it.

The two cookies are named, added at the second P8 change control on 2026-08-11 on the client session's escalation. The session cookie is `dana_session` and the CSRF cookie is `dana_csrf`, which is what the server has set since P1. They are fixed here because the client has to read the second one and cannot import the server's constant, `src/client` compiling into the browser bundle, so with no name in this section `api/csrf.ts` preferred a guess and fell back to whatever the sole readable cookie turned out to be. That fallback is worse than the guess it protects: it is correct exactly while nothing else sets a readable cookie, and on the day something does, every mutation carries the wrong value and earns a 403 that says nothing about why. The recommendation the escalation carried, moving both names into `app/src/shared`, is declined. That directory is the contract as code, the section 7 schemas and types both sides import, and a transport detail of this section is not part of that contract; naming them here lets each side transcribe one specified constant, which is the discipline the acceptance suite already runs on for section 9's copy, restating rather than importing so that neither side takes its definition of correct from the other. Removing the fallback is a client return this change control routes. The third cookie, the short-lived pending-authorization pointer, is deliberately not named: nothing outside the auth module reads it.

### 11.7 Reminder scheduler

The 8.6 delivery loop runs in-process: a 60-second interval in the server, guarded against overlapping passes, executing the poll-classify-send-mark cycle in a transaction that claims due rows with SELECT ... FOR UPDATE SKIP LOCKED. Consequences, each intended:

- A missed tick self-heals: the poll is over fire_at <= now(), so the next pass picks up anything a missed one would have sent, inside the 6-hour stale window.
- The deploy overlap window can run two instances for about ninety seconds; SKIP LOCKED makes concurrent ticks contend safely instead of double-sending. A crash between send and mark can duplicate at most one batch; 8.6 accepts duplicates.
- Tick liveness is monitored separately from process liveness (11.12), because a dead interval inside a live server is invisible to an uptime check.
- The same pass prunes expired session rows, so 8.6's statement that the reminder loop is the only background execution stays true: one scheduled process, two duties.

The pass is a plain callable function and must stay one: if hosting ever moves somewhere without an always-on process, the replacement is an external per-minute trigger (Google Cloud Scheduler or equivalent) hitting an authenticated endpoint that runs one pass.

That callable is the acceptance suite's only way in, ratified here at the P7 mid-package change control on 2026-08-10 rather than left assumed, the way 11.10 ratified options.notifications when the same need appeared for sends. Everything else the suite reaches, it reaches over HTTP through the 11.10 seam, and frozen section 7 offers no endpoint that runs a pass, so without this the delivery criteria could not be written at all. `app/src/server/scheduler/index.ts` exports the pass as `createReminderPass(deps)` or as `runReminderPass(deps)`, either name, with deps of { dbClient, notifications } reusing 11.10's own option names for the same two things. The tolerance over the name is deliberate and costs nothing: the harness accepts both, so the choice is the implementing session's and no drift is possible in the suite. What is fixed is only what the suite must know in advance, the module path and the two dependencies, both already determined by 11.10 and by the scheduler directory this section's implementer owns; the pass's internals, its transaction shape and its return value are untouched by this and stay that session's. Two things it is not. It is not an HTTP endpoint, adding one being a change to frozen section 7 that the paragraph above contemplates only if hosting moves. And it is not a second export path for production, which composes the same callable at boot as it always did.

### 11.8 Email

Resend, one provider for the three templates (invite, share grant, reminder), behind a notification module that logs instead of sending in development and tests; the 11.10 construction seam's options.notifications sink, when injected, replaces that logging so the acceptance suite can observe sends. The 10.7 deliverability checklist applies unchanged. The free tier (3,000 emails per month, 100 per day, as of 2026-07) covers v1; the daily cap is the number to watch if reminder volume grows.

### 11.9 Recurrence and time

- The 4.11 RRULE subset is implemented by an in-repo iterator module, not a runtime library. Reason, recorded: rrule.js is unmaintained (last publish about three years ago) and models results as reinterpreted UTC Dates, which collides with Dana's floating dates. The iterator is differential-tested against rrule 2.8.1 as a development-only oracle; where they disagree, RFC 5545 adjudicates, never the oracle.
- UNTIL is written in RFC 5545's DATE form, YYYYMMDD, and a rule string spelling it any other way is outside the 4.11 subset and answers 422 like any other free-form input. This is a reading of frozen 4.11 rather than a change to it, recorded at the P6 mid-package change control on 2026-08-10 because the grammar module and the acceptance suite would otherwise each derive it and could derive it differently. 4.11 defines the column as an RFC 5545 RRULE value string and calls UNTIL "a date, inclusive per RFC 5545"; within an RRULE that value is a DATE or DATE-TIME, and the DATE form carries no separators. The extended spelling 2026-07-27 is therefore not a valid value string of the RFC that 4.11 names, so admitting it would widen the frozen text rather than read it, and 4.11's own rule that only strings the preset builder can produce are valid independently forecloses accepting both spellings, since a builder emits one. The conventions line of `00-index.md` governs the dates this specification writes and the dates its wire fields carry, both of which stay extended, and both spellings are ISO 8601 in any case; the interior of a value string another standard defines is that standard's. rrule 2.8.1, the oracle above, parses the basic form, so nothing translates between our string and the oracle's, which is where a divergence the oracle exists to reveal would hide.
- Luxon 3 performs all IANA timezone math. Both DST rules of 8.6 are implemented explicitly in the fire-instant module because Luxon guarantees neither: for a nonexistent local time Luxon advances by the gap length (02:30 becomes 03:30) where 8.6 requires the first valid instant after the gap (03:00), so the module detects the gap and clamps; for an ambiguous local time Luxon's documentation declares the choice undefined, so the module selects the earlier instant itself. AC-144 and AC-145 pin the two rules, one each and by name against the raw behaviors above; AC-083 to AC-086 pin the zone arithmetic they sit on. Until the P7 mid-package change control of 2026-08-10 this sentence named only the second group and claimed it pinned both, which is the over-claim section 13 item 25 recorded at the P7 kickoff and which the amendment numbering AC-144 and AC-145 closed.

### 11.10 Testing infrastructure

- Vitest 4 runs unit and acceptance tests. The acceptance suite exercises section 7 over HTTP against the real Express app in-process.
- The suite reaches that application through one construction seam: createApp(options?) in app/src/server/index.ts, Platform's file. It is synchronous, performs no I/O, and opens no database. options.dbClient injects the app/db/client.ts handle, the only way a test's in-memory PGlite database can arrive; the boot path always passes its own. options.auth injects { issuerUrl, clientId, clientSecret, appOrigin, allowInsecureRequests } and wins over the environment variables that remain the production path (GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_ISSUER_URL, APP_ORIGIN, OIDC_ALLOW_INSECURE); the issuer is injectable because a module that hardcodes accounts.google.com cannot be tested at all. options.notifications injects a sink { send(message) }: when present, the 11.8 notification module delivers each outbound message to it instead of logging, which is what makes a send observable under test at all, since 11.8 forbids real sending there and 10.5 keeps recipient addresses out of the logs. Each delivered message identifies its template and its recipient; the remaining keys are the module's own. Absent the sink, 11.8 stands unchanged: log in development and tests, send in production. Routes that touch the database require options.dbClient and fail only when called without it, which lets database-free surfaces (health, route-presence probes) construct the application bare.
- The database under test is selected by one seam in `app/db/client.ts`: PGlite (embedded Postgres 18, in-process, no Docker, runs on Windows) by default, or any real Postgres via TEST_DATABASE_URL. The variable is scoped to test and database-script processes: a server entrypoint passes its connection string explicitly (DATABASE_URL) and clears TEST_DATABASE_URL from its environment before opening the seam. CI runs the full suite both ways: PGlite for parity with local runs, and a real Postgres 18 server as the second leg. That leg's vehicle belongs to the runner rather than to this sentence: a postgres:18 service container on a GitHub-hosted runner, and the runner host's own Postgres 18 cluster on a self-hosted one (11.11). What the leg is an authority for is the engine rather than the operating system around it: a real client and server across a socket, a pool holding several sessions so that a second concurrent transaction is expressible where 11.15 records PGlite cannot hold one, the real planner, and the packaged pg_trgm rather than the contrib build. It was called the production-fidelity authority until 2026-08-11, and that name over-claimed in exactly one place, which the bullet below fixes. PGlite's pg_trgm ships in its main package (contrib import). PGlite is alpha-badged; the named fallback behind the same seam is the embedded-postgres npm package (real Postgres binaries, Windows x64, no Docker or admin rights).
- **The text ordering the suite runs on is fixed by the test database's own locale, never inherited from whatever cluster hosts it.** Ruled 2026-08-11 at the local-CI change control. Section 6's preamble asks its orderings to make any two agents produce byte-identical result sequences, and neither the migrations nor the query modules write COLLATE, so every ordering over a text column takes the database default: 7.4 and Q2 over lower(folder name), and 7.3's roster over display_name, which is not case-folded. The second leg's database is therefore created explicitly, and this statement is its normative form:

  ```sql
  CREATE DATABASE dana_test OWNER dana_ci TEMPLATE template0 ENCODING 'UTF8'
    LOCALE_PROVIDER builtin BUILTIN_LOCALE 'C.UTF-8' LC_COLLATE 'C' LC_CTYPE 'C';

  ALTER DATABASE dana_test SET lc_messages = 'C';
  ```

  **Both statements are normative, and the second was learned the hard way.** Amended 2026-08-11 at the local-CI merge review, after the first execution of this leg turned it up. The locale a database is created with fixes how it sorts and folds text; it does not fix the language the server writes its error messages in, which is the separate lc_messages GUC, inherited from the cluster and superuser-context so a database owner cannot set it. On the machine this leg first ran on that cluster is French, and one acceptance assertion reads the server's own message prose rather than an identifier: AC-001's adversarial NOT NULL case asserts that the rejection contains `null value in column "folder_id"`, deliberately, because the bare column name also appears in the statement it sent and a fragment satisfiable by the statement text would prove nothing. It was the only one of the suite's nine such assertions to fail, the other eight naming constraints and indexes, which appear verbatim in a translated message. The second statement therefore belongs beside the first: a test database whose locale is pinned in one dimension and inherited in another is pinned in neither, and a rebuild of `dana_test` that omits this line reintroduces exactly the red it was written to close.

  Postgres 18's builtin provider is the only one Postgres itself guarantees identical on every platform and every version, being code point order over Postgres's own Unicode tables rather than an operating system's collation library, and it is already what PGlite does. Measured on 2026-08-11 against the installed PGlite (server 18.3): its database reports LC_COLLATE C with a UTF-8 ctype, its default ordering is byte-identical to the builtin pg_c_utf8 collation over a probe carrying case, accents, punctuation and digits, and its case mapping is full Unicode, which the builtin C.UTF-8 locale also provides, so Q8's ILIKE and its trigram search fold the same way on both legs. Pinning the second leg the same way means a disagreement between the two legs can only be an engine difference, which is the only thing that leg exists to find. It also puts the database under the same ordering as the acceptance suite's own oracle, JavaScript's < over strings being UTF-16 code unit order, which is what AC-069 sorts with to assert 7.3's roster order; under a linguistic collation that criterion agreed with the database only for as long as its fixture avoided case, accent and punctuation differences.

  Verify rather than assume. Three checks, all runnable with TEST_DATABASE_URL set:

  ```sql
  SELECT datlocprovider, datlocale, pg_encoding_to_char(encoding)
    FROM pg_database WHERE datname = current_database();  -- must answer b, C.UTF-8, UTF8

  SELECT string_agg(v, '|' ORDER BY v) FROM (VALUES
    ('Zebra'),('apple'),('Apple'),('a-b'),('ab'),('coté'),('côte'),('_x')) AS s(v);
  -- must answer Apple|Zebra|_x|a-b|ab|apple|coté|côte, on this leg and on PGlite alike

  SHOW lc_messages;  -- must answer C, never a language name
  ```

  What the ruling gives up is section 13 item 29: no leg any longer runs a linguistic collation, so the ordering a production Render Postgres serves is checked by nothing. It was checked by nothing before either, PGlite having been LC_COLLATE C since P0 while the container leg was glibc en_US.utf8 by the image's own LANG, which is proof that no criterion could ever have distinguished the two and stayed green on both.
- The AC-001 constraint catalog test asserts structured facts from pg_constraint and pg_index (constraint type, columns, on-delete targets, partial predicates, names), never deparsed SQL text, so the same test passes on every Postgres the suite runs against.
- Playwright drives end-to-end tests on Windows and in CI, using the seed dataset and the development login endpoint for sessions.

### 11.11 Hosting and delivery

- Render: one Starter web service plus one Render Postgres instance (cheapest paid tier), same region, deployed from GitHub on push to main. Production is exactly one instance (11.1). Combined cost as of 2026-07: about 13 to 14 USD per month.
- Render Postgres is paid from day one because the free tier expires after 30 days and has no recovery capability. The paid tier's point-in-time recovery (3-day window on the Hobby workspace) is the primary backup. The runbook's quarterly drill restores into a scratch instance, runs the constraint catalog test against it, and destroys it; a monthly pg_dump kept off-platform guards against account-level failure.
- CI is GitHub Actions: npm ci, lint, typecheck, test on PGlite, test on a real Postgres 18, build, Playwright. Seven steps in that order. The set and the order are normative and move only by amendment here; where the job runs, and where its Postgres comes from, are job configuration rather than steps and move without touching either, exactly as the service container always was configuration rather than a step. Two forms are admitted, the second ruled 2026-08-11 after hosted runs stopped starting on an account billing failure and the owner chose not to buy hosted minutes: a GitHub-hosted runner with a postgres:18 service container, and a self-hosted runner with the host machine's own Postgres 18 cluster, whose test database 11.10 fixes. A self-hosted runner is still GitHub Actions, the workflow, the triggering events, the checks and the run history being unchanged and only the executing machine moving, so the opening clause of this bullet is unamended. Three consequences are load-bearing. A self-hosted runner executes whatever a workflow on any pushed branch tells it to, on a machine holding the owner's own data, which is acceptable exactly while this repository is private and every writer is the owner or a session he runs; making it public, or admitting an outside collaborator, revokes that and is the revisit trigger. CI then exists only while that machine is powered and the runner service is up, and a job queued against an absent runner waits rather than failing, so a pushed branch has no verdict until the machine is available: a cost the release ritual pays, not a defect to debug. And on the self-hosted form the Playwright step may drop `--with-deps`, which installs Linux system packages and has nothing to do on Windows; the step itself does not move.
- Merges to main require green CI. This project enforces that through the Integration Steward rather than through a protected branch: checked 2026-08-11, the repository is private on a plan that offers neither branch protection nor rulesets, so the rule has always been the protocol's rather than the platform's, and a red or absent CI run blocks a merge because the definition of done says so.
- Environments: production and local only, no standing staging. The release ritual is CI green, deploy, then the production smoke subset (health, auth round trip, one CRUD cycle). A throwaway Render service restored from point-in-time recovery substitutes for staging when a release warrants a rehearsal.
- Secrets: Render environment variables in production, GitHub Actions secrets for anything a hosted runner must reach, a gitignored .env locally, and an `.env.example` naming every variable. One rule is stated positively because its violation is silent: a credential for a resource GitHub cannot reach is never stored at GitHub. The self-hosted runner's TEST_DATABASE_URL is the first of these and lives in the runner installation's own `.env` file, outside the repository and outside every working tree, which the runner reads into each job's environment. A repository secret was rejected for it, and the reasoning is worth keeping because it inverts the usual answer: every workflow on every branch can read a repository secret, workflow files are code the sessions of this build edit and push, and the string describes a database on the owner's own machine that GitHub has no route to, so storing it there widens exposure and buys nothing. A machine-wide environment variable was rejected for the same plaintext at a wider blast radius, every process on the machine rather than the runner's jobs, and a service restart to rotate. The role that string authenticates is never the superuser: a dedicated `dana_ci` login role with CREATEDB owns `dana_test`, which is all the migrations need, pg_trgm having been a trusted extension since Postgres 13 and so installable by a database owner. The workflow never echoes the variable, and anything that must print it masks it first.

### 11.12 Observability

- Sentry (free tier) receives server and client errors; AC-104 proves the wiring.
- Better Stack (free tier): an uptime monitor on /api/health, and a heartbeat the scheduler pass pings after each successful cycle; heartbeat silence beyond 10 minutes alerts. /api/health also reports seconds since the last completed pass.
- Logs go to stdout. Render retains them 7 days on the Hobby workspace, which does not meet 10.5's 30-day retention, so a workspace log stream must drain them to an external store holding at least 30 days. The store is chosen at P9 (candidates to verify at that point: Axiom, Better Stack Logs); any syslog-compatible store satisfying 10.5 may substitute without amending this section.

### 11.13 Design artifacts

The design contract between the designer and implementing agents is repo-committed, matching the protocol rule that state lives in artifacts. Figma is the designer's private workshop; nothing builds against it directly. Section 9 always wins over any design artifact on structure and copy: an artifact implying a different page structure, a different control or different wording is an escalation to the Integration Steward and never an edit.

It binds the design, not this specification. A `DES` record reaches Dana only by being read into a numbered section, and until it is, it is evidence rather than a rule |
| `screen-registry.csv` | Twenty-eight rows, one per required v1 surface, each mapping the surface to its spec sections, acceptance criteria, required subcomponents, required interactions, normative copy references, states and status | The surface inventory and the cross-reference. It is the first file an implementing session should open, being the only artifact that maps a screen to the criteria that assert it and to the copy that is normative on it |
| `prototype/` | Seventy files: a running React 19, Vite 8 and Tailwind 4 application with twenty shadcn components under `src/components/ui/`, thirteen screens including `states-page.tsx` and `shell-page.tsx`, `fixtures.ts`, and `src/styles/tokens.css` with `src/styles/app.css` | Appearance. It is the visual source the client is ported from, and it is the review artifact, being interactive where a still was not. Its `states-page.tsx` stacks every task-row state on one surface and is the reference for row states specifically |
| `visual_foundation/` | The rendering foundation board, `Dana Visual Foundation.dc.html` in eight numbered sections, plus the two mark assets | The token values themselves. Section 08 is a complete token table its author wrote for `app/src/client/styles/tokens.css` specifically, and it is the origin both token files below were transcribed from |
| `notes.md` | The designer's implementation, behaviour and QA notes | Behaviour the prototype implies and a value list could not carry |

**Two files now carry token values, and neither is a copy of the other.** `app/src/client/styles/tokens.css` is the single tokens file of 11.4 and that rule does not move: it is the only place in the application where a raw colour, type size, spacing step or radius may be written, and it was transcribed from section 08 of the foundation board at 34c0b29. `docs/design/prototype/src/styles/tokens.css` was transcribed from the same board by the designer, into a different vocabulary and for a different consumer. Checked value by value at this kickoff, the two agree on every primitive they share, the graphite ramp, the cobalt accent, the four semantic families, the ten folder swatches, the radii and the two elevations, and they differ in three ways that are vocabulary rather than disagreement: the spacing scale is spelled `--spacing-N` in ours and `--space-N` in his, the icon stroke is `--icon-stroke` in ours and `--icon-stroke-width` in his, and his file adds a shadcn role layer (`--background`, `--primary`, `--sidebar` and their kin) that ours has no equivalent for because ours is consumed by named component classes rather than by utility strings. So the ordering is: the board adjudicates a value, our file is where that value lives in the application, and his file is read for the two things the board never carried.

Those two things are why his token file is named here at all rather than dismissed as a duplicate. It carries the **layout dimensions** the board has no section for, `--shell-sidebar-width: 256px`, `--shell-content-max: 1120px`, `--control-height: 40px`, `--task-row-height: 44px` and their neighbours, recorded there as the Session 4 approved desktop shell; and it carries the **role mapping** that says which primitive plays which part. The absence of the first set from our file is not a detail, it is the direct cause of what P8 shipped: a client whose tokens file described every colour correctly and never said how wide the sidebar is.

Two known-stale pointers inside the designer's own files, recorded here rather than corrected, because agents read that directory and never write it. `prototype/README.md` directs a reader to `docs/design/screens/`, deleted at 552d4a5, and calls `prototype/src/styles/tokens.css` the authoritative visual tokens, which is true of the values and not of the file, 11.4 naming ours. And `prototype/src/styles/app.css` sets `min-width: 1180px` on both `html` and `body`, which is a decision about the prototype's own delivery scope and is not normative on Dana; it must not be ported, and the reason is in section 13 item 32.

### 11.15 Known hazards for implementers

Facts agents get wrong because training data lags the installed versions. Read before touching the area; when in doubt, open the installed package's documentation, not memory.

- FullCalendar 7 imports standard plugins from @fullcalendar/react subpath entrypoints; the standalone @fullcalendar/daygrid package is v6-only.
- Tailwind 4 is configured in CSS (@theme in tokens.css) through @tailwindcss/vite; there is no tailwind.config.js, and v3 configuration idioms are defects.
- React Router runs in library mode; importing loader, action, or framework-mode APIs is a defect.
- zod is v4; check its breaking changes against v3 idioms before writing schemas.
- Luxon's raw DST gap and ambiguity behavior must never be used directly for fire instants (11.9).
- Express 5 handles rejected promises in handlers natively; async wrapper hacks from Express 4 tutorials are noise.
- PGlite is real Postgres but single-connection; tests must not assume parallel connections against one instance. What that costs is narrower than the sentence reads, measured at the P3 merge review after three sessions and a package fix had been routed on the wider inference. One connection serializes statements, not handler logic: two requests in flight interleave their awaits, so a read-then-write race is fully expressible on the default backend, and two concurrent step adds against a task holding 49 steps do leave 51 where the count and the insert are not one decision. What genuinely needs a second connection is a second concurrent transaction. That is what a test must not assume here, rather than concurrency itself.
- tsc compiles and emits a tsconfig-excluded file whenever any resolvable import references it, literal dynamic import() included. The dev-login exclusion of 11.6 therefore holds only when the loader uses a computed import specifier and treats the load failure in a production build as the route not existing (404).
- Intl.DateTimeFormat as an IANA oracle is tolerant beyond the tzdb: it accepts ECMA-402 offset identifiers (+05:30) that are not IANA names and would break the 11.9 zone math, and it matches names case-insensitively. Every IANA validation goes through the shared validator (app/src/shared/timezone.ts), whose sign guard closes the offset hole; an independent re-check, such as the acceptance harness's, must refuse leading signs the same way.
