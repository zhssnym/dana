## 13. Open questions and assumptions

Every unresolved external fact and every assumption this spec rests on, each with what changes if it is wrong. Nothing else in the document is knowingly uncertain.

1. **Google email claim for dotted Gmail variants.** Unverified whether the OpenID email claim returns the address exactly as registered. The matching rule (lowercase equality) and its mitigation (visible pending invites with cancel and resend) hold either way; if variants prove common, add gmail.com dot-normalization behind a feature flag in v1.1.
2. **Google account deletion policy text.** The mechanism of 8.10 is required regardless; verify the current policy wording during launch review to confirm nothing extra (such as a data export) is mandated.
3. **Hosting cron frequency tiers. Resolved 2026-07-29.** Verified: Vercel Hobby cron is limited to daily frequency with hourly precision, and per-minute schedules require the Pro plan. Moot for v1: the scheduler runs in-process on an always-on host (11.7) and the 8.6 contract is unchanged. The facts are recorded so the rejection in 11.14 stays checkable.
4. **rrule library conformance. Resolved by construction, 2026-07-29.** The 4.11 subset is implemented by an in-repo iterator (11.9); rrule 2.8.1 serves only as a development-time differential oracle. UNTIL inclusivity is therefore our own code, pinned by AC-071 to AC-078; a disagreement with the oracle is adjudicated against RFC 5545, never absorbed silently.
5. **iOS PWA push constraints.** Irrelevant to v1 (email only); verify before scheduling push for v1.1.
6. **Scale assumption behind caps.** Open lists cap at 1000 rows instead of paginating, assuming personal-scale data. If real accounts approach the cap, add keyset cursors to the view endpoints; the change is isolated to section 7.10 responses.
7. **Single reminder per task.** Assumed sufficient (the source design always spoke of one). If multiple are demanded, reminders gets its own id key and PUT becomes POST plus DELETE; fire logic is unchanged per row.
8. **Silent timezone auto-sync.** Assumed acceptable that travel moves today and reminder instants. If travelers complain, add a per-user timezone lock toggle; one column, one guard in the sync.
9. **Verified email presence.** Assumed every allowed Google sign-in supplies a verified email (unverified ones are rejected outright). If Workspace edge cases surface, the rejection page is the containment.
10. **Floating due_time across timezones.** Accepted that a shared 15:00 reads as each member's local 15:00. If cross-timezone coordination becomes a real use case, a per-task timezone column is the v2 change; storage stays floating.
11. **Postgres 15 or later. Resolved 2026-07-29: Postgres 18 everywhere.** Production and CI pin Postgres 18 (the host's current default for new databases), matching the embedded engine local tests run on (PGlite). Section 4's reference dialect remains Postgres 16 and nothing in the schema requires more than 15, so the column-targeted ON DELETE SET NULL form of 4.5 is safe on every engine in use.
12. **Invite non-expiry.** Assumed safe because acceptance is login-gated with no secret in the link. Revisit trigger: any report of confusing stale grants; the change is a status sweep job plus an expires display, no schema change.
13. **UNTIL-only recurrence ends.** COUNT stays unsupported. If demanded, it requires a durable occurrence ordinal on the series; that is a schema addition, deliberately deferred.
14. **Landing copy. Closed 2026-08-12 at the P8 merge review.** Final wording was the designer's and the human owner wrote it himself on 2026-08-11 instead, which is his to do: the constraint this item recorded was never who held the pen but section 9.2's no-AI-claim rule, and the copy that landed carries it. RFC 0001 already read this item as closing when P8 landed the page, so what was outstanding was the record rather than the decision. AC-159 asserts the page, the no-AI claim included, so the rule this item existed to protect is now pinned by number rather than by anyone remembering it. **Closed a third time 2026-08-24, at S13.** The section this item protects has stopped carrying the copy at all: on the owner's ruling of that date, 9.2 states the rules copy is written under and the design record holds the sentences, so the no-AI rule this item recorded is now one named instance of a broader rule that section states, that the page claims no capability Dana does not ship. What moved is where the sentences live, which was never what was outstanding here; AC-159 asserts the rule either way, and it does so without depending on a copy table that no longer exists.
15. **YEARLY recurrence anchored on 29 February.** 4.11 restricts BYMONTHDAY for MONTHLY only, so a yearly rule anchored on a 29 February due date is legal input, and the spec is silent on its semantics. The iterator implements RFC 5545 behavior: instances occur only in leap years. Recorded here as an assumption; folding one sentence into 4.11 is a frozen-section amendment to make at the next authorized change to section 4's text. If leap-year-only proves surprising to users, the alternative (28 February in common years) is an iterator change plus an update to this item, with no schema change. The same existence check produces the short-month skip recorded as item 22, which is this decision's monthly sibling and reached the specification the same way; the one-sentence amendment to 4.11 that this item is waiting for should carry both.
16. **Drizzle migrator transaction scope and locking. Recorded 2026-07-31.** Verified in the installed drizzle-orm source at the P0 merge: the programmatic migrator wraps each run, not each file, in one transaction, so all pending files commit or roll back together, strictly stronger than per-file atomicity, and 11.5 records it. The migrator also takes no lock while applying, safe exactly while production is one instance with serial deploys; 11.1's second-instance checklist names the consequence. The acceptance harness serializes its own parallel-worker migrations under an advisory lock for the shared-database case. Revisit trigger: any drizzle-orm upgrade re-verifies both facts in the installed source.
17. **openid-client leaves code-flow ID token signatures unverified by default. Recorded 2026-08-03.** openid-client 6 takes OIDC Core 3.1.3.7 item 6's permission to rely on the token endpoint's TLS channel instead of verifying the ID token's signature in the authorization code flow. The acceptance criteria forbid that reliance (a rogue-key token must be refused), so `app/src/server/auth/oidc.ts` switches on enableNonRepudiationChecks, verified both ways against the installed version: without it a rogue-key token established a session, with it the token is refused. Revisit trigger: any openid-client upgrade re-verifies in the installed source that the switch exists and still forces signature verification, and that the default has not moved.
18. **Drizzle statement errors embed bound parameters. Recorded 2026-08-03.** DrizzleQueryError's message embeds the failed statement's SQL and its bound parameters, and Error.stack opens with that message, so logging a database error's stack or message verbatim leaks row content against 10.5; proven with an invite email address during the P1 wiring pass. The boot file's 5xx handler strips the wrapper's message and keeps its frames, and the P0 test harness already skips the wrapper in rejection matching for the same reason. Revisit trigger: any drizzle-orm upgrade re-verifies the wrapper's message shape, alongside item 16's checks.
19. **Email collision across google_sub. Parked 2026-08-03 by the human owner.** A sign-in whose google_sub is new but whose email already belongs to an active account trips users_email_active_idx; the callback refuses cleanly, and no account is linked, merged, or replaced (verified live when the P1 shape review's own helper tripped the path). Which account should win is a product decision deliberately deferred until evidence arrives. Item 1, the Gmail dotted-variant claim, is the same question from another angle, and the two resolve together. Revisit trigger: any real-user report of a refused sign-in on an email that already has an account.
20. **The folder list is deliberately uncapped. Recorded 2026-08-04 at the P2 merge.** Section 6 enumerates the lists the 1000-row cap of 10.3 covers, and GET /folders is not among them, while nothing in the frozen text bounds how many folders a user may be a member of. The absence is deliberate and rests on a social bound rather than a numeric one: owned folders stop at 10.3's 200-custom cap, and every further membership requires a mutual roster connection plus a manual add into a folder holding at most 25 members. If the bound fails, the change is a cap or cursor isolated to the 7.4 list response, the same shape item 6 records for the view lists; nothing else moves. Revisit trigger: any real account's folder list approaching the row count the capped lists stop at.
21. **Q4's Important page has no index of its own, and that is adequate for v1. Recorded 2026-08-07 at the P4 change control.** 4.12 names an index for every query of section 6 except Q4: there is none on `tasks.important`. The P4 row gave the Query engineer two doors, justify the omission on its EXPLAIN record or route a request to `01-data-and-invariants.md` with the query that earns a new index, and it took the first. The record measures the plan against real Postgres 18 rather than reasoning about it: the star is applied as a filter, over a sequential scan by choice and over the same skip-scanned `tasks_folder_status_due_idx` with the sequential option removed. The justification is the scale rather than the plan. The rows this page reads are already bounded by the accessible-folder scope and the two open statuses, and the response is capped at 1000, so a partial index on (important) WHERE important would start to pay only once one account held tens of thousands of open starred rows, and it would cost a write on every star. This is an accepted bet of the same kind as item 6, not a defect: the omission is 4.12's, deliberate or not, and this records what it costs. Revisit trigger: any real account whose Important page reads slowly, or any measurement showing the filter dominating that query's plan at a row count a v1 account can reach. The change is one migration adding the partial index; no query text moves, because the planner picks it up or does not.
22. **A bare FREQ=MONTHLY anchored on the 29th, 30th or 31st skips the months too short to hold it. Recorded 2026-08-10 at the P6 merge review, escalated by the engine session.** 4.11 excludes BYMONTHDAY 29 to 31 precisely to avoid RFC 5545's skip semantics, but the exclusion reaches rule parts and not anchors: DTSTART is never stored in the string, so the day of the month comes from due_date, and a task due the 31st carrying a bare FREQ=MONTHLY is legal input the subset never refuses and the specification never describes. The iterator implements RFC 5545 behavior, which is item 15's choice one frequency down and falls out of the same existence check: an instance occurs only in months that hold the anchor's day, so a task due 31 January next falls due 31 March, with February skipped rather than clamped to the 28th and April skipped rather than clamped to the 30th. It is pinned by the iterator's unit tests and agrees with the rrule 2.8.1 oracle of 11.9. It is recorded here rather than folded into 4.11 for item 15's reason: that is a frozen section, and this is the second sentence the same authorized amendment should carry when one is next made. If skipping proves surprising, the alternative is clamping to the month's last day, an iterator change with no schema change and no effect on stored rows, plus an update to this item. Revisit trigger: any report that a monthly repeat anchored on a long month's last day went missing for a month or two.
23. **The calendar response is bounded by its 62 days and by nothing else, and ghosts multiply that bound rather than adding to it. Recorded 2026-08-10 at the P6 merge review, disclosed by the endpoint shape review.** 7.10 gives GET /views/planned/calendar neither the 1000-row cap nor the truncated flag every capped body carries, which is the P4 reading of section 6's cap rule: that rule enumerates the pages it covers and the calendar is not among them. Real rows are bounded by the range, but the virtual array holds up to one instance per day per series, so its ceiling is 62 elements multiplied by the number of accessible pending rule-carrying tasks rather than added to the real rows. While the array answered empty, which it did from P4 until this package, the bound was the real rows alone; it is real from P6. Nothing in 10.3 is violated and no implementation defect is implied, the response being exactly what Q3C and 8.5 specify. What makes this a bet rather than a gap is scale, the shape item 6 records: a personal account viewing one month carries a handful of series and a few dozen ghosts. It is recorded rather than fixed because no shape can report a truncation the frozen body has no key for, so bounding it is an amendment to 7.10 and to section 6's cap list; the human owner ruled on 2026-08-10 to record the bet and make that amendment only if evidence arrives. Revisit trigger: any real account whose calendar response size or render time is noticed, or any month view where ghosts visibly dominate the real rows.
24. **Q3C's projection statement reads a rule-carrying predicate for which 4.12 names no index, and that is adequate for v1. Recorded 2026-08-10 at the P6 merge review.** The calendar is the one endpoint of section 6 issuing two statements, because the rows 8.5 projects from are not the rows the calendar draws: Q3C scopes ghosts by accessible, pending and rule-carrying and by nothing else, so a series whose current occurrence precedes the requested range still projects into it, which AC-143 pins. The justification is the scale rather than the plan: the fetch is already bounded by the accessible-folder scope and one status, and a partial index on (recurrence_rule) WHERE recurrence_rule IS NOT NULL would begin to pay only once an account held tens of thousands of open series, while costing a write on every task that gains or loses a rule. Revisit trigger: any real account whose calendar reads slowly, or any measurement showing this filter dominating the statement's plan at a row count a v1 account can reach. 25. **The two DST rules of 8.6 have no oracle, by construction, and the acceptance criteria are their only independent check. Ruled 2026-08-10 at the P7 kickoff.** Item 4 records the strategy that covered the hardest arithmetic of P6, an in-repo iterator differential-tested against rrule 2.8.1, and it does not carry over, which is recorded here so a later reader does not assume it did. An oracle adjudicates where two implementations of one standard should agree, and 8.6's two rules are not tzdb arithmetic: a nonexistent local time has no correct answer and an ambiguous one has two, so both rules are Dana policy chosen where the standard is silent, and no library implements them. Luxon is worse than absent here, it is an anti-oracle for exactly these two cases per 11.9, advancing by the gap length where 8.6 requires the first valid instant after it and leaving the fold undefined where 8.6 requires the earlier instant. A second date library was considered and rejected: it would agree with Luxon on the offsets, disagree with the module on the policy, and re-report what 11.9 already records, at the cost of a dependency; and the cheapest candidate is foreclosed by 11.15, Intl.DateTimeFormat being Luxon's own engine rather than an independent one, so that comparison would be circular. What is owed instead is the anti-oracle assertion, in the fire-instant module's own unit tests per protocol section 8: raw Luxon and the module are asserted in the same test to differ in each of the two named ways, so the override is proven necessary rather than assumed, on the shape of items 16, 17 and 18. Fixtures on both sides use historical transition dates in zones whose rules have been stable for decades, never a future date and never a zone that recently changed its rules, because the Node runtime and the embedded engine of 11.10 carry tzdb copies that move independently under a CI runner. Revisit trigger: any Luxon upgrade re-verifies both anti-oracle assertions in the installed version, since a raw behavior that moved toward 8.6 would make the clamp redundant and one that moved away could make it wrong, and either would be silent. If a future release ever guarantees both rules, the module's override becomes deletable and this item records why it existed. **The coverage half of this item is closed, 2026-08-10 at the P7 mid-package change control.** This item was written because the acceptance criteria are the only independent check on these two rules and no criterion instantiated either, 11.9 having claimed AC-083 to AC-086 pinned both. The tester session split the problem the way the kickoff expected: those four keep the zone arithmetic, where a conversion has one right answer, and the two policy rules take AC-144 and AC-145, each asserting the module against the raw Luxon behavior by name so the override is proven on the acceptance side as well as in the unit tests. 11.9's closing sentence names them. Everything else in this item stands unchanged and is not closed by it: the anti-oracle unit tests, the fixture rule, and the Luxon-upgrade revisit trigger are standing obligations, and the reason no oracle exists has not altered.

29. **No CI leg runs a linguistic collation, so the text ordering production actually serves is checked by nothing. Recorded 2026-08-11 at the local-CI change control.** Section 6 fixes exact orderings over text columns, 4.12 names no collation on any index, and no query writes COLLATE, so every one of them takes the database default. Three defaults have been in play and only two are ours: PGlite has been LC_COLLATE C since P0, the postgres:18 container was glibc en_US.utf8 by the image's own LANG, and a production Render Postgres is glibc en_US.UTF-8 unless something says otherwise. 11.10 now pins both test legs to the builtin C.UTF-8 locale, which makes them agree with each other and with the acceptance suite's own JavaScript oracle, and leaves production the odd one out. Two things make this a recorded bet rather than a regression introduced here. It is not new: the suite has been green on C and on en_US.utf8 at the same time since P0, which is proof that no criterion can distinguish them, so the container leg was never in fact exercising the production collation either, and the phrase 11.10 used for it was the over-claim rather than the coverage. And the exposure is narrow. 7.4 and Q2 sort folders by lower(name), where case is already folded and the remaining difference needs an accent or a punctuation mark inside a folder name; 7.3's roster sorts display_name without folding, so under C every display name beginning with an uppercase letter sorts before every lowercase one and under glibc it does not, which is visible on a roster mixing capitalisations. Closing it, if it must close, is one of three and the choice is the human owner's: accept it, create the production database with the same builtin C.UTF-8 locale so all three agree, or write the collation into the orderings themselves, which amends frozen section 7 as well as section 6 and is therefore the most expensive by a wide margin. Revisit trigger: any report that a connections list reads in the wrong order, or any release that moves production off its host's default locale.

32. **Whether Dana v1 owes a mobile layout is a product question the specification never asked, so it was packaged for the human owner rather than ruled, and he has answered it.
