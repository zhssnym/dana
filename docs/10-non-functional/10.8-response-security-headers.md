### 10.8 Response security headers

Every response carries a Content-Security-Policy, a `Reporting-Endpoints` header naming
where refusals are reported, and `Referrer-Policy: strict-origin-when-cross-origin`. The
headers are `securityHeaders` in `createApp` (`app/src/server/index.ts`), set ahead of every
handler so refusals and errors carry them too; the canonical-host redirect of 11.11 is the
one response in front of them, carrying no document. HSTS is the edge's, set by the host in
front of the process, never by the process itself. The 7.15 serving rules keep their own
stricter per-file headers (nosniff on everything served, attachment for kind file) and this
section does not relax them.

**The policy is sized to what the client actually loads and no wider.** Its base is
`default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'` and `base-uri 'self'`;
every source admitted beyond `'self'` must answer something the product does, and the
comment above `securityHeaders` gives each one its reason. The rules that decide what may
be added:

- **Scripts are `'self'` plus the hash of the one inline theme script in `app/index.html`**
  (9.7's pre-paint theme). Never `'unsafe-inline'`: widening the directive that decides
  whether an injected script runs is not a trade to make for anything. Not a nonce either,
  because the process serves `index.html` as a static file and has no render step to put one
  in. **`blob:` and `data:` never enter `script-src`**, where they would let a script be
  assembled at runtime from a URL no policy can pin.
- **`blob:` and `data:` are admitted only where they fetch bytes the document already
  holds**: images (build-inlined assets, crop previews, in-flight attachment previews), media
  (a just-recorded voice note), and `connect-src data:` (the crop rebuilding a File through
  `fetch()`). They reach no network and name no origin.
- **A third-party host is admitted only when it is fixed and trusted, never chosen at
  runtime.** The admitted ones are Google's user-content CDN for account pictures (the
  identity provider the session already rests on, and no route writes a caller-supplied
  string into `users.avatar_url`), Sentry's ingest hosts for 11.12's client errors, and, in
  `frame-src`, exactly the two embed players the folder composer creates. Direct media URLs
  stay links. A host chosen at runtime, such as a cover-photo search result, is proxied
  through this origin instead (7.15), because a directive wide enough for one arbitrary host
  admits any.
- **`style-src` carries `'unsafe-inline'`**: React style attributes carry runtime data and
  inline styles execute nothing.
- `worker-src` and `child-src` are unstated, so the service worker falls back to `script-src`,
  which resolves to `'self'` for `/sw.js`; that fallback is why a change to `script-src` must
  be checked against the worker.

**The theme hash depends on `.gitattributes`.** It sets `* text=auto eol=lf`; a CRLF checkout
of `app/index.html` digests differently, the policy then names a hash the served document
does not carry, and the theme script is refused in production silently. Changing that line,
or checking the repository out in a way that bypasses it, breaks production. Development
cannot show any of this, because `npm run dev` serves the document from Vite with no policy;
a policy change is verified against the production build.

**Refusals are reported.** A CSP refusal raises no error the server sees or the client
reports, so the policy carries both `report-uri` and `report-to`, and `Reporting-Endpoints`
names the endpoint absolutely under `APP_ORIGIN` (relative when that is unset, development
only). Both generations are sent because browsers are split across them; a browser honouring
both sends one report.

The endpoint is `POST /api/csp-report` (`app/src/server/routes/csp-report.ts`, filters and
budgets in `app/src/server/security/csp-report.ts`):

- **Outside `/api/v1`, with no session and no CSRF token**, because the browser posts it from
  its own networking stack. It is safe open because it reads nothing, writes nothing, takes
  no database handle, and does only one log line and at most one Sentry message.
- **204 for a report it drops exactly as for one it keeps**, so the status is never an oracle
  for the filters. Only the request's shape varies it: an oversized or non-JSON body is 400
  (`CSP_REPORT_BODY_LIMIT`), and the 10.4 limiter's refusal is 429.
- **Dropped before logging**: a report whose document origin is not `APP_ORIGIN`; a report
  whose blocked URI has a browser-extension or browser-internal scheme; and `data:` under
  `style-src` only, where reader modes inject it and `'unsafe-inline'` means the refusal
  cannot be Dana's. A `data:` refusal under `script-src` is kept. At most
  `MAX_VIOLATIONS_PER_BODY` reports are read from one batched body.
- **Sentry is bounded twice**: an absolute budget per window (`SENTRY_BUDGET_PER_WINDOW`,
  `SENTRY_WINDOW_MS`) and at most one event per fingerprint. Both are needed, because a
  free-tier quota counts events, not issues, and a fingerprint built from a stranger's string
  is unbounded; so the fingerprint, message and tags use only the whitelisted values the log
  line carries. When the budget is spent, exactly one message says so. **The log line is never
  throttled**: the log is the complete record, and Sentry is only how anyone learns of it.
- **Only the canonical host reports.** A deployment reachable on a second host reports nothing
  from it. That is accepted because `APP_ORIGIN` is also what 10.1's `redirect_uri` and 11.8's
  mail links are built from, so a second host is already half-configured, but it is a blind
  spot.

What a kept report writes is 10.5's, and what it sends to Sentry is 11.12's. Nothing here
proves a browser actually delivers a report, so a week with no `csp_violation` line is not
evidence that the policy fits.
